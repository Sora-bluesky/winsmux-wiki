# デスクトップアプリ {#desktop-app}

Hermes デスクトップアプリは、CLI やゲートウェイで使うのと**同じ**エージェントを中心に作られたネイティブアプリです。設定も API キーもセッションもスキルも記憶も、すべて共通です。別製品でも簡易版でもなく、同じ Hermes Agent のコアと設定をそのまま使い、現代的でよく考えられた UI から動かします。ターミナルで `hermes` を使ったことがあれば、そこで整えた内容はすでにここにも反映されていますし、ここでの操作はターミナル側にも現れます。

**macOS、Windows、Linux** で動作します。

:::tip どのインターフェースがどれなのか
Hermes には、同じエージェントとやり取りするフロントエンドがいくつかあります。

- **デスクトップアプリ**（このページ） — チャット・設定・管理のために作られた UI を持つネイティブアプリケーションです。
- **CLI**（`hermes`）と **[TUI](/hermes/docs/user-guide/tui/)**（`hermes --tui`） — ターミナル上のインターフェースです。
- **[Web ダッシュボード](/hermes/docs/user-guide/features/web-dashboard/)**（`hermes dashboard`） — ブラウザで開く管理画面です。任意で使える **Chat** タブは、疑似端末を介して TUI を埋め込んでいます。

そのときの状況に合うものを選んでください。状態は共有されるので、あるインターフェースで始めたセッションを別のインターフェースで再開できます。
:::

## インストール {#install}

[Hermes Desktop のインストール手順](/hermes/docs/getting-started/installation/)に従ってください。

すでに Hermes を導入済みなら、次を実行するだけです。

```bash
hermes desktop
```

これで、現在の設定・キー・セッション・スキルがそのまま使われます。

## アプリでできること {#whats-in-the-app}

デスクトップアプリは、チャットを中心に据えたウィンドウと、左側のサイドバーによるナビゲーションで構成されています。複数のエージェントとの会話を同時に扱い、メッセージングのプロバイダを設定し、成果物を作り、プロジェクトのフォルダ構成をたどり、複数のプロジェクトを並行して進められるように作られています。

### チャット {#chat}

アプリの中心です。次のことができます。

- **応答のストリーミング表示** — エージェントが作業する様子を、ツールの動作状況と構造化されたツール呼び出しの要約とともにその場で見られます。
- **他の Hermes の画面とまったく同じ会話履歴** — ここで始めたセッションは CLI / TUI で再開でき、その逆もできます。
- **ファイルのドラッグ＆ドロップ** — チャット領域のどこにでも落とせば、次のメッセージに添付されます。
- **右側のプレビュー欄** — Web ページ、ファイル、ツールの出力を横に並べて表示しながら、チャットを続けられます。
- **入力欄の履歴とキューの編集** — 入力欄が空の状態で上下の矢印キーを押すと、以前のプロンプトを呼び出して使い回せます。送信待ちのメッセージも、送られる前に編集できます。ターンがキューに溜まっている状態で Stop（または Esc）を押すとキューが一時停止し、入力欄の上に展開されます。そこから再開したり、個々の項目を送信・編集・削除したりできます。
- **会話のタイムライン欄** — チャットが長くなると、記録の端にプロンプトごとの目印が並んだ細い欄が現れます。カーソルを合わせるとプロンプトの一覧が開き、クリックすれば会話のその位置まで一気に移動できます。（チャットのやり取りがある程度たまると表示されます。）
- **ページ内検索** — **Cmd/Ctrl+F** を押すと、表示中のチャット記録を検索する検索バーが開きます。Enter / Shift+Enter（検索バーを開いている間は Cmd/Ctrl+G / Cmd/Ctrl+Shift+G でも可）で一致箇所を順に移動でき、Esc で閉じます。

#### ステータスバー {#status-bar}

チャットの下端にあるバーには、セッションの状態がその場で表示され、設定画面を開かずに使える操作がまとまっています。

- **セッションごとの YOLO 切り替え** — このセッションだけ YOLO を切り替えます（TUI と同じ挙動です）。YOLO は危険なコマンドの承認確認を飛ばすので、何を外しているのかを理解したうえで使ってください。[セキュリティ → YOLO モード](/hermes/docs/user-guide/security/#yolo-mode)を参照してください。
- **コンテキスト使用量メーター** — セッションのコンテキストウィンドウがどれだけ埋まっているかを「% full」でその場に表示します。クリックすると **Context Usage** のポップオーバーが開き、カテゴリ別（システムプロンプト、ツール定義、スキル、記憶、ルール、MCP、サブエージェントの定義、そして会話そのもの）のトークン内訳を確認できます。圧縮が始まる前に、何がウィンドウを消費しているのかを正確につかめます。
- **表示項目のカスタマイズ** — ステータスバーを右クリック（**Show in status bar**）すると、コンテキストメーター、ワークスペース、モデル、承認、ターン / セッションのタイマー、ターミナル、Command Center、バックエンドのバージョンなど、何を表示するかを選べます。バー自体を隠すこともできます（**Cmd/Ctrl+Shift+S** で切り替え）。

同梱のローカルバックエンドではなく、別の端末で動く Hermes に対してチャットしたい場合は、下の[リモートのバックエンドに接続する](#connecting-to-a-remote-backend)を参照してください。リモートに置いたダッシュボードへの接続（認証の関門、`/api/ws` のチャット用ソケット、WebSocket のクローズコードの切り分け）の全体像は、[Web ダッシュボード → Hermes Desktop をリモートのバックエンドにつなぐ](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend)にまとめてあります。

#### リポジトリの検出 {#repository-discovery}

Hermes Desktop は、ホームディレクトリを一定の深さまで走査して、Projects サイドバーに出すローカルの Git リポジトリを見つけます。この動作は **Settings → Workspace** でプロファイルごとに変更できるほか、`config.yaml` でも設定できます。

```yaml
desktop:
  repo_scan_enabled: true
  repo_scan_roots: []
  repo_scan_exclude_paths: []
```

- `repo_scan_enabled: false` にすると、ファイルシステムの走査を完全に止めます。そのプロファイルでディスク検出のキャッシュに残っている行は消去されますが、明示的に登録したプロジェクトと、意図して開いた Hermes セッションから推定されたリポジトリは引き続き使えます。
- `repo_scan_roots` にフォルダの一覧を設定すると、走査範囲をそこに限定できます。空の一覧のままなら、既定どおりホームディレクトリを走査します。
- `repo_scan_exclude_paths` には、配下をまるごと飛ばしたいフォルダを指定します。

これらの値を変更すると、そのプロファイルのディスク検出キャッシュだけが無効になり、方針に沿った再取得が始まります。**Hide from sidebar** は、これとは別に項目ごとに整理するための操作です。

#### モデルを選ぶ {#choosing-a-model}

モデルの選択欄は**入力欄**の中、マイクのすぐ左にあります。クリックすると、モデル・推論の労力・fast モードを 1 つのドロップダウンから切り替えられます。

- **入力欄の選択欄は UI 上の状態として残るだけで、既定値には触れません。** 選んだ内容は端末ごとにローカルに記憶され、新しいチャットや再起動をまたいでも既定値に戻らず**引き継がれます**。一度選んでおけば、次の `Cmd/Ctrl+N` はそのモデルで開きます。チャットが進行している状態でモデルを切り替えると、変更の範囲は**そのチャット**に限定されます。いずれの場合も、選択はセッションの作成 / 切り替えのときに一緒に運ばれ、プロファイルの既定値として書き込まれることは**ありません**。（[プロファイル](#sessions--profiles)を切り替えると、そのプロファイル自身の既定値で改めて初期化されます。）
- **既定値は Settings → Model で設定します。** そこで指定した「main」のモデルが**プロファイルごとの全体の既定値**で、新しいチャット・cron・サブエージェント・補助的な処理はここを起点に始まります。既定値を書き込むのはこの場所だけです。[プロファイル](#sessions--profiles)ごとに、それぞれの既定値を持ちます。
- **モデルごとの労力 / fast の設定。** デスクトップアプリでは、モデルごとに推論の労力と fast モードの選択が記憶され、そのモデルを選ぶたびにセッションへ再適用されます。これはデスクトップ側の便宜的な仕組みで、cron やサブエージェントには影響しません。
- **チャットの途中で切り替えるとプロンプトキャッシュが無効になります。** 進行中のチャットでモデルを変えると、次のメッセージでは会話全体が入力として読み直され、割引のない料金がかかります（プロバイダのプロンプトキャッシュはモデルごとに紐づいているためです）。たまに切り替えるぶんには問題ありませんが、長いチャットでは行き来を繰り返すより、新しいモデルで新しいチャットを始めたほうが安く済むことが多いです。

### ファイルブラウザ {#file-browser}

アプリから離れずに作業ディレクトリを見て回り、中身を確認できます。エージェントがファイルを読み・書き・編集していく様子を追いかけるのに便利です。最初に開くプロジェクトのディレクトリは `hermes desktop --cwd <path>`（または環境変数 `HERMES_DESKTOP_CWD`）で指定します。

### 成果物 {#artifacts}

**Artifacts** のビューは、セッションが生み出したもの（**画像・ファイル・リンク**）を 1 つのギャラリーに集め、検索したり見て回ったりできるようにします。サイドバー、コマンドパレット（**Artifacts — Browse generated outputs**）、あるいは自分で割り当てた `nav.artifacts` のショートカットから開けます。最近のセッションの出力は自動的に取り込まれ、それぞれの成果物にはどのセッションが作ったのかが表示され、そのチャットへ戻れます。画像とファイルはプレビューで開き、ダウンロード / ブラウザで開く / コピーの操作ができます。

### ウィンドウ・タブ・ペイン {#windows-tabs-panes}

このアプリは、いくつもの作業を同時に進められるように作られています。

- **タブ** — **Cmd/Ctrl+T** で新しいセッションのタブを開きます。**Ctrl+Tab** / **Ctrl+Shift+Tab** でセッションを順に切り替え、**Ctrl+1…9** で最近のセッションに位置指定で移動します。**Cmd/Ctrl+W** で選択中のタブを閉じ、**Cmd/Ctrl+Shift+T** で最後に閉じたタブを開き直します。
- **複数のウィンドウ** — **Cmd/Ctrl+Shift+N** で新しいウィンドウを開きます。どのセッションもコンテキストメニュー（**New window**）やコマンドパレットから切り離せます。切り離したウィンドウは、全体のサイドバーなしでそのチャットだけを表示するので、長く動かすセッションを別のモニターに置いておくのに向いています。エージェントの出力は、そのセッションを表示しているすべてのウィンドウに流れます。
- **ペイン** — **Cmd/Ctrl+B** で左のサイドバー、**Cmd/Ctrl+J** で右のサイドバーを開閉し、**Cmd/Ctrl+\\** でサイドバーの左右を入れ替えます。

### ターミナル {#terminal}

右のサイドバーには、ファイルブラウザの隣に本物のターミナルがあります。

- **Ctrl+`** でターミナルを表示します（1 つもなければ新たに開きます）。**Ctrl+Shift+`** でもう 1 つ増やせます。複数のターミナルはタブの列に並び、**Ctrl+Shift+↓/↑** で行き来し、**Ctrl+Shift+W** で選択中のものを閉じます。
- **隠しても shell は残ります。** パネルを閉じたり隠したりしても shell は終了しません。開いているターミナルは、明示的に閉じるまでスクロールバックも実行中のプロセスもそのままの状態で保持されます。
- **チャットに追加** — ターミナルの出力を選択して、次のメッセージの手がかりとして入力欄に送り込めます。

### Git のレビューと worktree {#git-review-worktrees}

Git リポジトリの中で動いているセッションでは、アプリに組み込まれたバージョン管理の画面が使えます。

- **レビューペイン** — **Cmd/Ctrl+G** で、作業ツリーのレビューペインを開閉します。ブランチと ahead / behind の状態、変更されたファイル（一覧表示かツリー表示）、そして **Uncommitted**・**Branch**・**Last turn**（直前のターンでエージェントが変更した分だけ）に絞った差分が見られます。ファイルをステージ / 解除し、変更を元に戻し、コミットメッセージを書いて（**Generate commit message** で生成もできます）、**Commit** または **Commit & Push** を実行できます。GitHub CLI（`gh`）を使った **Create PR** もでき、**Ask Hermes to open PR** で一連の作業をまるごとエージェントに任せることもできます。ここからブランチを作ったり切り替えたりもできます。
- **worktree** — **Cmd/Ctrl+Shift+B**（またはサイドバーでプロジェクトを選んで **New worktree**）で、新しいブランチ上に Git の worktree を作ります。これにより、自分のチェックアウトに触れないまま、エージェントがリポジトリの並行した複製で作業できます。worktree はプロジェクトの下に独立したレーンとして現れ、削除するときは worktree のディレクトリごと消す（ブランチは残ります）か、レーンを隠してディスク上には残すかを選べます。コミットしていない変更がある場合は強制的に削除する選択肢も出ます。

### 記憶のグラフ {#memory-graph}

**Memory Graph**（コマンドパレット → *Memory Graph*、またはステータスバーの項目）は、Hermes が自分のために学んだ内容を対話的に見渡せる地図です。スキルと記憶が、拡大縮小できるノードのグラフとして時系列とともに並び、**All / Used / Learned** で絞り込めます。共有用の操作から、この地図の配置を短いコードとして書き出して誰かに渡せます（配置だけで、記憶やスキルの文面は一切含まれません）。同じ形式のコードを読み込むこともできます。

### Quick Entry {#quick-entry}

Quick Entry は、**システムのどこからでも呼び出せるグローバルなホットキー**で開く小さな入力欄です。メインウィンドウに切り替えたり、そもそも開いたりしなくても、プロンプトを投げられます。**Settings → Advanced → Quick Entry** で有効にします。既定のショートカットは **Ctrl/Cmd+Shift+Space** で、修飾キーを 1 つ以上含めれば自分で決められます。その組み合わせを他のアプリがすでに使っている場合は、設定の行にその旨が表示されるので、別のものを選べます。

### 音声 {#voice}

Hermes に話しかけ、その返事を聞けます。他の場所で使えるものと同じ[音声モード](/hermes/docs/user-guide/features/voice-mode/)です。macOS では、マイクの利用許可を求める確認が一度だけ表示されます。

### HUD モード {#hud-mode}

**⌘/Ctrl+Shift+H**（またはタイトルバーのボタン）を押すと、チャットが枠のない常に最前面のフローティングバーとして切り離され、作業中の画面の上に浮かびます。アプリのウィンドウは脇へ退き、HUD には進行中の会話と入力欄が残ります。どこに置くかがそのまま文脈になります。バーの位置によって、どのアプリ・どの画面について尋ねているのかが Hermes に伝わるので、「これ」「ここ」「このページ」といった言葉が、その下にあるものを指すようになります。

- **バーを動かす** — 入力欄のどこかを**長めに押し続けてから**ドラッグします。短く押した場合はそのまま入力になり、押し続けるとウィンドウをつかめます。HUD を動かす方法はこれだけです（ドラッグ用のタイトルバーはありません）。
- **大きさを変える** — バーの右下の角をドラッグします。
- **カーソルの位置へ寄せる** — **⌘/Ctrl+Shift+G**（グローバルなホットキーなので、どのアプリからでも効きます）で、HUD がカーソルのある場所へ移動します。
- **終了する** — バーの終了ボタンを押すか、もう一度 **⌘/Ctrl+Shift+H** を押します。セッションはそのままに、アプリのウィンドウが戻ってきます。

### 設定と初回の案内 {#settings-onboarding}

プロバイダ・モデル・ツール・認証情報を、YAML を編集するのではなく本物の UI から管理できます。初回起動時の案内に沿えば、数秒で最初のメッセージを送れます。設定の各画面は、プロバイダとキー、モデルの選択、ツールセットの構成、MCP サーバー、ゲートウェイ、セッション管理をカバーします。

- **プロバイダの設定画面** — 推論のプロバイダを管理する専用の場所です。プロバイダごとにサインインして認証情報を保存する、アカウント / API キーの操作画面が用意されています。
- **メニューにすべてのプロバイダとモデルが並びます** — GUI にはプロバイダの一覧全体と、`hermes model` が把握しているすべてのモデルが表示されるので、選び抜かれた一部ではなく CLI と同じカタログから選べます。
- **xAI Grok の OAuth** — Grok はランチャー上で OAuth の主要なプロバイダとして扱われます。他の OAuth プロバイダと同じく、ブラウザ経由の手順でサインインします。
- **GUI からのツールバックエンドのインストール** — ツールバックエンドのセットアップ後の導入手順を、ターミナルに降りずにアプリから直接実行できます。
- **ターミナルのフォント選択** — **Settings → Appearance** で、インストール済みのフォントを選べます。`MesloLGS NF` のような Nerd Font を選べば、対話用とエージェント用のどちらのターミナルでも Powerlevel10k の区切りやアイコンが正しく表示されます。この設定はプロファイルごとに保存されます。
- **補助モデルについての警告** — 補助的な処理（タイトル付け、要約などの補助タスク）が別のプロバイダに固定されたまま、メインのモデルだけを新しいプロバイダに切り替えると、アプリが警告します。知らないうちに 2 つのプロバイダに作業が分かれてしまうのを防げます。
- **VS Code Marketplace のテーマ** — 内蔵のテーマに加えて、外観の設定から VS Code Marketplace をその場で検索できます。好きなカラーテーマを選べば、アプリがダウンロードして変換し、デスクトップ用のテーマとして導入します。同じ取り込み機能はコマンドパレット（*Install theme*）からも使え、取り込んだテーマは外観の設定から削除できます。
- **コンピューターをスリープさせない** — **Settings → Advanced → Keep computer awake** を使うと、端末がスリープしなくなるので、長時間や夜通しのエージェントの実行が止まりません（画面が暗くなることはあります）。これは端末ごとの設定です。

初回起動時の案内は、統一されたオーバーレイのデザインで作り直されています。**Choose provider later** を選べば、プロバイダの設定を後回しにして先にアプリの中に入れます。

#### プロファイルごとの設定：「Applies to」の適用範囲 {#per-profile-settings-the-applies-to-scope}

[プロファイル](/hermes/docs/user-guide/profiles/)が 2 つ以上ある場合、設定ファイルに紐づく設定ページ（**Model、Workspace、Safety、Memory & Context、Voice、Chat、Advanced、Tools & Keys**）と **Messaging** のオーバーレイの上部に、共通の **Applies to** のチップの行が表示されます。ここで、編集内容をどのプロファイルに適用するかを選びます。

- 既定では**現在使っているプロファイルに追従**します。これは従来どおりの挙動で、使っているプロファイルをそのまま編集します。
- 別のプロファイルを選べば、アプリ全体を切り替えずに*そのプロファイルの*設定を確認・編集できます。選択は設定ページを移動しても保たれます。
- アプリで使うプロファイル自体を切り替えると選択はリセットされるので、以前に選んだプロファイルに気づかないまま編集が入り続けることはありません。
- プロファイルが 2 つ未満のときは、チップの行はまったく表示されません。

（Gateways のページはプロファイルの扱いが異なり、**Per-profile overrides** の項目で対応します。Capabilities と Scheduled Jobs のビューには、それぞれ独自の適用範囲の選択欄があります。）

### 管理用の画面 {#management-panes}

このアプリは、Hermes の管理機能全般も画面上に用意しているので、ターミナルに降りる必要がありません。

- **Skills** — [スキル](/hermes/docs/user-guide/features/skills/)の閲覧・導入・管理ができます。
- **記憶のグラフ（Star Map）** — チャットで `/journey`（別名 `/learning`、`/memory-graph`）と入力すると、学んだスキルと記憶の移り変わりを星座のように見られる画面が開き、再生用のつまみで時間をたどれます。ノードはこのパネルから直接編集・削除できます（スキルは保管され、記憶は削除されます）。[学習の軌跡](/hermes/docs/user-guide/features/memory/#learning-journey-journey)を参照してください。
- **Cron** — [定期実行のジョブ](/hermes/docs/reference/cli-commands/#hermes-cron)を確認・管理できます。
- **Profiles** — [Hermes のプロファイル](/hermes/docs/user-guide/profiles/)（設定・スキル・セッションが分離されたもの）を切り替えます。
- **Messaging** — ゲートウェイのチャンネルを設定します。
- **Agents** と **Command Center** — 複数のエージェントによる作業を差配するための画面です。

### Bot Mode（組み込み） {#bot-mode-built-in}

**Bot Mode** はアプリに同梱されていて、既定で有効になっています。これは「エージェント 1 体につきチャット 1 つ」の
名簿で、[Hermes のプロファイル](/hermes/docs/user-guide/profiles/)がそれぞれ 1 体のボットとして並びます。各ボットは自分の
アバター（幾何学的な顔、アップロードした画像、AI が生成した肖像、ドット絵の
ペット）、決まった **Bot Chat** の会話、そして自分の **Routines**
（Hermes の cron に支えられた繰り返しの作業）を持ちます。名簿は左の
サイドバーに、会話の一覧の下に重なる 2 つ目のペインとしてではなく、
会話の隣のタブ、つまり **Sessions | Bots** のタブの列として置かれます。以前の
重ねる配置になっていた導入環境は、自動的に一度だけタブの列へ
移されます。自分で手を加えて配置している場合は、その配置は変更されません。**Cronjobs**（Routines）のペインは、
Bots のタブを表示している間だけチャットの横に現れ、Sessions に戻ると
消えます（古いデスクトップ版では常に表示されたままになります）。

新しいエージェントは名簿から作れます。名前 / 肩書き / 説明に加えて、
詳細を開くと能力の設定一式（モデル、SOUL、スキル、ツールセット、MCP サーバー）が現れます。ボットは
セクションにまとめられ、複数のボットが議論するグループチャットも開けます。
グループチャットは、Discord のような独立した行として名簿に並びます。メンバーの
アバターが重なって表示され、人数、その部屋の最新の発言のプレビュー、そして
「needs you」のバッジが付き、ボットの行と同じピン留め + 新しい順の
並びの中に混ざります。グループの行をクリックすると、その部屋が
**メインのチャットウィンドウ**を占めるタブとして開きます（古いデスクトップ版では
ボットのサイドパネルの中で開きます）。

ボット同士もやり取りします。どのチャットでも `@researcher have a look at this` のように入力すれば、
現在のボットがそのメッセージを渡して結果を報告しますし、ボットは互いの Bot Chat に直接
届きます（`hermes -p <bot> chat`）。バックエンドは、各ボットの決まった **Bot Chat** の
セッションにメッセージのやり取りの手順を自動的に教えます
（設定は `agent.bot_mode_protocol` で、既定は有効です）。仲間のボットが CLI から
ヘッドレスで開いた場合も同様なので、SOUL.md に手を入れなくても
ボット同士の返信や受け渡しが成り立ち、普段のセッションはそのままに保たれます。

Bot Mode のセッション、つまり各ボットの決まった Bot Chat とグループチャットの
メンバーごとのセッションは、全体の Sessions のサイドバーには常に表示されません。これらは
Bots のペイン（名簿の行、部屋の表示、各ボットのセッション一覧）の中にあり、自分の会話と
混ざることはありません。

使わないボットはしまっておけます。ボットの行を右クリックして **Hide
Bot** を選びます。隠したボットは名簿から消えますが、動作は続きます。@ でのメンションはこれまでどおり
解決され、グループチャットの所属も変わりません。1 体でも隠れているボットがあると Bots のヘッダーに
目のアイコンが現れ、クリックすると隠したボットがその場所に薄く表示されます（右クリック → **Unhide Bot** で戻せます）。
隠したボットに未読の動きがあると、目のアイコンに点が付きます。隠れているかどうかの
状態はボットのプロファイルに保存されるので、端末をまたいでも
ボットについて回ります。

必要なければ、**Settings → Plugins → Bots** で無効にできます。名簿・
Routines のペイン・入力欄の処理がその場で解除され、再起動は要りません。

エージェントの作成（複数の端末にまたがる **Create on** の選択欄を含む）、接続をまたいだ名簿、
ボット同士のメンション、グループチャットで誰が返事をするかの決まり方についての
詳しい説明は [Bot Mode: A Roster of Agents](/hermes/docs/user-guide/bot-mode/) にあります。

### キーボードと画面の移動 {#keyboard-navigation}

- **コマンドパレット** — **Cmd+K** または **Cmd+P**（Windows / Linux では Ctrl+K / Ctrl+P）を押すと、キーボードだけで操作を呼び出しアプリ内を移動できます。任意のページや設定の項目を開く、タイトルや id からセッションへ移動する、モデル / テーマ / 配色を切り替える、ターミナルを開く、ゲートウェイを再起動する、Hermes を更新する、といったことができます。
- **割り当てを変えられるショートカット** — **Settings → Keyboard Shortcuts**（または **Cmd/Ctrl+/**）でショートカットのパネルが開き、ほとんどの割り当てを変更できます。プロファイルの切り替え、セッション間の移動、表示の切り替え、デスクトップのプラグインが追加したショートカットまで対象です。重複した割り当ては衝突として表示されます。覚えておくとよい既定値をいくつか挙げると、**Cmd/Ctrl+N** で新しいセッション、**Cmd/Ctrl+.** で Command Center、**Cmd/Ctrl+,** で設定、**Cmd/Ctrl+Shift+F** でセッションの検索、**Cmd/Ctrl+1–9** でプロファイルの切り替え、**Shift+X** で明暗の切り替えです。
- **拡大縮小のショートカットの調整** — 画面の拡大縮小を半段階ずつ動かせるので、文字の大きさを細かく調整できます。
- **UI の言語の切り替え** — アプリの表示言語をアプリ内で変更できます。簡体字中国語（zh-Hans）にも対応します。

### セッションとプロファイル {#sessions-profiles}

- **セッション一覧の刷新** — 保管の機能や整理の仕組みを備えた形にセッション一覧を作り直したので、数が増えても扱いやすい状態を保てます。
- **id でセッションを検索** — 特定のセッションを id から直接探せます。
- **複数プロファイルの同時利用** — 複数の[プロファイル](/hermes/docs/user-guide/profiles/)にまたがるセッションを同時に動かせます。プロファイルをまたぐ `@session` のリンクで、別のプロファイルのセッションを参照することもできます。
- **プロファイルの書き出し / 読み込み** — 設定一式をファイル 1 つで共有できます。**⌘K → Export profile…**（またはレールにあるプロファイルの四角を右クリック）で、スキル・記憶・人格・cron・プラグイン・設定を含む `.tar.gz` が書き出されます。API キーは取り除かれます。デスクトップから書き出すと、外観と画面まわり（スキン、明暗のモード、独自のテーマ、そのプロファイルのレールの色、ウィンドウの配置）も一緒に入るので、読み込んだ側では送り手が見ていたとおりの見た目で開きます。読み込みは **⌘K → Import profile…** か、レールの **+** の隣にあるボタンから行います。適用されると、そのまま新しいプロファイルに入ります。同じ書庫は、チャットでの `/export` / `/import` や、シェルからの `hermes profile export` / `import` でも使えます。[プロファイルのファイルを書き出す・読み込む](/hermes/docs/user-guide/profile-distributions/#export-and-import-a-profile-file)を参照してください。

## 更新する {#updating}

アプリは裏側で更新を確認し、準備ができるとワンクリックでの更新を案内します。

デスクトップアプリと、それがやり取りする Hermes のバックエンドは、別々のタイミングで更新されます。アプリの本体は手元の端末に、バックエンドはそれが動いている場所にあります。更新の対象が複数ある場合（リモートのゲートウェイがある、あるいは複数のゲートウェイを登録している場合）、更新の操作（About パネルの **Update now**、⌘K の **Update Hermes** の行、更新の準備ができたことを知らせる通知）は**すべて**を更新します。まず接続中のバックエンド、次に対象となる登録済みのゲートウェイすべて（Hermes Cloud の項目はプラットフォーム側が管理するため飛ばされます）、そして最後にデスクトップアプリ自体という順です。クライアント側の更新を適用するとアプリが再起動するためです。端末 1 台だけの構成なら、ボタン 1 つで済む体験は変わりません。

バックエンドを更新したあとは、アプリが自身のバージョンも確認し直します。GUI 側が古いままであれば、**Update desktop app** のワンクリック操作つきで警告するので、リモートのバックエンドを更新した結果、気づかないまま古いデスクトップ版に取り残されることはありません。

[手動での更新手順](https://hermes-agent.nousresearch.com/docs/getting-started/updating)も GUI で使えます。

## アンインストール {#uninstalling}

**Settings → About → Danger zone** を開き、どこまで削除するかを選びます。

- **Uninstall Chat GUI only** — デスクトップアプリとそのデータを削除します。Hermes のエージェント、設定、チャットは残ります。（`hermes uninstall --gui` と同じです。）
- **Uninstall GUI + agent, keep my data** — アプリとエージェントを削除しますが、再導入に備えて設定・チャット・秘密情報は残します。（`hermes uninstall` と同じです。）
- **Uninstall everything** — アプリ、エージェント、そしてすべての利用者データを削除します。（`hermes uninstall --full` と同じです。）

処理を終えるためにアプリは閉じます（終了後に後片付けが走るので、動作中のアプリ本体とその venv を削除できます）。ローカルにエージェントが入っていない場合（たとえばリモートのバックエンドにつないだ GUI だけの「lite」なクライアント）は、エージェントを削除する選択肢は自動的に隠れます。

同じことはターミナルからもできます。GUI だけなら `hermes uninstall --gui`、エージェントも含めるなら `hermes uninstall` / `hermes uninstall --full` です。

:::note
**ソースのチェックアウト**（`hermes desktop` の開発ビルド）から `hermes uninstall --gui` を実行すると、ワークスペースの `node_modules` と `apps/desktop/{dist,release}` のビルド成果物も削除されます。これらは GUI のビルド成果物だからです。`hermes desktop`（または `npm install` と再ビルド）で元に戻せますが、デスクトップアプリ自体に手を入れている最中なら、あとで依存関係を入れ直すことになると思っておいてください。
:::

## CLI の早見表：`hermes desktop` {#cli-reference-hermes-desktop}

CLI から起動するには、`hermes desktop` と実行するだけです。既定では、ワークスペースの Node の依存関係を入れ、現在の OS 向けに展開済みの Electron アプリをビルドしてから、その成果物を起動します。

| フラグ               | 説明                                                                                       |
| -------------------- | ----------------------------------------------------------------------------------------- |
| `--skip-build`       | npm のインストール / パッケージ化を飛ばし、`apps/desktop/release` にある展開済みのアプリを起動します |
| `--force-build`      | 内容のスタンプが一致していても、強制的にすべてビルドし直します                              |
| `--build-only`       | デスクトップアプリをビルドするだけで起動はしません（`hermes update` が使います）           |
| `--source`           | パッケージ化されたアプリではなく、`apps/desktop/dist` に対して `electron .` で起動します    |
| `--cwd PATH`         | デスクトップでのチャットのセッションが最初に開くプロジェクトのディレクトリを指定します（`HERMES_DESKTOP_CWD` を設定します） |
| `--hermes-root PATH` | アプリが使う Hermes のソースの場所を上書きします（`HERMES_DESKTOP_HERMES_ROOT` を設定します） |
| `--ignore-existing`  | バックエンドを決めるときに、`PATH` 上にすでにある `hermes` の CLI を無視させます            |
| `--fake-boot`        | 起動時の UI を確認するために、起動の遅延を決まった値にします                                |

## 仕組み {#how-it-works}

パッケージ化されたアプリには、Electron のシェルとネイティブな React のチャット画面が入っています。初回の起動時には、Hermes Agent のランタイムを `HERMES_HOME`（`~/.hermes`、Windows では `%LOCALAPPDATA%\hermes`）に導入できます。これは **CLI で入れたときとまったく同じ配置**で、だからこそ両者を行き来できます。バックエンドの決定は、まず `HERMES_DESKTOP_HERMES_ROOT` を尊重し、次に完了済みの管理下のインストール、次に `PATH` 上で見つかった `hermes`（`--ignore-existing` / `HERMES_DESKTOP_IGNORE_EXISTING=1` が設定されている場合を除く）、最後に Nix のようなパッケージ作成者向けの `HERMES_DESKTOP_HERMES` による明示的なコマンドの上書き、という順で行われます。React のレンダラーは、アプリが自動で立ち上げるヘッドレスのバックエンド、つまり `tui_gateway` の JSON-RPC / WebSocket API を提供する `hermes serve` のプロセスとやり取りし、`hermes --tui` を埋め込むのではなくエージェントのランタイムを再利用します。デスクトップアプリは**それだけで完結**していて、自前の `hermes serve` のバックエンドを動かし、[Web ダッシュボード](/hermes/docs/user-guide/features/web-dashboard/)を開くことも必要とすることもありません。（`serve` コマンドを持たない古いランタイムでは、自動的にヘッドレスの `dashboard --no-open` に切り替わるので、アプリの更新がバックエンドを追い越してしまうことはありません。）インストール・バックエンドの決定・自動更新の処理は、Electron のメインプロセスに置かれています。

## リモートのバックエンドに接続する {#connecting-to-a-remote-backend}

既定では、アプリは自分自身の**ローカルの**バックエンドを起動して管理します。その代わりに、別の端末で動いている Hermes のバックエンド、たとえば VPS、自宅のサーバー、Tailscale の向こうにある Mini などを指定することもできます。

接続に関する設定は 1 つのページにまとまっています。**Settings → Gateways** です。（古い版ではこれが **Gateway** と **Connections** の 2 つのページに分かれていましたが、現在は統合され、古い `?tab=connections` のリンクは統合後のページへ転送されます。）

**Settings → Gateways → Connection mode** では、ローカルのゲートウェイ以外の選択肢が示されます。

- **Remote gateway** — 自分で動かしている `hermes serve` のバックエンドの URL を入力してサインインします。この節の残りで説明するのは、この方式です。
- **Hermes Cloud** — Hermes Cloud に一度サインインし、アカウントにあるエージェントから選びます。URL を貼り付ける必要はありません。アプリがエージェントを見つけ（アカウントが複数の組織にまたがる場合は組織の選択欄が出ます）、選ぶとセッションが自動的にそちらへ切り替わります。接続している間は、ステータスバーにクラウドへの接続が表示されます。

ゲートウェイへの接続は**端末単位**です。Gateways のページは、このデスクトップがどのゲートウェイのバックエンドに接続できるかを管理し、プロファイルは接続したゲートウェイ*から*見つかります。セッションが選ぶゲートウェイは一度に 1 つで、隣のプロファイルのレールでは、そのゲートウェイ上で見つかったプロファイルを選びます。

### 複数の接続を登録する仕組み {#the-multi-connection-registry}

同じ **Settings → Gateways** のページを下へたどると、**Registered gateways** があります。ここでは、アプリが把握しているすべての Hermes のゲートウェイに名前を付けて一覧管理します。ローカルのランタイム、いくつでも登録できるリモートのゲートウェイ（LAN、Tailscale、インターネット）、Hermes Cloud のインスタンス、SSH のホストが、まとめて 1 か所に保存されます。サイドバーのプロファイルのレールの右端にあるプラグのボタン（**Connect another Hermes gateway…**）や、**⌘K → Gateways** からも移動できます。まとめられたエージェントの名簿、`@name-device` の書き方、複数の端末をまたいだ更新、プラグイン SDK の機能を含む詳しい説明は、[Connecting Desktop to Many Hermes Instances](/hermes/docs/user-guide/multi-connection-desktop/) にあります。

- **接続には重複しない名前が必要です**（「Homelab」「Work laptop」のような端末の名前）。同じ名前のプロファイルが複数の登録済みゲートウェイに存在する場合、各画面では `@profile-device` の形で区別されます（例：`@research-homelab`）。
- **ゲートウェイは Sessions のサイドバーから切り替えます。** ゲートウェイを 2 つ以上登録すると名前付きの選択欄が現れ、登録の数がどれだけ増えても、ゲートウェイがプロファイルのように見えてしまうことなく扱えます。隣のプロファイルのレールにはそのゲートウェイのエージェントだけが並び、そこで最後に使ったプロファイルが記憶されます。プロファイルが多い場合は、そちらはそちらでまとめて表示されます。
- **再起動後に何を開くかを選べます。** **Open on launch** は、これまでと同じ **Primary gateway** を既定にすることも、接続に成功したら **Last used** のゲートウェイを再開するようにすることもできます。この設定はアプリケーションの本体とは別の場所に保存されるので、Desktop を更新しても残ります。
- 接続の**追加 / 編集 / 削除 / テスト**は、このパネルから行います。**Add** の流れでは 4 種類すべて、**Local**、**Hermes Cloud**、**Remote gateway**、**SSH** を選べます（アプリが管理するローカルの項目が存在する間、Local のボタンは押せません。クラウドの追加については、上に書いたサインインと検出の流れへ案内が出ます）。ローカルの項目はアプリが管理していて、削除できません。**Test** は、その接続自身の HTTP と WebSocket の経路を直接確かめます。
- **重複は保存の時点で拒否されます。** **local** の項目は常に 1 つだけです。リモートとクラウドの項目は、正規化した URL（前後の空白を除き、末尾のスラッシュを取り、小文字にしたもの）で、両方の種類にまたがって重複を判定します。SSH の項目は、正規化した `user@host:port` とリモートのプロファイルで判定します。
- 既存の設定は、この仕組みを備えた版を初めて実行したときに**自動的に取り込まれます**。現在の全体の接続設定と、プロファイルごとの古い上書き設定が、名前付きの項目になります。古い設定ファイルはそのまま残るので、以前の版も引き続き動きます。
- クラウドの項目は、手で URL を打ち込むのではなく、上に書いた Hermes Cloud のサインインと検出の流れから作られます。
- トークンは OS のキーリングで暗号化して保存されます（キーリングのない Linux では、明示的に選べば平文で保存できます）。

並べて使うための経路の振り分けはすでに動いています。登録された各ゲートウェイは、必要になった時点で自分のバックエンドとソケットにつなぎ（接続 + プロファイルの組み合わせごとに区別されます）、プラグイン SDK はまとめられたエージェントの名簿（`host.agents()` / `host.ensureAgent()`）を提供します。Gateways のページの **Update all instances** は、対象となるすべてのゲートウェイに `hermes update` を一度に送ります。Hermes Cloud の項目は飛ばされ（プラットフォーム側が更新します）、それぞれのインスタンスが自分の結果を報告します。

:::info リモートのバックエンドとは、動いている `hermes serve` のプロセスのことです
「リモートのバックエンド」とは、リモートの端末で動いている **`hermes serve`** のサーバーのことで、デスクトップアプリが接続する相手はこのプロセスです。このバックエンドが実際に動いていて到達できる状態でなければ、この節の内容は何も成り立ちません。デスクトップアプリがこれを起動してくれるわけではないので、リモートのホストでは自分（または `systemd` のサービス）が `hermes serve` を動かし続け、そこにアプリがつなぎます。メッセージングのチャンネル（Telegram、Discord など）も使う場合、**ゲートウェイ**は*別の*長時間動くプロセスで、こちらは自分で起動します。手順のあとの補足を参照してください。
:::

接続は 2 つの側面から成ります。バックエンド側では**認証プロバイダ**で保護し、アプリ側ではバックエンドの URL を入力してサインインします。バックエンドをループバック以外のアドレスに割り当てると、認証の関門が自動的に有効になり、設定した認証プロバイダがデスクトップアプリを通す役割を果たします。

**バックエンドがどこにあるかで、プロバイダを選んでください。**

- **OAuth（Nous Portal） — 自分の端末の外から届く構成なら、こちらを推奨します。** ログインは Nous のアカウントに照らして検証されるので、VPS、公開されたホスト、その他あらゆるリモートのバックエンドに適した選択肢です。`hermes dashboard register`（または Portal の [`/local-dashboards`](https://portal.nousresearch.com/local-dashboards) のページ）でダッシュボードを登録して OAuth のクライアントを用意し、アプリから **Sign in with Nous Research** でサインインします。自前の OIDC プロバイダを運用している場合も、同じやり方で使えます。
- **ユーザー名とパスワード — ローカルや信頼できるネットワークでのみ。** バックエンドが同じ信頼できる LAN 上にあるか、VPN（Tailscale など）経由でしか届かない場合の、いちばん手軽な方法です。外部の ID プロバイダを使わずに、共有の認証情報 1 組で保護するだけなので、**インターネットに公開したダッシュボードには使わないでください**。その場合は OAuth を選んでください。

この節の残りでは、信頼できるネットワーク上でいちばん早く立ち上がるユーザー名とパスワードの方法を説明します。OAuth の方法については、[Web ダッシュボード → 既定のプロバイダ：Nous Research](/hermes/docs/user-guide/features/web-dashboard/#default-provider-nous-research)を参照してください。

### バックエンド側（リモートの端末）での作業 {#on-the-backend-the-remote-machine}

ユーザー名とパスワードを設定し、届くアドレスに割り当ててバックエンドを起動します。認証情報は `~/.hermes/.env`（モード 0600 の秘密情報のファイル）に置きます。

```bash
# 1. Set the dashboard login credentials.
cat >> ~/.hermes/.env <<'EOF'
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
# Recommended: a stable signing secret so sessions survive restarts.
# Without it a random key is generated per boot and you'll be logged out
# on every restart.
HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
EOF
chmod 600 ~/.hermes/.env

# 2. Run the backend bound to a reachable address. The non-loopback bind
#    engages the auth gate; the username/password provider handles login.
hermes serve --host 0.0.0.0 --port 9119
```

デスクトップアプリから接続できるようにしておきたい間は、この `hermes serve` のプロセスを動かし続けてください。止まってしまうと、アプリはバックエンドに届かなくなります。ログアウトや再起動をまたいでも残るように、`systemd`、`tmux`、あるいは好みのプロセス管理の仕組みの下で動かしてください。

これとは別に、メッセージングのチャンネルを使っているなら、リモートのホストで**ゲートウェイが動いている**ことも確認してください。デスクトップアプリがやり取りするのは `hermes serve` のバックエンドですが、Telegram / Discord / Slack のゲートウェイのセッションは別のプロセスで、こちらは自分で起動して動かし続けます。ゲートウェイの設定については[メッセージング](/hermes/docs/user-guide/messaging/)を参照してください。

パスワードを平文のまま置いておきたくない場合は、代わりに `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH` に scrypt のハッシュを設定してください。ハッシュは `python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"` で計算できます。設定できる項目の全体（config.yaml のキー、すべての環境変数、レートの制限）は [Web ダッシュボード → ユーザー名とパスワードのプロバイダ](/hermes/docs/user-guide/features/web-dashboard/#usernamepassword-provider-no-oauth-idp)にあります。

バックエンドを systemd のサービスとして動かす場合は、そのユニットに `EnvironmentFile=%h/.hermes/.env` を指定して、起動時に認証情報が環境に入るようにしてください。

:::warning
バックエンドは `.env`（API キーや秘密情報）を読み書きし、エージェントのコマンドを実行できます。上に示した**ユーザー名とパスワード**の構成は信頼できるネットワーク向けです。パスワードで保護しただけのバックエンドを、インターネットにそのまま公開しないでください。VPN の内側に置いてください。[Tailscale](https://tailscale.com/) はすっきりした選択肢です。端末の tailscale の IP に割り当て（`--host <tailscale-ip>`）、リモートの URL として `http://<tailscale-ip>:9119` を使えば、自分の tailnet からしか届かなくなります。インターネット越しにバックエンドへ届かせたい場合は、代わりに **OAuth（Nous Portal）**のプロバイダを使ってください。
:::

### アプリ側での作業 {#in-the-app}

**Settings → Gateways → Remote gateway** で操作します。

1. **Remote URL** — `http://<backend-host>:9119`（リバースプロキシを前段に置く場合は `/hermes` のようなパスの接頭辞も使えます）
2. **Sign in** — アプリはバックエンドが提示するプロバイダを判別して、ボタンの表示を変えます。ユーザー名とパスワードのバックエンドなら **Sign in** のボタンが出て、認証情報の入力欄が開きます（手順 1 で設定した認証情報を入力します）。OAuth のバックエンドなら **Sign in with `<provider>`**（たとえば *Sign in with Nous Research*）が出て、そのプロバイダのブラウザでのサインインが始まります。どちらの場合も、最終的にアプリはバックエンドに対して認証済みのセッションを持ちます。
3. **Save and reconnect** — デスクトップの画面をリモートのバックエンドに切り替えます。セッションは自動的に読み直され、`HERMES_DASHBOARD_BASIC_AUTH_SECRET` を設定してあれば、再起動してもサインインした状態が続きます。

UI を使わずに、アプリを起動する前に環境変数 `HERMES_DESKTOP_REMOTE_URL` でバックエンドの URL を指定することもできます（アプリ内の設定より優先されます）。その場合も、サインインは Gateways の設定パネルから行います。

:::note プロファイルごとのリモートのホスト
リモートのゲートウェイのホストは[プロファイル](/hermes/docs/user-guide/profiles/)ごとに設定されるので、プロファイルごとに別々のリモートのバックエンドを向けたり、ローカルのままにしたりできます。プロファイルを切り替えると、アプリが接続するリモートのホストも切り替わります。
:::

### 困ったときは {#troubleshooting}

- **サインインが 401 や「Invalid credentials」で失敗する** — ユーザー名かパスワードが、バックエンドの `HERMES_DASHBOARD_BASIC_AUTH_USERNAME` / `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD` と一致していません。バックエンドは、存在しないユーザーの場合もパスワードが違う場合も同じ一般的なエラーを返す（どちらなのかを推測されないようにする）ので、両方を確かめてください。関門が有効かどうかは `curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'` で確認できます。`true` が返り、`"basic"` が含まれているはずです。
- **「Sign in」のボタンが出ず、セッショントークンを求められる** — バックエンド側で、ユーザー名とパスワードのプロバイダが有効になっていません。`/api/status` の `auth_providers` に `"basic"` が並びません。ユーザー名と、パスワード（またはパスワードのハッシュ）の両方が `~/.hermes/.env` に設定されていて、ダッシュボードのプロセスが実際にそれを読み込んでいることを確認してください。
- **再起動のたびにサインアウトされる** — `HERMES_DASHBOARD_BASIC_AUTH_SECRET` に変わらない値を設定してください。設定がないと、トークンの署名に使うキーが起動のたびに作り直され、すべてのセッションが無効になります。
- **接続を拒否される / 応答がない** — バックエンドが `127.0.0.1`（既定）に割り当てられているか、ファイアウォールや VPN がそのポートを塞いでいます。`0.0.0.0` か tailscale の IP に割り当て、信頼できるネットワークに向けてポートを開けてください。

同じ設定を Web ダッシュボード側から見た説明は、[Web ダッシュボード → Hermes Desktop をリモートのバックエンドにつなぐ](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend)にあります。環境変数は[環境変数 → Web ダッシュボードと Hermes Desktop](/hermes/docs/reference/environment-variables/#web-dashboard--hermes-desktop)にまとめてあります。

## デスクトップアプリを拡張する {#extending-the-desktop-app}

デスクトップアプリは、外からの追加を前提に作られています。ペイン、ページ、サイドバーの項目、ステータスバーの
項目、パレットのコマンド、キーの割り当て、テーマは、どれも 1 つの SDK を通して登録され、
自分でも追加できます。プラグインは、`$HERMES_HOME/desktop-plugins/<id>/plugin.js` に置く
ESM のファイル 1 つです。アプリは数秒のうちにこれを読み込み、保存するたびに
その場で読み直します。導入済みのプラグインは **Settings → Plugins** で随時管理できます。

すべての項目については [Desktop Plugin SDK](/hermes/docs/developer-guide/desktop-plugin-sdk/) を
参照してください。（これは [Web ダッシュボードのプラグインの仕組み](/hermes/docs/user-guide/features/extending-the-dashboard/)とは別のものです。）

同じ Settings → Plugins のページにある **Agent plugins** の項目では、自分で導入した
バックエンド側（エージェント側）の[プラグイン](/hermes/docs/user-guide/features/plugins/)、つまり user、
git、project、pip、portable の各方式で入れたものを管理します。リポジトリに同梱された組み込みのもの（プラットフォームの
アダプタ、プロバイダのプラグインなど）はここには並びません。これらは既定で有効な状態で
配布され、それぞれの画面から設定するので、この項目は自分で追加したものだけに
絞られます。プロファイルが 2 つ以上ある場合、この項目にも独自の **Applies to** の選択欄が付き、
アプリ全体を切り替えずに別のプロファイルのエージェントのプラグインを一覧・切り替えできます（バックエンドの
`plugins.manage` の RPC は、このために任意の `profile` のパラメータを受け付けます）。

## 困ったときは {#troubleshooting}

起動時のログは `HERMES_HOME/logs/desktop.log` に出ます（バックエンドの出力と、直近の Python のトレースバックが含まれます）。アプリが起動の失敗を報告したら、まずここを見てください。CLI から追いかけることもできます。

```bash
hermes logs gui -f
```

よく使うリセットは次のとおりです。

```bash
# Force a clean first-launch setup (macOS/Linux)
rm "$HOME/.hermes/hermes-agent/.hermes-bootstrap-complete"

# Rebuild a broken Python venv (macOS/Linux)
rm -rf "$HOME/.hermes/hermes-agent/venv"

# Reset a stuck macOS microphone prompt
tccutil reset Microphone com.nousresearch.hermes
```

### 「The host key has CHANGED since you last connected」（SSH のリモート） {#the-host-key-has-changed-since-you-last-connected-ssh-remote}

SSH のリモートを入れ直したりホストキーが変わったりすると、SSH は接続を拒んで
止まり、Desktop は再試行せずにエラーの表示を出したままにします（古いキーを消さないかぎり、
再試行しても成功しないからです）。その変化が想定どおりのものかを確認したうえで、
古い項目を削除し、表示から再試行してください。

```bash
ssh-keygen -R <host>
```

項目を消したら **Retry** をクリックしてください（または Settings → Gateway で接続を設定し直してください）。
止まっていた状態が解除され、次の起動で新たに接続を試みます。

### 「Build desktop app」が Electron のダウンロードで止まる {#build-desktop-app-stuck-on-electron-download}

ビルドは、Electron のランタイム（約 114&nbsp;MB）を `github.com/electron/electron/releases` からダウンロードします。インストーラーが **Build desktop app** の手順で止まり、その場の出力に `retrying attempt=…` が繰り返し出ている場合は、ネットワーク（ファイアウォール、プロキシ、地域の制限）によって GitHub が遮断されているか、速度を絞られています。

インストーラーはこれを自動で立て直します。ビルドに失敗すると、(1) 壊れたキャッシュ上の Electron の zip を消して再試行し、それでも失敗して (2) `ELECTRON_MIRROR` を設定していなければ、Electron の事実上のコミュニティのミラーである `npmmirror.com` を通してもう一度試します。`@electron/get` はダウンロードした内容の SHASUM を確認しますが、そのチェックサムも同じミラーから来るので、これで検出できるのは壊れたり途中で切れたりしたダウンロードであって、乗っ取られたミラーではありません。第三者のホストを信用したくない場合は、自分の `ELECTRON_MIRROR` を指定してください（下記）。ビルドは、設定済みのものを上書きしません。

**自分でミラーを選ぶ**場合（社内の信頼できるものなど）は、インストールの前に `ELECTRON_MIRROR` を設定するか、手動でビルドし直してください。ビルドはこの設定を尊重し、上書きしません。

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ \
  bash -c 'cd "$HOME/.hermes/hermes-agent/apps/desktop" && CSC_IDENTITY_AUTO_DISCOVERY=false npm run pack'
```

壊れたキャッシュ上の zip を手で消す場合は、次のとおりです。

```bash
rm -f "$HOME/Library/Caches/electron"/electron-*.zip   # macOS
rm -f "$HOME/.cache/electron"/electron-*.zip            # Linux
```

## ソースからビルドする {#building-from-source}

アプリそのものに手を入れたい場合は、リポジトリのルートで一度ワークスペースの依存関係を入れてから、`apps/desktop` で開発用のサーバーを動かします。

```bash
npm install          # from repo root — links apps/desktop, web, apps/shared
cd apps/desktop
npm run dev          # Vite renderer + Electron, which boots the Python backend
```

特定のチェックアウトを指定したり、実際の設定から切り離して動かしたりするには、次のようにします。

```bash
HERMES_DESKTOP_HERMES_ROOT=/path/to/clone npm run dev
HERMES_HOME=/tmp/throwaway npm run dev
npm run dev:fake-boot   # exercise the startup overlay with deterministic delays
```

インストーラーをビルドするには、次のようにします。

```bash
npm run dist:mac     # DMG + zip
npm run dist:win     # NSIS + MSI
npm run dist:linux   # AppImage + deb + rpm
npm run pack         # unpacked app under release/ (no installer)
```

macOS と Windows の署名・公証は、必要な認証情報が環境にあれば自動的に実行されます（macOS では `CSC_LINK` / `CSC_KEY_PASSWORD` / `APPLE_*`、Windows では `WIN_CSC_*`）。

### macOS の権限とローカルでの再ビルド（TCC） {#macos-permissions-and-local-rebuilds-tcc}

macOS は、権限の許可（フルディスクアクセス、デスクトップ / ダウンロード / 書類、
アクセシビリティ、オートメーション、マイク）を、アプリの置き場所ではなく*コード署名の識別子*に
紐づけて覚えています。手元でビルドしたアプリや自動更新されたアプリは、識別子を固定した
安定したアドホックの署名で署名されるので、更新をまたいでも許可はそのまま残ります。

いちばん確実にしたい場合、つまり yabai や skhd の利用者が頼っているのと同じ仕組みである
証明書に紐づいた識別子にしたい場合は、自己署名のコード署名証明書を
一度作り、Hermes にそれを使うよう指定します。

1. キーチェーンアクセス → 証明書アシスタント → **証明書を作成…**
2. 名前は `Hermes Local Signing`、識別情報のタイプは*自己署名ルート*、
   証明書のタイプは**コード署名**にします。
3. `hermes config set desktop.macos_signing_identity "Hermes Local Signing"`

次回の更新では、再ビルドされたアプリがその証明書で署名し直されるので、TCC の許可は
すべて残ります。Apple Developer のアカウントは必要ありません。公証された正式なビルドは
自動的に判別され、署名し直されることはありません。

一点だけ注意があります。署名の識別子を変えると（この修正の適用後の最初の更新も含みます）
アプリの識別子が一度だけ変わるので、macOS が最後にもう一度だけ確認を求めます。
それ以降は許可が安定します。権限が反応しなくなった場合は、
`tccutil reset All com.nousresearch.hermes` でリセットして許可し直してください。
