# Hermes Desktop {#hermes-desktop}

Hermes のデスクトップアプリは、CLI やゲートウェイで使うのと **同じ** エージェントを中心に組み立てられたネイティブアプリです。設定も、API キーも、セッションも、スキルも、記憶もすべて同じものを使います。別製品でも簡易版でもなく、同じ Hermes Agent の中核と設定をそのまま使い、今風のよく練られた画面から動かします。端末で `hermes` を使ったことがあるなら、そこで整えたものはすでにここにあり、ここでの操作もそちらに現れます。

動作するのは **macOS、Windows、Linux** です。

:::tip どれがどの画面？
Hermes には、同じエージェントに話しかける入口がいくつかあります。

- **デスクトップアプリ**（このページ） — チャット、設定、管理のために作り込まれた画面を持つネイティブアプリです。
- **CLI**（`hermes`）と **[TUI](/hermes/docs/user-guide/tui/)**（`hermes --tui`） — 端末上の画面です。
- **[Web ダッシュボード](/hermes/docs/user-guide/features/web-dashboard/)**（`hermes dashboard`） — ブラウザーで開く管理画面です。任意で使える **Chat** タブは、擬似端末を通して TUI を埋め込んでいます。

その時々で合うものを選んでください。状態は共有されるので、片方で始めたセッションをもう片方で続けられます。
:::

## インストール {#install}

アプリは [Hermes Desktop の製品ページ](https://hermes-agent.nousresearch.com/desktop) からダウンロードするか、[Hermes Desktop のインストール手順](/hermes/docs/getting-started/installation/) に従ってください。

すでに Hermes を入れているなら、次を実行するだけです。

```bash
hermes desktop
```

いま使っている設定、キー、セッション、スキルがそのまま使われます。

## アプリの中身 {#whats-in-the-app}

デスクトップアプリはチャットを中心に据えたウィンドウで、左のサイドバーから各所へ移動します。複数のエージェントとの会話を同時に扱い、メッセージング連携を設定し、成果物を作り、プロジェクトのフォルダー構成をたどり、いくつものプロジェクトを並行して進められるように作られています。

### チャット {#chat}

アプリの中心です。次のことができます。

- **応答の逐次表示** — エージェントが動いている間、ツールの動きと、まとまったツール呼び出しの要約がその場で見えます。
- **他の入口とまったく同じ会話履歴** — ここで始めたセッションは CLI や TUI で再開でき、その逆もできます。
- **ファイルのドラッグ&ドロップ** — チャット領域のどこにでも落とせば、次のメッセージに添付されます。
- **右側のプレビュー欄** — Web ページ、ファイル、ツールの出力を横に並べて表示しながら、チャットを続けられます。
- **アプリ内ブラウザーのコメントモード** — プレビューのブラウザーバーで **Annotate** を押し、表示中のページの要素をクリック（または枠でドラッグ）して、メモを書きます。保存したコメントは番号付きのピンとしてページに残ります。ピンを保存しても会話は進みません。書き終えたら **Add N comments** で、ピンごとに切り出したスクリーンショットと、各コメントを指す短い指示が入力欄に添えられ、送信は自分で行います。要素へのコメントには、その CSS セレクター、マークアップ、そして配置に関わる算出済みのスタイルが付くので、エージェントは絵から推測するのではなく、あなたのソースの中から該当箇所を見つけられます。パスワードや隠しフィールドの値、キーやトークンらしく見える属性は、マークアップが外に出る前にページ上で伏せられます。数が多い場合は、ページのどの部分にあるコメントかでまとめられて届くので、20 個ほどのコメントが 1 件ずつの作業ではなく、いくつかのまとまった作業になります。しかもそれぞれのまとまりは別々の DOM の枝なので、たいてい触るファイルも別になり、並行して作業者に渡しても安全です。ピンの番号は 1 つ消しても崩れず、チャットを切り替えると積み重ねは消えます。
- **入力欄の履歴と、待ち行列の編集** — 何も入力していない状態で上下の矢印キーを押すと、以前の指示を呼び戻して使い回せます。送信待ちに並べたメッセージも、送られる前なら編集できます。待ち行列がある状態で Stop（または Esc）を押すと行列は一時停止し、入力欄の上に展開されます。そこから再開したり、1 件ずつ送信・編集・削除したりできます。
- **会話の時系列バー** — 長いチャットには、やり取りの端に沿って細い目印の帯が出ます。指示 1 つにつき 1 つの目印です。重ねると指示の一覧が開き、クリックすると会話のその位置へ一気に移動します。（何度かやり取りをすると現れます。）
- **ページ内検索** — **Cmd/Ctrl+F** で検索バーが開き、表示中の会話を検索できます。Enter / Shift+Enter（バーを開いている間は Cmd/Ctrl+G / Cmd/Ctrl+Shift+G でも可）で一致箇所を順に送り、Esc で閉じます。

#### ステータスバー {#status-bar}

チャットの下端に並ぶバーには、セッションの現在の状態が表示され、設定を開かずに素早く操作できる項目が並びます。

- **セッションごとの YOLO 切り替え** — このセッションだけ YOLO を切り替えます（TUI と同じ挙動です）。YOLO は危険なコマンドの承認確認を飛ばすので、何を外しているのかを分かったうえで使ってください。[セキュリティ → YOLO モード](/hermes/docs/user-guide/security/#yolo-mode) をご覧ください。
- **文脈の使用量メーター** — そのセッションの文脈窓が何 % 埋まっているかを、その場で示します。クリックすると **Context Usage** のポップオーバーが開き、種類ごと（システムプロンプト、ツールの定義、スキル、記憶、ルール、MCP、サブエージェントの定義、そして会話そのもの）のトークン内訳が見えるので、圧縮が始まる前に何が窓を食っているのかが正確に分かります。
- **キャッシュのヒット率と 1 秒あたりのトークン数** — 既定では表示されません。右クリックのメニューから有効にします。キャッシュのヒット率は、このセッションの入力トークンのうちプロバイダーのプロンプトキャッシュから返された割合です（キャッシュされたトークンは安いので、高いほど安く済みます。温まるにつれてセッションが安くなっていく様子が見られます）。1 秒あたりのトークン数は、直近 10 回のモデル呼び出しで平均した出力の速度です。どちらもやり取りの最中に更新されます。
- **表示項目の選択** — ステータスバーを右クリック（**Show in status bar**）すると、何を表示するかを選べます。文脈メーター、キャッシュのヒット率、1 秒あたりのトークン数、作業場所、モデル、承認、やり取りやセッションの経過時間、ターミナル、Command Center、バックエンドのバージョンなどです。バー自体を隠すこともできます（**Cmd/Ctrl+Shift+S** で切り替わります）。

同梱の手元のバックエンドではなく、別の端末で動いている Hermes に対してチャットしたい場合は、下の [離れたバックエンドにつなぐ](#connecting-to-a-remote-backend) をご覧ください。離れた場所でホストされているダッシュボードへの接続がどう働くか（認証の関門、`/api/ws` のチャットソケット、WebSocket の切断コードの見分け方）まで含めた全体像は、[Web ダッシュボード → Hermes Desktop を離れたバックエンドにつなぐ](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend) にあります。

#### リポジトリの検出 {#repository-discovery}

Hermes Desktop は、Projects サイドバーに出す手元の Git リポジトリを、ホームディレクトリを一定の深さまで走査して見つけます。この動きはプロファイルごとに **Settings → Workspace** で、あるいは `config.yaml` で変えられます。

```yaml
desktop:
  repo_scan_enabled: true
  repo_scan_roots: []
  repo_scan_exclude_paths: []
```

- `repo_scan_enabled: false` にすると、ファイルシステムの走査を完全に止めます。そのプロファイルについて、ディスク検出のキャッシュ行は消えます。明示的に登録したプロジェクトと、意図して開いた Hermes セッションから分かったリポジトリは、引き続き使えます。
- `repo_scan_roots` にフォルダーの一覧を設定すると、走査先を絞れます。空の一覧なら、既定のホームディレクトリ走査のままです。
- `repo_scan_exclude_paths` には、その配下をまるごと飛ばしたいフォルダーを指定します。

これらの値を変えると、そのプロファイルのディスク検出キャッシュだけが無効になり、設定に沿った再走査が始まります。**Hide from sidebar** は、これとは別の、項目ごとの整理操作のままです。

#### モデルを選ぶ {#choosing-a-model}

モデルの選択欄は **入力欄** の、マイクのすぐ左にあります。クリックすると、モデル、推論の強さ、高速モードを 1 つのドロップダウンから切り替えられます。

- **入力欄の選択は画面上の状態であり、既定値には触れません。** 選択は端末ごとに手元で覚えられ、新しいチャットや再起動をまたいで **引き継がれます**。既定値に戻ることはありません。一度選べば、次の `Cmd/Ctrl+N` はそのモデルで開きます。チャットを開いている状態でモデルを切り替えると、変更はその **いま開いているチャット** に限られます。どちらの場合も、選択はセッションの作成や切り替えのときに一緒に運ばれ、プロファイルの既定値として書き込まれることは **ありません**。例外が 1 つあります。`model.default` や `model.provider` をまだ設定していない新しいプロファイルでは、最初の選択が保存されます。そうしないと、再起動したときに紛れ込んだ API キーの環境変数に頼ることになり、本当の既定値がないからです。保存の扱いは `/model` と同じ規則（`model.persist_switch_by_default`）に従います。既定値を意図して変えるときは **Settings → Model** を使ってください。（[プロファイル](#sessions--profiles) を切り替えると、そのプロファイル自身の既定値が読み直されます。）
- **既定値は Settings → Model で設定します。** その「主」モデルが **プロファイルごとの全体の既定値** です。新しいチャット、cron、サブエージェント、補助的な処理はそこから始まり、これを書き込むのはこの場所だけです。[プロファイル](#sessions--profiles) はそれぞれ自分の既定値を持ちます。
- **モデルごとの強さと高速モードの記憶。** デスクトップアプリでは、モデルごとに推論の強さと高速モードの選択を覚えていて、そのモデルを選ぶたびにセッションへ適用し直します。これはデスクトップ側の便利機能で、cron やサブエージェントを変えるものではありません。
- **チャットの途中で切り替えるとプロンプトキャッシュが無効になります。** 開いているチャットの中でモデルを切り替えると、次のメッセージは会話全体を入力の正規料金で読み直します（プロバイダーのプロンプトキャッシュはモデルごとに分かれているからです）。たまになら問題ありませんが、長いチャットでは、行ったり来たりするより新しいモデルで新しいチャットを始めたほうが安く済むことがよくあります。

### ファイルブラウザー {#file-browser}

アプリを離れずに作業ディレクトリを見て回り、中身を確認できます。エージェントがファイルを読み、書き、直していく様子を追うのに便利です。最初のプロジェクトディレクトリは `hermes desktop --cwd <path>`（または環境変数 `HERMES_DESKTOP_CWD`）で指定します。

### 成果物 {#artifacts}

**Artifacts** の画面は、セッションが生み出したもの — **画像、ファイル、リンク** — を 1 つの検索できるギャラリーに集めます。サイドバー、コマンドパレット（**Artifacts — Browse generated outputs**）、あるいは自分で割り当てた `nav.artifacts` のショートカットから開けます。最近のセッションの出力は自動で取り込まれます。どの成果物にも、それを生んだセッションが示され、そのチャットへ戻れます。画像やファイルはプレビューで開き、ダウンロード、ブラウザーで開く、コピーの操作ができます。

### ウィンドウ、タブ、ペイン {#windows-tabs-panes}

このアプリは、いくつものことを同時に進められるように作られています。

- **タブ** — **Cmd/Ctrl+T** で新しいセッションのタブが開きます。**Ctrl+Tab** / **Ctrl+Shift+Tab** でセッションを順に切り替え、**Ctrl+1…9** で最近のセッションへ位置指定で飛べます。**Cmd/Ctrl+W** で選択中のタブを閉じ、**Cmd/Ctrl+Shift+T** で最後に閉じたものを開き直します。
- **複数のウィンドウ** — **Cmd/Ctrl+Shift+N** で新しいウィンドウが開きます。どのセッションも、右クリックメニュー（**New window**）やコマンドパレットから独立したウィンドウに切り出せます。切り出したウィンドウは、全体のサイドバーなしでそのチャットだけを表示します。長く動くセッションを別のモニターに置いておくのに便利です。エージェントの出力は、そのセッションを表示しているすべてのウィンドウへ流れます。
- **ペイン** — **Cmd/Ctrl+B** で左のサイドバー、**Cmd/Ctrl+J** で右のサイドバーを切り替え、**Cmd/Ctrl+\\** でサイドバーの左右を入れ替えます。

### ターミナル {#terminal}

右のサイドバーには、ファイルブラウザーの隣に本物のターミナルがあります。

- **Ctrl+`** でターミナルを表示します（1 つもなければ新しく開きます）。**Ctrl+Shift+`** でもう 1 つ増やせます。複数のターミナルはタブの帯に並び、**Ctrl+Shift+↓/↑** で行き来し、**Ctrl+Shift+W** で選択中のものを閉じます。
- **隠れていてもシェルは生き続けます。** パネルを閉じたり隠したりしても、シェルは止まりません。開いているターミナルはすべて、履歴も動作中のプロセスもそのままに保たれ、明示的に閉じるまで残ります。
- **Add to chat** — ターミナルの出力を選び、次のメッセージの材料として入力欄へ送れます。

### Git のレビューと worktree {#git-review-worktrees}

Git リポジトリの中で動いているセッションには、バージョン管理の画面が組み込まれています。

- **レビューのペイン** — **Cmd/Ctrl+G** で作業ツリーのレビューペインを開閉します。ブランチと進み・遅れの状況、変更されたファイル（一覧表示かツリー表示）、そして **Uncommitted**、**Branch**、**Last turn**（直近のやり取りでエージェントが変えた分だけ）に絞った差分が見られます。ファイルのステージや取り消し、変更の巻き戻し、コミットメッセージの記入（**Generate commit message** で生成も可能）ができ、**Commit** や **Commit & Push** を実行できます。GitHub CLI（`gh`）を使った **Create PR** や、まるごとエージェントに任せる **Ask Hermes to open PR** もここからです。ブランチの作成と切り替えもここでできます。
- **worktree** — **Cmd/Ctrl+Shift+B**（またはサイドバーでプロジェクトの **New worktree**）で、新しいブランチ上に Git の worktree を作ります。これにより、いまのチェックアウトに触れずに、エージェントがリポジトリの並行した複製で作業できます。worktree はプロジェクトの下に独立した並びとして現れます。取り除くときは、worktree のディレクトリを削除する（ブランチは残ります）か、ディスクに残したまま並びから隠すかを選べます。コミットしていない変更があるときは、強制するかどうかも選べます。

### 記憶のグラフ {#memory-graph}

**Memory Graph**（コマンドパレット → *Memory Graph*、またはステータスバーの項目）は、Hermes があなたのために学んだことを地図にしたものです。スキルと記憶が、拡大縮小できるノードのグラフとして時系列とともに並び、**All / Used / Learned** で絞り込めます。共有の操作から、地図の配置を短いコードとして書き出して人に渡せます（配置だけで、記憶やスキルの中身は含まれません）。同じ形でコードを取り込むこともできます。

### Quick Entry {#quick-entry}

Quick Entry は、**システムのどこからでも呼び出せる全体ホットキー** で開く、小さな入力欄です。主ウィンドウに切り替えることなく（開いてすらいなくても）、指示を投げられます。**Settings → Advanced → Quick Entry** で有効にします。既定のショートカットは **Ctrl/Cmd+Shift+Space** で、自分で決めることもできます（修飾キーを 1 つ以上含める必要があります）。その組み合わせを別のアプリが既に使っている場合は、設定の行がそれを知らせるので、別のものを選べます。

### 音声 {#voice}

Hermes に話しかけ、その返事を聞けます。ほかの場所でも使える [音声モード](/hermes/docs/user-guide/features/voice-mode/) と同じものです。macOS では、マイクの利用許可が最初に一度だけ確認されます。

### HUD モード {#hud-mode}

**⌘/Ctrl+Shift+H**（またはタイトルバーのボタン）で、チャットを枠のない常に手前の細いバーとして切り離し、いま作業している画面の上に浮かせます。アプリのウィンドウは脇に退き、HUD には進行中の会話と入力欄が残ります。どこに置くかが文脈になります。バーの位置から、どのアプリのどの画面について尋ねているのかを Hermes が読み取るので、「これ」「ここ」「そのページ」がバーの下にあるものを指します。

- **バーを動かす** — macOS と Windows では、入力欄のどこかを **長押し** してからドラッグします。Linux / X11 では **Ctrl** を押しながら主ボタンでドラッグすると、すぐつかめます（選択中の文字の上でも同じです）。長押しも引き続き使えます。つかんだまま仮想デスクトップ切り替えのショートカットを押せば、HUD を別の仮想デスクトップへ連れていけます。ネイティブの Wayland では、入力欄のバーがコンポジター側のドラッグ用の取っ手になります（アプリが自分のウィンドウ位置を決められないため、これが唯一の動かし方です）。
- **大きさを変える** — バーの端や角をドラッグします。反対側の端は固定されたままです。ネイティブの Wayland では右端と下端だけが使えます。コンポジターが、アプリ自身に最上位ウィンドウの位置決めを許していないからです。
- **配置を戻す** — バーにある破棄の操作で、既定の大きさと（X11 / macOS / Windows では）位置に戻ります。保存された大きさのせいで HUD が使いものにならなくなったときに使ってください。
- **ポインターの位置へ寄せる** — **⌘/Ctrl+Shift+G**（全体ホットキーなので、どのアプリからでも効きます）で、HUD がカーソルのある場所へ飛びます。ネイティブの Wayland では何も起きません。配置はコンポジターが握っているからです。
- **抜ける** — バーの終了ボタンを押すか、もう一度 **⌘/Ctrl+Shift+H** を押します。セッションはそのままで、アプリのウィンドウが戻ります。

#### Linux / Wayland {#linux-wayland}

Electron 20 以降は、Wayland のセッションではすでにネイティブの Wayland クライアントとして動きます。その経路では、ドラッグ、クリックの透過、大きさの変更が働きます。

**Hyprland**（Omarchy を含む）では、HUD がマップされたあとにコンポジターの IPC を通して浮かせて固定します。そうしないと Hyprland がほかのウィンドウと同じようにタイル配置してしまい、`always-on-top` は無視され、コンポジター側のドラッグも効きません。追加のウィンドウルールは要りません。

一部のコンポジター（とくに COSMIC）は、ネイティブの Wayland ウィンドウに対して `always-on-top` を無視します。そこで固定を効かせたい場合は、XWayland の下でアプリを動かしてください。

```yaml
desktop:
  ozone_platform_hint: x11
```

これは起動時に `ELECTRON_OZONE_PLATFORM_HINT` へ橋渡しされます（明示的な環境変数のほうが優先されます）。引き換えとして、X11 はマウスを無視したウィンドウを元に戻せないため、HUD はクリックが透過しない普通のウィンドウのままになります。KDE の環境では、X11 の ozone バックエンドでキーボードが効かなくなるという報告もあります。常に手前に固定したい事情がなければ、この設定は `auto` のままにしておいてください。

### 設定と初回の案内 {#settings-onboarding}

プロバイダー、モデル、ツール、認証情報を、YAML を編集せずに本物の画面から管理できます。初回の案内は、最初のメッセージまで数秒で連れていってくれます。設定の各画面は、プロバイダーとキー、モデルの選択、ツールセットの設定、MCP サーバー、ゲートウェイ、セッションの管理を扱います。

- **プロバイダーの設定画面** — 推論のプロバイダーを管理する専用の場所です。アカウントと API キーの画面から、サインインしてプロバイダーごとに認証情報を保存できます。この中の **Local Models** の画面では、端末上で動く llama.cpp の実行環境を入れて管理します。[ローカルモデル](/hermes/docs/user-guide/local-models/) をご覧ください。
- **メニューにすべてのプロバイダーとモデルが並びます** — GUI には、プロバイダーの一覧と `hermes model` が知っているすべてのモデルが出るので、選りすぐりの一部ではなく、CLI と同じ品揃えから選べます。
- **xAI Grok の OAuth** — Grok は起動画面で正式に扱われる OAuth のプロバイダーです。ほかの OAuth のプロバイダーと同じく、ブラウザーの流れでサインインします。
- **ツールのバックエンドを GUI から導入** — ツールのバックエンドの導入後の手順を、端末に降りずにアプリから直接実行できます。
- **ターミナルのフォント選択** — **Settings → Appearance** で、入っているフォントを選べます。`MesloLGS NF` のような Nerd Font を使えば、対話用でもエージェント用でもターミナル上で Powerlevel10k の区切りやアイコンが描かれます。この設定はプロファイルごとに保存されます。
- **起動時に前回のチャットを開く** — 既定では、アプリを立ち上げ直したときに前回の続きから始まります。常に新しいチャットで始めたい場合は **Settings → Appearance** で切るか、`config.yaml` に `display.resume_last_session: false` を設定してください。ディープリンクや明示的な行き先は、どちらの設定でも上書きされません。
- **補助モデルについての注意** — 主モデルを新しいプロバイダーに切り替えたのに、補助的な処理（タイトル付け、要約などの手伝い）が別のプロバイダーに固定されたままだと、アプリが知らせます。気づかないうちに 2 つのプロバイダーへ作業が分かれてしまうのを防ぐためです。
- **VS Code Marketplace のテーマ** — 組み込みのテーマに加えて、外観の設定から VS Code Marketplace をその場で検索できます。好きな配色テーマを選ぶと、アプリがダウンロードして変換し、デスクトップのテーマとして取り込みます。同じ取り込み機能はコマンドパレット（*Install theme*）からも使え、取り込んだテーマは外観の設定から削除できます。
- **コンピューターを起きたままにする** — **Settings → Advanced → Keep computer awake** を使うと、端末がスリープしなくなるので、長時間や夜通しのエージェントの実行が止まりません（画面は暗くなることがあります）。これはコンピューターごとの設定です。

初回の案内は統一されたオーバーレイの設計に作り直されています。**Choose provider later** を選べば、プロバイダーの設定を飛ばして先にアプリへ入れます。

#### プロファイルごとの設定: 「Applies to」の範囲 {#per-profile-settings-the-applies-to-scope}

[プロファイル](/hermes/docs/user-guide/profiles/) が 2 つ以上あると、設定ファイルに紐づく設定ページ — **Model、Workspace、Safety、Memory & Context、Voice、Chat、Advanced、Tools & Keys** — と **Messaging** のオーバーレイの上部に、共通の **Applies to** のチップ列が出ます。ここで、編集の対象となるプロファイルを選びます。

- 既定の選択は **いま使っているプロファイルに従います**。これは以前とまったく同じ挙動で、使っているプロファイルを編集する形です。
- 別のプロファイルを選べば、アプリ全体を切り替えずに *そのプロファイルの* 設定を見て編集できます。設定ページを移動しても選択は保たれます。
- アプリの使用中プロファイルを切り替えると、この選択はリセットされます。以前に選んだプロファイルへ、気づかないまま編集が入り続けるのを防ぐためです。
- プロファイルが 2 つ未満のときは、このチップ列自体が表示されません。

（Gateways のページは **Per-profile overrides** の項でプロファイルを別の形で扱います。Capabilities と Scheduled Jobs の画面は、それぞれ独自の範囲選択を持っています。）

### 管理の画面 {#management-panes}

アプリは、端末に降りなくて済むように、Hermes の管理まわりも幅広く画面にしています。

- **Skills** — [スキル](/hermes/docs/user-guide/features/skills/) を探し、入れ、管理します。Skills タブには、入れてあるスキルが有効・無効の切り替えとともに並び、その下に Hermes に同梱されている任意スキルの一覧が続きます。各項目にはワンクリックの **Install** ボタンがあり、完了するとその行が導入済みの一覧へ移ります。
- **記憶のグラフ（Star Map）** — チャットで `/journey`（別名 `/learning`、`/memory-graph`）と打つと、学んできたスキルと記憶が時間とともに並ぶ星座のような画面が開き、再生用のつまみで時間をたどれます。ノードはこのパネルから直接編集・削除できます（スキルは保管され、記憶は取り除かれます）。[学びの軌跡](/hermes/docs/user-guide/features/memory/#learning-journey-journey) をご覧ください。
- **Cron** — [定期実行のジョブ](/hermes/docs/reference/cli-commands/#hermes-cron) を確認して管理します。
- **Profiles** — [Hermes のプロファイル](/hermes/docs/user-guide/profiles/)（設定・スキル・セッションが独立したもの）を切り替えます。
- **Messaging** — ゲートウェイの連絡経路を設定します。
- **Agents** と **Command Center** — 複数のエージェントで進める作業のための画面です。

### Bot Mode（組み込み） {#bot-mode-built-in}

**Bot Mode** はアプリに同梱され、既定で有効です。「エージェント 1 体につきチャット 1 つ」の
一覧で、[Hermes のプロファイル](/hermes/docs/user-guide/profiles/) がそれぞれボットとして現れます。自分の
アバター（幾何学的な顔、アップロードした画像、AI が生成した肖像、ドット絵の
ペット）、唯一の **Bot Chat** の会話、そして自分の **Routines**
（Hermes の cron に支えられた繰り返しの作業）を持ちます。一覧は左の
サイドバーで、会話の隣のタブ — **Sessions | Bots** のタブの
帯 — として置かれます。セッション一覧の下に積む 2 つ目のペインではありません。
以前の積み重ね型の配置になっていた環境は、一度だけ自動でタブの帯へ
移されます。自分でペインを配置していた場合は、その配置には手を付けません。
**Cronjobs**（Routines）のペインは、Bots タブを開いている間だけチャットの横に並び、
Sessions に戻ると消えます（古いデスクトップでは常に表示されたままです）。

新しいエージェントはこの一覧から作れます。
Name / Title / Description に加えて、Advanced を開けば設定できるものが
すべて出ます（モデル、SOUL、スキル、ツールセット、MCP サーバー）。セクションに
まとめたり、複数のボットが一緒に検討するグループチャットを開いたりもできます。
グループチャットは Discord のような独立した行として一覧に現れ — 参加者の
アバターが重なり、参加人数、その部屋の直近の一言の抜粋、そして
「needs you」のバッジが付きます — ボットの行と同じ、固定と新しさによる
並び順の中に混ざります。グループの行をクリックすると、その部屋が
**主チャットのウィンドウ** を占めるタブとして開きます（古いデスクトップでは
ボットの側パネルの中に開きます）。

ボット同士もメッセージを送り合います。どのチャットでも `@researcher have a look at this` と打てば、
いま話しているボットがそのメッセージを引き渡し、結果を報告します。ボットは
互いの Bot Chat へ直接届きます（`hermes -p <bot> chat`）。バックエンドは、
各ボットの唯一の **Bot Chat** セッションにメッセージの取り決めを
自動で教えます（設定は `agent.bot_mode_protocol`、既定は有効）。仲間のボットが
CLI から画面なしで開いたときも同じです。そのため、あなたの SOUL.md に触れることなく
ボット同士の返信と引き渡しが動き、通常のセッションにも影響しません。

Bot Mode のセッション — 各ボットの唯一の Bot Chat と、グループチャットの
参加者セッション — は、全体の Sessions サイドバーからは常に隠れています。
それらは Bots ペインの中（一覧の行、部屋の表示、各ボットのセッション
一覧）にあり、あなた自身の会話と混ざることはありません。

使っていないボットはしまっておけます。ボットの行を右クリック → **Hide
Bot** です。隠れたボットは一覧から消えますが、働き続けます。@メンションは
これまでどおり解決され、グループチャットの所属もそのままです。1 つでも隠すと
Bots のヘッダーに目のアイコンが現れます。クリックすると隠れているボットが
薄く表示され（右クリック → **Unhide Bot** で戻せます）、隠れているボットに
未読の動きがあると目のアイコンに点が付きます。隠しているかどうかは
ボットのプロファイルに保存されるので、端末をまたいでも引き継がれます。

要らない場合は **Settings → Plugins → Bots** で切ってください。一覧、
Routines ペイン、入力欄の中間処理がその場で解除されます。再起動は要りません。

エージェントの作成（複数の端末にまたがる **Create on** の選択欄を含む）、
接続をまたいだ一覧、ボット同士のメンション、グループチャットで誰が返すかの
決まり方まで含めた案内は [Bot Mode: エージェントの一覧](/hermes/docs/user-guide/bot-mode/) にあります。

### キーボードと移動 {#keyboard-navigation}

- **コマンドパレット** — **Cmd+K** または **Cmd+P**（Windows / Linux では Ctrl+K / Ctrl+P）を押すと、キーボードから操作を呼び出してアプリの中を移動できます。任意のページや設定の項目を開く、タイトルや id でセッションへ飛ぶ、モデル・テーマ・配色モードを切り替える、ターミナルを開く、ゲートウェイを再起動する、Hermes を更新する、などです。
- **割り当てを変えられるショートカット** — **Settings → Keyboard Shortcuts**（または **Cmd/Ctrl+/**）でショートカットのパネルが開き、ほとんどの割り当てを変えられます。プロファイルの切り替え、セッションの移動、表示の切り替え、そしてデスクトップのプラグインが追加したショートカットも対象です。重複した割り当ては競合として示されます。覚えておくとよい既定値をいくつか挙げます。**Cmd/Ctrl+N** で新しいセッション、**Cmd/Ctrl+.** で Command Center、**Cmd/Ctrl+,** で設定、**Cmd/Ctrl+Shift+F** でセッションの検索、**Cmd/Ctrl+1–9** でプロファイルの切り替え、**Shift+X** で明暗の切り替えです。
- **拡大縮小の独自ショートカット** — 画面を半段階ずつ拡大縮小できるので、文字の大きさを細かく調整できます。
- **画面の言語切り替え** — アプリの表示言語をアプリ内で変えられます。英語、簡体字中国語（zh-Hans）、繁体字中国語（zh-Hant）、日本語、アラビア語（右から左）、ロシア語に対応しています。

### セッションとプロファイル {#sessions-profiles}

- **セッション一覧の作り直し** — 保管の機能と全般的な整理の仕組みを備えた一覧に作り直されており、数が増えても扱いやすいままです。
- **id でセッションを検索** — 特定のセッションを id から直接見つけられます。
- **複数プロファイルの同時セッション** — 複数の [プロファイル](/hermes/docs/user-guide/profiles/) にまたがるセッションを同時に動かせます。プロファイルをまたぐ `@session` のリンクで、別のプロファイルのセッションを参照することもできます。
- **プロファイルの書き出しと取り込み** — 設定一式を 1 つのファイルとして渡せます。**⌘K → Export profile…**（またはレールにあるプロファイルの四角を右クリック）で、スキル、記憶、人格、cron、プラグイン、設定を含む `.tar.gz` が書き出されます。API キーは取り除かれます。デスクトップから書き出すと、見た目と画面まわり — スキン、明暗のモード、独自のテーマ、そのプロファイルのレールの色、ウィンドウの配置 — も一緒に入るので、取り込んだプロファイルは送り手が見ていたとおりの姿で現れます。取り込みは **⌘K → Import profile…**、またはレールの **+** の隣のボタンから行います。上書き分を適用して、その新しいプロファイルへ切り替わります。同じ書庫は、チャットの `/export` / `/import` でも、シェルからの `hermes profile export` / `import` でも使えます。[プロファイルのファイルを書き出す・取り込む](/hermes/docs/user-guide/profile-distributions/#export-and-import-a-profile-file) をご覧ください。

## 更新する {#updating}

アプリは裏側で更新を確認し、用意ができるとワンクリックの更新を案内します。

デスクトップアプリと、それが話しかける Hermes のバックエンドは、別々のタイミングで更新されます。アプリの本体はあなたの端末に、バックエンドはそれが動いている場所にあります。更新の対象が複数ある場合（離れたゲートウェイや、登録済みの複数のゲートウェイ）、更新の入口 — About パネルの **Update now**、⌘K の **Update Hermes** の行、更新の準備ができたときの通知 — はいずれも **すべて** を更新します。まず接続しているバックエンド、次に対象となるほかの登録済みゲートウェイ（Hermes Cloud の項目は提供側で管理されるため飛ばされます）、そして最後にデスクトップアプリ本体です。クライアント側の更新を当てるとアプリが再起動するからです。端末が 1 台だけの環境では、これまでどおりボタン 1 つで済みます。

バックエンドを更新したあと、アプリは自分自身のバージョンも確認し直し、GUI がまだ古ければワンクリックの **Update desktop app** を添えて知らせます。離れたバックエンドを更新したせいで、気づかないまま古いデスクトップを使い続けることはありません。

[手動での更新手順](https://hermes-agent.nousresearch.com/docs/getting-started/updating) も GUI で使えます。

## アンインストールする {#uninstalling}

**Settings → About → Danger zone** を開き、どこまで取り除くかを選びます。

- **Uninstall Chat GUI only** — デスクトップアプリとそのデータだけを取り除きます。Hermes のエージェント、設定、チャットは残ります。（`hermes uninstall --gui` と同じです。）
- **Uninstall GUI + agent, keep my data** — アプリとエージェントを取り除きますが、あとで入れ直せるように設定、チャット、秘密情報は残します。（`hermes uninstall` と同じです。）
- **Uninstall everything** — アプリ、エージェント、そしてすべての利用者データを取り除きます。（`hermes uninstall --full` と同じです。）

処理を終えるためにアプリは閉じます（動作中のアプリ本体と自分の venv を取り除けるよう、後片付けは終了後に走ります）。手元にエージェントが入っていない場合（たとえば離れたバックエンドにつないだ GUI だけの軽量なクライアント）、エージェントを取り除く選択肢は自動的に隠れます。

同じことは端末からもできます。GUI だけなら `hermes uninstall --gui`、エージェントも含めるなら `hermes uninstall` か `hermes uninstall --full` です。

:::note
**ソースのチェックアウト**（`hermes desktop` の開発ビルド）から `hermes uninstall --gui` を実行すると、作業領域の `node_modules` と `apps/desktop/{dist,release}` のビルド成果物も取り除かれます。これらは GUI のビルド成果物だからです。`hermes desktop`（または `npm install` と再ビルド）で元に戻せますが、デスクトップアプリ自体に手を入れている最中なら、そのあと依存関係を入れ直すことになると考えておいてください。
:::

## CLI 早見表: `hermes desktop` {#cli-reference-hermes-desktop}

CLI から起動するには `hermes desktop` を実行するだけです。既定では、作業領域の Node の依存関係を入れ、いまの OS 向けに展開済みの Electron アプリをビルドし、そのパッケージ済みの成果物を起動します。

| フラグ | 説明 |
| -------------------- | ----------------------------------------------------------------------------------------- |
| `--skip-build`       | npm の install とパッケージ処理を飛ばし、`apps/desktop/release` にある展開済みのアプリを起動します |
| `--force-build`      | 内容の刻印が一致していても、まるごと再ビルドします |
| `--build-only`       | デスクトップアプリをビルドするだけで起動しません（`hermes update` が使います） |
| `--source`           | パッケージ済みのアプリではなく、`apps/desktop/dist` に対して `electron .` で起動します |
| `--cwd PATH`         | デスクトップのチャットセッションの最初のプロジェクトディレクトリを指定します（`HERMES_DESKTOP_CWD` を設定します） |
| `--hermes-root PATH` | アプリが使う Hermes のソースの起点を上書きします（`HERMES_DESKTOP_HERMES_ROOT` を設定します） |
| `--ignore-existing`  | バックエンドを決めるとき、すでに `PATH` にある `hermes` を無視させます |
| `--fake-boot`        | 起動画面を確かめるために、決まった長さの起動待ちを入れます |

## 仕組み {#how-it-works}

パッケージ済みのアプリには、Electron の外枠と、React で書かれたネイティブのチャット画面が入っています。初回の起動時には、Hermes Agent の実行環境を `HERMES_HOME`（`~/.hermes`、Windows なら `%LOCALAPPDATA%\hermes`）へ入れられます。これは **CLI でインストールしたときとまったく同じ構成** で、だからこそ両者は行き来できます。バックエンドの決め方は、まず `HERMES_DESKTOP_HERMES_ROOT`、次に完了した管理下のインストール、次に `PATH` 上で見つかった `hermes`（`--ignore-existing` や `HERMES_DESKTOP_IGNORE_EXISTING=1` が設定されていない場合）、最後に Nix のようなパッケージ作成者向けの明示的な `HERMES_DESKTOP_HERMES` による上書き、の順です。React の描画側は、アプリが立ち上げる画面なしのバックエンド — `tui_gateway` の JSON-RPC / WebSocket API を提供する `hermes serve` のプロセス — と話し、`hermes --tui` を抱え込むのではなくエージェントの実行環境を再利用します。デスクトップアプリは **それだけで完結** しています。自前の `hermes serve` のバックエンドを動かし、[Web ダッシュボード](/hermes/docs/user-guide/features/web-dashboard/) を開くことも必要とすることもありません。（`serve` コマンドより古い実行環境では、自動的に画面なしの `dashboard --no-open` に切り替わるので、アプリの更新がバックエンドを追い越すことはありません。）インストール、バックエンドの決定、自己更新の処理は Electron の主プロセスにあります。

## 離れたバックエンドにつなぐ {#connecting-to-a-remote-backend}

既定では、アプリは自前の **手元の** バックエンドを起動して管理します。その代わりに、別の端末で動いている Hermes のバックエンド — VPS、自宅のサーバー、Tailscale の内側にある Mini など — を見に行かせることもできます。

接続まわりはすべて 1 つの設定ページにまとまっています。**Settings → Gateways** です。（以前は **Gateway** と **Connections** の別々のページに分かれていました。いまは統合されており、古い `?tab=connections` のディープリンクは統合後のページへ転送されます。）

**Settings → Gateways → Connection mode** で、手元のゲートウェイ以外の選択肢が出ます。

- **Remote gateway** — 自分で動かしている `hermes serve` のバックエンドの URL を入れて、サインインします。この節の残りで説明するのは、この方式です。
- **Hermes Cloud** — Hermes Cloud に一度サインインし、アカウントにあるエージェントから選びます。URL を貼り付ける必要はありません。アプリがあなたのエージェントを見つけ（アカウントが複数の組織にまたがる場合は組織の選択欄が出ます）、どれかにつなぐとセッションが自動で切り替わります。接続している間は、ステータスバーにクラウドの接続が表示されます。

ゲートウェイの接続は **端末単位** です。Gateways のページは、このデスクトップがどのゲートウェイのバックエンドにつなげるかを管理し、プロファイルはつないだゲートウェイ *から* 見つかります。セッションは一度に 1 つのゲートウェイを選び、その隣のプロファイルのレールは、そのゲートウェイ上で見つかったプロファイルを選びます。

### 複数接続の登録 {#the-multi-connection-registry}

同じ **Settings → Gateways** のページを下へ進むと、**Registered gateways** で、アプリが知っているすべての Hermes ゲートウェイに名前を付けた一覧を管理できます。手元の実行環境、いくつでも登録できる離れたゲートウェイ（LAN、Tailscale、インターネット)、Hermes Cloud の環境、SSH の接続先が、すべて 1 か所にまとめて保存されます。サイドバーのプロファイルのレールの右端にあるプラグのボタン（**Connect another Hermes gateway…**）や、**⌘K → Gateways** からも開けます。まとめたエージェントの一覧、`@name-device` の呼び名、まとめての更新、プラグイン SDK の窓口まで含めた案内は [デスクトップを複数の Hermes 環境につなぐ](/hermes/docs/user-guide/multi-connection-desktop/) にあります。

- **接続にはそれぞれ固有の名前が要ります**（「Homelab」「Work laptop」のような端末名です）。同じプロファイル名が複数の登録済みゲートウェイに存在する場合、各所で `@profile-device` の形で区別されます（たとえば `@research-homelab`）。
- **ゲートウェイは Sessions のサイドバーから切り替えます。** ゲートウェイを 2 つ以上登録すると名前付きの選択欄が現れ、登録がいくつになっても、ゲートウェイがプロファイルのように見えてしまうことなく扱えます。隣のプロファイルのレールにはそのゲートウェイのエージェントだけが並び、そこで最後に使ったプロファイルを覚えています。プロファイルが多い場合は、そちらはそちらでまとまって表示されます。
- **起動時に何を開くかを選べます。** **Open on launch** は、従来どおりの **Primary gateway** を既定として保ちますが、接続に成功したあとに **Last used** のゲートウェイを再開させることもできます。この設定はアプリ本体の外に保存されるので、デスクトップの更新をまたいでも残ります。
- 接続の **追加・編集・削除・確認** はこのパネルから行います。**Add** では 4 種類すべて — **Local**、**Hermes Cloud**、**Remote gateway**、**SSH** — を選べます（アプリが管理する手元の項目がある間、Local のボタンは押せません。クラウドの追加については、上のサインインと検出の流れを案内するヒントが出ます）。手元の項目はアプリが管理しているので削除できません。**Test** は、その接続の HTTP と WebSocket の経路をそれぞれ直接確かめます。
- **重複は保存時に弾かれます**。**local** の項目は常に 1 つだけです。離れたゲートウェイとクラウドの項目は、正規化した URL（前後の空白を除き、末尾のスラッシュを外し、小文字にしたもの。両方の種類をまたいで比較します）で重複を判定します。SSH の項目は、正規化した `user@host:port` と接続先のプロファイルで判定します。
- 登録の仕組みが入ったビルドを初めて動かしたとき、既存の設定は **自動で取り込まれます**。いまの全体の接続設定と、従来のプロファイルごとの上書きが、名前付きの項目になります。従来の設定ファイルには手を付けないので、古いビルドもそのまま動きます。
- クラウドの項目は、上で説明した Hermes Cloud のサインインと検出の流れから作られるもので、手で打ち込む URL からではありません。
- トークンは OS のキーリングで暗号化して保存されます（キーリングのない Linux では、明示的に選んだ場合のみ平文になります）。

並べての振り分けはすでに動いています。登録された各ゲートウェイは、必要になったときに自分のバックエンドとソケットへつなぎ（接続とプロファイルの組み合わせごとに分かれます）、プラグイン SDK はまとめたエージェントの一覧を提供し（`host.agents()` / `host.ensureAgent()`）、Gateways ページの **Update all instances** は対象となるすべてのゲートウェイへ一度に `hermes update` を送ります。Hermes Cloud の項目は飛ばされ（提供側が更新します）、それぞれの環境が自分の結果を報告します。

:::info 離れたバックエンドとは、動作中の `hermes serve` のプロセスです
「離れたバックエンド」とは、その端末で動いている **`hermes serve`** のサーバーのことです。デスクトップアプリがつなぐ先はこのプロセスです。そのバックエンドが実際に立ち上がっていて到達できない限り、この節の内容はどれも働きません。デスクトップアプリがそれを起動することはありません。あなた（あるいは `systemd` のサービス）が離れたホスト側で `hermes serve` を動かし続け、アプリはそこに取り付きます。メッセージングの経路（Telegram、Discord など）も使うなら、**ゲートウェイ** は *別の* 長く動くプロセスで、そちらは自分で起動します。設定手順のあとの注記をご覧ください。
:::

接続は 2 つの半分でできています。バックエンド側では **認証プロバイダー** で守り、アプリ側ではバックエンドの URL を入れてサインインします。バックエンドをループバック以外のアドレスに割り当てると、自動的に認証の関門が働くようになり、設定したプロバイダーがデスクトップアプリを通す役目を果たします。

**バックエンドがどこにあるかでプロバイダーを選んでください。**

- **OAuth（Nous Portal） — 自分の端末の外から届くものには、こちらが向いています。** ログインは Nous のアカウントに照らして確かめられるので、VPS、公開されたホスト、離れたバックエンド全般に適した選択肢です。`hermes dashboard register`（または Portal の [`/local-dashboards`](https://portal.nousresearch.com/local-dashboards) のページ）でダッシュボードを登録して OAuth クライアントを用意し、アプリから **Sign in with Nous Research** でサインインします。自前の ID プロバイダーを運用している場合は、自己ホストの OIDC プロバイダーも同じように使えます。
- **ユーザー名とパスワード — 手元や信頼できるネットワークでのみ使ってください。** バックエンドが同じ信頼できる LAN にあるか、VPN（たとえば Tailscale）経由でしか届かない場合の、いちばん簡単な選択肢です。外部の ID プロバイダーを使わず、共有の資格情報 1 組で守る方式なので、**インターネットに公開したダッシュボードには使わないでください**。その場合は OAuth を選びます。

この節の残りでは、信頼できるネットワークで手早く立ち上げられるユーザー名とパスワードの手順を示します。OAuth の手順は [Web ダッシュボード → 既定のプロバイダー: Nous Research](/hermes/docs/user-guide/features/web-dashboard/#default-provider-nous-research) をご覧ください。

### バックエンド側（離れた端末）で {#on-the-backend-the-remote-machine}

ユーザー名とパスワードを決め、届くアドレスに割り当ててバックエンドを起動します。資格情報は `~/.hermes/.env`（秘密情報のファイル。パーミッションは 0600）に置きます。

```bash
# 1. Set the dashboard login credentials.
cat >> ~/.hermes/.env <<'EOF'
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
# Recommended: a stable signing secret so sessions survive restarts.
# Without it a random key is generated per boot and you'll be logged out
# on every restart.
HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
EOF
chmod 600 ~/.hermes/.env

# 2. Run the backend bound to a reachable address. The non-loopback bind
#    engages the auth gate; the username/password provider handles login.
hermes serve --host 0.0.0.0 --port 9119
```

デスクトップアプリからつなげるようにしておきたい間は、その `hermes serve` のプロセスを動かし続けてください。止まると、アプリはバックエンドに届かなくなります。ログアウトや再起動をまたいで生き残るよう、`systemd`、`tmux`、あるいは好みのプロセス管理の下で動かしてください。

これとは別に、メッセージングの経路に頼っているなら、離れたホストで **ゲートウェイが動いていること** を確かめてください。デスクトップアプリが話す相手は `hermes serve` のバックエンドですが、Telegram / Discord / Slack のゲートウェイのセッションは別のプロセスで、そちらは自分で起動して動かし続けます。ゲートウェイの設定は [メッセージング](/hermes/docs/user-guide/messaging/) をご覧ください。

パスワードを平文のまま置いておきたくない場合は、代わりに `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH` に scrypt のハッシュを設定します。ハッシュは `python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"` で計算できます。設定できるものの全体（config.yaml のキー、すべての環境変数、流量制限）は [Web ダッシュボード → ユーザー名とパスワードのプロバイダー](/hermes/docs/user-guide/features/web-dashboard/#usernamepassword-provider-no-oauth-idp) にあります。

バックエンドを systemd のサービスとして動かす場合は、そのユニットに `EnvironmentFile=%h/.hermes/.env` を指定して、起動時に資格情報が環境へ入るようにしてください。

:::warning
バックエンドはあなたの `.env`（API キーや秘密情報）を読み書きし、エージェントのコマンドも実行できます。上に示した **ユーザー名とパスワード** の設定は、信頼できるネットワーク向けです。パスワードで守っただけのバックエンドを、そのままインターネットへ公開しないでください。VPN の内側に置きます。[Tailscale](https://tailscale.com/) はすっきりした選択肢です。端末の tailscale の IP に割り当て（`--host <tailscale-ip>`）、Remote URL には `http://<tailscale-ip>:9119` を使えば、あなたの tailnet からしか届かなくなります。インターネット越しにバックエンドへ届かせたい場合は、代わりに **OAuth（Nous Portal）** のプロバイダーを使ってください。
:::

### アプリ側で {#in-the-app}

**Settings → Gateways → Remote gateway** で設定します。

1. **Remote URL** — `http://<backend-host>:9119`（リバースプロキシを前に置いている場合、`/hermes` のようなパスの接頭辞も使えます）
2. **Sign in** — アプリはバックエンドが提示しているプロバイダーを見分け、ボタンを合わせます。ユーザー名とパスワードのバックエンドなら **Sign in** のボタンが出て、資格情報の入力欄が開きます（手順 1 で決めたものを入れます）。OAuth のバックエンドなら **Sign in with `<provider>`**（たとえば *Sign in with Nous Research*）が出て、そのプロバイダーのブラウザーでのサインインが始まります。どちらの場合も、最終的にアプリはバックエンドに対して認証済みのセッションを持ちます。
3. **Save and reconnect** — デスクトップの外枠を、離れたバックエンドへ切り替えます。セッションは自動で更新されます。`HERMES_DASHBOARD_BASIC_AUTH_SECRET` を設定していれば、再起動をまたいでもサインインしたままです。

画面を使わずに、アプリを起動する前に環境変数 `HERMES_DESKTOP_REMOTE_URL` でバックエンドの URL を指定することもできます（アプリ内の設定より優先されます）。サインインは、これまでどおり Gateways の設定パネルから行います。

:::note プロファイルごとの接続先
離れたゲートウェイのホストは [プロファイル](/hermes/docs/user-guide/profiles/) ごとに設定されるので、プロファイルごとに別々の接続先を持つことも（手元のままにしておくことも）できます。プロファイルを切り替えると、アプリがつなぐ先も切り替わります。
:::

### うまくいかないとき {#troubleshooting}

- **サインインが 401 や「Invalid credentials」で失敗する** — ユーザー名かパスワードが、バックエンド側の `HERMES_DASHBOARD_BASIC_AUTH_USERNAME` / `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD` と合っていません。バックエンドは、存在しないユーザーの場合もパスワード違いの場合も同じ一般的なエラーを返すので（どちらなのかを探れないようにするためです）、両方を確かめてください。関門が働いているかどうかは `curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'` で確認できます。`true` が返り、`"basic"` が含まれているはずです。
- **「Sign in」のボタンが出ず、代わりにセッショントークンを求められる** — バックエンドのユーザー名とパスワードのプロバイダーが有効になっていません。`/api/status` の `auth_providers` に `"basic"` が並びません。`~/.hermes/.env` にユーザー名とパスワード（またはパスワードのハッシュ）の両方が設定されていること、そしてダッシュボードのプロセスがそれを実際に読み込んでいることを確かめてください。
- **再起動のたびにサインアウトされる** — `HERMES_DASHBOARD_BASIC_AUTH_SECRET` に変わらない値を設定してください。設定していないと、トークンの署名鍵が起動ごとに作り直され、すべてのセッションが無効になります。
- **接続を拒まれる、または時間切れになる** — バックエンドが `127.0.0.1`（既定）に割り当てられているか、ファイアウォールや VPN がポートを塞いでいます。`0.0.0.0` か tailscale の IP に割り当て、信頼できるネットワークに向けてポートを開けてください。

同じ設定を Web ダッシュボードの側から見た説明は [Web ダッシュボード → Hermes Desktop を離れたバックエンドにつなぐ](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend) にあります。環境変数の一覧は [環境変数 → Web ダッシュボードと Hermes Desktop](/hermes/docs/reference/environment-variables/#web-dashboard--hermes-desktop) にまとまっています。

## デスクトップアプリを拡張する {#extending-the-desktop-app}

デスクトップアプリは、外から足していける作りです。ペイン、ページ、サイドバーの移動、ステータスバーの
項目、パレットのコマンド、キー割り当て、テーマは、すべて 1 つの SDK を通して登録されており、
あなた自身のものを足せます。プラグインは 1 つの ESM ファイルで、
`$HERMES_HOME/desktop-plugins/<id>/plugin.js` に置くだけです。アプリは数秒で読み込み、
保存のたびに再読み込みします。入れたプラグインは **Settings → Plugins** からその場で管理できます。

詳しい内容は [デスクトッププラグイン SDK](/hermes/docs/developer-guide/desktop-plugin-sdk/) を
ご覧ください。（これは [Web ダッシュボードのプラグインの仕組み](/hermes/docs/user-guide/features/extending-the-dashboard/) とは別のものです。）

同じ Settings → Plugins のページにある **Agent plugins** の項では、あなたが入れた
バックエンド（エージェント側）の [プラグイン](/hermes/docs/user-guide/features/plugins/) を管理します。ユーザー、
git、プロジェクト、pip、可搬形式での導入が対象です。リポジトリに同梱されている組み込みのもの（基盤の
アダプター、プロバイダーのプラグインなど）はここには並びません。それらは既定で有効な状態で
配られ、それぞれの画面から設定するからです。おかげでこの項は、自分で足したものだけに
集中できます。プロファイルが 2 つ以上ある場合、この項にも専用の **Applies to** の
選択欄が出るので、アプリ全体を切り替えずに別のプロファイルのエージェントプラグインを
確認したり切り替えたりできます（そのためにバックエンドの
`plugins.manage` RPC は任意の `profile` パラメーターを受け取ります）。

## うまくいかないとき {#troubleshooting}

### 失敗したやり取りは、どの層で失敗したかを示します {#failed-turns-name-the-failing-layer}

やり取りが失敗すると、チャットには **どの層が失敗したか** を示すエラーの
カードが出ます。プロバイダーやモデル、独自のエンドポイント、逐次通信の接続、
認証、請求、ゲートウェイ、手元の実行環境、ディスクといった具合で、
一般的なエラー通知で済ませません。カードには、失敗の内容に合った復旧の操作が並びます。

- **Retry** — 失敗したやり取りをその場で実行し直します（内容の
  ポリシーによる拒否など、やり直しても必ず同じ結果になる場合は表示されません）。
- **Switch provider** — プロバイダー、エンドポイント、認証、請求の失敗のときに、
  Settings → Models へ飛びます。
- **Open logs** — `HERMES_HOME/logs` をファイル管理のアプリで開きます。離れた
  接続やクラウドの接続では、ボタンの表示が **Open Desktop logs** になります。失敗した
  やり取りのゲートウェイやエージェントのログは離れた端末にあるので、
  こちらは手元のデスクトップ側のログ（通信の証跡）を開きます。
- **Send diagnostics** — 明示的な同意の確認のあと、伏せ字処理をした診断情報の束を
  Nous の内部保管先へ送ります（`hermes debug share --nous` と同じ経路です。
  秘密情報は必ず伏せられ、その束を見られるのは Nous の担当者だけで、
  14 日後に自動で消えます）。成功すると、問い合わせのやり取りに貼れる
  非公開の閲覧リンクと、GitHub Issues、Nous Portal のサポート、Discord への
  近道が得られます。離れた接続やクラウドの接続では、バックエンドが自分の
  エージェントやゲートウェイのログをまとめ、手元のデスクトップのログも並べて添えるので、
  サポート側は両方を見られます。
- **Copy error details** — 不具合の報告や Discord に貼れる、短い文字だけの
  まとめ（層、コード、プロバイダーとモデル、エラーの文面）をコピーします。

この層の判定は、エージェントのやり直し処理が使うのと同じ分類器から来ています。
だから、文面からの推測ではなく、実際の失敗の意味を映します。
この情報がなかった頃の古いバックエンドでも、一般的な題名と
Retry / Open logs / Copy error details の操作を備えたカードは表示されます。

起動時のログは `HERMES_HOME/logs/desktop.log` に残ります（バックエンドの出力と、直近の Python のトレースバックも含まれます）。アプリが起動に失敗したと言ってきたら、まずここを見てください。CLI から追いかけることもできます。

```bash
hermes logs gui -f
```

よく使うリセットです。

```bash
# Force a clean first-launch setup (macOS/Linux)
rm "$HOME/.hermes/hermes-agent/.hermes-bootstrap-complete"

# Rebuild a broken Python venv (macOS/Linux)
rm -rf "$HOME/.hermes/hermes-agent/venv"

# Reset a stuck macOS microphone prompt
tccutil reset Microphone com.nousresearch.hermes
```

### 「The host key has CHANGED since you last connected」（SSH の接続先） {#the-host-key-has-changed-since-you-last-connected-ssh-remote}

SSH の接続先を入れ直したり、ホスト鍵を入れ替えたりした場合、SSH は安全側に倒れて
失敗し、デスクトップはやり直さずにエラーの覆いを表示したままにします（古い鍵を消すまで、
やり直しても成功しようがないからです）。その変化が想定どおりであることを確かめ、
古い項目を取り除いてから、覆いのところでやり直してください。

```bash
ssh-keygen -R <host>
```

項目を消したら **Retry** を押します（または Settings → Gateway で接続を適用し直します）。
留め金が外れ、次の起動で新しくつなぎ直します。

### 「Build desktop app」が Electron のダウンロードで止まる {#build-desktop-app-stuck-on-electron-download}

ビルドは Electron の実行環境（約 114&nbsp;MB）を `github.com/electron/electron/releases` から取得します。インストーラーが **Build desktop app** の段階で止まり、出力に `retrying attempt=…` が繰り返し出ている場合、あなたのネットワーク（ファイアウォール、プロキシ、地域）で GitHub が塞がれているか、速度を絞られています。

インストーラーはこれを自分で切り抜けます。ビルドに失敗すると、まず(1) 壊れたキャッシュ済みの Electron の zip を消してやり直し、(2) それでも失敗し、かつ `ELECTRON_MIRROR` を設定していない場合は、Electron の事実上の共同体ミラーである `npmmirror.com` を通してもう一度だけ試します。`@electron/get` はダウンロードの SHASUM を確かめますが、そのチェックサムも同じミラーから来ます。つまり壊れたり途中で切れたりしたダウンロードは捕まえられますが、ミラーそのものが乗っ取られていた場合は別です。第三者のホストを信用したくない場合は、自分の `ELECTRON_MIRROR` を指定してください（下記）。あなたが設定したものを、ビルドが上書きすることはありません。

**自分でミラーを選ぶ**（社内や信頼できるものなど）には、インストールの前に `ELECTRON_MIRROR` を設定するか、手動で再ビルドします。ビルドはこの設定を尊重し、上書きしません。

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ \
  bash -c 'cd "$HOME/.hermes/hermes-agent/apps/desktop" && CSC_IDENTITY_AUTO_DISCOVERY=false npm run pack'
```

壊れたキャッシュ済みの zip を手で消すには、次のようにします。

```bash
rm -f "$HOME/Library/Caches/electron"/electron-*.zip   # macOS
rm -f "$HOME/.cache/electron"/electron-*.zip            # Linux
```

## ソースからビルドする {#building-from-source}

アプリ自体に手を入れたい場合は、リポジトリの起点で作業領域の依存関係を一度入れてから、`apps/desktop` で開発用のサーバーを動かします。

```bash
npm install          # from repo root — links apps/desktop, web, apps/shared
cd apps/desktop
npm run dev          # Vite renderer + Electron, which boots the Python backend
```

特定のチェックアウトを見に行かせたり、本番の設定から隔離したりするには、次のようにします。

```bash
HERMES_DESKTOP_HERMES_ROOT=/path/to/clone npm run dev
HERMES_HOME=/tmp/throwaway npm run dev
npm run dev:fake-boot   # exercise the startup overlay with deterministic delays
```

インストーラーを作ります。

```bash
npm run dist:mac     # DMG + zip
npm run dist:win     # NSIS + MSI
npm run dist:linux   # AppImage + deb + rpm
npm run pack         # unpacked app under release/ (no installer)
```

macOS と Windows の署名や公証は、必要な資格情報が環境にあれば自動で走ります（macOS は `CSC_LINK` / `CSC_KEY_PASSWORD` / `APPLE_*`、Windows は `WIN_CSC_*`）。

### macOS の許可と、手元での再ビルド（TCC） {#macos-permissions-and-local-rebuilds-tcc}

**フォルダーごとの確認を、1 つの設定で全部黙らせられます。** macOS は Hermes が
各フォルダーに触れるたびに種類ごと（デスクトップ、次にダウンロード、次に書類…）に
確認を出します。**フルディスクアクセス** を 1 つ許可すれば、そのすべてを恒久的に
まとめて覆えます。Hermes の署名の識別子は変わらないので、更新をまたいでも残ります。

1. システム設定 → **プライバシーとセキュリティ → フルディスクアクセス**（または
   `open "x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles"` を実行）
2. お使いの端末アプリを有効にします。デスクトップアプリを使うなら **Hermes.app** も。
3. 一度、完全に終了してから起動し直します。

`hermes doctor` は、いまの端末の文脈がすでにこの許可を持っているかを報告し、
持っていない場合は macOS 上の `hermes setup` がこの案内を表示します。

macOS は許可（フルディスクアクセス、デスクトップ・ダウンロード・書類、
アクセシビリティ、オートメーション、マイク）を、アプリのパスではなく *コード署名の識別子* に
紐づけて覚えます。手元でビルドしたアプリや自己更新したアプリは、識別子を固定した
アドホック署名で署名されるので、許可は更新をまたいで残ります。

一度だけの注意です。識別子を固定する署名の修正（PR #73681）*より前* のビルドに与えた
許可は、古い cdhash に紐づいた条件を持っています。macOS はそうした古い許可について
切り替えを ON のまま表示し続けますが、保存された許可が再ビルド後のバイナリと
一致しないため、それでも確認を出し直します。しかも最近の確認画面には許可のボタンが
ないので、確かめ直すものが何もないように見えます。そうなった場合は、古い許可を
一度リセットして与え直してください。

```bash
tccutil reset ScreenCapture com.nousresearch.hermes   # repeat per service
```

そのあとシステム設定で新しい項目を ON にし、Hermes を完全に終了してから起動し直します。
それ以降、許可は安定します。

いちばん確実にしたい場合 — 証明書に裏打ちされた識別子で、yabai や skhd の
利用者が頼っているのと同じ仕組みです — は、自己署名のコード署名証明書を
一度作り、Hermes にそれを使うよう伝えます。次のコマンド 1 つですべてが
済みます（ログイン用のキーチェーンに証明書を作り、`codesign` からの
利用を許可し、設定を書き、パッケージ済みのアプリに署名し直します）。

```bash
hermes desktop --setup-tcc-identity
```

手動で行う場合は、次のとおりです。

1. キーチェーンアクセス → 証明書アシスタント → **証明書を作成…**
2. 名前: `Hermes Local Signing`、識別情報のタイプ: *自己署名ルート*、
   証明書のタイプ: **コード署名**。
3. キーチェーンアクセスで新しい証明書をダブルクリック → **信頼** → 
   **コード署名** を *常に信頼* に設定します（取り込んだ自己署名の証明書は、
   コード署名について信頼されるまで有効な署名の識別子になりません。
   そのあと `security find-identity -v -p codesigning` に並ぶはずです）。
4. `hermes config set desktop.macos_signing_identity "Hermes Local Signing"`

別の名前で証明書を作ったり使ったりするには、コマンドに `--identity <name>` を
付けます（既定は `Hermes Local Signing`）。このコマンドは何度実行しても同じ結果になるので、
更新のあとに実行し直して、設定を指し直し、再ビルドされたアプリに署名し直せます。

次回の更新では、再ビルドされたアプリがその証明書で署名し直されるので、TCC の許可は
すべて残ります。Apple の開発者アカウントは要りません。公証されたリリースのビルドは
見分けられ、署名し直されることはありません。

一度だけの注意です。署名の識別子を変えると（この修正のあとの最初の更新も含みます）
アプリの識別子が一度だけ変わるので、macOS が最後に一度だけ確認を出し直します。
それ以降、許可は安定します。もし許可が引っかかったままになったら、
`tccutil reset All com.nousresearch.hermes` でリセットして与え直してください。
