# Merge Reconciler {#merge-reconciler}

二つの「エージェント」のブランチ間で起きた git のマージ衝突を、どちらにも肩入れしない第三者として解決します。相手の作業とぶつかったときにエージェント自身が解決しようとすると、相手の変更を上書きするか、自分の変更を丸ごと諦めるかのどちらかになりがちです。相手の文脈を持っておらず、自分の側に偏るからです。この skill はその対策で、両方の差分と両者が述べた意図を受け取り、マージキューの調停役のように統合結果を作る中立の仲裁者です。

## 使いどころ {#when-to-use}

- 並行して進めているキャンペーン（かんばん方式の開発パイプライン、並列 PR の一斉投入、複数ワークツリーでのリファクタ）で、二つのエージェントのブランチやワークツリーがぶつかったとき。
- `git merge` や `git rebase` が二つのエージェントの作業の衝突で止まり、どちらの当事者にも自分で裁定させたくないとき。
- 一人のエージェントが自分の作業の中で起こした衝突や、ロックファイル・生成物の些細な衝突には使わないでください（そちらは作り直せば済みます）。

## 前提 {#prerequisites}

- 止まったマージが残っているリポジトリのチェックアウト。または、二つのブランチ名と、自分でマージを実行してよい権限。
- 双方の意図がわかる材料。かんばんの完了サマリー（`terminal` で `hermes kanban show <task-id>` を実行して取得）、PR の本文、少なくとも各ブランチのコミットメッセージ。
- ビルドやテストのコマンド（プロジェクトにあれば）。

## 進め方 {#how-to-run}

**単独で使う** — 衝突したリポジトリの中で、人間（またはエージェント）がこの skill を呼び出します。skill を読み込んだら、手順を上から順に実行します。

**中立のエージェントを立てる** — 複数エージェントのキャンペーンではこちらが望ましい形です。

- `delegate_task`: リポジトリのパス、両方のブランチ名、双方の意図のまとめをそのまま含んだタスク文と、この skill に従うようにという指示を渡して、サブエージェントを立ち上げます。
- かんばんを使う場合: **第三のプロファイル**（どちらの作業者のプロファイルでもないもの）に割り当てた調停用のカードを作り、衝突している二枚のカードを両方とも親として結び付けます — `kanban_create(title="reconcile branch-a x branch-b", assignee="reconciler",
  parents=["t_a", "t_b"])`。親カードへのリンクが双方の完了サマリーを調停役の文脈へ自動的に運んでくれます。カード本文にはリポジトリのパスと二つのブランチ名を書いてください。

## 早見表 {#quick-reference}

| ハンクの種類 | 意味 | 解決の仕方 |
|---|---|---|
| disjoint-intent | 二つの変更は別々の目的のもので、両立できる | 両方を取り込む |
| same-question-different-answer | 一つの設計上の問いに、双方が別々の答えを出した | 述べられた意図に沿って片方を選び、その判断を明示する |
| superseded | 一方の前提が、もう一方の変更によって成り立たなくなった | 生き残る側を残し、理由を書き添える |

中立性の約束: 自分を呼び出した側に有利な判断をしないこと。衝突している箇所だけに手を入れること（ついでの修正はしない）。設計上の問いに対する選択は、必ず引き継ぎのサマリーに明記すること。

## 手順 {#procedure}

### 1. 双方の材料を集める {#1-gather-both-sides}

- `terminal` で実行します。`git status` で衝突している状態と対象ファイルを確認し、`git merge-base <A> <B>` を取り、衝突しているファイルごとに双方について `git log --oneline <base>..<side>` と `git diff <base>..<side> -- <file>` を見ます。マージが止まっている状態では、片方が `HEAD`、もう片方が `MERGE_HEAD` です。
- 双方の意図を集めます。完了サマリーやメタデータなら `hermes kanban show <task-id>`、あるいは PR の本文、または上で見たコミットメッセージから拾います。ファイルに手を付ける前に、片側につき一文で意図を書き出しておきます。
- ここまでできたら次へ: 双方の意図を自分の言葉で言えて、衝突しているすべてのファイルについて双方の差分が手元にある状態です。

### 2. 衝突しているハンクをすべて分類する {#2-classify-every-conflicted-hunk}

- 衝突しているファイルを `read_file` で開き、`<<<<<<<`／`=======`／`>>>>>>>` の各ブロックを見つけます。
- 早見表の種類のうち、ちょうど一つを各ハンクに割り当てます。判断の基準は述べられた意図であって、どちらの変更が見栄えがよいかではありません。
- 一つのハンクに独立した判断が複数含まれている場合（きれいに統合できる新しいロジックに加えて、双方が違う答えを出した見た目や丸め方の選択が混ざっている、など）は、小さな判断に分けてそれぞれを分類します。
- 一つのファイルの中で種類が混ざるのはよくあることです。あるハンクは設計の衝突でも、隣のハンクは両立できる変更かもしれません。ファイル単位ではなくハンク単位で分類します。
- ここまでできたら次へ: すべてのハンクに種類と一行の理由が書かれた状態です。

### 3. 中立性の約束を守って解決する {#3-resolve-under-the-impartiality-contract}

- 各ハンクを `patch` で編集します（ファイル全体を書き直すなら `write_file`）。
  - disjoint-intent → 双方の意図が完全に満たされるように、両方の変更を統合します。
  - same-question-different-answer → 述べられた意図に最もよく応える答えを選びます（たとえば「厳密に検証する」という意図は、その作業が正確さを求めていたなら「手早く既定値で済ませる」より優先します）。どちらも求めていない折衷案を作ってはいけません。
  - superseded → 生き残る側を残し、成り立たなくなった前提を削ります。
- 自分を呼び出した側に有利な判断をしないでください。意図が本当に拮抗するなら、当てずっぽうで決めずにエスカレーションします（かんばんのカードをブロックする、報告して戻す）。
- 衝突マーカーの外は何も変えないでください。整形も、名前の変更も、ついでの修正もしません。
- 解決したファイルは `terminal` から `git add` します。
- ここまでできたら次へ: `search_files` でリポジトリ内に `<<<<<<<` が一つも見つからず、解決したファイルがすべてステージされた状態です。

### 4. 検証する {#4-verify}

- `terminal` からプロジェクトのビルドやテストを実行します。少なくとも、触ったモジュールを読み込むか実行してみてください。統合後の動きの中に双方の意図が見て取れる必要があります（たとえば、A 側の新しい挙動と B 側の別方向の追加が両方そろっている、など）。
- マージを完了させます。`git commit` でよく、既定のマージメッセージに各ハンクの判断を並べた本文を添えれば十分です。
- ここまでできたら次へ: 検証が通り、マージコミットができている状態です。

### 5. 引き継ぐ {#5-hand-back}

- すべてのハンクの判断を並べた完了サマリーを作ります。書式は `file:lines — class — which side(s) kept — rationale` です。same-question-different-answer のハンクについては、設計上の問いと自分が選んだ答えを書き、人間が後から覆せるようにします。設計の判断を埋もれさせてはいけません。
- かんばんなら `kanban_complete(summary=...)`、単独で使っているならサマリーを出力します。
- ここまでできたら次へ: サマリーが届き、すべてのハンクが載っている状態です。

## つまずきやすいところ {#pitfalls}

- **自分の側に有利な判断**: 衝突している当事者のどちらかに呼び出された場合、構造上どうしても偏ります。そのことを明言し、もう一方の意図を意識して重く見てください。そもそもこれが起きないよう、第三のプロファイルを立てる形をおすすめします。
- 設計の衝突で **折衷案にする** と、誰も設計していない混ざりものができます。片方を選び、その判断を明示してください。
- **ファイル単位の分類**: ファイルの中で種類が混ざるのが普通です。ファイル全体を一つの種類として扱うと、両立できたはずの変更が黙って捨てられます。
- **ついでの修正** はマージをレビュー不能にし、本来のエージェントから判断を奪います。
- **意図がわからない**: コミットメッセージだけでは情報が薄いことがあります。かんばんの完了サマリーや PR の本文を優先してください。どちらの意図も復元できないなら、推測せずエスカレーションします。
- **常習箇所**: 同じファイルで何度も衝突が起きるなら、それは調停の仕事ではなくホットスポットの兆候です。旗を立てて（たとえば `hotspot: <path> — <reason>` というかんばんのコメント）、新しい衝突を毎回さばくのではなく、そのファイルを分割するよう全体の調整役に判断させてください。

## 確認 {#verification}

- `git status` が、対象ブランチにマージコミットがある状態でクリーンなツリーを示すこと。
- 衝突マーカーが残っていないこと（`search_files` でパターン `<<<<<<<` を検索）。
- ビルドやテストが通り、双方の意図が実際に確認できること。落とした意図があるなら、サマリーに明記されていること。
- 引き継ぎのサマリーに、すべてのハンクが種類と理由付きで列挙されていること。
