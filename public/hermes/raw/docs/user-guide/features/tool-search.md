# ツール検索 {#tool-search}

MCP サーバーや、中核ではないプラグインのツールをたくさん
セッションに付けていると、その JSON スキーマだけで毎ターン
文脈の窓のかなりの部分を食いつぶします。実際に頼まれた用事に
関係するのはそのうち数個だけ、という場合でもです。

**ツール検索**は、この問題に対して Hermes が用意した、任意で
使える段階的な開示の層です。有効にすると、モデルから見える
ツールの並びで MCP とプラグインのツールが3つの橋渡しツールに
置き換わり、モデルは必要になったツールのスキーマだけを
そのつど読み込みます。

:::info Hermes の組み込みツールは先送りされません
Hermes の中核となる能力を担うツール（`terminal`、
`read_file`、`write_file`、`patch`、`search_files`、`todo`、`memory`、
`browser_*`、`web_search`、`web_extract`、`clarify`、`execute_code`、
`delegate_task`、`session_search`、その他
`_HERMES_CORE_TOOLS` に含まれるもの）は*常に*そのまま
読み込まれます。先送りの対象になるのは MCP のツールと、
中核ではないプラグインのツールだけです。
:::

## 仕組み {#how-it-works}

あるターンでツール検索が働くと、先送りされたツールの代わりに
モデルからは次の3つのツールが見えます。

```
tool_search(query, limit?)     — search the deferred-tool catalog
tool_describe(name)            — load the full schema for one tool
tool_call(name, arguments)     — invoke a deferred tool
```

典型的なやり取りはこうなります。

```
Model: tool_search("create a github issue")
  → { matches: [{ name: "mcp_github_create_issue", ... }, ...] }
Model: tool_describe("mcp_github_create_issue")
  → { parameters: { type: "object", properties: { ... } } }
Model: tool_call("mcp_github_create_issue", { title: "...", body: "..." })
  → { ok: true, issue_number: 42 }
```

モデルが `tool_call` を呼ぶと、Hermes は**橋渡しの包みを外し**、
モデルが直接呼んだのとまったく同じように本来のツールへ
つなぎます。ツール呼び出し前後のフック、安全策、承認を求める
確認は、すべて `tool_call` ではなく本来のツール名に対して
働きます。CLI やゲートウェイの動作表示も包みを外すので、
橋渡しではなく本来のツールが見えます。

## いつ働くのか {#when-does-it-activate}

ツール検索は**段階的な開示**をします。先送りできる
（MCP やプラグインの）ツールが*ひとつでも*あれば橋渡しが働き、
ツールの数に応じて変わるのは、スキーマを先送りするかどうかでは
なく、目録をどこまで見せ続けるかです。

| 段階 | 条件 | モデルから見えるもの |
| --- | --- | --- |
| **0** | MCP やプラグインのツールがない | すべてのツールがそのまま。橋渡しなし。素通しです。 |
| **1** | 先送りした目録の一覧が予算に収まる | 橋渡しに加えて、スキルと同じ形式で先送りしたツールを全件並べた目録（名前と短い説明。予算を超えると名前だけに落ちます）。落とし方は**サーバー単位**です。大きすぎるサーバー（Cloudflare）が小さいサーバー（Linear）と一緒に付いているとき、小さいほうはツールごとの一覧を保ったまま、大きすぎるサーバーだけが要約の一行にまとまります。 |
| **2** | 名前だけにしてもすべてのサーバーのツール一覧が予算を超える（たとえば Cloudflare の平たい API 面だけで約 3,300 のツールがあり、その名前だけで約 32K トークンになります） | 橋渡しのみ、加えてサーバーごとに一行の要約（サーバー名とツール数）。どの領域に手が届くかはモデルに分かりますが、個々のツールは `tool_search` からしか見つけられません。 |

一覧の予算は `min(threshold_pct% of context, listing_max_tokens)` です。
この判断はツールの並びを組み立てるたびにやり直されるので、
セッションの途中で MCP サーバーを足したり外したりすると、
次に組み立てられるときに段階が移ります。

## 設定 {#configuration}

```yaml
tools:
  tool_search:
    enabled: auto       # auto (default), on, or off
    threshold_pct: 5    # listing budget as a percentage of context
    search_default_limit: 5
    max_search_limit: 20
    listing: auto       # embed a grouped name+description catalog manifest
    listing_max_tokens: 4000
```

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `enabled` | `auto` | `auto`／`on` は先送りできるツールがひとつでもあれば働きます。`off` は完全に無効にします（すべてそのまま読み込まれます）。 |
| `threshold_pct` | `5` | 一覧の予算を、使っているモデルの文脈長に対する割合で指定します。範囲は 0〜100 です。 |
| `search_default_limit` | `5` | モデルが `limit` を付けずに `tool_search` を呼んだときに返す件数です。 |
| `max_search_limit` | `20` | モデルが `limit` で要求できる上限です。範囲は 1〜50 です。 |
| `listing` | `auto` | 先送りしたツールを全件並べた、スキルと同じ形式の目録（名前と説明の先頭の一文、60 文字以内、MCP サーバーごとにまとめたもの）を `tool_search` の橋渡しの説明文に埋め込みます。`auto` は予算に収まるときに含めます（収まらなければ名前だけ、さらに段階2のサーバー要約へと落ちます）。`on`／`off` はどちらかに固定します。 |
| `listing_max_tokens` | `4000` | 文脈の大きさにかかわらず、埋め込む一覧に掛ける絶対の上限です。範囲は 200〜60000 です。目録が大きいと名前だけ、あるいはサーバーごとの要約に落ちますが、完全なスキーマは検索から取り出せます。 |

### 一覧がある理由 {#why-the-listing-exists}

これがないと、先送りされた能力は*見えなくなります*。実際に動かして
測ったところ、モデルは見えている中核のツールで代用したり
（先送りされた GitHub のツールを探さずにターミナルで `gh` を走らせる）、
`tool_search` を呼ばずに「そんな機能はない」と言い切ったりしました。
一覧はスキルのやり方をツールに当てはめたものです。どの能力もいつでも
名前で見つけられる状態を保ちつつ、詳しい引数のスキーマは先送りしたまま
にします。モデルが一覧の中に目当てのツール名をそのまま見つけられれば、
`tool_search` を飛ばして `tool_describe` に直行でき、往復を一度
省けます。

昔ながらの真偽値の書き方に切り替えることもできます。

```yaml
tools:
  tool_search: true   # equivalent to {enabled: auto}
```

## 使わないほうがよい場面 {#when-not-to-use-it}

ツール検索は、ターンごとに一定のトークン（3つの橋渡しツールの
スキーマと目録の一覧）と、まだ読み込んでいないツールについて
少なくとも一往復（describe → call）を支払う代わりに、先送りした
スキーマの分を節約します。
段階1では一覧がすべての能力を見せ続けるので、探すための
往復はたいてい起きません。モデルはそのまま
`tool_describe` へ向かいます。実際に動かして測ったところ、
一覧を出す方式は、そのまま読み込む場合と同じだけ用事をこなしながら、
橋渡しだけの場合より安く済みました。

小さなツールの集まりで、これまでどおり常にそのまま読み込ませたい
場合は `enabled: off` にしてください。

## 避けられないやりくり {#trade-offs-that-dont-go-away}

これらはプロンプトキャッシュの整合性という前提から来るもので、
段階的な開示という設計につきものです。この実装に固有のものでは
ありません。

- **まだ読み込んでいないツールでは一往復増えます。** 先送りされた
  ツールが初めて必要になったとき、そのスキーマを見つけて読み込むために
  モデルの呼び出しが一度か二度余計にかかります。静的な側での
  トークンの節約は本物ですが、その一部は実行時に返す形になります。
- **先送りしたスキーマはキャッシュの恩恵を受けません。** 読み込んだ
  `tool_describe` の結果は会話の履歴に入るので、次のターン以降は
  キャッシュされますが、システムプロンプトの前方一致キャッシュの
  恩恵は受けられません。
- **モデルの実力に左右されます。** ツール検索は、モデルが目当ての
  ツールに対してまともな検索語を書けることを前提にしています。
  小さいモデルはこれが不得手です。公表されている Anthropic の数値
  （Opus 4 でツール検索あり 74% / なし 49%）は良くなる幅を示すと同時に、
  26 ポイントほどはまだ探し当てられていないことも示しています。
- **ツールの構成を変えるとキャッシュが無効になります。** セッションの
  途中でツールを足したり外したりすると、橋渡しツールの説明文
  （先送りしたツールの数を含みます）と目録が変わるため、
  プロンプトキャッシュが無効になります。これはツールの構成を
  変えるとき全般に共通するやりくりです。

## 実装の詳細 {#implementation-details}

- **取り出し方:** ツール名・説明・引数名を分かち書きしたものに対する
  BM25 です。BM25 が正のスコアを一件も返さないときは、ツール名への
  素朴な部分一致に切り替わります。これは IDF がゼロになる退化した
  ケース（たとえば目録のすべてのツール名に「github」が含まれる状態で
  `"github"` を検索する場合）への備えです。
- **目録はターンをまたいで持ち越しません。** 組み立てのたびに、
  そのときのツール定義の一覧から作り直します。セッションごとの
  `Map` は持ちません。これによって、保存した目録が実際のツールの
  登録内容とずれていく類のバグを避けられます。
- **目録はそのセッションのツールセットに限られます。** `tool_search`、
  `tool_describe`、`tool_call` が見て呼べるのは、そのセッションに
  実際に与えられたツールだけです。ツールセットを絞られたサブエージェント、
  かんばんのワーカー、ゲートウェイのセッションが、橋渡しを使って
  その範囲の外のツールを見つけたり呼んだりすることはできません。
  先送りされる目録は、そのセッション自身で有効・無効になっている
  ツールセットのうち先送りできる部分であって、プロセス全体の
  登録内容ではありません。
- **JavaScript のサンドボックスはありません。** Hermes はより単純な
  「構造化されたツール」方式（検索・説明・呼び出しをただの関数として
  持つ形）を採っています。他の実装が用意している JavaScript の
  サンドボックスによる「コードモード」は面積が大きすぎるので、
  こちらでは採りません。
