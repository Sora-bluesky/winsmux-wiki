# ツール検索 {#tool-search}

MCP サーバーやコア以外のプラグインツールをたくさんセッションにつないでいると、
その JSON スキーマだけで、毎ターンのコンテキストウィンドウのかなりの割合を
使ってしまいます。ユーザーが実際に頼んだことに関係するツールは、そのうちの
ほんの数個ということも珍しくありません。

**ツール検索** は、その問題のために Hermes が用意した、任意で有効にする
段階的開示のしくみです。有効になると、モデルから見えるツール一覧では MCP
ツールとプラグインツールが 3 つの橋渡しツールに置き換わり、モデルは必要に
なったツールのスキーマだけをその都度読み込みます。

:::info Hermes の組み込みツールは遅延しません
Hermes の中核となる機能をかたちづくるツール（`terminal`、
`read_file`、`write_file`、`patch`、`search_files`、`todo`、`memory`、
`browser_*`、`web_search`、`web_extract`、`clarify`、`execute_code`、
`delegate_task`、`session_search` をはじめとする
`_HERMES_CORE_TOOLS` の面々）は *つねに* そのまま読み込まれます。遅延の
対象になるのは MCP ツールと、コア以外のプラグインツールだけです。
:::

## しくみ {#how-it-works}

そのターンでツール検索が有効になると、遅延されたツールの代わりに、次の 3 つの
ツールがモデルから見えます。

```
tool_search(queries, limit?)   — search the deferred-tool catalog (one or more queries)
tool_describe(names)           — load the full schemas for one or more tools
tool_call(name, arguments)     — invoke a deferred tool
```

やり取りは、たとえば次のように進みます。

```
Model: tool_search(["create a github issue", "send a slack message"])
  → { results: [ { query: "create a github issue",
                   matches: ["mcp_github_create_issue", ...] },
                 { query: "send a slack message",
                   matches: ["mcp_slack_post_message", ...] } ],
      tools: { mcp_github_create_issue: { description: "...",
                                          required: ["title"], ... },
               mcp_slack_post_message: { ... } } }
Model: tool_describe(["mcp_github_create_issue", "mcp_slack_post_message"])
  → { tools: { mcp_github_create_issue: { parameters: { ... } },
               mcp_slack_post_message: { parameters: { ... } } } }
Model: tool_call("mcp_github_create_issue", { title: "...", body: "..." })
  → { ok: true, issue_number: 42 }
```

`tool_search` の呼び出しに渡した各クエリは、同じカタログに対してそれぞれ
独立に検索されます（`limit` はクエリごとに効きます）。クエリごとのまとまりが
持つのはツール名だけで、一致した各ツールの説明と必須パラメータ名は、共有の
`tools` マップに一度だけ入ります。クエリは語幹に直して扱われるので、
"issues" と書いても `create_issue` が見つかります。一致がひとつも無かった
クエリのまとまりには、つながっているサーバーをまとめた `available_sources`
が添えられます。単語が噛み合わなかっただけの取りこぼしを、機能が無いのだと
読み違えずに済みます。
`tool_describe` は、頼まれた名前をすべて 1 回の呼び出しで解決します。知らない
名前は `not_found` に載るだけで、残りの処理は失敗しません。

モデルが `tool_call` を呼ぶと、Hermes は **橋渡しを外して**、モデルが直接
呼んだのとまったく同じように、その下にある本体のツールを動かします。ツール
呼び出し前のフック、ガードレール、承認の確認、ツール呼び出し後のフックは、
すべて `tool_call` ではなく本物のツール名に対して動きます。CLI とゲートウェイの
実行の流れの表示でも橋渡しは外れるので、目に入るのは橋渡しではなく本体の
ツールです。

## いつ有効になるのか {#when-does-it-activate}

ツール検索は **段階を分けた開示** を使います。遅延できる（MCP・プラグインの）
ツールが *ひとつでも* あれば橋渡しは有効になり、カタログの大きさで変わるのは
スキーマを遅延するかどうかではなく、カタログのどこまでを見せ続けるかです。

| 段階 | 条件 | モデルから見えるもの |
| --- | --- | --- |
| **0** | MCP・プラグインのツールが無い | すべてのツールをそのまま読み込み、橋渡しなし。素通しです。 |
| **1** | 遅延したカタログの一覧が予算に収まる | 橋渡しと、遅延した全ツールをスキルのように並べた一覧（名前と短い説明。予算を超えると名前だけに落とします）。落とし方は **サーバーごと** です。巨大なサーバー（Cloudflare）と小さなサーバー（Linear）が並んでつながっているときは、小さいほうはツールごとの一覧を保ったまま、巨大なほうだけが 1 行の要約に畳まれます。 |
| **2** | どのサーバーも名前だけに落としてなお、ツールごとの一覧が予算を超える（たとえば Cloudflare の平坦な API だけで、ツールはおよそ 3,300 個、その名前だけで約 32K トークン） | 橋渡しだけと、サーバーごとに 1 行の要約（サーバー名とツール数）。どの領域に手が届くかはモデルに伝わり、個々のツールは `tool_search` を通してだけ見つかります。 |

一覧の予算は `min(threshold_pct% of context, listing_max_tokens)` です。
この判定はツール一覧を組み立てるたびにやり直されるので、セッションの途中で
MCP サーバーを足したり外したりすると、次の組み立てのときに段階が移ります。

## 設定 {#configuration}

```yaml
tools:
  tool_search:
    enabled: auto       # auto (default), on, or off
    threshold_pct: 5    # listing budget as a percentage of context
    search_default_limit: 5
    max_search_limit: 25
    listing: auto       # embed a grouped name+description catalog manifest
    listing_max_tokens: 4000
```

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `enabled` | `auto` | `auto`/`on` は、遅延できるツールがひとつでもあれば有効にします。`off` は完全に止めます（すべてそのまま読み込まれます）。`auto` はいまのところ `on` の別名で、スキーマがコンテキストに収まるときは埋め込み、収まらないときだけ遅延する将来の動きのために取ってあります。いまの動きをそのまま保ちたいなら `on` か `off` を書いておいてください。 |
| `threshold_pct` | `5` | 一覧の予算を、使っているモデルのコンテキスト長に対する割合で指定します。範囲は 0〜100 です。 |
| `search_default_limit` | `5` | モデルが `limit` を付けずに `tool_search` を呼んだとき、1 クエリあたりに返す件数です。 |
| `max_search_limit` | `25` | モデルが `limit` で指定できる上限（クエリごと）です。範囲は 1〜50 です。 |
| `listing` | `auto` | 遅延した全ツールをスキルのように並べた一覧（名前と説明の 1 文目、60 文字以内、MCP サーバーごとにまとめたもの）を、`tool_search` の橋渡しツールの説明に埋め込みます。`auto` は予算に収まるときだけ入れます（収まらなければ名前だけ、それでも収まらなければ段階 2 のサーバー要約へ落とします）。`on`/`off` はどちらかに固定します。 |
| `listing_max_tokens` | `4000` | コンテキストの大きさに関わらず、埋め込む一覧に掛ける絶対の上限です。範囲は 200〜60000 です。大きなカタログは名前だけ、あるいはサーバーごとの要約へ落ちますが、完全なスキーマは検索から取れるままです。 |

1 回の呼び出しで渡せる配列の上限は、設定ではなく内部の安全弁です。上限を超えた
呼び出しはエラーを返すので、モデルはもっと小さなまとまりに分けて呼び直せます。

### なぜ一覧を出すのか {#why-the-listing-exists}

一覧が無いと、遅延した機能はモデルから *見えなく* なります。実際に動かして
測ってみると、モデルは目に見える中核ツールで代用したり（遅延した GitHub の
ツールを探さずに、端末で `gh` を実行してしまう）、`tool_search` を呼ばずに
「そんな機能は無い」と言い切ったりしました。この一覧は、スキルでうまくいった
やり方をツールにも当てはめたものです。どの機能もいつでも名前で見つけられる
ままにしつつ、パラメータの完全なスキーマは遅延させておきます。ねらいどおりの
ツール名が一覧に見えていれば、モデルは `tool_search` を飛ばして
`tool_describe` へ直行でき、往復が 1 回減ります。

昔ながらの真偽値の書き方に切り替えることもできます。

```yaml
tools:
  tool_search: true   # equivalent to {enabled: auto}
```

## 使わないほうがよいとき {#when-not-to-use-it}

ツール検索は、遅延したスキーマぶんの節約と引き換えに、毎ターン決まった量の
トークン（3 つの橋渡しツールのスキーマと、カタログの一覧）と、まだ読み込んで
いないツールを使うときの往復 1 回以上（describe してから call）を払います。
段階 1 では一覧がすべての機能を見せ続けるので、探すための往復はたいてい
消えてなくなり、モデルは `tool_describe` へ直行します。実際に測ってみると、
一覧を出すやり方は、そのまま読み込む場合と同じだけタスクをこなしながら、
橋渡しだけの場合より安く済みました。

小さなツール群を、これまでどおりつねにそのまま読み込ませたいなら、
`enabled: off` にしてください。

## 消えないトレードオフ {#trade-offs-that-dont-go-away}

以下はプロンプトキャッシュを壊さないという前提から来るもので、この実装に
固有の話ではなく、段階的開示という設計につきものです。

- **まだ読み込んでいないツールでは往復が 1 回増えます。** 遅延したツールが
  初めて必要になったとき、モデルはスキーマを見つけて読み込むために 1〜2 回
  余計に呼ばれます。静的な側でのトークン節約は本物ですが、その一部は実行時に
  払い戻すことになります。
- **遅延したスキーマにキャッシュの恩恵はありません。** 読み込んだ
  `tool_describe` の結果は会話の履歴に入るので、次のターン以降はキャッシュに
  乗りますが、システムプロンプトのキャッシュ前置きの恩恵は受けません。
- **遅延したスキーマは、プロバイダー側の検証を受けません。** `tool_describe`
  を使えばモデルは遅延したツールのスキーマを読めますが、プロバイダーから見えて
  いるのは、あくまで汎用の `tool_call.arguments` というオブジェクトだけです。
  そのため Hermes は、実行に移す前に本体の引数を自分で型合わせして検証します。
  Hermes が安全に検証しきれないスキーマ、たとえば壊れたスキーマや外部参照に
  ついては、そのツールなり MCP サーバーなりが引き続き責任を持ちます。
- **モデルの実力に左右されます。** ツール検索は、欲しいツールにたどり着く
  検索クエリをモデルが書けることを前提にしています。小さいモデルはこれが
  うまくありません。Anthropic が公表した数字（Opus 4 で、ツール検索ありが
  74%、なしが 49%）は伸びしろを示すと同時に、26 ポイントぶんはいまだに
  探し当てられていないことも示しています。
- **ツールを増減させるとキャッシュが無効になります。** セッションの途中で
  ツールを足したり外したりすると、橋渡しツールの説明（遅延したツールの数を
  含みます）とカタログが変わるので、プロンプトキャッシュは無効になります。
  これはツールを差し替えるときにいつも起きることで、ここだけの話ではありません。

## 実装の詳細 {#implementation-details}

- **検索のしかた：** ツール名、提供元の名前（そのツールが属する MCP サーバーや
  プラグインのツール群。おかげで `"linear"` と検索すれば、ツール自身の名前に
  サービス名が入っていなくてもそのサーバーのツールが見つかります）、説明文、
  パラメータ名を単語に分けたうえで BM25 を掛けます。索引側とクエリ側の両方に
  Snowball の語幹処理（英語）を適用しているので、語形が違っても一致します
  （"issues" で `create_issue` が見つかります）。クエリのどの単語もどの文書にも
  当たらなかったときは、ツール名に対する素直な部分一致へ切り替えます（たとえば
  単語が `github` のときに `"hub"` で検索した場合です）。
- **並列実行でも橋渡しは外れます。** まとめて実行する計画を立てるとき、同時に
  走らせてよいかどうかは、橋渡しの名前そのものではなく `tool_call` の
  *下にある* 本体のツールで判断します。ですから
  `supports_parallel_tool_calls: true` を指定して並列を許した MCP サーバーは、
  橋渡し越しに呼ばれても同時実行のままですし、`tool_search` と
  `tool_describe` の問い合わせも、読み取り専用のツールと同じようにまとめて
  同時に走ります。
- **カタログはターンをまたいで持ち越しません。** 組み立てのたびに、そのときの
  ツール定義の一覧から作り直します。セッションを鍵にした `Map` は使いません。
  こうしておけば、しまい込んだカタログが生きているツール一覧とずれていく、
  という類のバグが起きません。
- **カタログはそのセッションのツール群だけを見ます。** `tool_search`、
  `tool_describe`、`tool_call` が目にし、呼び出せるのは、そのセッションに実際に
  与えられたツールだけです。ツール群の一部だけを許されたサブエージェント、
  かんばんの作業役、ゲートウェイのセッションは、橋渡しを使ってもその外側の
  ツールを見つけたり呼んだりできません。遅延カタログは、そのセッション自身で
  有効・無効になっているツール群のうち遅延できるぶんであって、プロセス全体の
  持ち物ではありません。
- **JS のサンドボックスは使いません。** Hermes は、より単純な「構造化ツール」
  方式（検索・説明・呼び出しをただの関数として置く方式）を採っています。
  他の実装にある JS サンドボックスの「コードモード」は守るべき面が広すぎるので、
  こちらは見送っています。
