# 繰り返しのループ（`/loop`） {#recurring-loops-loop}

`/loop` は、プロンプト（やスラッシュコマンド）を**今のセッションの中で**決まった調子で流し直します。目覚めるたびに本物のエージェントのターンが動きます。Hermes はそのときの状態を新しく読み — 最新の CI の結果、今の待ち行列の深さ、たった今のファイルの中身を — 仕事をして、報告し、次の時間が来るまで静かにしています。

これは **Claude Code の `/loop`**（ここでも使える `/proactive` という別名も含めて）に対する Hermes なりの答えです。[`/goal`](/hermes/docs/user-guide/features/goals/) が判定役に導かれる「この目的が達成されるまで働き続けて」であるのに対し、`/loop` は時計に導かれる「何かが止めろと言うまで、N 分ごとに（あるいはちょうどよい間合いで）これをまたやって」です。

## どんなときに使うか {#when-to-use-it}

- **外の状態を見張る。** 「デプロイ／CI の実行／待ち行列を見ていて、変わったら教えて」。これが本命の使い道です。
- **緑になるまで繰り返す。** 「テストを走らせて、落ちたところを直して、通るまで繰り返して」。
- **作業中の見張り。** 同じ会話で別のことをしながら、エラーの率や長い仕事の進み具合を気にかけておきます。
- **定期的な片づけ。** 長いセッションの間、N 分ごとに lint をかけ直したり、状況をまとめ直したりします。

作業を**人の手を離れて**動かしたいとき — 夜通し、本物の予定表に沿って、端末を再起動しても生き残る形で — は、代わりに [cron の仕事](/hermes/docs/user-guide/features/cron/)を使ってください。`/loop` はセッションの中に住み、cron はどのセッションの外にも住んでいます。そして、終わりの定義がはっきりした1つの目的が相手なら、たいていは [`/goal`](/hermes/docs/user-guide/features/goals/) のほうが合います。

## さっそく使う {#quick-start}

```
/loop 5m check the deploy status and tell me if it's live yet
```

こう見えます。

1. **ループが受け付けられる** — `↻ Loop set (every 5m): check the deploy status…`
2. **最初の目覚めはすぐ起きる** — 次に手が空いたのを確かめる回（ゲートウェイなら次の 15 秒ごとの見回り）で、Hermes が目覚めの合図を差し込み、今の状態を相手に普通のターンを走らせます。
3. **繰り返す** — そのあとは 5 分ごとに、止まる条件が発火するか、こちらが止めるまで続きます。

スラッシュコマンドも同じ手軽さでループにできます。

```
/loop 10m /recap
```

## 2つの間合いの決め方 {#the-two-cadence-modes}

**間隔を決め打ちする — 時計はこちらが決める。** 間隔（`30s`、`5m`、`2h`、`1h30m`）を渡すと、ループはその予定どおりに発火します。見張りたいものが向こうの都合で動くときに使います。

```
/loop 2m poll the build at ci.example.com/job/42 and ping me the moment it finishes
```

**自分で間合いを取る — 時計は Hermes が決める。** 間隔を省くと、ループは自分で調子を取ります。下限（既定では1分）から始まり、エージェントの返事が変わらないあいだは 2分、4分、8分と倍々に間を空け、上限（既定では15分）まで下がります。返事が前回と違った瞬間、間合いは下限へ戻ります。変化の判定は手元での要約値の比較（時刻は無視されます）なので、何も起きていない待ち時間に余計な費用はかかりません。

```
/loop keep an eye on the migration and summarize progress
```

目安はこうです。**外の時計が仕事を動かすなら間隔を決め打ち、仕事のほうがリズムを作るなら自分で間合いを取る。**

## 止まる条件 {#stop-conditions}

次のどれかが発火すると、ループは終わります。

| 条件 | やり方 |
|---|---|
| エージェントが終わったと判断する | 目覚めの合図がエージェントに、仕事が終わったか意味をなくしたときは返事の最後の行に `LOOP_COMPLETE` だけを書くよう教えます。 |
| 回数の上限 | `--times N` — N 回目覚めたら止まります。 |
| 証拠にもとづく条件 | `--until <condition>` — 目覚めるたびに、`/goal` を支えているのと同じ補助の判定役が、返事をこの条件と突き合わせます。条件が達成できないと判定役が裁定した場合、ループは回数の予算まで発火し続けるのではなく、理由を添えて**一時停止**します（fail-open。判定役が壊れてもループが固まることはありません）。 |
| こちらの操作 | `/loop stop`（残しておきたいなら `/loop pause`）。 |
| 最後の砦としての予算 | `loops.max_ticks`（既定は 100）に達するとループは一時停止します。人の目のないセッションが延々とトークンを燃やさないためです。`0` なら上限なしです。 |

例です。

```
/loop 2m poll CI --times 30
/loop 5m watch the queue --until queue depth reaches zero
```

## コマンド {#commands}

| コマンド | 何をするか |
|---|---|
| `/loop [interval] <prompt> [--times N] [--until <cond>]` | このセッションのループを始めます（すでにあれば置き換えます）。最初の目覚めはすぐに、そのあとは決めた間合いで発火します。 |
| `/loop` または `/loop status` | 間合い、これまでの発火回数、次の目覚めまでの時間を表示します。 |
| `/loop pause` | ループを残したまま、発火だけ止めます。 |
| `/loop resume` | 続きから動かします。 |
| `/loop stop` | ループを終わらせます。 |
| `/proactive …` | `/loop` の別名です（Claude Code に合わせたもの）。 |

CLI、TUI（`hermes --tui`）、ウェブのダッシュボードのチャット、デスクトップアプリ、そしてすべてのゲートウェイ（Telegram、Discord、Slack、WhatsApp、…）で動きます。メッセージのやり取りをする場では、こちらが何も送っていない間もゲートウェイが目覚めを起こします。ループはそのチャットのセッションのものなので、結果は普通の返信として届きます。

## `/goal` と組み合わせる {#mixing-with-goal}

どちらの機能も、手が空いた切れ目に人工のターンを差し込みます。そこで1つの決まりに従います。**動いている目的がセッションの持ち主です。** `/goal` が実際に引っ張っているあいだ（判定役が「続けろ」と言っているあいだ）は、ループの目覚めが順番を譲ります。目的が終わるか、一時停止するか、待ちの関所（`/goal wait`、または判定役が自動で出す WAIT の裁定）で停まった時点で、ループは空いた時間を使って再開します。停めておいた目的と `/loop` の組み合わせは自然です。目的が大きな非同期の相手を待っているあいだ、ループが別のものの脈を取り続けます。

本物のこちらからのメッセージは、どちらよりも常に優先されます。目覚めが発火するのは、セッションの手が空いていて、こちらの送ったものが何も待っていないときだけです。

## ふるまいの細かいところ {#behavior-details}

- **目覚めは普通のユーザー役のターンです。** システムプロンプトを書き換えたり、道具立てを差し替えたりしません。プロンプトのキャッシュはそのまま効きます。
- **`/resume` と圧縮を越えて生き残ります。** ループの状態はセッションごとに残り、文脈の圧縮の境目も `/goal` と同じように越えていきます。
- **1つのセッションにつきループは1つです。** 新しく `/loop` を設定すると古いものと置き換わります。いくつも走らせたいならセッションをいくつも走らせてください（あるいは、たくさんの予定を扱うなら cron を使ってください）。
- **目覚めのターンを Ctrl+C で中断するとループは一時停止します。** `/loop resume` で戻せるので、取り消しがちゃんと取り消しとして働きます。
- **トークンの費用は間合いに比例します。** 発火のたびにエージェントの1ターンがまるごと動きます。実際に状態が変わる頻度に間隔を合わせてください。何も起きない待ち時間には、自分で間合いを取らせるほうが向いています。

## 設定 {#configuration}

```yaml
# ~/.hermes/config.yaml
loops:
  min_interval_seconds: 30       # floor for fixed intervals
  max_ticks: 100                 # backstop budget (0 = unlimited)
  self_paced_floor_seconds: 60   # self-paced starting cadence
  self_paced_ceiling_seconds: 900  # self-paced max backoff
```

`--until` の判定役は `goal_judge` という補助のタスクを通るので、`auxiliary.goal_judge.*` の上書き（プロバイダ、モデル、max_tokens）はループの条件にもそのまま効きます。

## `/loop` と `/goal` と cron {#loop-vs-goal-vs-cron}

| | `/loop` | `/goal` | cron |
|---|---|---|---|
| **きっかけ** | 時計（または自分で取る間合い） | ターンごとの判定役の裁定 | 予定表。どのセッションの外にもある |
| **住んでいる場所** | 今のセッション | 今のセッション | 実行ごとの専用セッション |
| **終わるとき** | 止まる条件／上限／こちらの操作 | 目的の達成／予算／こちらの操作 | こちらが仕事を消したとき |
| **向いている用途** | 見張り、監視、定期的な流し直し | 1つの目的を、終わるまで繰り返す | 人の手を離れた、長い時間軸の予定 |
