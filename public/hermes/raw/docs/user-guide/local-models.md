# ローカルモデル {#local-models}

Hermes はオープンなモデルを、自分の端末のなかだけで動かせます。推論エンジン
（llama.cpp）のダウンロードと管理、手元のハードウェアに合うビルドの選択、
メモリのやりくりまで Hermes が引き受けるので、コンテキスト長も GPU
レイヤー数も量子化も設定せずに済みます。使う人はモデルを選ぶだけで、
あとは Hermes がやります。

何も端末の外には出ません。アカウントも API キーも要らず、モデルを
ダウンロードしたあとはネットワークにもつなぎません。

## 導入 {#getting-started}

1. **設定 → Providers → Local Models** を開きます（初回設定の途中で
   **Run models locally** を選んでも構いません）。
2. **Install runtime** を押します。手元のハードウェア向けの公式 llama.cpp
   ビルド（数百 MB）を Hermes がダウンロードして検証し、以後は最新に
   保ちます。
3. カタログからモデルを選んで **Download** を押します。
4. **Use** を押します。これ以降の新しいチャットは、ローカルのモデルで
   動きます。

流れはこれだけです。サーバーは Hermes と一緒に起動・終了し、アプリを
再起動しても設定は残ります。クラウドの提供元に戻すのも、モデル選択の
画面でひと押しです。

## 何をダウンロードするかを Hermes がどう決めるか {#how-hermes-picks-what-to-download}

カタログにあるモデルは、ダウンロードする前にすべて**手元の端末**を基準に
評価されます。各行にはこう表示されます。

- **メモリの収まり** — 緑（*Fits your GPU*: GPU のメモリだけで動きます）、
  アンバー（*Uses system RAM*: 動きますが遅くなります）、赤（*Too big for
  this machine*: この端末には大きすぎます）。
- **コンテキスト** — 起動時のウィンドウと、広げられる上限。
- 手元のハードウェア向けに選ばれたビルドのダウンロードサイズ。

モデルにはいくつかの品質段階（量子化）があります。Hermes は GPU だけで
動かしきれる範囲でもっとも品質の高いビルドを選び、メモリが少ない端末には
同じモデルのより小さなビルドを、同じ保証のまま渡します。4 bit を下回ると
品質の劣化が大きすぎるため、それより小さいビルドは提示しません。4 bit の
ビルドをシステム RAM にあふれさせても動かない端末は、そのモデルを動かせない
ということです。

収まらないモデルも理由付きで表示され続けるので、ハードウェアを更新すると
何が使えるようになるかがいつでも分かります。

## メモリ管理のしくみ {#how-memory-management-works}

ローカルのモデルはメモリの置き場所で成否が決まります。そこで Hermes は
端から端まで自分で管理し、つまみを一切出しません。

- **モデルは GPU に完全に収まるコンテキスト長で起動し**、会話が長くなって
  余裕が必要になるにつれて、そのモデル本来の上限へ向けて広がります。長い
  セッションの途中でステータス欄に "Context window grown" と出ることが
  ありますが、これはウィンドウが広がっただけで、エラーではありません。
- **推奨モデルにはどれも 64K 以上のコンテキスト長が確保されます。** モデルが
  GPU のメモリより大きい場合、Hermes はあふれた分をいちばん影響の小さい順に
  システム RAM へ置きます（まずエキスパートの重みから。アテンションの
  キャッシュは決して外に出しません）。速度をいくらか譲って、コンテキストの
  保証を守るためです。
- **会話の圧縮が始まるのは、そのモデルの上限まで広げきったあとだけです。**
  先に広げるほうが常に優先されます。
- 使われていないモデルは 15 分で解放され、GPU のメモリが空きます。次に
  メッセージを送ると自動で読み込み直されます。

## ステータスバー {#the-status-bar}

ステータスバーを右クリックして **System resources** を有効にすると、ローカル
モデルの実行中に GPU の使用率・GPU メモリ・RAM をその場で見られます。
コンテキストのメーターは、そのモデルが実際に動いているウィンドウを
常に映します。

## ほかのモデルを探す {#finding-more-models}

カタログは出発点であって、そこで打ち止めというわけではありません。同じ
ページの **Find more models** から Hugging Face 全体を検索できます。

- 結果にはダウンロード数と、手元の端末に合わせたファイルごとの収まり判定が
  出ます。ダウンロードする前に、そのビルドが GPU だけで動くかどうかが
  分かります。
- ダウンロードしたものは、カタログのモデルとまったく同じように扱われます。
  Hermes がモデルファイル自体を読んで、コンテキスト長とメモリの置き場所を
  決めます。違いは 1 つだけで、コミュニティのモデルには「検証済み」の
  テストバッジが付きません。
- すでに `.gguf` ファイルを持っている場合は、**Add model file** でコピーせずに
  ライブラリへ登録できます（元のファイルはその場に残ります）。登録した
  時点ですぐ使えます。

## 自分の llama-server を使う {#using-your-own-llama-server}

すでに llama-server が端末で動いている場合、Hermes はそれを見つけて、自前で
起動する代わりにそちらを使います。カスタムのエンドポイントを OpenAI 互換の
サーバーへ向ければ、すべて手で制御できます。管理された実行環境は既定で
あって、必須ではありません。手動で組む場合（Ollama、MLX、独自ビルド、画面の
ないコマンドライン端末）は、
[Ollama で Hermes をローカルに動かす](/hermes/docs/guides/local-ollama-setup/) と
[Mac でローカル LLM を動かす](/hermes/docs/guides/local-llm-on-mac/) をご覧ください。

## 設定 {#configuration}

管理された実行環境は `config.yaml` の `local_runtime` セクションで制御します。
デスクトップの画面がこの値を書き込みますが、コマンドラインや画面なしの
環境のために内容を記しておきます。

```yaml
local_runtime:
  enabled: false     # true = start the managed server with Hermes.
                     # The desktop "Use" button sets this automatically.
  backend: auto      # auto | cuda | metal | vulkan | hip | cpu
  tag: b10362        # pinned llama.cpp release; Hermes updates it with
                     # each release after re-validation
```

モデルと実行環境のビルドは Hermes のホームディレクトリ（`models/` と
`runtimes/llamacpp/`）に置かれます。ローカルのモデルをメインのモデルに
するときは、いつもどおり `model.provider: llamacpp` と `model.default` の
設定を使います。ほかの提供元とまったく同じ形です。

## 必要なものと制限 {#requirements-and-limits}

- **Windows と Linux:** NVIDIA GPU（CUDA）または CPU。**macOS:** Apple
  Silicon（Metal）。AMD の GPU には Vulkan ビルドが対応します。
- メモリ 8 GB 以上の GPU なら、カタログの小さいモデルは余裕をもって動きます。
  16 GB 以上あれば 27〜35B のモデルを高い品質で動かせます。
- モデルのダウンロードは転送中にカタログのバイト数と突き合わせて確認します。
  途中で切れたものは削除して報告するので、半端なまま使われることはありません。
  （SHA-256 での検証は実行エンジンの zip だけです。）
- モデルを削除すると、そのモデルが用意したファイルは画像向けのアダプターや
  投機的デコードの相棒まで含めて、すべて消えます。
