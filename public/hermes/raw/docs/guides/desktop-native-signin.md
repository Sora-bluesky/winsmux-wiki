# デスクトップアプリのネイティブサインイン（RFC 8252） {#desktop-native-sign-in-rfc-8252}

Hermes デスクトップアプリが **ゲート付きゲートウェイ**（OAuth プロバイダーの
背後に置かれた、ホスト型またはセルフホスト型のダッシュボード）に接続するとき、
サインインの方法は 2 つあります。

1. **ネイティブサインイン（RFC 8252）** — アプリが**普段お使いのシステム
   ブラウザ**を開き、すでに信頼しているブラウザ上で承認すると、アプリが
   トークンを受け取って OS のキーチェーンに保存します。**埋め込みウェブビューも
   ブラウザのセッション Cookie も使いません。** ゲートウェイが対応していれば、
   こちらが既定になります。
2. **埋め込みサインイン（従来方式のフォールバック）** — アプリが小さな内蔵
   ブラウザウィンドウを開き、ゲートウェイのセッション Cookie を取り込みます。
   ゲートウェイが古いビルドでネイティブサインインを表明していない場合に、
   自動で使われます。

どちらを使うかを選ぶ必要はありません。アプリがゲートウェイの対応状況を検出し、
最適なほうを選びます。このページでは、そのとき何が起きているのか、そしてなぜ
そうしているのかを説明します。

## ネイティブサインインを使う理由 {#why-native-sign-in}

OAuth のためにネイティブアプリの中にブラウザを埋め込むやり方には、よく知られた
欠点があります。ログインページから既存のブラウザセッションが見えないため
認証情報の再入力や MFA のやり直しが必要になり、パスワードマネージャーやパスキーが
動かないことも多く、しかもアプリは非公開のウェブビューからセッション Cookie を
読み出すことに依存します。RFC 8252（"OAuth 2.0 for Native Apps"）は、そうした
問題をすべて避けるための業界のベストプラクティスです。**認可はシステム
ブラウザで行い、アプリにはアプリ自身のトークンを渡す**というものです。

Hermes に即して言うと、ネイティブサインインは次を意味します。

- **埋め込みウェブビューを使いません。** 認可は Safari / Chrome / Firefox /
  Edge など、普段お使いのブラウザで行われるので、ログイン状態も拡張機能も
  パスキーもそのまま活きます。
- **セッション Cookie を使いません。** アプリが持つのは OAuth の
  **アクセストークン**（短命）と**リフレッシュトークン**で、OS のキーチェーン
  （Electron の `safeStorage`）によって保存時に暗号化されます。REST 呼び出しと
  WebSocket チケットの認証には、Cookie ではなく `Authorization: Bearer`
  ヘッダーを使います。

## 動作の流れ {#how-it-works}

```
Desktop app                Gateway (/auth/native/*)          Nous Portal (IDP)
   │ 1. open loopback 127.0.0.1:<random port>
   │ 2. system browser ─►  /auth/native/authorize
   │    (PKCE challenge)    (starts the normal PKCE login) ─► /oauth/authorize
   │                        ◄──── code ──── /auth/callback ◄──┘
   │                        3. mint one-time gateway code
   │ ◄─ 302 127.0.0.1/cb?code=… ─┘
   │ 4. POST /auth/native/token (code + PKCE verifier)
   │ ◄─ 5. { access_token, refresh_token, expires_at } ───────┘
   │ 6. store in OS keychain; use Bearer for REST + WS tickets
```

ゲートウェイはこの流れを**仲介**します。つまり、*デスクトップアプリから見れば*
認可サーバーであり、上流の ID プロバイダー（Nous Portal）から見れば OAuth
クライアントです。上流の `client_id` と許可されたリダイレクト URI が
ゲートウェイ自身のオリジンに紐づいているため、この形が必要になります。
デスクトップアプリが Portal の直接のクライアントになることはできないからです。
それでもデスクトップ側は RFC 8252 の体験をひととおり得られます。自分専用の
PKCE ペア、自分専用のループバックリダイレクト、そして自分が所有するトークンです。

**PKCE（RFC 7636）** がループバックの区間を保護します。ワンタイムの
ゲートウェイコードは、アプリの外に出ることのないコードベリファイアーがなければ
役に立ちません。このコードは 1 回きりで、有効期間も短く設定されています。

## 対応状況の検出とフォールバック {#capability-detection-fallback}

デスクトップアプリは、ゲートウェイの公開エンドポイント `/api/status` を読み、
そこで表明される `auth_flows` 配列を確認します。

| `auth_flows` の値 | 意味 |
|--------------------|---------|
| `["cookie", "native_pkce"]` | ゲートウェイがネイティブサインインに対応 → アプリはこちらを使います |
| `["cookie"]` | ゲートウェイは従来方式のみ対応 → アプリは埋め込みウェブビューを使います |
| *(項目そのものがない)* | 古いゲートウェイ → アプリは埋め込みウェブビューを使います |

ネイティブサインインが表明されていても、手元の事情で失敗することがあります。
たとえばセキュリティ製品がループバックの待ち受けを遮断した場合や、ブラウザの
タブを閉じてしまった場合です。そのときアプリは**自動的に埋め込み方式へ
フォールバック**するので、サインイン自体は続けられます。

## トークンのライフサイクル {#token-lifecycle}

- **アクセストークン**: 短命（数分）です。すべての REST 呼び出しと、WebSocket
  チケットの発行時に `Authorization: Bearer` として送られます。
- **リフレッシュトークン**: より長命で、使うたびに入れ替わります。アクセス
  トークンの期限が近づくと、アプリが `/auth/native/refresh` を呼んで両方の
  トークンを入れ替え、キーチェーンを更新します。
- **完全な期限切れ**: リフレッシュトークンが使えなくなっている場合（期限切れ、
  失効、再利用の検知）、アプリは保存済みのトークンを消去し、あらためて
  サインインを求めます。
- **サインアウト**: そのゲートウェイに対するネイティブトークン（キーチェーン）と、
  従来方式のセッション Cookie の両方を消去します。

## ゲートウェイ運用者の方へ {#for-gateway-operators}

ネイティブサインインは、対話的なセッションプロバイダーが登録されている
ゲート付きゲートウェイであれば自動的に利用できます。設定は不要です。
`/auth/native/*` のルートと `auth_flows` の表明は、ダッシュボード認証サブ
システムに最初から含まれています。OAuth プロバイダー（同梱の **Nous**
プロバイダーなど）は上流 IDP へのリダイレクトを仲介します。パスワード方式の
プロバイダー（同梱の **basic-auth** プラグインなど）の場合は、システム
ブラウザがゲートウェイの `/login` 認証フォームに着地します。これによって OS の
パスワードマネージャー（macOS のパスワードなど）がフォームを自動入力できます。
埋め込みのデスクトップウェブビューでは実現できないことです。トークンだけの
認証情報（drain など）は対話的なサインインではないため、`native_pkce` を
表明しません。

関連するエンドポイントは次のとおりです（いずれも公開・認証前のブートストラップ用で、
既存の `/auth/*` OAuth ルートと同じ扱いです）。

- `GET /auth/native/authorize` — 仲介型の PKCE ログインを開始します
- `POST /auth/native/token` — ループバックのコードとベリファイアーをトークンに交換します
- `POST /auth/native/refresh` — アプリのリフレッシュトークンからトークンを入れ替えます
