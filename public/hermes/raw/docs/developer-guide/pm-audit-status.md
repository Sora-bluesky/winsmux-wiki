# PM 監査の修正状況 {#pm-audit-remediation-status}

これは過去の監査の記録であり、最新の HEAD のリリース状況を示すページではありません。
以下の件数とネイティブ環境での受領記録は、それぞれに書かれたリビジョンにだけ当てはまります。
その後の作業で、共有バンドルの組み立て、署名付きパッケージの E2E、安定版の
リリースゲート、Termux の APT 配布、Python 3.14 が加わりました。これらの変更によって、
以前のテストの受領記録の範囲がさかのぼって広がるわけではありません。

現在の実装の取り決めについては、[パッケージ管理](/hermes/docs/reference/package-management/)、
[共有バンドルビルド](/hermes/docs/developer-guide/shared-bundle-builds/)、[安定版リリース](/hermes/docs/developer-guide/stable-releases/)、
[バンドル版の更新の受け入れ検査](https://github.com/NousResearch/hermes-agent/blob/main/tests/install/BUNDLED_UPDATES.md)を参照してください。

この変更は、ブランチ全体を対象にした監査で見つかった問題の修正を取り込むものです。
リリースの証明書ではありません。監査では `49945b14029e09fef608db9ede899377cdb54e11` を
マージベース `433f7196760e5d76f77ea6d5464ee7f1b602a4ee` と比較しました。

## ドキュメント監査後のランタイムの修正 {#runtime-repairs-after-the-documentation-audit}

監査では、Electron での Python の配置の食い違い、Nix で Python の系列が固定されていること、
cryptography の要件の矛盾、クリーンな Windows でのセットアップの失敗が見つかりました。
その後の対応では、それぞれを担当する実装を変更しています。

- バンドルビルダーは、完成したペイロードを検査し、その起動パスを公開します。
  Electron はこの取り決めをそのまま使い、ペイロードの探索、取り込み、作成は行いません。
- Nix は、Python のメジャー・マイナーバージョンを `pm/lock.json` から選びます。uv2nix の環境、
  パッケージの上書き、追加パッケージ、開発者用シェルは、その系列を使います。
  実際の Nix の評価とビルドの受け入れ検査は、引き続き CI のゲートです。
- cryptography の直接の要件とセキュリティ上の上書きは、`uv.lock` にある修正済みの
  バージョンに合わせてあります。上書きは、引き続きベンダー SDK の古い上限を回避します。
- ブートストラップは uv の終了を待ってから、Python から直接 PM を実行します。
  これにより、ブートストラップが実行ファイルを掴んだままにならず、PM が自分の uv のエントリーを置き換えられます。
- PM の受領記録の公開では、共有ロックの下で、標準ライブラリだけを使ったアトミックな JSON の書き込みを行います。
  失敗の報告で `utils` 経由の PyYAML の import はしなくなりました。
- 使われていなかった開発シェルのコマンドは削除しました。セットアップと、有効化、
  `deactivate` が、PM を使う開発者向けの唯一の経路です。

ネイティブの Windows での確認は、使い捨てのホームで、空のツールストアから始めました。
セットアップが完了し、PM が依存関係の世代を公開し、PowerShell での有効化によって
ストアのインタープリターとソースの CLI が動きました。別に行った PM のインストールも、
実際の依存関係の確認に通りました。これらの確認は、署名付きパッケージのインストール、
更新、Nix のビルドを証明するものではありません。PM のプラグイン・設定と YAML の、より広い結び付きは変わっていません。
[開発者向けのワークフロー](/hermes/docs/reference/package-management/#developer-workflow)では、
ランタイムの有効化と、それとは独立したテスト用・エディター用の環境を区別しています。

| 取り決め | 担当と証拠 |

## 残っているゲート {#remaining-gates}

- 最終的な HEAD でのネイティブの CI で、再試行でだけ成功する失敗なしに最新の修正を確認する必要があります。
- メンテナーが `needs-decision` の扱いを決め、レビューのあとに
  `ci-reviewed` を付ける必要があります。手動の CI では、PR 専用のレビューゲートは飛ばされます。
- パッケージの自動更新と再起動は、引き続き別の E2E の作業系統が担当します。

正準となる PM の PR を1つにするよう求めたトリアージの依頼に従い、PR #95281 は
#102765 に置き換えられたものとして閉じました。重複のラベルは外しました。承認の
ラベルを自分で付けることはしていません。

[a27cd5902a での検証済みの CI](https://github.com/NousResearch/hermes-agent/actions/runs/34059149746)。
正確な HEAD での検証には、上流の検証用ブランチで同じワークフローを使います。
以前の GitHub のグラフでの失敗では、
`resource_exhausted: gitmon refuses to schedule us: fail-fast:network` が報告されていました。

外部の監査ディレクトリには、元の指摘、正確なテストの選択、
実行ごとのログ、ソースのスナップショット、レビューの裁定が入っています。ホストのアプリケーション、
証明書の信頼、本番のサービスは、その監査のあいだ変更していません。
その監査ではリリースを公開していません。これは、その後の実行について述べたものではありません。
