# NeMo Relay 共有メトリクス {#nemo-relay-shared-metrics}

Hermes は、Relay がネイティブ wheel を公開しているプラットフォームでは、NeMo Relay を通常の実行時依存として含んでいます。
共有メトリクスの連携は Hermes に組み込まれており、Hermes の observability プラグインは必要ありません。
それ以外のネイティブ環境でも、Hermes は Relay なしで import できます。
そうした環境では、機能を明示的に絞った何もしないホストを使います。
Hermes の実行はそのまま使えますが、Relay のスコープ、ミドルウェア、プラグイン、サブスクライバーは使えません。
`hermes-agent[nemo-relay]` extra は、既存のインストールコマンドとの互換のための、何もしない別名として残っています。

> [!WARNING]
> この変更で、Hermes の `observability/nemo_relay` プラグインは削除されます。既存の利用者は、
> `plugins.enabled` から `observability/nemo_relay`（または旧名の `nemo_relay`）を外し、
> エクスポーターの設定を、`HERMES_NEMO_RELAY_PLUGINS_TOML` で指定する Relay の
> `plugins.toml` へ移す必要があります。旧来の
> `HERMES_NEMO_RELAY_ATOF_*` と `HERMES_NEMO_RELAY_ATIF_*` の環境変数では、
> エクスポーターはもう有効になりません。新しい環境変数を設定しない限り、Hermes は
> Relay のプラグイン検出、設定の重ね合わせ、ミドルウェア、エクスポーターを動かしません。

Hermes には、0.8 系の中で NeMo Relay 0.8.3 以降が必要です。
この系列が、Hermes が管理下のプロバイダー呼び出しとツール呼び出しに使う、provider-codec と正規のツール結果の取り決めを提供しています。

## 実行時依存とデータの境界 {#runtime-dependency-and-data-boundary}

Hermes は、範囲を限った `>=0.8.3,<0.9` の依存指定から、プラットフォーム別の `nemo-relay` ネイティブ wheel をインストールします。
公開パッケージは [NVIDIA NeMo Relay リポジトリ](https://github.com/NVIDIA/NeMo-Relay) からビルドされています。
対応していないプラットフォームでは、別の実装をダウンロードするのではなく、上で説明した明示的な何もしないランタイムを使います。

運用者が用意する型付きのネイティブプラグインは、Relay 0.8 向けにビルドし直す必要があります。
`grpc-v1` ワーカーは、ツールのコールバック、ツール実行のインターセプト、手動のツール終了 API を使っている場合、生成し直してビルドし直す必要があります。

Relay の管理下実行が有効なときは、設定したインターセプターが実際の呼び出しに作用できるよう、プロバイダーへのリクエストとレスポンスが Hermes プロセス内のそのネイティブモジュールを通ります。
これは共有メトリクスのデータの取り決めとは別のものです。
共有メトリクスのモードでは、詳細な observability 用のネットワークエクスポーターは入らず、そのサブスクライバーが受け付けるのは、後述するバージョン付きで許可リストに載った射影だけです。
付録 A で説明する、利用者が自分で有効にするパッケージ送信器が唯一の外向きの経路です。
利用者が `enabled` と `send` の両方を有効にしない限り何も送信せず、送るのもリアルタイムのスパンではなくパッケージ単位です。
別途設定した詳細な observability プラグインや動的プラグインを有効にすると、別のデータ経路ができることがあり、それぞれ独自のポリシー審査が必要です。

収集は、Hermes のポリシーで有効にしない限りオフのままです。

```yaml
telemetry:
  shared_metrics:
    enabled: true
```

この選択は、プロファイル自身の `config.yaml` から読み取ります。
マシン側で管理される設定の上書きで、プロファイルに代わって共有メトリクスを有効・無効にすることはできません。

Relay プラグインの有効化はネイティブランタイムが受け持ち、明示的に有効にする形のままです。
設定したミドルウェア、エクスポーター、動的プラグインを有効にするには、`HERMES_NEMO_RELAY_PLUGINS_TOML` に使う `plugins.toml` を指定します。
この環境変数が未設定のとき、Hermes は Relay のプラグイン初期化を呼び出さないので、Relay はプラグイン設定の検出や重ね合わせを行いません。
設定されていて、指定したファイルの読み込みに成功した場合、Relay は対応するユーザー用とシステム用の `plugins.toml` を検出し、指定した静的設定をその上に重ねます。
リポジトリ内の `.nemo-relay/plugins.toml` は無視されます。
動的な `[[plugins.dynamic]]` の記述は、指定したファイルからだけ読み込みます。
指定したファイルを読み込めない場合、Hermes はエラーを報告し、Relay の初期化を呼び出さず、周囲の設定の検出にも切り替えません。

## 継続セッションのセッションスパン分割 {#session-span-segmentation-for-continuous-sessions}

Relay は、スコープが閉じたときにスパンを出力します。
継続するゲートウェイのセッションは何日も開いたままになることがあるので、各ターンのスパンは通常どおり出力されても、セッションのスパンは開いたままです。
任意の分割機能を使うと、ターンの区切りでセッションのスコープだけを切り替えられます。

```yaml
gateway:
  telemetry:
    session_segments:
      on_compaction: false  # rotate after context compaction
      max_turns: 0          # 0 = unlimited; N = turns per segment
```

| キー | 既定値 | 動き |
|---|---:|---|
| `on_compaction` | `false` | 圧縮が完了したあと、次のターンの区切りで切り替えます。 |
| `max_turns` | `0` | 完了したターンが N 回に達するごとに切り替えます。`0` は上限なしです。 |

どちらも既定値のままなら、セッション全体で1つのセッションスコープが保たれます。
切り替えたスパンは同じ `session_id` を持ち、`hermes.session.segment` と `hermes.session.segment_reason`（`compaction` または `max_turns`）が加わります。

## 作業ディレクトリのスコープデータ {#working-directory-scope-data}

Hermes がセッションやタスクの論理的な作業ディレクトリを把握している場合、
`hermes.session` と `hermes.turn` の開始スコープには、ATOF でそれが `data.cwd` として含まれます。
そのため、タスクの worktree で動くターンは、それを持つセッションと値が異なることがあります。
作業ディレクトリが分からない場合は省かれます。スコープ終了時のデータは、引き続き結果のために予約されています。

作業ディレクトリは Relay のスコープ入力なので、ATOF だけでなく、有効になっているすべての
Relay サブスクライバーから見えます。パスからはユーザー名、リポジトリ名、マウントの構成が分かることがあります。
Relay は作業ディレクトリでイベントを絞り込みません。パスをホストの外に出したくない場合は、
信頼できるローカルのコレクターを使うか、そのプロセスではリモートのエクスポーターを有効にしないでください。

## プロセス全体のプラグインポリシーとプロファイルの分離 {#process-wide-plugin-policy-and-profile-isolation}

Relay プラグインの設定は、Hermes のプロファイル設定ではなく、プロセス単位のデプロイ上の選択です。
最初にホストされたプロファイルが遅延初期化のきっかけになり、同じ Hermes プロセスがホストするほかのプロファイルはすべて、その結果できた静的ミドルウェア、動的プラグイン、サブスクライバー、エクスポーター、ガードレールのポリシーを共有します。
初期化に成功すると、Hermes は次のログを出します。

```text
Relay plugins are active process-wide and apply to all profiles hosted by this Hermes process.
```

共有のポリシーの中でも、プロファイルのスコープは因果関係の分離を保ちます。
ATIF はイベントを最上位の Agent スコープごとにまとめるので、同時に動くプロファイルのセッションは、1本に混ざった軌跡ではなく別々の軌跡になります。
ATOF などのグローバルなサブスクライバーは、ホストされているすべてのプロファイルのイベントを観測します。
静的・動的なミドルウェアも同様に、すべてのプロファイルの管理下の呼び出しで動きます。

別のワーカープロセスで動くワーカープラグインは、プロファイルごとのセキュリティ境界にはなりません。
プロセス全体で1回の有効化により、ホストされているすべてのプロファイルからの呼び出しが、呼び出し元プロファイルの Relay スコープのスタックを保ったまま、そのワーカーへ振り分けられます。
ネイティブの動的プラグインは Hermes プロセスに読み込まれ、同じポリシーの境界を共有します。

信頼レベル、プラグインの認証情報、エクスポーターの送り先、ガードレールのポリシーが異なるプロファイルは、別々の Hermes プロセスで動かしてください。
このプロセス全体のプラグインの取り決めは、各プロファイルが独立して持つ共有メトリクスへの同意、ローカルの SQLite の状態、ATIF の軌跡のまとまりには影響しません。

Hermes のコアは、Relay ホストを1つ持ち、Hermes のセッションごとに分離された Relay セッションスコープを1つ持ちます。
コアのライフサイクルを生成する側は、`agent.relay_runtime` を使って共有のセッションハンドルを取得するか、そのセッションの文脈で Relay のスコープ、LLM、ツール、mark の API を実行します。
新しい製品向けの mark に、Hermes プラグインとしての登録は必要ありません。
共有メトリクスの mark には、引き続きバージョン付きの許可リストで承認されたフィールドだけを含める必要があります。
必須の依存になったからといって、収集やプライバシーのポリシーが変わるわけではありません。

## 現在の対象範囲 {#current-slices}

現在の縦割りの対象範囲では、仮名化したプロファイルの活動、論理的なモデル呼び出し、最上位のタスク実行、ツールと承認の結果、スキルのライフサイクルと再利用を記録します。

```text
Hermes turn, API, tool, and approval hooks
  -> Relay session, task, LLM, tool, and mark lifecycle
  -> Hermes shared-metrics subscriber
  -> SQLite counters
  -> immutable JSON delta package
```

Hermes は、メトリクス専用のライフサイクルに空の `LLMRequest` を送ります。
これは、上で説明したネイティブランタイムを通る管理下実行の呼び出しとは別のものです。
終端のメトリクスイベントには、Hermes がその論理的な呼び出しに使ったモデル識別子とプロバイダーの経路が含まれます。
たとえば `openrouter` 経由の `nvidia/nemotron-3-ultra` です。
これらの識別子は小文字にそろえ、構造上の長さも制限していますが、リポジトリに含まれるモデル一覧による正規化はしていません。
料金やモデルファミリーの分類はメトリクスのバックエンドの役割です。
プロンプト、レスポンス、エンドポイント、エラー、セッション ID、タスク ID、リクエスト ID は、メトリクスイベントにもパッケージにも含まれません。
新しい呼び出しは `hermes.model_route.count` を使います。
以前の `hermes.model_call.count` の取り決めは、古いビルドで作られた未送出のローカルカウンターをデータを失わずに出力できるよう、読み取り専用で残しています。

同意したうえでの最初のセッション開始時に、空の `hermes.client.active` Relay mark を出します。
プロファイル単位のサブスクライバーは、ランダムな UUID のインストール識別子を作り、トランザクションの compare-and-set を使って、直近24時間の範囲ごとに client-active のカウンターを最大1回だけ記録します。
このメトリクスには次元がありません。
Hermes のバージョン、OS の種類、アーキテクチャ、インストール方法は、値の範囲を限ったパッケージのリソースとして扱います。
同時に動く Hermes プロセスは SQLite のラッチを共有するので、同時に起動しても1つのインストールを二重に数えることはありません。
後のセッションやタスクが再び mark を出そうとすることはありますが、直近24時間の範囲が過ぎるまでサブスクライバーが抑止します。

タスク実行はそれぞれ、`hermes.task_run` という名前の Relay `Function` スコープで、所有する Hermes セッションを親に持ちます。
開始時のカウンターに含まれるのは、範囲を限った実行面と入口の値だけです。
終端のカウンターには、範囲を限った結果、終了理由、終了状態、所要時間、論理的なモデル呼び出し回数、終端に達したツール呼び出し回数、プロバイダーへの再試行回数の区分が含まれます。
再試行とは、同じ Hermes API リクエスト ID に対する追加のプロバイダー試行のことで、論理的なモデル呼び出し回数を水増ししません。
ツール呼び出しは、終端のツール結果を観測したあと、Hermes のツール呼び出し ID で重複を除きます。
外側の `AIAgent` 実行の境界が、通常の戻り、早期の戻り、例外、キャンセルのいずれでもタスクを閉じます。
コンテキスト圧縮の途中で Hermes が会話のセッションを切り替えた場合も、実行中のタスクの所有はタスク ID に従います。

ツールの呼び出しはそれぞれ、`hermes.tool_call` という名前の Relay ツールライフサイクルで表します。
終端のカウンターに含まれるのは、範囲を限ったツールの分類、結果、承認の結果、待ち時間、明示的な再試行回数の区分だけです。
Hermes は、実行時のレジストリにすでに宣言されているツールセットから分類を導きます。
独自のツールセットや認識できないツールセットは、ツール名やプラグイン名を出力するのではなく `other` にまとめます。
Hermes は、同じツール名の繰り返しや隣り合う呼び出しから再試行を推測しません。
フックが明示的な再試行の関係を渡さない場合、再試行の区分は `unknown` になります。
承認の判断は `hermes.tool_approval` mark として出し、ツール呼び出しに紐づくもの、または明示的に `unattributed` として記録します。
ツール名、呼び出し ID、引数、結果、コマンド、説明、エラーの文言は、共有メトリクスのイベントにもパッケージにも含まれません。
開始したツールがタスク終了時にまだ開いていた場合は、失敗、タイムアウト、キャンセルのいずれかとして閉じ、タスクのツール回数の区分に含めたままにします。

スキルの変更に成功すると、範囲を限った操作と由来だけを持つ `hermes.skill.lifecycle` mark を出します。
スキルの読み込みに成功すると、範囲を限った由来、初回利用か再利用かの状態、パッチ後の再利用の状態、利用回数の区分を持つ `hermes.skill.load` mark を出します。
Hermes は、再利用とパッチ世代の連続性を、既存の `skills/.usage.json` の状態の中でトランザクションとして導きます。
スキル名や正確な回数・世代が、Relay のメトリクスイベント、SQLite の次元、パッケージに入ることはありません。
新しいパッチ後の利用は `reused_after_patch` として1回だけ数え、その後の利用は次のパッチまで通常の再利用として扱います。
パッチ後のタスク結果との結び付けは、その範囲と複数スキルの場合の意味が決まるまで先送りしています。

ローカルの状態は次の場所に書き込まれます。

```text
$HERMES_HOME/telemetry/shared_metrics/metrics.sqlite3
$HERMES_HOME/telemetry/shared_metrics/outbox/*.json
```

データベースには、トランザクションで扱う集計と、パッケージの outbox の状態を保存します。
パッケージファイルは、閉じた JSON スキーマに適合する変更不可の差分文書で、アトミックな置き換えで書き込みます。
各パッケージには、Hermes のバージョン、OS の種類、アーキテクチャ、インストール方法を、範囲を限ったクライアントのリソースとして記録します。
認識できないプラットフォームやインストールの値は `unknown` として出力し、生のプラットフォーム文字列、ホスト名、パスは含めません。
すべてパッケージ化済みの集計行と、出力に成功したパッケージの行とファイルは、ローカルに30日間保持します。
未処理のパッケージ行と、未出力の差分を持つカウンターは削除しません。
既存の outbox ファイルでは、パッケージスキーマ v1 はそのままです。
新しいパッケージは v2 を使います。
v2 は廃止したモデル呼び出しの取り決めと現行のモデル経路の取り決めの両方を受け付けるので、アップグレード時に未送出のカウンターを安全に出し切れます。

各パッケージには、ランダムな UUID として生成した `install_id` が含まれます。
スキーマ上のフィールド名とは違い、現在の範囲は1つの `HERMES_HOME` なので、正確には永続的な仮名のプロファイル識別子です。
ハードウェア、アカウント、ホスト、パス、認証情報のデータから導いたものではありません。
そのプロファイルのパッケージ間では一定なので、それらのローカルパッケージを結び付けることができます。
`$HERMES_HOME/telemetry/shared_metrics` を削除すると、すべての集計とパッケージファイルと一緒に識別子もリセットされます。

リモートへの送信は利用者が自分で有効にするもので、既定ではオフです。
永続的なローカル識別子をリモートで再利用するには、同意、識別子の範囲、リセット時の動き、保持期間、削除を扱う、製品とプライバシーについての別の判断が必要でした。
その判断はすでに下されています。

> それらの判断は
> [付録 A](#appendix-a-remote-exporter-decisions-phase-2) に記録しており、それを実装した
> エクスポーターも提供済みです。収集だけでは今も何も送信しません。送信器が動くのは
> `telemetry.shared_metrics.send` も true のときだけです。送信する各パッケージは、
> 固定の `install_id` をそのまま持ちます（製品判断、
> 2026-08-27。置き換えられた HMAC 仮名の設計を含む記録は A.2 を参照してください）。

インストール識別子の範囲は1つの `HERMES_HOME` です。
リセットするには、Hermes のプロセスを止めてから `$HERMES_HOME/telemetry/shared_metrics` を削除します。
これは意図して、古い識別子、集計データベース、キューにあるローカルパッケージをまとめて消します。
次に同意したセッションで新しい識別子が作られます。
共有メトリクスを無効にすると新しい収集は止まりますが、それまでに収集したローカルの状態を黙って削除することはありません。

## スモークテスト {#smoke-test}

決定的な応答を返すローカルのモデルサーバーに対して、実際の Hermes CLI のターンを実行します。

```bash
./.venv/bin/python scripts/smoke_nemo_relay_shared_metrics.py
```

このスクリプトは、既定ではインストール済みの `nemo-relay` 依存を使います。
ローカルでビルドした Relay バインディングを試すときだけ、`--relay-python ../nemo-relay/python` を渡してください。

スモークテストでは、ローカルモデルが最終回答の前に実際の `read_file` ツール呼び出しを要求します。
続いて、インストール済みの Relay バインディングを通して、作成、読み込み、再利用、パッチ、編集、古くなった状態、アーカイブ、復元、インストールの各スキル遷移を実行します。
SQLite のモデル・プロバイダー・タスク・ツール・スキルのカウンターを確認し、出力されたすべての差分パッケージを閉じたスキーマで検証し、仮名の client-active カウンターを確認し、プロンプト、レスポンス、ツール呼び出し ID、ツール結果、スキル名の目印がパッケージに含まれていないことを確かめます。

## 付録 A: リモートエクスポーターに関する判断（フェーズ2） {#appendix-a-remote-exporter-decisions-phase-2}

状態: **実装済み。**
この付録は、「現在の対象範囲」が将来のリモートエクスポーターに先送りしていた、製品とプライバシーについての問いに答えるものです。
何を決めたか、なぜそう決めたかを記録し、実装のあとも理由が残るようにしています。

送信は既定でオフで、`telemetry.shared_metrics.enabled` と `telemetry.shared_metrics.send` の両方が必要です。

エクスポーターは、`$HERMES_HOME/telemetry/shared_metrics/outbox/` にすでに書き込まれたパッケージファイルを、Hermes のテレメトリー取り込みサービスへ送ります。
このサービスが検証するのは外枠（`schema_version` と UUID の `package_id`）だけで、本文はそのまま S3 に保存します。

### A.1 同意 {#a1-consent}

送信は、収集とは **別に利用者が自分で有効にするもの** で、新しい設定キーで指定します。

```yaml
telemetry:
  shared_metrics:
    enabled: false   # collect locally
    send: false      # NEW: transmit to the Nous telemetry service
```

- `send` の既定値は **false** です。収集だけでは決して送信しません。
- `send` には `enabled` が必要です。ただし、送信を有効にすれば収集も有効になる、という **意味ではありません**。
  送信のフラグが、黙って収集を有効にしてはいけないからです。`send: true` で `enabled: false` の場合は、
  警告を出すだけで何もしません。
- `enabled` と同じく、`send` はプロファイルが持つ設定で、管理側スコープの設定で
  上書きされることはありません。

**パッケージを送信するのは、その期間全体が記録済みの同意期間に収まるときだけです。**
同意は、共有メトリクスの SQLite ストア（`send_consent_windows`）に明示的な区間として保存します。
区間は `send: true` を初めて観測したときに開き、その後の観測のたびに先へ確認が延び、`send: false` を観測したときに閉じます。
閉じる時点は壁時計の時刻ではなく、最後に *確認できた* 時点です。
1つの照合処理が、プロセスが起動するたびに設定からこの表を導きます。
そのため、セットアップウィザードでの変更、`config.yaml` の手編集、処理途中での取り消しがすべて同じ経路をたどり、どれを使っても状態の変化を取りこぼしません。

期間が最初の同意期間より前にあるパッケージ、同意期間の間に落ちるパッケージ、最新の確認時点を越えるパッケージは除外します。
このゲートは閉じる側に倒れます。
そのため、新しいパッケージは期間が終わってから、最大でプロセスの起動1回分待つと送信の対象になります。

ゲートの基準はパッケージの作成時刻ではなく **期間** です。
1つの期間は、別々の日に作られる複数のパッケージに分かれます。
その日の最初のパッケージはその日のうちに書き込まれ、同じ期間の残りのパッケージはたいてい翌日に続きます。
作成時刻を基準にすると、ある期間の後半だけを送って前半を落とし、**黙って少なく数えた** 1日を報告することになります。
期間を基準にすれば、同意は先に向かってだけ効き、送信する期間はどれも欠けがありません。

ローカルの履歴は最大30日前までさかのぼることがあり、そのデータは何もアップロードしないという約束のもとで集めたものです。
同意を先に向かってだけ尊重することで失うのは、そもそも送る許可を得ていなかった最大30日分の未送信分だけです。

### A.2 識別子の範囲: 固定の install_id をそのまま送信する {#a2-identity-scope-the-stable-installid-is-transmitted-as-is}

**判断の記録。**
このエクスポーターの当初の設計（およびこの付録の改訂1〜8）では、識別子ではなく鍵付きの仮名を送信していました。
`HMAC-SHA256(key = locally-held rotating salt, message = install_id)` で、salt は30日ごとに入れ替えていました。
**2026-08-27**、機能の提供前（同意した利用者も本番での送信もゼロ）に、製品の責任者は、分析に必要なのは **期間をまたいで一定の識別子** だと判断しました。
継続率の曲線や、インストールの長期的な動きを見るためのもので、入れ替えは設計上それを壊します。
仮名化の層は、その場で弱めるのではなく、丸ごと取り除きました。

現在送信しているものは次のとおりです。

- 各パッケージは `install_id` をそのまま持ちます。上で説明した、プロファイル単位の永続的な
  ランダム UUID です。
- ローカルで生成し（`uuid4`）、ハードウェア、アカウント、ユーザー、マシンから導いた情報は含まず、
  識別するのは人ではなく *プロファイル* です。
- 利用者が共有メトリクスのディレクトリを削除して作り直すまで一定です（A.4 を参照）。

結果として起きることを、取り繕わずに書いておきます。

- 1つのプロファイルのパッケージは、期間ごとではなく **無期限に** 結び付きます。
  1つのインストールの日々の外枠の並びを長期にわたって結び付けられるのは、残ってしまった性質ではなく、今は設計どおりの動きです。
- 旧設計についての A.3 の残存リスク分析（一定の `resource` の組み合わせと、
  連続した期間が入れ替えの境界をまたいでつながる問題）は意味を失いました。またぐべき期間の
  境界がもう無いからです。
- セットアップウィザードの同意の文言は、この識別子の方式を明示しています。
  導出を取り除いたのと同じ変更で文言も更新したので、提供したどのビルドでも、古い文言のもとで同意を集めたことはありません。

**バイト単位で同じ再送は引き続き保証します。**
送信する id は、パッケージを最初に準備したときに行（`sent_install_id`）へ記録し、送信する本文は常にその記録した値から組み立て直すので、再試行でも同じバイト列になります。
取り決めがこれを要求しています。
同じ `package_id` を異なる内容で再送したときの動きは未定義です。
（id が一定になったので、記録した写しが入れ替えへの対策として必須というわけではなくなりましたが、監査用の列として、また将来識別子の意味が変わったときの安価な保険として残しています。）

### A.3 入れ替え: 削除済み（判断の記録） {#a3-rotation-removed-decision-record}

salt の入れ替えは、導出と一緒に削除しました（製品判断、2026-08-27）。
この節は、以前の設計が何をしていたか、なぜ削除を受け入れたかの記録として残しています。

- 入れ替えは、長期的な結び付けを制限するためにありました。30日の期間ごとに1つの識別子で、
  期間をまたぐと無関係な識別子になります。
- 文書化していた残存リスク（分析の全文は git 履歴を参照）: 外枠の一定で情報量の少ない
  `resource` の組み合わせと、連続する日ごとの期間によって、珍しい構成ではいずれにせよ
  期間をまたいでつながりうるため、境界は壁ではなく、コストを上げるだけのものでした。
- 入れ替えをやめることになった製品上の必要: 期間をまたいだ連続性こそ、継続率の分析に
  必要なものです。誠実な分析をおもに妨げる一方で、本気で突き合わせようとする相手には
  コストを上げるだけの境界は、一定の識別子が要件になった時点で、割に合わない取引だと判断しました。

ストアに salt は無く、入れ替えの予定も無く、パイプラインのどこにも導出された識別子はありません。

### A.4 リセット時の動き {#a4-reset-behavior}

`$HERMES_HOME/telemetry/shared_metrics` を削除すると、上で説明したとおり、ローカルの識別子、集計、パッケージファイルが今もリセットされます。
ただし、正直に書いておくべき注意点が2つ加わりました。

- リセットで `install_id` が作り直されるので、その後のパッケージは **新しい**
  識別子で送信されます。ローカルのリセットで、リモート側でも新しい識別子になります。
- リセットで **送信を取り消すことはできません**。すでに送信したパッケージは、
  送ったときの識別子のまま取り込みサービスの保存先に残ります。v1 の取り決めには、
  読み戻しや削除の API はありません。

`send: false` にすると、送信はすぐに止まります。
同意はパッケージを送る前に毎回読み直すので、処理の途中であっても、まとめて全部を送り切るのではなく、いま送っているパッケージの後で止まります。
すでに送信したパッケージは削除せず、ローカルでの収集も止めません。

送信をオフにすると、**同意期間も閉じます**。
閉じる時点は壁時計の時刻ではなく、同意を実際に観測した最後の時点です。
期間がある同意期間と次の同意期間の間に落ちるパッケージは、後で送信を有効にし直しても送信しません。
これは、オンとオフを何回繰り返しても、プロセスが動いていない間の手編集でも、時計がどちらの方向に飛んでも成り立ちます
（同意期間の開始は、ストアにすでにあるどのタイムスタンプより後に切り上げます。観測の印は1回の呼び出しごとに限られた幅しか進まないので、1回だけおかしな未来の値が来ても確認の範囲が何年も先へ引っ張られることはありません。閉じる時点が、閉じる観測自身の時計より後になることもありません）。
以前の、1つの動く同意開始日の方式とは違い、閉じて開き直しても、前の同意期間の未配送分は捨てません。
それらのパッケージは自分の区間の中に収まったまま、送信の対象であり続けます。

意図したアップグレード時の結果が1つあります。
区間方式より前の同意モデル（`send_consent_windows` ができる前）で出力したパッケージは、記録済みの最初の同意期間より前にあるため、アップグレード後に送信されることはありません。
これは閉じる側に倒した結果です。
それらを送るために古い動く日付の印を持ち込み直すと、5回のレビューで不健全だとわかった意味合いを持ち込み直すことになります。
失うのはせいぜい未配送分だけで、収集したデータを失うことはありません。

### A.5 保持期間 {#a5-retention}

- **ローカル:** 変更なしです。出力に成功した履歴は30日間保持し、未処理の差分は
  出力するまで保持します。送信の状態でローカルの保持期間が **延びることはありません**。
  送信できなかったパッケージも30日で削除します。
  恒久的に到達できない送り先に向けてローカルが際限なく膨らむほうが、1か月壊れたままのインストールのメトリクスを失うより悪い失敗だからです。
- **リモート:** 生のパッケージは、本番では期限なく、ステージングでは
  30日間、S3 に保持します。

### A.6 削除 {#a6-deletion}

v1 の取り決めにはリモートでの削除の経路が無く、この付録もそれを新たに作ることはしません。
利用者ができることは次のとおりです。

| 操作 | 効果 |
|---|---|
| `send: false` | それ以上のパッケージはマシンの外へ出ません |
| `enabled: false` | 収集が止まります。既存のローカルの状態は残ります |
| `.../shared_metrics` を削除 | ローカルの識別子、集計、ファイルがリセットされます。以後の送信は新しい install_id を使います |
| 送信済みのデータを削除 | 利用者自身ではできません。運用者が S3 バケットを操作する必要があります |

要求に応じた削除の義務を負うことになった場合でも、今は探す経路が直接的です。
利用者の `install_id`（ローカルのストアから読めます）が、その利用者のデータが保存されているキーです。
サービス側の削除 API を作るかどうかは、実装の細部ではなく、新しい製品判断のままです。

### A.7 outbox ディレクトリとは何か {#a7-what-the-outbox-directory-is}

フェーズ2の計画中に一度誤読され、それが利用者のデータを削除しかねない形だったので、記録しておきます。

このディレクトリは **ローカルの履歴であって、送信キューではありません**。
`package_outbox` は SQLite のテーブルで、その `exported_at` 列の意味は「ディスクに書き込んだ」であり、「送信した」ではありません。
ファイルは変更不可で、**経過日数だけ** を基準に削除します。

取り込みの取り決めでは、送信側は `202` を受け取ったらパッケージを outbox から削除すべきとされています。
**エクスポーターはこれを行いません。**
受領確認で削除すると、利用者の30日分のローカル履歴を送信キューに流用することになり、保持すると約束した状態を壊してしまいます。
代わりに、送信の状態は `package_outbox` テーブルの新しい列に持たせており、ファイルは送信によって一切変更されません。

### A.8 範囲についての注記 {#a8-scope-note}

パッケージ本文の中の `install_id` フィールドは、生成した側が書いたとおりに送信します（同じ値を記録している行の固定済みの `sent_install_id` から書き直します）。
ほかのペイロードのフィールドは変わらず、何も追加されず、サービスは本文全体を中身を見ないデータとして扱います。
そのため、ペイロードのスキーマの変更は、これまでどおり送信側の関心事のままです。
