# ソース版の更新の仕上げを誰が受け持つか {#source-update-completion-ownership}

## 段階の継ぎ目 {#phase-seam}

コマンドのプロセスが受け持つのは、受け入れの判定、更新のロックと出力の寿命、更新前の
棚卸し、すべてのプロファイルのスナップショット、ゲートウェイの一時停止、Git の選択・stash・復元と
構文・HEAD の検査、そして ZIP のダウンロード・展開・未コミット変更の再確認・リリースの接ぎ木・入れ替えです。
コードを入れ替える前に、仕上げ用の受け渡しの仕組みを読み込んでおきます。最終的なツリーが
選ばれたら（上流のマージも含みます）、Git、すでに最新だった場合の再試行、ZIP のいずれの経路も、
**そのツリーにある** `update_completion.py` へ、版付きの JSON の依頼を 1 つ送ります。コマンドのプロセスでは、
キャッシュ済みのアプリのモジュールを追い出したり読み込み直したりはしません。

依頼に含まれるのは、正規化したソースとデータの置き場所、デスクトップ製品の選択、対話と
ゲートウェイのどちらの動作か、更新前の版、使用中と兄弟のスナップショットの識別子、
直列化した実行環境の計画、開いている受領記録の識別子とデータ、Windows で一時停止した分の引換券です。
中身はデータだけで、呼び出し可能なオブジェクトや pickle は決して含みません。対話的な設定の問いかけに
答えられるよう、標準入力は引き継いだままにします。ゲートウェイの動作では、対話しない振る舞いを保ちます。
子プロセスの出力は見えたままで、親の更新の出力にも写されます。

## 新しいコードの受け持ち {#new-code-owner}

標準ライブラリだけで書かれた入口が、手元にある Python を `-I -S` 付きで起動するので、
古い site-packages や実行可能な `.pth` ファイルは初期化されません。専用のバイトコードのキャッシュの
置き場所を使い、新しいチェックアウトのものを読み込む前に古いキャッシュのファイルを締め出します。その明示的な

記録済みの依存関係の和集合を用意したうえで、新しい有効化の環境で選ばれた Python を起動します。
このインタプリタも site の初期化を切った状態で起動し、アプリのものを読み込む前に、
実行環境の受け持ちが選ばれた世代を借り受けて有効にします。アプリの仕上げのコードを読み込むのは、このインタプリタだけです。同じ
受領記録と対応付けの識別子が、この準備の境目をまたいで引き継がれます（PM の結果も含みます）。
選ばれた Python による仕上げが受け持つのは、起動用ファイルの公開、ビルド処理、キャッシュの
無効化、すべてのプロファイルの設定・状態・スキルの手入れ、プロセスの走査、
一群のプロセスの再起動、Windows での再開、ダッシュボードの重複の整理、そして検証です。

種類ごとの既存の再起動と中断からの回復の手順はそのまま残ります。監視役やプロセスの一時的な失敗は、
新旧の世代が混ざった読み込みがなくても実際に起きるからです。なくなるのは、
追い出しと読み込み直しによる回避策と、再試行と ZIP それぞれに独立していた後半の組み立てだけです。
ゲートウェイの終了状態は、再起動で更新処理の cgroup が終わってしまう前に書き込まれ、
あとで失敗すれば格下げされます。検証が最後の受領記録を公開します。

## 親の生存期間と失敗 {#parent-lifecycle-and-failures}

親は子を待ち、子の 0 以外の結果をそのまま伝えます（シグナルは、シェルと同じく
128+シグナル番号に対応付けます）。子は 0 で終了するだけでは成功になりません。
一致する受領記録の識別子を持った最終の応答が必要です。その応答は、
更新された Windows の引換券を返します。これにより、親が登録している緊急時の再開が、
すでに終わった作業を繰り返さずに済みます。親が通常どおり終わるときには、手入れの処理は何もしません。

親は、子の仕上げが確認されるまで元の受領記録を持ち続けます。
子の出力が無い、または失敗した場合は、その受領記録を既存のコマンドの境目での
失敗処理に残します。標準ライブラリだけの準備処理は、アプリのものを読み込めない場合でも、
対応付けた PM の失敗データを返し、プロセスの境目ごとに負のシグナルによる終了を
整えます。POSIX では、仕上げが新しいセッションとプロセスグループを持ちます。
取り消すときはロックを手放す前にそのグループを終了させます（Windows では、手元に保持している
子に対して `taskkill /T` でツリーごと終了させます）。親は仕上げのプロセスを起動する前に、
保留中の一群のプロセスに対する責務を記録します。準備を始められなかった場合も同じです。親による Windows の緊急時の再開は、
子を実行できないときや子が強制終了されたときの、最後の手段としての生存期間の責務として残ります。
子が失敗しても、保留中の一群のプロセスに対する責務は決して消されません。手入れが始まったあとで
コードが自動で巻き戻されることはありません（SQLite のスナップショットはファイルを失ったときの回復手段であって、巻き戻しではありません）。

## 過去の仕組みとの互換 {#historical-surface}

これまでに出荷され、たどり着けるすべての更新処理の履歴から固定した名前は、
すべて引き続き解決できます。過去の依存関係のフックは、標準ライブラリだけの引き継ぎの橋渡しを保ちます。
古い親は待ち、受領記録と回復の状態を運び、引退したインストーラを再開することはありません。
新たに引退した準備と、モジュールの読み込み直しのフックのうち、未完了と明示されたものは
0 以外で止まり、もう一度 `hermes update` を求めます。欠けている仕上げの依頼を作り出すことはできません。
現在の Git・最新・ZIP の呼び出し元は、正規の仕上げの受け渡しの仕組みだけを使い、過去の引き継ぎの入口は使いません。
固定されていない、ブランチにしかない再試行の組み立ては、互換用の層を作らずに削除します。ACP の手軽な
公開は、起動用ファイルの受け持ちが持つ `expose_cli` を使います。過去の ACP の入口は
変換役にすぎず、2 つめの書き手になることはありません。固定した名前の集合は、削ったり、
タグだけの網羅に置き換えたりすることはありません。現在の経路で新しく読み込むものは、その履歴と合わせて扱います。

## 検証 {#verification}

使うのは、隔離したデータの置き場所、使い捨ての Git リポジトリ、依存関係・ビルド・サービスの偽の
差し替え部品だけです。互換性のないモジュールをキャッシュした古いプロセスで、
実際の Git の移行を通って新しいコードへ移ること、選ばれた Python での実行、受領記録の識別子と
スナップショットの引き渡し、0 以外や突然の子の終了、ロックの解放、Windows の引換券の
返却を確かめます。既存の対象を絞ったテストが、ZIP の未コミット変更の確認と接ぎ木、スナップショット、一群のプロセスの
突き合わせ、監視役の時間の扱い、過去の名前の読み込みを扱います。ネイティブのサービスの再起動と
Windows / macOS での受け入れの確認は、別に必須の検証の流れとして残ります。この実装のテストの実行では、
稼働中の利用者のサービスや利用者の状態には一切触れません。
