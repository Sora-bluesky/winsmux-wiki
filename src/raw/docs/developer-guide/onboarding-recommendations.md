# オンボーディングでのおすすめ {#onboarding-recommendations}

案内つきのオンボーディングは、ユーザーのアプリの好みと、観測できた機能をもとに、できることを提案します。アクセス権を与えるわけではなく、接続の手順を別にもう1つ作るわけでもありません。この機能は、既存の `HERMES_GUEST_ONBOARDING` の流れの中にとどまります。

## 何を優先するか {#what-takes-priority}

既存の `machineSetupLeads()` の判定は、これまでどおり、セットアップしたばかりの端末や、RTX / DGX Spark と認識した端末では、端末のセットアップを先頭に出し、ほかの作業は **Something else** の後ろに回します。「新しい端末」という判定は既存の経過日数による推定で、OS をインストールした日付の証明ではありません。経過日数がわからない Spark には、ハードウェアに合わせた案内を出しますが、OS が新しいとは言いません。

それ以外の場合、案内はアプリを使う関連性の高い作業を優先し、接続なしでできる代わりの案も添えます。アプリを検出しても、それで出せる選択肢は最大1つです。残りの選択肢は、ユーザーの目標やほかの機能から選びます。同じアプリについて複数の案を出すのは、ユーザーが明示的に求めたときだけです。受信箱を使う作業を選んだ場合は、許可を得たうえで本物の受信箱のデータを使います。許可がないときに、見せかけの受信箱を作ることはしません。必要な接続が飛ばされたり使えなかったりすると、その作業は止まったままです。ユーザーは別の作業を選ぶか、データを自分で渡せます。

## カタログのメタデータ {#catalog-metadata}

実行時に実際のカタログを読みます。項目に、おすすめ用の新しいメタデータを足す必要はありません。検出はカタログ上の名前（slug の区切り文字は空白として扱います）で行い、作業の案はモデルが説明文から導きます。項目を消せば、以降のスナップショットからも消えます。特定の製品向けの項目、パッケージ、インストール手順を、オンボーディングの変更に含めてはいけません。

カタログの管理者は、必要に応じてもっと詳しいヒントを書けます。

```yaml
suggest:
  keywords: [example, modeling]
  hosts: [example.com]
  applications: [Example Studio]
  requires_app: true
  examples:
    - Light a product render in Example Studio
```

- `keywords` と `hosts` の意味は、これまでと変わりません。`applications`、`examples`、`requires_app` は、任意で足せる項目です。
- `applications` には、安全なラベルや別名を最大 16 個、それぞれ 80 文字以内で書きます。パス、シェルの引数、正規表現、スクリプトは書けません。
- `examples` には、表示できる1行の「できること」を最大 6 個、それぞれ 240 文字以内で書きます。モデルがこれを、既存の選択肢チップ用の短いラベルにまとめます。
- `requires_app` を true にするのは、手元のアプリが前提条件のときだけです。デスクトップアプリが入っていることは、クラウドのサービスとの関連性を示す手がかりにはなりますが、必須条件とは限りません。
- 例に挙げる機能やセットアップの前提条件は、その連携の実際のドキュメントと照らし合わせて確認する必要があります。カタログに項目があることは、アカウントへのアクセス、利用資格、アドオンの準備、道具との実際の接続を証明するものではありません。

管理アプリの選択画面は、選び抜いた先頭の項目を保ちつつ、実際のカタログにある有効なほかの行も検索できるようにします。新しく配備された管理コネクタが、slug が先頭の一覧にないというだけで捨てられることは、もうありません。ポータル側に新しいメタデータの API を用意する必要もありません。

## 検出と範囲 {#discovery-and-scope}

`GET /api/mcp/catalog?detect_apps=true` を使うと、次が足されます。

- `entries[].detected_apps`: カタログから導いたアプリ名、または任意で明示した別名のうち、一致したものだけ。
- `discovery`: `{scope: "backend", status: "ok" | "unavailable", platform: string}`。

既定のカタログの取得では、アプリの検出はしません。任意の検出は、MCP のプロセスが動く **バックエンドの端末** で、アプリの標準的な置き場所と、PATH 上の安全な候補名との完全一致を確かめます。アプリを起動したり、MCP を立ち上げたり、パッケージを入れたり、アプリの文書を読んだり、ネットワークにつないだりはしません。インストール済みソフトの全一覧も、ファイルシステムのパスも返しません。

検出には、見るディレクトリ数、項目数、時間の上限があります。インストール済みソフトを漏れなく洗い出すものではありません。アクセスに失敗した、上限に達した、対応していないホストだった、という場合は `unavailable` を返します。見つかったという結果は役に立ちますが、見つからなかったことは「無い」ことの証拠にはなりません。macOS のアプリバンドル、Linux のデスクトップエントリ、Windows の共通のプログラムフォルダには、それぞれのプラットフォーム用の読み取り方があります。Windows のレジストリの列挙は含まれません。

Desktop は、カタログの取得先を、案内や引き継ぎで使っているバックエンドとプロファイルに固定します。デスクトップ側で観測したアプリと、リモートの MCP ホストを組み合わせることはしません。一時プロファイルでの API の確認では、読み取り専用のアプリ検出のために実際の OS のホームを使い続けられます。その場合も、インストール済みのプロファイルの設定は読みません。

## おすすめと実行の境界 {#recommendation-and-execution-boundaries}

おすすめの順位は、作業との関連がはっきりしていることと、選ばれたアプリを、設定の有無やアプリが入っているという手がかりより優先します。無効にされている連携は、ユーザーがはっきり関心を示さない限り、自動では再び出しません。手元のアプリが必須の項目は、検出で見つかったか、すでに設定があるときだけ候補になります。1つの種には、カタログ全体ではなく、少数の候補だけが入ります。

案内は、セッションが作られたときに読み取り専用のスナップショットを受け取ります。引き継ぎでは、作業するプロファイル向けにそのスナップショットを取り直し、選ばれた候補のセットアップのメモを全文含めます。どちらの経路も、既存のシステムプロンプトを書き換えたり、接続の権限を覚えておいたり、セットアップを実行したりはしません。カタログが古いか使えない場合は、既存のオンボーディングの動きに戻ります。

| 手がかり | 意味 | 次の手 |
| --- | --- | --- |
| アプリは検出、MCP はなし | アプリの手がかりはあるが、セットアップはまだ必要 | 既存の `manage_connections` のインストール承認 |
| MCP は設定済みだが無効、明示的な要望あり | 設定はあるが、意図して止めてある | 既存の有効化の承認 |
| MCP が設定済みで有効 | 設定があるだけで、接続は未確認 | 使える道具を調べ、使う前に確認する |
| 管理アプリが未接続 | アカウントの許可が必要 | 既存の管理接続カード |
| 飛ばされた、使えない、またはセッションに機能がない | 許可されていない、使えない | 止まった作業を説明する。迂回や自動の再試行はしない |

MCP が対象のとき、`status` は `manage_connections` で使える操作では **ありません**。スナップショットが `setupAction`（`install`、`enable`、または null）を渡し、許可は本当に必要なときだけ求めます。管理アカウントの状態の確認は、別の、対応済みの操作のままです。この区別は、プロンプトの文面だけでなく、実際に生成された道具の引数で確かめています。

古い入力欄の提案の仕組みは、ホストされた HTTP の OAuth しか完了できません。新しいメタデータのせいで手元のエディタが無関係なその流れへ回されないよう、手元のアプリの項目と OAuth 以外の項目は除外しています。オンボーディングは代わりに、共通の接続の操作を使います。

## 接続の操作の作業との互換性 {#compatibility-with-the-connection-operation-work}

この実装は、公開されている `manage_connections` の道具と、既存のカタログの API を使います。接続の操作の状態、生成された RPC の契約、アカウントの識別子、OAuth のコールバック、再試行の持ち主、監視の動き、確定した結果の扱いは変えません。

現在の連携と、Sid がまだマージ待ちの [接続の操作の PR](https://github.com/NousResearch/hermes-agent/pull/111008) の両方と照らし合わせて確認しました。その PR は MCP の実行をバックエンドへ移しますが、おすすめは、いまどちら側で操作を実行しているかに依存しません。任意のカタログの項目は古いクライアントとの互換を保ち、項目がなくても古いバックエンドとの互換が保たれます。Sid が取りやめたポータルのツールキットのメタデータ API には依存していません。

オンボーディングの手順書とそのテストには、意図した製品方針の重なりが1つあります。「アカウントなしの代わりのものを作る」という古い要件が、受け入れた作業の実際の前提条件に置き換わっています。この重なりは、ブランチが合流するときにすり合わせる必要があり、矛盾する指示として残してはいけません。将来の未知の互換性を壊す API の変更との互換までは、保証していません。

## 検証の境界 {#verification-boundaries}

契約テストは、カタログの解析、明示的に有効にしたときだけの読み取り専用の検出、A/B/A のプロファイルの分離、メタデータがない場合、順位づけ、バックエンドに固定した種の作成、MCP の正しいセットアップ操作、新しい端末や Spark の優先の維持を対象にしています。

合成したオンボーディングのやりとりに対して実際に推論させれば、おすすめされる結果と、生成されるセットアップ操作を確かめられます。アプリの実際の検出では、本当にインストールされたアプリの手がかりを確かめられます。ただし、どちらも OAuth の完了や Blender の中での実行を証明するものではありません。それには、アプリのアドオンやサーバー、ユーザーの承認、害のない道具の実動作の確認が必要です。実際に返ってきた項目のセットアップのメモを読んでください。オンボーディングは、独自の連携手順を用意しません。
