# Bot Mode {#bot-mode}

**Bot Mode** は、[Hermes のプロファイル](/hermes/docs/user-guide/profiles/) を、名前を持った **Bot** の一団に変えます。Bot はそれぞれ自分の役割、モデル、記憶、スキル、アバターを持ちます。繰り返しの仕事をこなし、グループチャットで一緒に考え、互いに直接メッセージを送ります。専門の Bot を一度作れば、それはずっとそこにいて、クリック 1 つで呼び出せます。

Bot Mode は **[デスクトップアプリ](/hermes/docs/user-guide/desktop/) に組み込まれて出荷**され、**既定で有効**です。インストールは要りません。左のサイドバーで Sessions の隣に **Bots** タブとして現れ、Bots タブを開いている間は会話の横に **Routines** のタイルが並びます。

:::tip Bot はプロファイルです
新しく覚えることはありません。Bot は Hermes のプロファイル **そのもの** です。`~/.hermes/profiles/<name>/` の下で、設定、記憶、スキル、認証情報、チャットの履歴が分かれています。Bot Mode はその上にかぶせた画面なので、そこでやったことは CLI からも見えます。`hermes -p <bot> chat` で同じエージェントが開きますし、Bot の定期の仕事は `hermes cron list` に出てきます。本体への手当ても、常駐のデーモンも、余分な保存領域も要りません。
:::

## Bots のペイン {#the-bots-pane}

一覧には、エージェントのプロファイルごとに 1 行が並びます。アバター、最新のメッセージの抜粋、時刻が出ます。

- **Bot をクリック**するとそのチャットに入ります。どの Bot にも、生まれた瞬間に作られて（そして固定される）唯一の **Bot Chat** という会話があります。
- **Active now** — 一覧の上の帯に、いま働いている Bot がすべて出ます。ゲートウェイが処理中のプロファイルに加え、直近 90 秒以内に書き込んだ Bot が並びます。それぞれのチップからその Bot のチャットを開けます。この帯が一覧の並びを変えることはなく、みんなが手を止めていれば消えます。
- **検索** は、入力に合わせて一覧を絞り込みます。
- **Bot を隠す** — 行を右クリックして **Hide Bot** を選ぶと、使っていない Bot を一覧と Active now の帯から外せます。隠すのは見た目だけの話です。@ で呼べば届きますし、グループチャットの参加状況もそのままで、定期の仕事も動き続けます。1 つでも隠すとペインのヘッダーに **目のアイコン** が出ます。押すと隠れている Bot が薄く表示されるので、右クリックして **Unhide Bot** で戻せます。隠した Bot は通知を出しませんが、未読の動きは静かに溜まっていき、何かあったことが分かるように目のアイコンに点が付きます。隠したかどうかは Bot のプロファイルの情報に保存されるので、そのバックエンドにつながっているどのデスクトップでも同じ状態になります。

:::note 唯一の Bot Chat は、ずっと続く会話です
Bot の唯一のチャットの中で `/new`（や `/reset`）と打つと、それまでの関係が使い捨てのセッションに分岐してしまいます。Bot Mode が約束しているのは、まさにそれが起きないことです。そこで入力欄はこれを `/compact` に振り替えます。作業の文脈は新しくなり、会話は同じままです。同じプロファイルの普通のセッションでは、`/new` はこれまでどおり自由に使えます。
:::

## Bot を作る {#creating-a-bot}

一覧で **New Agent** を押します。手早い道は 3 つの入力欄 — **Name**、**Title**、**Description** — だけで、Bot は数秒で生まれ、新しい Bot Chat の最初のメッセージとして自己紹介をします。

**Advanced** を開くと、できることがひととおり出てきます。

- **既存のプロファイルから複製する** — 別の Bot の設定、スキル、SOUL、記憶から始めます。まっさらから始めたいときは **Fresh profile** を選びます。
- **空で作る** — 同梱のスキルをすべて飛ばして、最小限のプロファイルにします。
- **モデルとプロバイダの固定** — その Bot だけのモデルを決めます。Hermes が知っているプロバイダとモデルの組み合わせならどれでも使えますし、Bot ごとに違うモデルを並べて動かせます。設定しなければ、起動時のプロファイルから引き継ぎます。
- **独自の SOUL.md** — その Bot の人格と、常に守ってほしい指示です。
- **スキルごと、ツールセットごと、MCP サーバーごとの有効化** — この専門家に必要なものだけに印を付けます。
- **キーの共有** — 既定では、新しい Bot はメインのプロファイルと OAuth・トークンの入れ物を 1 つ共有します。こうしておけば、認証情報を更新したときに互いを無効にしてしまうことがありません。（古いゲートウェイでは代わりに認証情報を複製します。動きはしますが、別々になります。）

### どの端末に置くかを選ぶ（"Create on"） {#choosing-which-machine-it-lives-on-create-on}

[Settings → Connections](/hermes/docs/user-guide/multi-connection-desktop/) に接続を 2 つ以上登録していると、New Agent のダイアログに **Create on** の選択欄が増えます。端末を選ぶと、プロファイルは **その** 端末のバックエンドに作られます。今開いているウィンドウのゲートウェイが切り替わることはありません。新しい Bot は接続先の Bot として一覧に現れ（同じ名前が複数の端末にある場合は `@name-device` という呼び名が付きます）、そこでチャットすると、その端末に処理が回ります。

接続が 1 つだけ（多くの場合はこちら）なら選択欄は出ず、Bot は今つながっている端末に作られます。以前とまったく同じ動きです。

離れた端末に作るときの注意点です。

- **複製元** は *作成先* の端末のプロファイル（その `default`）です。離れた端末には、こちらのローカルのプロファイルはありません。
- Capabilities タブは作成先の端末のバックエンドにつながるので、作成中に設定したスキル、ツール、MCP サーバーは、その Bot が住むことになる端末に置かれます。（古いデスクトップのビルドでは、離れた端末が相手のときは Skills / Tools / MCP のチェックリストを控えておく方式に切り替わります。どちらも作成先の端末のカタログを読みます。）
- ダイアログを取り消すと、作りかけのプロファイルは、それを作った側の端末で破棄されます。

**Edit Profile**（Bot を右クリック）を使うと、動いているプロファイルに対して同じ画面をいつでも開き直せます。アバター、肩書き、説明、モデルの固定、スキル、ツールセット、MCP サーバー、SOUL.md の全文を編集できます。

**Duplicate**（右クリック）は Bot をまるごと複製します。設定、スキル、SOUL.md、記憶、見た目まで写します。**Delete Profile** はプロファイルを完全に削除します。デスクトップのプロファイルのメニューと同じ、取り返しのつかない操作の確認を挟みます。既定のプロファイルは削除できません。

## アバター {#avatars}

どの Bot にも顔があります。

- **ブロブの顔**（既定） — Bot の名前から決まる、やわらかい体の顔です。名前が同じなら、顔もずっと同じです。New Agent で名前を打っている間、顔はそれに合わせて変わっていきます。**Randomize** で引き直し、**Lock face** で気に入った顔を名前が変わっても固定し、6 つの輪郭（丸、有機的、四角、こぶ、雲、太陽）のどれかを指定しつつ、それ以外は名前から決めることもできます。
- **幾何学の顔** — おなじみの 7 つの形 × 10 色で、Bot が働いている間はまばたきする目が動きます。
- **アップロードした画像** — 好きな絵を使えます。
- **AI が描いた似顔絵** — 画像のバックエンドを設定していれば、その場で生成できます（標準の `image.generate` の RPC を使うので、ローカルのゲートウェイでも離れたゲートウェイでも動きます）。
- **ドット絵のペット** — [petdex のギャラリー](/hermes/docs/user-guide/features/pets/) の相棒が、Bot が働いている間アバターの横で跳ねます。ギャラリーはターミナルで `hermes pets` を実行すると見られます。

Bot の見た目、肩書き、説明はバックエンド側のプロファイルの情報として保存されるので、そのバックエンドにつながっているどのデスクトップでも同じ Bot が同じように見えます。

## Routines {#routines}

**Routines** のペインは、繰り返しの仕事を、それをやる Bot に紐づけます。「毎朝メールの受信箱をまとめて」は、その担当の Bot の隣に置かれます。このペインは Bots タブを開いている間だけチャットの横に並び、Sessions に戻ると引っ込みます（古いデスクトップのビルドでは常に出たままです）。予定は形の決まった選択画面で組み立てます（まず頻度を選び、そのあと必要な項目だけを入力します）。Advanced の欄では Hermes の予定の文字列をそのまま書けます。

Routines は、`[bot:<name>] <routine>` という名前空間を持つただの [Hermes の cron のジョブ](/hermes/docs/user-guide/features/cron/) です。`hermes cron list` にも、本体の Cron のページにも出てきます。実行結果はその Bot のチャットの履歴に届くので、その Bot と話すときと同じ場所に結果があります。

## グループとグループチャット {#groups-and-group-chats}

ローカルの Bot を右クリックして **Manage groups** を選ぶと、いくつでもグループチャットに入れたり外したりできます。既存のグループを個別に選ぶことも、その場で新しく作ることもできます。ローカルの参加状況は、バックエンドと同期されるプロファイルの情報に保存されるので、デスクトップをまたいでもそのプロファイルに付いてきます。以前の形式のグループを 1 つ持っている古いプロファイルもそのまま動きます。接続先の Bot は New Group Chat の選択画面から参加し、部屋の共有された状態の中でも、どの端末のものかが分かる形で保持されます。

**部屋はデスクトップ 1 つではなく、ゲートウェイに付いてきます。** 各部屋の直近の記録、参加者、画像、名前は、デスクトップがつながっている **すべての** ゲートウェイの共有プロファイル情報に写されます。ゲートウェイごとに版が管理されるので、2 つのデスクトップが同時に書いても、上書きではなく統合されます。同じゲートウェイに対して別の端末で Hermes Desktop を開けば（ローカルのネットワークでも、Tailscale 越しでも、どこからでも）、部屋は履歴ごと現れます。ゲートウェイだけを使うクライアントからも見えます。部屋には消えない内部の識別子があるので、名前を変えても変わるのはどこでも表示名だけですし、解散すればどのクライアントからも完全に消えます。そのとき接続していなかったクライアントからも消えます。同じ名前でグループを作り直すと、本当にまっさらな部屋になります。ゲートウェイが落ちたり外されたりしても、何も失われません。つながっているデスクトップはどれも部屋の全体をローカルに保っていて、つなぎ直したゲートウェイに改めて流し込みます。（進行の記録の全文は各デスクトップのローカルの保存領域に残ります。共有される写しは、直近の履歴だけを切り出したものです。）

グループは、Bot との個別チャットと同じ、動きのあった順に並ぶ一覧の中で独立した行になります。Bot は複数のグループに入っていても個別チャットの行は 1 つのままで、グループにはそれぞれ部屋の行があり、参加者の数、最新のメッセージの抜粋、時刻、こちらの判断待ちかどうかが出ます。

グループの行（Bot が 2〜6 体）で **Open chat** を押すと、全員で足並みをそろえる共有の部屋が開きます。

- こちらのメッセージをきっかけに、参加者のターンが最大 **3 巡** 順番に回ります。@ で呼ばれた Bot が答えます（誰も呼ばれていなければ全員が答えます）。それぞれの Bot は短く答えるか、見送ります。1 巡まるごと誰も話さなければ、その場は落ち着きます。
- Bot は `@name` で互いを引き込み、本当に判断が要ることは `@user` でこちらに投げます。そのとき、グループの行に **needs you** のバッジが出ます。
- 送信 1 回につき 10 メッセージ、3 巡という固い上限があるので、部屋が延々と回り続けることはありません。
- 参加者はそれぞれ `Group: <name>` という自分のセッションを持ち続けるので、部屋の文脈は他の会話と同じように残ります。
- **すべての Bot がすべてのメッセージに答えるわけではありません。** 話すかどうかは参加者それぞれの判断です。Bot は新しく足せることがあるときだけ答え、なければ見送ります。特定の参加者を @ で呼べば、その巡はその相手に絞られます。呼びかけた相手（あるいは言いたいことがある相手）が話し、残りは黙っていると考えてください。
- **部屋は端末をまたげます。** New Group Chat の選択画面では、登録済みのどの接続からでも Bot を席に着かせられます。参加者のターンはそれぞれ自分の端末で、そこにある `Group: <name>` のセッションの中で走ります。端末をまたぐ参加者には、部屋の中でも他の参加者の記録の中でも端末のバッジ（`dixie · Mac Mini`）が付き、区別のための `@name-device` という呼び名が部屋での呼びかけにも使えます。2 つの端末に同じ名前のエージェントがいても混ざりません。

## Bot どうしのメッセージ {#bot-to-bot-messaging}

Bot は差出人が分かる形で互いにメッセージを送れますし、どのチャットからでも仕事を渡せます。

- **@ で呼ぶ** — どのチャットでも `@researcher have a look at this` のように打つと、入力欄の `@` の補完が相手の Bot を選ぶ手助けをします。送信すると、その呼びかけは今の一覧に照らして解決され、いま話している Bot に誰のことかが正確に伝わります（プロファイル、分かりやすい名前、接続をまたぐ Bot なら端末まで）。そのあと Bot は自分でメッセージを書き、`message_agent` で送ります。こちらの文章がそのまま転送されることはなく、返事はそのエージェントからのものとして戻ってきます。メールアドレスや、知らない `@` はそのまま素通りします。つながっている別の端末の Bot にも同じように届きます。デスクトップがその接続のソケット越しにメッセージを中継します（後述の *端末をまたぐ Bot* を見てください）。
- **名前を変えた Bot も呼び名が付いてきます** — Bot に分かりやすい名前を付けると（チャットのヘッダーの鉛筆のアイコン、または `hermes profile rename`）、その名前で呼べるようになります。*Research Buddy* という肩書きの Bot は、普通のチャットでもグループの部屋でも `@research-buddy`（および `@researchbuddy`）で反応します。入力欄の `@` の補完は新しい呼び名を出しますが、以前のプロファイル名を打っても一致しますし、そちらも引き続き解決されます。
- **個別のメッセージ** — どの Bot Chat にも `message_agent` のツールがあります。Bot は `message_agent(target="researcher", message="…")` を呼んで仲間にメッセージを送ります。ツールは相手を今の一覧と突き合わせて確認し、送り主の `Message from 🤖 <sender> (@<sender>):` という差出人の表示を自動で付け、相手の唯一の Bot Chat に届けます。配送は **送りっぱなし** です。送り主は受け取った旨の返事をもらってターンを終え、返信はあとからバックグラウンドの完了通知として届きます。メッセージは本物の引数として運ばれるので（シェルの解釈は一切入らず、引用符、`$(...)`、バッククォートはそのまま届きます）、Bot はこちらの言葉を転送するのではなく、自分でメッセージを書きます。仲間の一覧は、各プロファイルの肩書きと説明から取った名前 **と役割** を含んだ形で、どの Bot Chat のシステムプロンプトにも入っています。だから Bot は、相手を選ぶ前に誰が何をする役かを知っています。このツールは、Bot Mode が管理しているインストール環境の、唯一の Bot Chat のセッションに **だけ** 存在します。普通のチャット、グループの部屋の参加者のセッション、CLI のセッションからは決して見えません。

バックエンドは、プロンプトを組み立てる時点で、各 Bot の唯一の Bot Chat のセッションにメッセージのやり取りの取り決めを自動で教えます。仲間が CLI から画面なしで開いた場合も同じです。この節が入るのは唯一の Bot Chat だけで、普通のセッションと SOUL.md には手を付けません。これは `config.yaml` の `agent.bot_mode_protocol` で制御します（既定は有効）。

```yaml
agent:
  bot_mode_protocol: true   # inject the bot-to-bot messaging protocol into canonical Bot Chats
```

:::note
Bot どうしの配送は、呼び出しの単位で行われます。受け取る側の Bot は、次に動いたときにメッセージを拾います。会話の途中で Bot に割り込む機能は今後の課題です。
:::

### 失敗したターンは安全にやり直します {#failed-turns-retry-safely}

配送のターンが失敗したとき、やり直すのは多くても 1 回で、しかもやり直して意味がある場合だけです。一時的な失敗（相手が動いていない、配送のタイムアウト、プロバイダのレート制限やサーバーのエラー）なら、同じ Bot Chat のセッションをそのまま走らせ直します。コンテキストが溢れて失敗した場合も同じセッションを走らせ直しますが、やり直しのターンでは、モデルを呼ぶ前に標準のコンテキスト圧縮でしきい値を超えた記録を縮めるので、元の試みでは入らなかったものが収まります。認証、利用枠、設定の失敗は自動でやり直しません。2 回目を試しても直らず、利用枠を減らすだけなので、失敗はすぐに表に出します。やり直しのターンが新しいセッションを始めることはありません。Bot Chat の履歴と文脈はそのまま残ります。

### 配送が失敗したとき: 種類の分かる理由 {#when-a-delivery-fails-typed-reasons}

Bot のターンや中継の配送が失敗すると、人が読むエラーの文章に加えて、機械が読める `reason` のコードが端から端まで運ばれます。相手側のゲートウェイが失敗を分類し（`provider_auth_or_access`、`provider_quota_limit`、`provider_rate_limit`、`provider_server_error`、`context_overflow`、`missing_config`、`model_unavailable`、`runtime_offline`、`queued_expired`、`delivery_timeout`、`target_busy`、`unknown`）、デスクトップがそれを渡し、送った側のエージェントの完了通知には、エラーの文章の前に `[reason: <code>]` が付きます。呼び出す側のエージェントは、プロバイダの文章を読み解く代わりにコードで分岐できます（「もう一度サインインして」なのか「あとで試して」なのか）。デスクトップの要対応のバッジも同じコードを使います。

### つながっている端末をまたいだメッセージ（デスクトップによる中継） {#messaging-across-connected-machines-the-desktop-relay}

**Settings → Connections** に登録したゲートウェイはすべて — ローカル、離れた URL、SSH、Hermes Cloud、docker — デスクトップが開いたまま保っている回線であり、Bot Mode はその回線をメッセージのやり取りに自動で使います。追加の設定は要りません。

- **一覧は勝手に行き渡ります。** デスクトップは動いている間、つながっている各ゲートウェイに、*他の* 接続にはどのエージェントがいるかを定期的に伝えます。すると、どの Bot Chat の仲間の一覧にもそれが載り（"Teammates on OTHER connected machines"）、名前、役割、どの端末にいるかが分かります。エージェントが増えたり、消えたり、名前が変わったりすると一覧も更新されます（capability epoch）。
- **`message_agent` で直接届きます。** 手元のノート PC の Bot は、ローカルの仲間とまったく同じように `message_agent(target="moxie", …)` でクラウドのエージェントにメッセージを送れます。同じ呼び名が複数の端末にある場合は `target="moxie@<connection>"` で区別します（ツールのエラーが、正確な書き方を Bot に教えてくれます）。配送はデスクトップに乗ります。送り側のゲートウェイがメッセージを積み、デスクトップが相手の接続のゲートウェイへ中継し、相手の Bot が自分の唯一の Bot Chat でターンを走らせ、返信はローカルの個別メッセージと同じバックグラウンドの完了通知として送り主に戻ります。
- **デスクトップが運び役です。** 接続をまたぐ配送は、両方の接続を知っているデスクトップが動いている間だけ働きます（ソケットと認証情報を持っているのはデスクトップです。ゲートウェイどうしが互いの認証を見ることはありません）。配送の途中でデスクトップを閉じた場合、送り側の Bot は宙ぶらりんにされるのではなく、返信が届かなかったと知らされます。デスクトップを挟まず、端末どうしで常時メッセージをやり取りしたい場合は、後述の相手先を登録してください（`hermes peer`）。2 つの経路は共存できます。

### 端末をまたいで Bot から個別メッセージを送る（`hermes peer`） {#bot-initiated-dms-across-machines-hermes-peer}

ある端末の Bot は、デスクトップを一切挟まずに **別の端末のゲートウェイ** にいる Bot へメッセージを送れます。相手のゲートウェイを *peer* として登録します（API サーバーの URL と `API_SERVER_KEY`）。

```bash
hermes peer add spark --url http://spark.lan:8377 --key <API_SERVER_KEY>
hermes peer list
hermes peer dm spark < /tmp/dm.txt        # message body from a file (nothing shell-interpreted)
hermes peer dm spark/researcher < /tmp/dm.txt   # named profile on a multiplexed peer
hermes peer run spark --idempotency-key ticket-123 < /tmp/long-task.txt
hermes peer status spark run_abc123
hermes peer stop spark run_abc123
```

`hermes peer dm` は、相手側の既存の API サーバー越しに、離れたエージェントの唯一の Bot Chat へ届け、そこでエージェントのターンを 1 回走らせ、返事を標準出力に出します。ローカルの `hermes -p <bot> chat` の、端末をまたぐ版そのものです。

`peer dm` は短い問い合わせと受け取りの確認にだけ使ってください。ターンが終わるまで HTTP の
接続を 1 本つかんだままになるからです。長いターンには `peer run` を使うと
`run_id` がすぐ返るので、`peer status` で様子を見ます。この実行は
唯一の Bot Chat の記録を引き継ぎ、`--idempotency-key` を同じ値で渡すと、やり直しても
二重に仕事を始めるのではなく最初の実行が返ってきます。中断したいときは `peer stop` に
その実行の ID をそのまま渡せば、別のターンを巻き込まずに止められます。

相手先を登録すると、どの Bot Chat にも教えられるメッセージのやり取りの取り決め（`agent.bot_mode_protocol`）に相手先の一覧が自動で含まれ、`message_agent` は相手先を直接受け取れるようになります — `message_agent(target="spark/researcher", …)`、あるいは相手先のメインのエージェントなら `target="spark"` です。つまり **Bot は自分で気づきます**。他の端末に仲間がいることも、その届け方も分かります。相手先を登録したり外したりすると、各 Bot Chat の取り決めは次のメッセージのときに更新されます（capability epoch）。

必要なのは次のとおりです。相手の端末で `api_server` のゲートウェイのプラットフォームが動いていて、強い `API_SERVER_KEY` が設定されていること。そこに届くかどうかはネットワーク側の話です（LAN、Tailscale、VPN）。このキーは認証情報なので、`~/.hermes/.env` に `HERMES_PEER_<NAME>_KEY` として置きます。相手先の名前と URL は `config.yaml` の `bot_peers` の下にあります。

:::note 片方向しか届かない場合（NAT）
ゲートウェイをまたぐ接続は、ゲートウェイどうしの直接の接続です。デスクトップは
見る側であって、中継役ではありません。家庭の NAT の内側にあるゲートウェイは公開された相手へ
外向きに接続できますが（ノート PC → VPS は動きます）、逆向きには入ってくる経路がありません
（VPS → 家庭は失敗します）。ネットワーク側で用意しているなら別です。グループチャットが
NAT の境目をまたぐなら、参加者全員が届くホスト（たいていは公開された VPS）に部屋の
主導権を置くか、Tailscale や VPN でネットワークをつないでください。
:::

## 端末をまたぐ Bot {#bots-across-machines}

**Settings → Connections** に複数のバックエンド — ローカルの実行環境、離れたゲートウェイ、SSH のホスト、Hermes Cloud のインスタンス — を登録すると、一覧には **すべての** 接続先の Bot がずっと表示され続けます。SSH の接続先は、離れた端末で何かを起動することなく内容を調べますし、一時的に届かなくなった端末も、消えるのではなく最後に分かっていた行を保ちます。同じプロファイル名が複数の接続先にある場合、呼び名は `@name-device` の形で区別されます（たとえば `@research-homelab`）。Bot のチャット、セッション、記憶、定期の仕事は、そのプロファイルを持っている端末にあります。

接続先の Bot をクリックしても、ウィンドウがその端末に移ることは **ありません**。今のチャットにいたまま `@mention` で呼ぶか、グループチャットに座らせるか、**Create on** の選択欄でその端末に新しいエージェントを直接作ってください。クラウドとローカルのエージェントは、こうしてひとつの一覧を共有します。Hermes Cloud のインスタンスと手元のデスクトップを（たとえば Tailscale や SSH 越しに）登録すれば、そこの Bot どうしがメッセージをやり取りでき、同じ部屋に同席でき、それぞれの作業はそれぞれの端末で走ります。端末をまたぐ Bot どうしの個別メッセージは、自動でデスクトップの中継を通ります（前述の *つながっている端末をまたいだメッセージ* を見てください）。

複数の接続についてひととおりの説明は、[Desktop を複数の Hermes につなぐ](/hermes/docs/user-guide/multi-connection-desktop/) を見てください。

## 使うのをやめる {#turning-it-off}

Bot Mode は同梱のデスクトップのプラグインです。**Settings → Plugins → Bots** で切ってください。一覧、Routines のペイン、入力欄の処理がその場で外れます。再起動は要りません。どちらにしても、プロファイル、セッション、cron のジョブには手が付きません。Bot Mode がデータを持つことはなく、ただ表示しているだけです。

サイドバーの普通のセッションの一覧から、唯一の Bot Chat を隠す設定もあります。そうすると Bots のペインの中だけに出てくるようになります。（これは本体の隠しセッションのフラグを使っています。古いゲートウェイでは、単に表示されたままになります。）

## CLI での同じこと {#cli-parity}

Bot はプロファイルなので、すべてにターミナルでの同等の操作があります。

| Bot Mode では | シェルからは |
| --- | --- |
| Bot と話す | `hermes -p <bot> chat` |
| Bot のファイル、スキル、記憶 | `~/.hermes/profiles/<bot>/` |
| Routines | `hermes cron list`（`[bot:<name>] …` という名前のジョブ） |
| プロファイルを作る・確かめる | `hermes profile create`、`hermes profile list` |

土台になっている仕組みは [プロファイル](/hermes/docs/user-guide/profiles/) を、CLI のすべてのコマンドは [プロファイルのコマンド](/hermes/docs/reference/profile-commands/) を見てください。
