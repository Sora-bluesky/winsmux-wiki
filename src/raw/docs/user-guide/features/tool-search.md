# ツール検索 {#tool-search}

セッションに多くの MCP サーバーやコア以外のプラグインツールをつないでいると、
その JSON スキーマだけで、毎ターンのコンテキストのかなりの割合を食ってしまいます。
実際に聞かれた内容に関係するのは、そのうち数個だけ、ということが多いのに、です。

**ツール検索**は、この問題に対する Hermes の「段階的に開示する」層で、自分で有効にして使います。
有効になると、MCP とプラグインのツールは、モデルから見えるツール一覧の中で 3 つの橋渡し用ツールに
置き換わり、モデルは個々のツールのスキーマを必要になった時点で読み込みます。

:::info Hermes 内蔵のツールは後回しにされません
Hermes の中核となる機能をなすツール（`terminal`、
`read_file`、`write_file`、`patch`、`search_files`、`todo`、`memory`、
`browser_*`、`web_search`、`web_extract`、`clarify`、`execute_code`、
`delegate_task`、`session_search`、そのほか
`_HERMES_CORE_TOOLS` に含まれるもの）は、*常に*そのまま読み込まれます。後回しの対象になるのは
MCP のツールと、コア以外のプラグインツールだけです。
:::

## しくみ {#how-it-works}

あるターンでツール検索が働くと、モデルには後回しにされたツールの代わりに、次の 3 つの
新しいツールが見えます。

```
tool_search(queries, limit?)   search the deferred-tool catalog (one or more queries)
tool_describe(names)           load the full schemas for one or more tools
tool_call(calls)               invoke deferred tools; `calls` is an array of {name, arguments}
```

`calls` は呼び出し 1 回につき 1 要素です。ローカルのツールを 1 つ呼ぶときも、要素 1 つの配列に
します。まとめて渡せるのは `connectors__` で始まる名前どうしだけで、混在した束や、ローカルを
複数まとめた束は拒否されます。

典型的なやり取りはこうなります。

```
Model: tool_search(["create a github issue", "send a slack message"])
  → { results: [ { query: "create a github issue",
                   matches: ["mcp_github_create_issue", ...] },
                 { query: "send a slack message",
                   matches: ["mcp_slack_post_message", ...] } ],
      tools: { mcp_github_create_issue: { description: "...",
                                          required: ["title"], ... },
               mcp_slack_post_message: { ... } } }
Model: tool_describe(["mcp_github_create_issue", "mcp_slack_post_message"])
  → { tools: { mcp_github_create_issue: { parameters: { ... } },
               mcp_slack_post_message: { parameters: { ... } } } }
Model: tool_call({ calls: [{ name: "mcp_github_create_issue",
                             arguments: { title: "...", body: "..." } }] })
  → { ok: true, issue_number: 42 }
```

`tool_search` の呼び出しに含まれる各クエリは、同じカタログに対してそれぞれ独立に検索されます
（`limit` はクエリごとに効きます）。クエリごとのまとまりにはツール名だけが入り、共有の `tools`
マップの側に、一致した各ツールの説明と必須パラメータ名が 1 回だけ入ります。クエリは語幹に
そろえられるので、「issues」で `create_issue` が見つかります。一致が 0 件だったクエリの
まとまりには、つながっているサーバーをまとめた `available_sources` が添えられます。単に語が
合わなかっただけなのに、その機能が存在しないと誤解されないようにするためです。
`tool_describe` は、要求された名前をすべて 1 回の呼び出しで解決します。知らない名前は
`not_found` に報告され、束の残りが失敗することはありません。

モデルが `tool_call` を呼ぶと、Hermes は**橋渡しの層をほどいて**、モデルが直接呼んだのと
まったく同じように下位のツールを実行します。ツール呼び出し前のフック、ガードレール、承認の
プロンプト、呼び出し後のフックは、すべて `tool_call` ではなく実際のツール名に対して走ります。
CLI やゲートウェイの動作表示も同じようにほどかれるので、橋渡しではなく下位のツールが見えます。

## どんなときに働くのか {#when-does-it-activate}

ツール検索は**段階的な開示**を使います。後回しにできる（MCP やプラグインの）ツールが*ひとつでも*
あれば橋渡しが働きます。カタログの規模に応じて変わるのは、カタログのどこまでを見えたままに
するかであって、スキーマを後回しにするかどうかではありません。

| 段階 | 条件 | モデルから見えるもの |
| --- | --- | --- |
| **0** | MCP やプラグインのツールが無い | すべてのツールがそのまま。橋渡し無し。素通りです。 |
| **1** | 後回しカタログの一覧が予算に収まる | 橋渡し ＋ 後回しにされた全ツールの、スキル形式の目録（名前と短い説明。予算を超えると名前だけに落とします）。落とし方は**サーバー単位**です。巨大なサーバー（Cloudflare）と小さなサーバー（Linear）が同時につながっている場合、小さい側はツールごとの一覧を保ち、巨大な側だけが要約 1 行にたたまれます。 |
| **2** | どのサーバーも名前だけにしてもなお、ツールごとの一覧が予算を超える（例: Cloudflare の平坦な API 面だけで約 3,300 ツール、その名前だけで約 32K トークン） | 橋渡しのみ ＋ サーバーごとに 1 行の要約（サーバー名とツール数）。どの領域に手が届くかはモデルに分かります。個々のツールは `tool_search` からのみ見つけられます。 |

一覧の予算は `min(threshold_pct% of context, listing_max_tokens)` です。
この判定はツール一覧を組み立てるたびにやり直されるので、セッションの途中で MCP サーバーを
足したり外したりすると、次の組み立てで段階が移ります。

## 設定 {#configuration}

```yaml
tools:
  tool_search:
    enabled: auto       # auto (default), on, or off
    threshold_pct: 5    # listing budget as a percentage of context
    search_default_limit: 5
    max_search_limit: 25
    listing: auto       # embed a grouped name+description catalog manifest
    listing_max_tokens: 4000
```

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `enabled` | `auto` | `auto` と `on` は、後回しにできるツールが 1 つでもあれば働きます。`off` は完全に無効化します（すべてそのまま読み込まれます）。`auto` は今のところ `on` の別名です。スキーマがコンテキストに収まるときは埋め込み、収まらないときだけ後回しにする、という将来のモード用に予約されています。アップグレードをまたいで今の挙動を保証したいなら、`on` か `off` を明示してください。 |
| `threshold_pct` | `5` | 使用中のモデルのコンテキスト長に対する、一覧の予算の割合。範囲は 0〜100 です。 |
| `search_default_limit` | `5` | モデルが `limit` を付けずに `tool_search` を呼んだときに返す、クエリごとの件数。 |
| `max_search_limit` | `25` | モデルが `limit` で要求できる上限（クエリごと）。範囲は 1〜50 です。 |
| `listing` | `auto` | 後回しにされた全ツールのスキル形式の目録（名前と説明の 1 文目、60 文字以内、MCP サーバーごとにまとめたもの）を、`tool_search` の橋渡しの説明文へ埋め込みます。`auto` は予算に収まるときに含めます（収まらなければ名前だけ、さらに段階 2 のサーバー要約へ落とします）。`on` と `off` はどちらかに固定します。 |
| `listing_max_tokens` | `4000` | コンテキストの大きさに関係なく、埋め込む一覧にかける絶対的な上限。範囲は 200〜60000 です。大きなカタログは名前だけ、あるいはサーバーごとの要約へ落ちますが、完全なスキーマは検索から取れます。 |

呼び出し 1 回あたりの配列の上限は、設定ではなく内部の安全弁です。上限を超えた呼び出しは
エラーを返すので、モデルはもっと小さい束で試し直せます。

### 一覧がある理由 {#why-the-listing-exists}

これが無いと、後回しにされた機能は*見えなくなります*。実際に測ってみると、モデルは見えている
コアのツールで代用したり（後回しの GitHub ツールを探さずに、ターミナルで `gh` を実行する）、
`tool_search` を呼ばずに「そんな機能は無い」と言い切ったりしました。この一覧は、スキルで使われて
いる型をツールに当てはめたものです。どの機能も常に名前で見つけられる状態を保ちつつ、
パラメータの完全なスキーマは後回しのままにします。一覧に目当てのツール名がそのまま見えていれば、
モデルは `tool_search` を飛ばして `tool_describe` へ直行でき、往復を 1 回節約できます。

旧来の真偽値の書き方に切り替えることもできます。

```yaml
tools:
  tool_search: true   # equivalent to {enabled: auto}
```

## コネクター（リモートのツール） {#connectors-remote-tools}

Nous Portal にサインインしていると、橋渡しはさらに**コネクター**にも手を伸ばします。これは
運用型のツールゲートウェイが提供するリモートのツールです。手元に登録されることはありません。
`tool_search` は各クエリをゲートウェイへ送り、ゲートウェイ側の一致をローカルのカタログへ
文書として加え（`source: "connectors"` の印が付き、`connectors__<connector>__<tool>` という
名前になります）、同じ BM25 の処理と同じ「もっとも珍しい語」の規則で両方を順位付けします。
そのため `limit` はまとまり全体に効き、クエリに答えられるコネクターのツールが、語を 1 つ
共有しているだけのローカルのツールに押し出されることはありません。ゲートウェイへの呼び出しは
30 秒で打ち切られ、遅かったり応答が無かったりする場合はローカルの結果だけに落ちます。
`tool_describe` はコネクターのスキーマをゲートウェイから取得し、`tool_call` は束の中の
コネクターの要素を、入力順にそれぞれ別のゲートウェイ要求として送ります（慣例的なスラッグでは
ゲートウェイが知らないツール名は、そのままの文字列でもう一度試すので、1 要素で 2 回の要求に
なることがあります）。もしあるコネクターが `GMAIL_X` と、文字どおりの `X` の両方を出していたら、
どちらも `connectors__gmail__X` に組み上がってしまい、実行されるのは `GMAIL_X` です。検索は
その片方を残してもう一方を落とし、警告を記録します。結果は件数を数え直したうえで、束の
元の順序へ差し戻されます。

```yaml
tools:
  connectors:
    enabled: true   # false — never touch connector routes; the bridge
                    # behaves exactly as if the feature didn't exist
```

サインアウトしている場合（またはアカウントに対してゲートウェイがコネクターを提供していない
場合）、ここまでの内容はすべて見えなくなります。ローカルの検索はこのページの他の部分で
説明したとおりに動き、モデルにエラーが見えることもありません。

まだ連携していないアカウントを必要とするコネクターの呼び出しは、接続用のリンクを添えた
`CONNECTION_REQUIRED` エラーを返します。`manage_connections` ツール（コネクターの橋渡しと
同じ条件で使えます）は、コネクターとその接続状態を一覧し、認可を開始し、利用者が終えるのを
待つこともできます。アカウントの接続解除は、利用者自身が Portal で行います。

`tool_call` は束をまとめて受け取ります。`calls` は `{name, arguments}` の要素からなる配列です
（1 件だけの呼び出しも、要素 1 つの配列にします）。束の中のコネクターの要素は、それぞれ別の
ゲートウェイ要求として順番に送られます。ローカルの後回しツールは、`tool_call` 1 回につき
1 要素のままです。承認は実行の前に要素ごとに片付き、要素と要素のあいだで `/stop` が入ると、
まだ始まっていないものは送られません（その枠は `INTERRUPTED` と報告されます）。

## 使わないほうがよいとき {#when-not-to-use-it}

ツール検索は、毎ターン一定のトークン費用（3 つの橋渡しツールのスキーマとカタログの一覧）と、
まだ読み込んでいないツールに対する最低 1 往復（describe → call）を払って、後回しにした
スキーマの分を節約する取引です。段階 1 では一覧がすべての機能を見える状態に保つので、
探すための往復はたいてい消えます。モデルは `tool_describe` へ直行します。実測では、一覧を
有効にしたモードは、すべてをそのまま読み込む場合と同じ課題成功率でありながら、橋渡しだけの
場合より費用が低く済みました。

小さなツール群に対して、以前のようにすべてをそのまま読み込ませたい場合は、
`enabled: off` にしてください。

## 消えないトレードオフ {#trade-offs-that-dont-go-away}

これらはプロンプトキャッシュの整合性という前提から来るもので、この実装に固有の話ではなく、
段階的に開示する設計すべてに付いて回ります。

- **まだ読み込んでいないツールでは往復が 1 回増えます。** モデルが後回しのツールを初めて
  必要とするとき、スキーマを探して読み込むためにモデル呼び出しを 1 〜 2 回余分に使います。
  静的な側でのトークン節約は本物ですが、その一部は実行時に払い戻すことになります。
- **後回しのスキーマにキャッシュの恩恵はありません。** 読み込んだ `tool_describe` の結果は
  会話履歴に入るので、以降のターンではキャッシュされます。ただし、システムプロンプトの
  キャッシュ接頭辞の恩恵を受けることはありません。
- **後回しのスキーマは、プロバイダー側の検証を受けられません。** `tool_describe` はモデルに
  後回しのツールのスキーマを読ませますが、プロバイダーからは汎用の `tool_call.arguments`
  オブジェクトしか見えません。そのため Hermes は、実行の前に下位の引数を手元で型変換し検証
  します。Hermes が安全に検証できないスキーマ（壊れたスキーマや外部参照など）については、
  実際のツールや MCP サーバーの側が責任を持ちます。
- **モデルの性能に左右されます。** ツール検索は、モデルが欲しいツールに対して、それなりの
  検索クエリを書けることを前提にしています。小さいモデルはこれがうまくありません。公表されて
  いる Anthropic の数字（Opus 4 でツール検索の有無により 49% → 74%）は上振れを示すと同時に、
  なお 26 ポイントほどが取り出しの失敗であることも示しています。
- **ツール構成をいじるとキャッシュが無効になります。** セッションの途中でツールを足したり
  外したりすると、橋渡しツールの説明文（後回しにされたツールの数を含みます）とカタログが
  変わるので、プロンプトキャッシュが無効になります。これはツール構成をいじるとき共通の
  トレードオフです。

## 実装の詳細 {#implementation-details}

- **取り出し:** 語に分けたツール名、ソース名（そのツールが属する MCP サーバーやプラグインの
  ツール群。ツール自身の名前にサービス名が入っていなくても、`"linear"` で検索すればその
  サーバーのツールが見つかります）、説明、パラメータ名に対する BM25 です。索引とクエリの
  両方に Snowball の語幹処理（英語）をかけているので、語形の違いが吸収されます（「issues」で
  `create_issue` が見つかります）。あるツールが結果に入るのは、クエリのもっとも珍しい語を
  含むときだけです（もっとも珍しい語とは、含むツール文書が最少の語、つまり意図を名指しする
  語のことです。`send` や `create` ではなく、`gmail`、`github`、`incident` の側です）。
  もっとも珍しい語がどのツールにも出てこないクエリは、ありふれた語を 1 つ共有するだけの
  `limit` 件のツールを返すのではなく、つながっているソースと再試行のヒントを添えた空の
  まとまりを返します。
- **並列実行では橋渡しがほどかれます。** 束の実行計画は、`tool_call` の文字どおりの橋渡しの
  名前ではなく、その*下位の*ツールを見て並列度を決めます。そのため
  `supports_parallel_tool_calls: true` で並列を選んだ MCP サーバーは、橋渡し経由で呼ばれても
  並列度を保ちますし、`tool_search` と `tool_describe` の検索は、他の読み取り専用ツールと
  同じようにまとめて並列に走ります。
- **カタログはターンをまたいで状態を持ちません。** 組み立てのたびに、現在のツール定義の
  一覧から作り直されます。セッションをキーにした `Map` はありません。保存したカタログが
  実際のツール登録とずれていく、という種類のバグを避けるためです。
- **カタログはセッションのツール群の範囲に限られます。** `tool_search`、
  `tool_describe`、`tool_call` が見て呼べるのは、そのセッションに実際に許可されたツールだけ
  です。ツール群の一部だけに制限されたサブエージェント、カンバンのワーカー、ゲートウェイの
  セッションは、その範囲の外にあるツールを橋渡し経由で見つけることも呼ぶこともできません。
  後回しカタログは、そのセッション自身の有効・無効なツール群のうち後回しにできる部分であって、
  プロセス全体の登録簿ではありません。
- **JS のサンドボックスはありません。** Hermes はより素朴な「構造化ツール」方式（search /
  describe / call をただの関数として置く方式）を使います。他の実装が用意している JS
  サンドボックスの「コードモード」は攻撃面が大きいので、こちらは採りません。
