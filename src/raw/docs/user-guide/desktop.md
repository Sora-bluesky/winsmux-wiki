# Hermes Desktop {#hermes-desktop}

Hermes のデスクトップアプリは、CLI やゲートウェイで使うのと**同じ**エージェントを中心に据えたネイティブアプリです。設定も API キーもセッションもスキルも記憶も、すべて共通です。別製品でも軽量な複製でもなく、Hermes Agent のコアと設定をそのまま使い、現代的で丁寧に設計された UI から動かします。端末で `hermes` を使ったことがあるなら、そこで整えたものはすでにここにありますし、ここでの操作もあちらに反映されます。

動作環境は **macOS（Apple Silicon）・Windows・Linux** です。対応状況の全体は [対応プラットフォーム](/hermes/docs/getting-started/platform-support/) を見てください。

:::tip どの画面がどれなのか
Hermes には、同じエージェントにつながる複数の入口があります。

- **デスクトップアプリ**（このページ） — 対話・設定・管理のために作り込んだ UI を持つネイティブアプリです。
- **CLI**（`hermes`）と **[TUI](/hermes/docs/user-guide/tui/)**（`hermes --tui`） — 端末上の画面です。
- **[Web ダッシュボード](/hermes/docs/user-guide/features/web-dashboard/)**（`hermes dashboard`） — ブラウザで開く管理画面です。任意で使える **Chat** タブは、疑似端末を通して TUI を埋め込んでいます。

そのときに合うものを選んでください。状態を共有しているので、片方で始めたセッションをもう片方で再開できます。
:::

## インストール {#install}

アプリは [Hermes Desktop の製品ページ](https://hermes-agent.nousresearch.com/desktop) からダウンロードするか、[Hermes Desktop のインストール手順](/hermes/docs/getting-started/installation/) に従って導入します。

すでに Hermes を入れてあるなら、次を実行するだけです。

```bash
hermes desktop
```

これで、いま使っている設定・キー・セッション・スキルがそのまま使われます。

## アプリの中身 {#whats-in-the-app}

デスクトップアプリは、対話を中心に置いたウィンドウと、左側のナビゲーション用サイドバーで構成されています。複数のエージェントとの会話を同時に扱い、メッセージ連携のプロバイダーを設定し、成果物を作り、プロジェクトのフォルダ構成をたどり、複数のプロジェクトを並行して進められるように作られています。

サイドバーの選択状態は、フォーカスされている対話ペインに追従します。セッションタブを開いたりフォーカスしたりすると、ページ側のハイライトは解除されます。Kanban のように拡張機能が追加したページも同様で、ワークスペースがそのページの経路を保持していても変わりません。

### チャット {#chat}

アプリの中心です。次のことができます。

- **応答のストリーミング** — エージェントが作業する様子を、ツールの実行状況と構造化された呼び出し概要つきで流します。ツールが画像を扱ったとき（たとえばバックエンドのファイルシステム上のファイルに対する `vision_analyze`）は、その実行状況の行を開けば画像が見えますし、押せば原寸で開けます。遠隔の接続では、画像はアプリを動かしている端末ではなくゲートウェイから取ってきます。
- **Markdown の改行**は Markdown の意味づけに従います。行末の半角スペース 2 つで強制改行になり、ふつうの改行はそのままやわらかい改行として扱われます。メディアとプレビューの抽出では、取り除いた添付範囲の外にある文字が保たれます。1 行目のコードのインデントや、閉じていないコードフェンスの空白も残ります。コードの表示とコピーでは、Markdown パーサーが渡した先頭の空行・行末のスペース・末尾の空行がそのまま保たれます。
- **他の画面と同じ会話履歴** — ここで始めたセッションは CLI や TUI で再開できますし、その逆もできます。
- **ファイルのドラッグ＆ドロップ** — 対話エリアのどこにでも落とせば、次のメッセージに添付されます。
- **下書きは裏でも独立して進みます** — 表示していない対話タブの下書きが更新されても、見えている入力欄のカーソル位置や選択範囲は動きません。
- **指示チップの操作** — URL のように操作できる参照にカーソルを合わせると、操作用のボタンが出ます。チップからボタンへ動かす間に少し猶予があるので、消える前に届きます。ボタンの上で動かしている間は出たままで、離れたあとは無関係なカーソルの動きで消えるのが遅れることはありません。操作を押しても下書きの選択範囲は保たれます。
- **右側のプレビュー欄** — Web ページ・ファイル・ツールの出力を横に並べて表示し、対話を続けながら確認できます。
- **状態を持つ枠は Hide と Close を使い分けます** — ブラウザ（または HTML のプレビュー）やターミナルの枠を抱えた区画には、Minimize ではなく **Hide** が出ます。Hide は区画を復元用の帯までたたみますが、枠の中身は載せたままです。表示中のページは保存前の入力・タイマー・スクロール位置・エージェントの `drive_preview` の操作対象を保ち、ターミナルは動いているシェルと履歴を保ち、**Restore** すれば読み込み直さずに同じ中身が出ます。たたまれた中身は反応しません。キーボードショートカットを取ることも、入力欄からフォーカスを奪うこともありません。ページやシェルを実際に手放すのは **Close**（タブの ×）です。
- **アプリ内ブラウザのコメントモード** — プレビューのブラウザバーで **Annotate** を押し、表示中のページの要素をクリック（または範囲をドラッグ）してメモを書きます。保存したコメントは番号つきのピンとしてページに残ります。ピンを保存してもターンは送信されません。書き終えたら **Add N comments** を押すと、ピンごとに切り抜いたスクリーンショットと、各コメントを示す短いプロンプトが入力欄に入ります。送信するかどうかは自分で決められます。要素へのコメントには CSS セレクタ・マークアップ・レイアウトに効く算出スタイルが添えられるので、エージェントは画像から推測せずソースの中の要素を見つけられます。パスワードや hidden フィールドの値、キーやトークンに見える属性は、マークアップがページから出る前に伏せられます。数が多いときは、ページのどの部分にあるコメントかでまとめて届くので、20 件あまりのコメントが 20 個の作業ではなく数個の作業になります。まとまりは別々の DOM の部分木なので、たいていは別のファイルに触れることになり、そのおかげで並行して作業させても安全です。ピンの番号は 1 つ消しても崩れず、対話を切り替えると積み上がったものは消えます。
- **入力履歴と送信待ちの編集** — 空の入力欄で上下の矢印キーを押すと、前のプロンプトを呼び出して再利用できます。送信待ちに積んだメッセージは送られる前に直せます。ターンが積まれている間に Stop（または Esc）を押すと待ち行列が止まり、入力欄の上に展開されます。そこから再開したり、個別に送信・編集・削除したりできます。
- **入力欄の上に出る進行状況** — Tasks の見出しを開くと、各段階を確認できます。長い一覧でも入力欄の上に収まる高さに収められ、展開した一覧の中をスクロールすれば、会話を動かさずに最後の項目まで届きます。
- **会話のタイムライン** — 長い対話には、記録の端に細い目盛りが並びます。プロンプト 1 つにつき 1 つです。カーソルを合わせるとプロンプトの一覧が開き、選べばその地点に飛べます。飛んだあとは、記録の先頭にある **Show earlier** で、そのプロンプトからさらに前へ、セッションの最初まで遡って読み込めます。（対話がある程度の長さになると現れます。）
- **読んでいた位置の記憶** — セッションに戻ったとき、いつも最新まで飛ぶのではなく、記録しておいた末尾からの距離が復元されます。末尾にいたセッションはそのまま新しい出力を追い続けます。**Scroll to bottom** を押せば最新の位置に戻れます。位置はこの Desktop のローカル保存領域に置かれ、バックエンド越しに同期はされません。
- **ページ内検索** — **Cmd/Ctrl+F** で検索バーが開き、表示中の対話記録を探せます。Enter / Shift+Enter（バーが開いている間は Cmd/Ctrl+G / Cmd/Ctrl+Shift+G でも）で一致箇所を順に移動し、Esc で閉じます。

非同期の cron や委任の完了は、たたまれた形でタイムラインに出ます。完了のラベルを開くと、ジョブの出力を含む本文を Markdown として読めます。長い報告はその中でスクロールします。タスクの指示文や配送用の情報は、報告の中身としては表示されません。

#### ステータスバー {#status-bar}

対話の下端に沿ったバーには、いまのセッションの状態が表示され、設定を開かなくても主な操作ができます。

- **セッションごとの YOLO 切り替え** — このセッションだけ YOLO を入切します（TUI と同じ挙動です）。YOLO は危険なコマンドの承認確認を飛ばすので、何を外すのかを分かったうえで使ってください。[セキュリティ → YOLO モード](/hermes/docs/user-guide/security/#yolo-mode) を参照してください。
- **コンテキスト使用量のメーター** — セッションのコンテキストウィンドウが何 % 埋まっているかを表示します。クリックすると **Context Usage** のポップオーバーが開き、種別ごと（システムプロンプト、ツール定義、スキル、記憶、ルール、MCP、サブエージェントの定義、そして会話そのもの）の使用量が分かります。圧縮が走る前に、何がウィンドウを食っているのかを正確につかめます。
- **キャッシュのヒット率と 1 秒あたりのトークン数** — 既定では出ません。右クリックのメニューから表示できます。キャッシュのヒット率は、このセッションのプロンプトのうちプロバイダーのプロンプトキャッシュから返った割合です（キャッシュされたトークンは安いので、高いほど安上がりです。セッションが温まるにつれて安くなっていく様子を眺められます）。1 秒あたりのトークン数は、直近 10 回のモデル呼び出しを平均した出力の速さです。どちらもターンの最中に更新され続けます。
- **表示する項目の選択** — ステータスバーを右クリックして（**Show in status bar**）、何を出すかを選べます。コンテキストのメーター、キャッシュのヒット率、1 秒あたりのトークン数、ワークスペース、モデル、承認、ターンとセッションの経過時間、ターミナル、Command Center、バックエンドの版などです。バーごと隠すこともできます（**Cmd/Ctrl+Shift+S** で切り替わります）。ワークスペースの項目のメニューに **Open containing folder** が出るのは、選んでいるセッションがこの端末で動いているときだけです。リモートのゲートウェイで動いているセッションはフォルダが向こうの端末にあるので、代わりに **Reveal in filetree** を使ってください。OS のファイルマネージャーがパスを見つけられないときは、何も起きないのではなく、その旨を知らせます。

同梱のローカルなバックエンドではなく、別の端末で動いている Hermes とやり取りしたいときは、後述の [リモートのバックエンドにつなぐ](#connecting-to-a-remote-backend) を見てください。リモートで動かすダッシュボードとの接続（認証の入口、`/api/ws` の対話用ソケット、WebSocket の切断コードの切り分け）の全体像は、[Web ダッシュボード → Hermes Desktop をリモートのバックエンドにつなぐ](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend) にあります。

#### フォント {#fonts}

**Settings → Appearance** には独立した 2 つのフォント設定があり、どちらもプロファイルごとに `config.yaml` に保存されます。

- **Chat Font**（`desktop.font_family`） — 対話と、アプリの UI 全体に効きます。OpenDyslexic や Atkinson Hyperlegible のような読みやすさ重視の書体は、システムに入れてあればすぐ使えます。選んだ書体の後ろにはテーマ側の書体が控えているので、足りない字形もきちんと出ます。空欄にするとテーマの書体になります。
- **Terminal Font**（`terminal.font_family`） — 埋め込みのターミナルペインに効きます。ここでは Nerd Fonts がシェルのアイコンを表示します。空欄にすると同梱の JetBrains Mono になります。

#### リポジトリの検出 {#repository-discovery}

Hermes Desktop は、ホームディレクトリを一定の深さまで走査して、サイドバーの Projects に出すローカルの Git リポジトリを見つけます。この動きは **Settings → Workspace** で、または `config.yaml` で、プロファイルごとに変えられます。

```yaml
desktop:
  repo_scan_enabled: true
  repo_scan_roots: []
  repo_scan_exclude_paths: []
```

- `repo_scan_enabled: false` にすると、ファイルシステムの走査を完全に止めます。そのプロファイルのディスク検出キャッシュの行は消えますが、明示的に登録したプロジェクトと、意図して始めた Hermes セッションから推定されたリポジトリはそのまま使えます。
- `repo_scan_roots` にフォルダの一覧を書くと、走査の範囲をそこに絞れます。空の一覧なら、既定のホームディレクトリ走査のままです。
- `repo_scan_exclude_paths` には、配下ごと飛ばしたいフォルダを書きます。

これらの値を変えると、そのプロファイルのディスク検出キャッシュだけが無効になり、設定に沿った再取得が始まります。**Hide from sidebar** は、これとは別の項目ごとの整理操作です。

**Group by → Projects** にすると、プロジェクトの行ごとに直近 3 件のセッションが並びます。それより多いプロジェクトの末尾には **Show all N sessions** の行が出て、その場で残りが開きます。サイドバーのメニューにある **Show all sessions** を切り替えれば、すべてのプロジェクトで一度に上限が外れます。

#### モデルを選ぶ {#choosing-a-model}

モデルの選択は **入力欄** の、マイクのすぐ左にあります。クリックすればモデルを切り替えられ、行にカーソルを合わせるとその選択肢（思考、effort、fast）が出ます。その隣の **reasoning のピル** には、いま使っているモデルの effort（`Med`、`High` など）が出ていて、押すと同じ選択肢が直接開きます。モデルの行を探さずに effort を変えられます。カタログ上 reasoning を制御できないモデルでは、このピルは出ません。Hermes の内部での段階を経路の側が抑えるとき（`ultra` は、その経路でいちばん強い水準、たとえば `max` として送られます）、ピルには両端が出て（`Ultra→Max`）、その吹き出しには CLI と同じ言い回しの `Ultra (sends Max on this route)` が書かれます。見えている水準が、実際に送られる水準だと分かるようにするためです。切り替えにリスクがあるとゲートウェイが判断したとき（大きなキャッシュを抱えている、費用の高いモデル、データが学習に使われる区分など）は、まずダイアログで確認します。**Switch anyway** で適用し、**Keep current model**（または Esc）ならそのままです。

**マイク** は音声入力です。カーソルを合わせると、ほかの音声関連の切り替えが上に広がります。**Read replies aloud** と、ウェイクワードの耳のマークです。オンになっている切り替えは塗りつぶされた円で示されます。音声での会話をまるごと始めるのは、右側の主ボタンのままです。HUD や幅の狭いタイルでは、同じ操作がマイクの後ろの 1 つのメニューにまとまります。音声入力が音声認識のプロバイダーと直接やり取りするとき（クライアントから直につなぐ音声）、その要求はゲートウェイ自身の文字起こしと同じ `stt.openai.timeout` の持ち時間（既定は 60 秒）に従います。応答の遅い接続先では、マイクが文字起こし中のまま固まらずに「Transcription timed out」で失敗します。

- **入力欄の選択は UI の一時的な状態で、既定には触れません。** この選択は端末ごとにローカルに覚えられ、新しい対話や再起動をまたいで**引き継がれます**。既定に戻ることはありません。一度選んでおけば、次の `Cmd/Ctrl+N` はそのモデルで開きます。対話が進んでいる状態でモデルを切り替えると、変更は**その対話**だけに効きます。いずれの場合も、選択はセッションの作成・切り替えについてまわるだけで、プロファイルの既定には**決して**書き込まれません。例外が 1 つあります。`model.default` も `model.provider` もまだ設定されていない新しいプロファイルでは、最初の選択が保存されます。再起動したときに、たまたま環境変数に残っていた API キーへ落ちてしまわないよう、実体のある既定を持たせるためです。保存の挙動は `/model` と同じ規則（`model.persist_switch_by_default`）に従います。既定を意図して変えるときは **Settings → Model** を使ってください。（[プロファイル](#sessions--profiles) を切り替えると、そのプロファイル自身の既定に戻ります。）
- **既定は Settings → Model で決めます。** この「メイン」のモデルが、**プロファイルごとの全体の既定**です。新しい対話・cron・サブエージェント・補助的な処理はここから始まりますし、これを書き込む場所もここだけです。[プロファイル](#sessions--profiles) はそれぞれ自分の既定を持ちます。
- **モデルごとの effort と fast の記憶。** デスクトップアプリでは、モデルごとに reasoning の effort と fast モードの選択が覚えられ、そのモデルを選ぶたびにセッションへ適用されます。これはデスクトップ側の便宜であって、cron やサブエージェントには影響しません。
- **対話の途中で切り替えるとプロンプトキャッシュが切れます。** 対話の最中にモデルを変えると、次のメッセージで会話全体が入力の正規料金で読み直されます（プロバイダーのプロンプトキャッシュはモデルごとだからです）。たまになら問題ありませんが、長い対話では、行き来するより新しいモデルで対話を始め直したほうが安く済むことが多いです。

### ファイルブラウザ {#file-browser}

アプリから離れずに作業ディレクトリをたどり、中身を確認できます。エージェントがファイルを読み、書き、直していく様子を追うのに便利です。最初に開くプロジェクトのディレクトリは `hermes desktop --cwd <path>`（または環境変数 `HERMES_DESKTOP_CWD`）で指定します。

### 成果物 {#artifacts}

入力欄の上に出るプレビューのリンクは、そのセッションからの提案であって、作業が終わったかどうかのチェックリストではありません。1 つ閉じると、画面を移動したり読み込み直したりしても、過去のツールの実行履歴からまた出てくることはありません。ツールが新しく成功すれば、同じファイルをもう一度勧めることはあります。読むだけのファイル確認や、失敗した書き込みでは提案は作られません。同じ名前のファイルは、見分けがつくだけのディレクトリの情報を添えて表示します。提案を閉じても、そのファイルや対話の記録が消えるわけではありません。`/goal` を変えても、その対話の成果物が消えることはありません。

リモートのゲートウェイにつないでいるとき、ファイルの成果物を開くと、そのゲートウェイ経由でダウンロードされます。使われるのは、その成果物を生んだプロファイルとセッションです。相対パスはセッションに保存された作業ディレクトリを起点に解決され、ホームからの相対パスはゲートウェイ側のホームを指します。Desktop を動かしている端末のホームではありません。Windows 形式の相対パスもスラッシュ区切りのパスと同じように認識され、file URI はドライブやネットワーク共有の情報を保ったままゲートウェイに渡されます。セッションや作業ディレクトリが見つからないときは、別のローカルファイルを選ぶのではなくエラーになります。

**Artifacts** のビューは、セッションが生み出したもの（**画像・ファイル・リンク**）を 1 つのギャラリーに集め、検索したり眺めたりできるようにします。サイドバー、コマンドパレット（**Artifacts — Browse generated outputs**）、あるいは自分で割り当てた `nav.artifacts` のショートカットから開けます。最近のセッションの出力は自動で取り込まれ、どのセッションが生んだかが成果物ごとに分かり、その対話に戻れます。画像とファイルはプレビューで開き、ダウンロード・ブラウザで開く・コピーの操作ができます。

### ウィンドウ・タブ・ペイン {#windows-tabs-panes}

このアプリは、いくつものことを同時に進められるように作られています。

- **タブ** — **Cmd/Ctrl+T** で新しいセッションのタブが開きます。**Ctrl+Tab** / **Ctrl+Shift+Tab** でセッションを順に切り替え、**Ctrl+1…9** で並び順から最近のセッションへ飛べます。**Cmd/Ctrl+W** でフォーカス中のタブを閉じ、**Cmd/Ctrl+Shift+T** で最後に閉じたものを開き直します。
- **複数のウィンドウ** — **Cmd/Ctrl+Shift+N** で新しいウィンドウが開きます。どのセッションも、右クリックメニュー（**New window**）やコマンドパレットから切り出せます。切り出したウィンドウは、全体のサイドバーなしでその対話だけを表示します。長く走らせるセッションを別のモニターに置いておくのに便利です。エージェントの出力は、そのセッションを表示しているすべてのウィンドウに流れます。
- **ペイン** — **Cmd/Ctrl+B** で左のサイドバー、**Cmd/Ctrl+J** で右のサイドバーを出し入れし、**Cmd/Ctrl+\\** でサイドバーの左右を入れ替えます。

### ターミナル {#terminal}

右のサイドバーには、ファイルブラウザと並んで本物のターミナルがあります。

- **Ctrl+`** でターミナルが出ます（1 つも無ければ新しく開きます）。**Ctrl+Shift+`** でもう 1 つ増やせます。複数のターミナルはタブの列に並び、**Ctrl+Shift+↓/↑** で行き来し、**Ctrl+Shift+W** で今のものを閉じます。
- **隠しても shell は生き続けます。** パネルを閉じたり隠したりしても shell は落ちません。開いてあるターミナルは、明示的に閉じるまで、スクロールバックも実行中のプロセスもそのまま保たれます。
- **Add to chat** — ターミナルの出力を選んで入力欄に送り、次のメッセージの材料にできます。

### 動いているサブエージェント {#live-subagents}

委任した作業者が動いている間は、入力欄の上に **Subagents** の枠が出て、人数・タスク名・経過時間・直近の動きが分かります。表示されるのは最大 3 人までで、見出しを開けば全員の一覧になり、選べば詳細と **Steer** / **Stop** の操作が出ます。枠はそれぞれの対話に属し、分割したペインでも同じです。Steer は、指示が次の区切りに向けて積まれたことを示すだけで、子のエージェントがすでに読んだという意味ではありません。[サブエージェントを見守る](/hermes/docs/user-guide/features/delegation/#monitoring-running-subagents-agents) も参照してください。

### Git のレビューと worktree {#git-review-worktrees}

Git リポジトリの中で動いているセッションには、バージョン管理の画面が組み込まれています。

- **レビューのペイン** — **Cmd/Ctrl+G** で作業ツリーのレビューペインを開け閉めします。ブランチと ahead/behind の状態、変更されたファイル（一覧表示かツリー表示）、そして **Uncommitted**・**Branch**・**Last turn**（直前のターンでエージェントが変えた分だけ）に絞った差分が見られます。ファイルをステージ／解除し、変更を戻し、コミットメッセージを書き（**Generate commit message** でも生成できます）、**Commit** または **Commit & Push** を押します。GitHub CLI（`gh`）を使う **Create PR** もありますし、**Ask Hermes to open PR** でまるごとエージェントに任せることもできます。ブランチの作成と切り替えもここからできます。
- **worktree** — **Cmd/Ctrl+Shift+B**（またはサイドバーのプロジェクトで **New worktree**）を押すと、新しいブランチの Git worktree が作られます。手元のチェックアウトに触れずに、エージェントがリポジトリの並行したコピーで作業できます。worktree はプロジェクトの下に自分の列として並び、消すときは worktree のディレクトリごと削除する（ブランチは残ります）か、列を隠してディスク上には残すかを選べます。コミットしていない変更があるときは強制的に消す選択肢も出ます。

### 記憶のグラフ {#memory-graph}

**Memory Graph**（コマンドパレット → *Memory Graph*、またはステータスバーの項目）は、Hermes があなたのために覚えたことを地図にしたものです。スキルと記憶が、拡大縮小できるノードのグラフと時系列として並び、**All / Used / Learned** で絞り込めます。共有の操作を使うと、地図の配置を短いコードとして書き出して誰かに渡せますし（配置だけで、記憶やスキルの文章は含まれません）、同じ形のコードを読み込むこともできます。

### Quick Entry {#quick-entry}

Quick Entry は、**システムのどこからでも全体のホットキーで呼び出せる**小さな入力欄です。メインのウィンドウに切り替えなくても（開いてすらいなくても）プロンプトを投げられます。**Settings → Advanced → Quick Entry** で有効にします。既定のショートカットは **Ctrl/Cmd+Shift+Space** で、自分の好きなものに変えられます（修飾キーを 1 つ以上含める必要があります）。その組み合わせを別のアプリが先に握っているときは、設定の行がそれを教えてくれるので、別のものを選べます。

### 音声 {#voice}

Hermes に話しかけ、返事を聞けます。ほかの画面でも使える [音声モード](/hermes/docs/user-guide/features/voice-mode/) と同じものです。macOS では、マイクの利用許可を OS が一度だけ尋ねてきます。

### HUD モード {#hud-mode}

**⌘/Ctrl+Shift+H**（またはタイトルバーのボタン）を押すと、対話が切り離され、装飾のない常に手前のバーとして、作業中の画面の上に浮かびます。アプリのウィンドウは脇にどき、HUD が進行中の会話と入力欄を引き継ぎます。バーをどこに置くかは文脈そのものです。バーの位置が、どのアプリとどの画面について尋ねているのかを Hermes に伝えるので、「これ」「ここ」「このページ」がバーの下にあるものとして解釈されます。

- **バーを動かす** — macOS と Windows では、入力欄のどこかを**少し長めに押してから**ドラッグします。Linux/X11 では、**Ctrl** を押しながら主ボタンでドラッグすればすぐつかめます（選択中の文字の上でも同じです）。長押しからのドラッグも使えます。つかんだまま仮想デスクトップ切り替えのショートカットを押せば、HUD を別のデスクトップへ連れていけます。ネイティブな Wayland では、入力欄のバーがコンポジタ側のドラッグハンドルになります（アプリは自分のウィンドウ位置を決められないので、動かす手段はこれだけです）。
- **大きさを変える** — バーの辺か角をドラッグします。反対側の辺は固定されたままです。ネイティブな Wayland で使えるのは右辺と下辺です。コンポジタが、アプリ自身にトップレベルのウィンドウ位置を決めさせないためです。
- **配置を戻す** — バーの破棄の操作で、既定の大きさと（X11 / macOS / Windows では）位置に戻ります。保存された大きさのせいで HUD が使いものにならなくなったときに使ってください。
- **カーソルの位置へ呼ぶ** — **⌘/Ctrl+Shift+G**（全体のホットキーで、どのアプリからでも効きます）で、HUD がカーソルのある場所へ飛びます。ネイティブな Wayland では何も起きません。配置はコンポジタが握っているからです。
- **抜ける** — バーの終了ボタンを押すか、**⌘/Ctrl+Shift+H** をもう一度押すか、HUD にフォーカスがある状態で **⌘/Ctrl+W** を押します。アプリのウィンドウがセッションごと手前に戻り、入力欄にカーソルが入ります。

#### Linux / Wayland {#linux-wayland}

Electron 20 以降は、Wayland のセッションではネイティブな Wayland クライアントとして動きます。ドラッグ・クリックの通り抜け・大きさの変更は、この経路で動作します。

**Hyprland**（Omarchy を含む）では、HUD がマップされたあとに、コンポジタの IPC を通して浮かせて固定します。そうしないと Hyprland はほかのウィンドウと同じようにタイル配置してしまい、`always-on-top` は無視され、コンポジタのドラッグも効きません。追加のウィンドウルールは要りません。

一部のコンポジタ（とくに COSMIC）は、ネイティブな Wayland のウィンドウに対して `always-on-top` を無視します。そこで固定を取り戻すには、アプリを XWayland で動かします。

```yaml
desktop:
  ozone_platform_hint: x11
```

これは起動時に `ELECTRON_OZONE_PLATFORM_HINT` へ橋渡しされます（環境変数で明示した値のほうが優先されます）。引き換えがあって、X11 はマウスを無視したウィンドウを元に戻せないため、HUD はクリックが通り抜けない実体のあるウィンドウのままになります。KDE の構成によっては、X11 の ozone バックエンドでキーボードが効かなくなるという報告もあります。常に手前が必要でないかぎり、この設定は `auto` のままにしておいてください。

#### WSLg（WSL2 から Windows の GPU を使う） {#wslg-windows-gpu-from-wsl2}

同じ端末の WSLg で動かす場合、Hermes は `--ozone-platform=wayland` を付けて起動します。XWayland で最大化したウィンドウの位置がずれたり、マウスの当たり判定がずれたりするのを避けるためです（[microsoft/wslg#1015](https://github.com/microsoft/wslg/issues/1015)）。どのプラットフォームを使うかは、Electron がアプリの JavaScript を読み込むより前、プロセスの起動時に決める必要があります。`--ozone-platform=x11` や `desktop.ozone_platform_hint: x11` を明示する方法も引き続き使えます。WSLg では、最小化・最大化・閉じるのボタンをアプリ自身が描画します。

`hermes gui` を WSL2 の中で動かしていて、`/dev/dxg` があり Mesa の `d3d12_dri.so` も入っている場合、ランチャーは Electron 向けに `GALLIUM_DRIVER=d3d12` を設定します。これで描画に、llvmpipe のソフトウェアラスタライザではなく Windows の GPU が使われます。環境に `GALLIUM_DRIVER`・`MESA_LOADER_DRIVER_OVERRIDE`・`LIBGL_ALWAYS_SOFTWARE`・`LIBGL_DRIVERS_PATH` を自分で設定してあるときは触りません（たとえば `GALLIUM_DRIVER=llvmpipe hermes gui` ならソフトウェア描画のままです）。

### 設定と初回の案内 {#settings-onboarding}

プロバイダー・モデル・ツール・資格情報を、YAML を編集するのではなく本物の UI から管理できます。初回の案内は、数秒で最初のメッセージまで連れていきます。設定のページは、プロバイダーとキー、モデルの選択、ツールセットの構成、MCP サーバー、ゲートウェイ、セッション管理をカバーします。

- **Providers の設定ページ** — 推論プロバイダーを管理する専用の場所で、Accounts / API キーの UI からサインインし、プロバイダーごとに資格情報を保存できます。Accounts と API キーは、設定の **Applies to** の選択を共有します。資格情報の読み書き、OAuth アカウントの削除、ここから始めるサインインは、いま対話に使っているプロファイルではなく、選ばれているプロファイルに対して行われます。サインインの流れは、資格情報の保存とモデルの選択までその対象を保ちます。**Applies to** を変えると、保存していない資格情報の下書きは破棄されます。サインインを閉じると待ち受けは止まり、遅れて届いた結果は無視されます。すでに送られた資格情報の書き込みは、もとのプロファイルで完了することがあります。外部で管理されている CLI の資格情報は、その CLI 自身が扱うので、このプロファイルの選択の対象外です。ここにある **Local Models** のビューからは、端末内で動く llama.cpp のランタイムを導入・管理できます。[ローカルモデル](/hermes/docs/user-guide/local-models/) を参照してください。
- **メニューにすべてのプロバイダーとモデルが並びます** — GUI には、プロバイダーの一覧と `hermes model` が知っているすべてのモデルが出ます。一部を選りすぐったものではなく、CLI と同じカタログから選べます。
- **API の方式を選べる独自の接続先** — **Settings → Providers → Custom Endpoints** には **API Mode** の選択があります（**Auto-detect**、**Chat Completions**、**Responses API**、**Anthropic Messages**）。独自のプロバイダーについて `hermes model` が出すのと同じ選択肢です。これは `config.yaml` に `providers.<id>.api_mode` として保存されるので、Responses しか受けない接続先や Anthropic 互換の接続先へ `/chat/completions` を呼びに行くことはなくなります。**Test** は `/v1/models` を叩くだけでなく、実際に使う通信の方式を確かめます。固定した方式の経路（Auto-detect ならそれが解決した方式の経路）へトークン 1 つ分の要求を送り、接続先がそれを提供していなければ、その方式の名前を挙げて失敗します。**Test** は、ゲートウェイが `/v1/models` で知らせる別名の情報（`canonical_model`、`reasoning_effort`）も保ちます。`gpt-5.6-sol-high` のような別名を選ぶと、正式なモデル名が保存され、その effort が `agent.reasoning_overrides` の下に固定されます。
- **xAI Grok の OAuth** — Grok はランチャーで一級の OAuth プロバイダーとして扱われます。ほかの OAuth プロバイダーと同じく、ブラウザの流れでサインインします。
- **ツールバックエンドの導入を GUI から** — ツールバックエンドの導入後の手順を、端末に降りずにアプリから実行できます。ターミナルのバックエンドを選ぶ画面で **Needs setup** と付いたものを選ぶと、まず確認を求められます。断れば、いま選ばれているバックエンドのままになります。
- **ターミナルのフォント選択** — **Settings → Appearance** で、インストール済みのフォントを選べます。`MesloLGS NF` のような Nerd Fonts なら、対話用のターミナルでもエージェント用のターミナルでも Powerlevel10k の区切りやアイコンが表示されます。この設定はプロファイルごとに保存されます。
- **Reasoning Blocks** — **Settings → Chat → Reasoning Blocks**（`config.yaml` の `display.show_reasoning`）で、モデルの思考を記録に出すか隠すかを切り替えます（切ると答えだけになります）。開いている対話は、設定を保存した時点で切り替わります。入力欄に `/reasoning hide` や `/reasoning show` と打っても同じ設定が入れ替わり、開いている記録はすぐそれに従います。
- **起動時に前回の対話を開く** — 既定では、冷えた状態から起動しても前回の続きから始まります。いつも新しい対話で始めたいときは **Settings → Appearance** で切るか、`config.yaml` に `display.resume_last_session: false` を書きます。ディープリンクや明示的な行き先は、どちらの設定でも上書きされません。
- **補助モデルの警告** — 補助的な処理（タイトル付け、要約など）が別のプロバイダーに固定されたまま、メインのモデルを新しいプロバイダーに切り替えると、アプリが警告します。気づかないうちに 2 つのプロバイダーへ作業が分かれてしまうのを防ぐためです。
- **処理ごとの reasoning の effort** — **Settings → Model → Auxiliary models** の各行には、プロバイダーとモデルの選択の隣に reasoning の選択があります。水準を選ぶか、**Off** か、**inherit · main model effort**（既定で、その処理の個別設定を外します）です。これは `config.yaml` に `auxiliary.<task>.reasoning_effort` として保存され、`hermes model` が書くのと同じキーです。設定してあれば行の概要にも出ます。圧縮やタイトル付けのようによく走る処理を低い reasoning か無しで回し、メインのエージェントは高いままにしておく、といった使い方ができます。
- **VS Code Marketplace のテーマ** — 内蔵のテーマに加えて、外観の設定から VS Code Marketplace をその場で検索できます。好きなカラーテーマを選べば、アプリがダウンロードして変換し、デスクトップのテーマとして入れてくれます。同じ取り込み機能はコマンドパレット（*Install theme*）からも使えますし、入れたテーマは外観の設定から消せます。
- **スリープさせない** — **Settings → Advanced → Keep computer awake** を使うと、端末がスリープしなくなるので、長時間や夜通しのエージェントの実行が止まりません（画面は暗くなることがあります）。これは端末ごとの設定です。

初回の案内は、統一されたオーバーレイのデザインで作り直されました。**Choose provider later** を選べば、プロバイダーの設定を後回しにして、先にアプリへ入れます。

#### プロファイルごとの設定: 「Applies to」の範囲 {#per-profile-settings-the-applies-to-scope}

[プロファイル](/hermes/docs/user-guide/profiles/) が 2 つ以上あるとき、設定ファイルに紐づく設定のページ（**Model、Workspace、Safety、Memory & Context、Voice、Chat、Advanced、Tools & Keys**）と **Messaging** のオーバーレイには、上部に共通の **Applies to** のチップの列が出ます。編集がどのプロファイルに効くかを、ここで選びます。

- 既定では**いま使っているプロファイルに追従**します。これまでどおり、使っているプロファイルを編集する動きです。
- 別のプロファイルを選べば、アプリ全体を切り替えずに*そのプロファイル*の設定を見て編集できます。選択は設定のページを移動しても保たれます。
- アプリの使用中プロファイルを切り替えると選択はリセットされるので、前に選んだプロファイルへ編集が黙って入り続けることはありません。
- プロファイルが 2 つ未満のときは、チップの列ごと表示されません。

（Gateways のページはプロファイルの扱いが違い、**Per-profile overrides** の小見出しで扱います。Capabilities と Scheduled Jobs のビューは、それぞれ自分の範囲選択を持っています。）

### 管理のページ {#management-panes}

端末に降りなくて済むように、Hermes の管理まわりもアプリに載っています。

- **Skills** — [スキル](/hermes/docs/user-guide/features/skills/) を探し、入れ、管理します。Skills のタブには、入れてあるスキルが有効・無効の切り替えとともに並び、その下に Hermes に付いてくる追加スキルのカタログが全部出ます。項目ごとに **Install** のボタンがひとつあり、押して終わればその行が、入れてあるものの一覧へ移ります。
- **記憶のグラフ（Star Map）** — 対話で `/journey`（別名 `/learning`、`/memory-graph`）と打つと、学んだスキルと記憶が時間とともに星座のように並ぶ画面が開き、再生のつまみで動かせます。ノードはそのパネルから編集・削除できます（スキルは保管され、記憶は消えます）。[学びの軌跡](/hermes/docs/user-guide/features/memory/#learning-journey-journey) を参照してください。
- **Cron** — [予約したジョブ](/hermes/docs/reference/cli-commands/#hermes-cron) を確認・管理します。**All profiles** を入れておくと、すべてのプロファイルのジョブをまとめて一覧できます。ジョブの実行履歴と操作（一時停止・再開・編集・削除）は、どのプロファイルを選んでいても、必ずそのジョブを持つプロファイルに対して行われます。
- **Profiles** — [Hermes のプロファイル](/hermes/docs/user-guide/profiles/)（設定・スキル・セッションが分かれたもの）を切り替えます。
- **Messaging** — ゲートウェイのチャンネルを設定します。Telegram には **Quick setup** のカードがあります。**Create with QR** を押し、Telegram でコードを読み取る（またはリンクを開く）と、Hermes がボットを作り、許可リストに載せるユーザー ID を検出し、資格情報を保存し、ゲートウェイを再起動するところまでやります。資格情報の保存・消去・有効化の切り替えをすると、ゲートウェイが実際に再起動するまで **Restart now** の帯がページに残ります。再起動に失敗したときも帯は残るので、もう一度試すか手で再起動できます。
- **Agents** と **Command Center** — 複数のエージェントで進めるための画面です。

### Bot Mode（内蔵） {#bot-mode-built-in}

**Bot Mode** はアプリに同梱されていて、既定で有効です。「エージェント 1 人につき対話 1 つ」の
名簿で、[Hermes のプロファイル](/hermes/docs/user-guide/profiles/) がそれぞれ、自分のアイコン
（幾何学的な顔、アップロードした画像、AI が描いた肖像、ドット絵のペット）と、自分の代表となる
**Bot Chat** の会話、そして自分の **Routines**（Hermes の cron に支えられた繰り返しのタスク）を
持つボットとして並びます。名簿は左のサイドバーに、会話の隣のタブ
（**Sessions | Bots** のタブの列）として置かれます。セッションの一覧の下に
積まれた 2 つ目のペインではありません。古い積み重ね型の配置で入った環境は、
一度だけ自動でタブの列に移されます。自分でペインを配置していた場合は、その配置は
そのまま残ります。**Cronjobs**（Routines）のペインは、Bots のタブを使っている間だけ
対話の横に出て、Sessions に戻すと消えます（古いデスクトップのビルドでは常に
表示されたままです）。

新しいエージェントは名簿から作れます。
Name / Title / Description に加えて、Advanced を開けば能力まわり
（モデル、SOUL、スキル、ツールセット、MCP サーバー）をひととおり指定できます。
セクションにまとめたり、複数のボットが議論するグループの対話を開いたりもできます。
グループの対話は、名簿の中に Discord のような独立した行として出ます。メンバーの
アイコンが重なり、人数、部屋の最新の一行のプレビュー、「あなたを待っています」の
バッジが並び、ボットの行と同じピン留めと新しさの順で混ざります。グループの行を押すと、
その部屋が**メインの対話ウィンドウ**を占めるタブとして開きます（古いデスクトップの
ビルドでは、ボットのサイドパネルの中に開きます）。

ボットどうしもやり取りします。どの対話でも `@researcher have a look at this` と打てば、
いま使っているボットがメッセージを渡して結果を報告しますし、ボットはお互いの
Bot Chat に直接届きます（`hermes -p <bot> chat`）。バックエンドは、各ボットの代表となる
**Bot Chat** のセッションに、やり取りの作法を自動で教え込みます
（設定は `agent.bot_mode_protocol`、既定は有効）。仲間のボットが CLI から画面なしで
開いたときも同じです。おかげで、SOUL.md に手を入れなくてもボットどうしの
返信と受け渡しが成り立ち、ふだんのセッションには何も影響しません。

Bot Mode のセッション、つまり各ボットの代表となる Bot Chat と、グループの対話の
メンバーごとのセッションは、全体の Sessions のサイドバーからは常に隠れています。
自分の会話に混ざるのではなく、Bots のペイン（名簿の行、部屋の表示、ボットごとの
セッション一覧）にあります。

使わないボットは片付けられます。ボットの行を右クリック → **Hide
Bot** です。隠したボットは名簿から消えますが働き続けます。@ でのメンションは
届きますし、グループの対話の所属もそのままです。1 つでも隠れていると Bots の
見出しに目のマークが出ます。押せば隠れたボットが薄く表示され（右クリック →
**Unhide Bot** で戻せます）、隠れたボットに未読があるときは目に点が付きます。
隠しているかどうかはボットのプロファイルに保存されるので、端末をまたいでも
ついてきます。

要らないなら、**Capabilities → Plugins → Bots** で **Desktop** のスイッチを切ってください。名簿、
routines のペイン、入力欄の処理がその場で外れます。再起動は要りません。

エージェントの作り方（複数の端末にまたがる **Create on** の選択を含む）、接続をまたいだ名簿、
ボットどうしのメンション、グループの対話で誰が答えるかの決め方まで、詳しくはこちらです。
[Bot Mode: エージェントの名簿](/hermes/docs/user-guide/bot-mode/)。

### キーボードと移動 {#keyboard-navigation}

- **コマンドパレット** — **Cmd+K** か **Cmd+P**（Windows / Linux では Ctrl+K / Ctrl+P）を押すと、キーボードから操作を呼び出してアプリ内を移動できます。任意のページや設定の節を開く、タイトルや id でセッションへ飛ぶ、モデルやテーマや配色を変える、ターミナルを開く、ゲートウェイを再起動する、Hermes を更新する、といったことができます。
- **割り当てを変えられるショートカット** — **Settings → Keyboard Shortcuts**（または **Cmd/Ctrl+/**）を開くと、ほとんどの割り当てを変えられます。プロファイルの切り替え、セッションの移動、表示の切り替え、デスクトップのプラグインが追加したショートカットまで対象です。重複した割り当ては衝突として示されます。覚えておくと便利な既定をいくつか挙げます。**Cmd/Ctrl+N** 新しいセッション、**Cmd/Ctrl+.** Command Center、**Cmd/Ctrl+,** 設定、**Cmd/Ctrl+Shift+F** セッションの検索、**Cmd/Ctrl+1–9** プロファイルの切り替え、**Shift+X** 明暗の切り替えです。
- **自分で決める拡大縮小のショートカット** — 画面を半段ずつ拡大縮小して、文字の大きさを細かく調整できます。
- **UI の言語切り替え** — アプリの表示言語をアプリ内で変えられます。英語、簡体字中国語（zh-Hans）、繁体字中国語（zh-Hant）、日本語、アラビア語（RTL）、ロシア語です。

### セッションとプロファイル {#sessions-profiles}

- **セッション一覧の刷新** — 保管の機能と全体的な整理を入れて作り直した一覧で、数が増えても扱えるようにしました。
- **id でセッションを探す** — 目的のセッションを id から直接見つけられます。
- **複数プロファイルの同時利用** — 複数の [プロファイル](/hermes/docs/user-guide/profiles/) のセッションを同時に走らせられます。別のプロファイルのセッションは、プロファイルをまたぐ `@session` のリンクで参照できます。
- **プロファイルの書き出しと読み込み** — 環境ひとそろいを 1 つのファイルとして渡せます。**⌘K → Export profile…**（またはレールのプロファイルの四角を右クリック）で、スキル・記憶・人格・cron・プラグイン・設定を含む `.tar.gz` が書き出されます。API キーは取り除かれます。デスクトップから書き出すと、見た目と画面まわり（スキン、明暗、独自のテーマ、プロファイルのレールの色、ウィンドウの配置）も一緒に入るので、読み込んだ側には送り手と同じ姿で届きます。読み込みは **⌘K → Import profile…** か、レールの **+** の隣のボタンから行い、上書きを適用して新しいプロファイルへ移ります。同じアーカイブは、対話での `/export` / `/import` や、シェルからの `hermes profile export` / `import` でも使えます。[プロファイルのファイルを書き出す・読み込む](/hermes/docs/user-guide/profile-distributions/#export-and-import-a-profile-file) を参照してください。

## 更新 {#updating}

アプリは裏で更新を確認し、準備ができたらワンクリックの更新を案内します。

裏での確認は、GitHub の API にブランチの先頭を尋ねます。匿名の GitHub へのリクエストは**ネットワークのアドレスごと**に 1 時間 60 回までなので、共有の回線（社内の NAT、VPN、プロキシ）ではこの端末がほとんど呼んでいなくても `GitHub API rate limit reached` と出ることがあります。代わりに 1 時間 5,000 回の枠を使うため、確認処理は次の順で最初に見つかった認証情報を使います。

1. アプリを起動した環境の `GITHUB_TOKEN`、次に `GH_TOKEN`。リクエストのたびに読み込まれ、保存されることはありません。
2. [GitHub CLI](https://cli.github.com/) 自身のログイン情報（`gh auth token`）。Dock や Finder、デスクトップのランチャーから起動したアプリは、シェルの変数を持たない最小限の環境を引き継ぐため、この段が助けになります。`gh` は `PATH` と、よくあるインストール先（Homebrew、`/usr/local/bin`、`~/.local/bin`、Windows の GitHub CLI インストーラー）から探します。結果はアプリを再起動するまで保持されるので、`gh` の実行は 1 回のセッションにつき多くても 1 度です。
3. 匿名のまま。

GitHub に拒否された認証情報（HTTP 401、期限切れか無効化）は `desktop.log` に 1 度だけ記録されます。記録されるのはどこから来た認証情報かだけで、トークンそのものは残りません。そのリクエストは匿名で試し直されます。更新の適用は API ではなく `git` を使うので、この制限の影響を受けません。

ローカルでの更新中は、詳しいビルドの出力が、いま使っているプロファイルの
`logs/update.log` に流れます。切り離された `--gateway` の更新も含みます。端末には
出ませんが、ビルドが終わる前に原因を追うときに読めます。Windows での受け渡しでは、
このログに新しい出力が増えることを進行とみなします。何も出力しない子プロセスは、
無反応の監視の対象のままです。プロセスが生きているというだけでは監視は解除されませんし、
更新を取り消しても、そのビルドが終わるのを待つわけではありません。

デスクトップアプリと、その先の Hermes バックエンドは、別々のタイミングで更新されます。アプリの入った端末と、バックエンドが動いている場所です。更新の対象が 2 つ以上あるとき（リモートのゲートウェイがある、あるいは登録済みのゲートウェイが複数ある）、更新の操作（About のパネルの **Update now**、⌘K の **Update Hermes** の行、更新準備完了の通知）は**すべて**を更新します。まずつながっているバックエンド、次に対象となるほかの登録済みゲートウェイ（Hermes Cloud の項目はプラットフォーム側が管理するので飛ばされます）、最後にデスクトップアプリ自身です。クライアントの更新を当てるとアプリが再起動するからです。1 台だけの環境では、これまでどおりボタン 1 つで終わります。

バックエンドを更新したあとは、アプリが自分の版も確かめ直し、GUI のほうが古ければワンクリックの **Update desktop app** を添えて知らせます。リモートのバックエンドを更新した結果、気づかないうちに古いデスクトップのビルドが残ることはありません。

[手作業での更新](https://hermes-agent.nousresearch.com/docs/getting-started/updating) も GUI で動きます。

## アンインストール {#uninstalling}

**Settings → About → Danger zone** を開き、どこまで消すかを選びます。

- **Uninstall Chat GUI only** — デスクトップアプリとそのデータを消します。Hermes のエージェント、設定、対話は残ります。（`hermes uninstall --gui` と同じです。）
- **Uninstall GUI + agent, keep my data** — アプリとエージェントを消し、設定・対話・秘密の情報は入れ直すときのために残します。（`hermes uninstall` と同じです。）
- **Uninstall everything** — アプリ、エージェント、ユーザーのデータをすべて消します。（`hermes uninstall --full` と同じです。）

処理を終えるためにアプリは閉じます（後片付けは終了後に走るので、動いていたアプリ本体と自分の venv を消せます）。ローカルにエージェントが入っていないとき（たとえば、リモートのバックエンドにつないだ GUI だけの軽量なクライアント）は、エージェントを消す選択肢は自動で隠れます。

同じことは端末からもできます。GUI だけなら `hermes uninstall --gui`、エージェントも消すなら `hermes uninstall` か `hermes uninstall --full` です。

:::note
**ソースのチェックアウト**（`hermes desktop` の開発用ビルド）から `hermes uninstall --gui` を走らせると、ワークスペースの `node_modules` と `apps/desktop/{dist,release}` のビルド成果も消えます。これらは GUI のビルド生成物だからです。`hermes desktop`（または `npm install` と再ビルド）で元に戻せますが、デスクトップアプリ自体をいじっている最中なら、あとで依存関係を入れ直すことになると思っておいてください。
:::

## CLI 早見表: `hermes desktop` {#cli-reference-hermes-desktop}

CLI から起動するなら、`hermes desktop` と打つだけです。既定では、ワークスペースの Node の依存関係を入れ、いまの OS 向けに展開済みの Electron アプリをビルドし、そのビルド済みのものを起動します。

Linux では、起動のたびに `$XDG_DATA_HOME/applications/hermes.desktop`（既定では `~/.local/share/applications/hermes.desktop`）が書き直され、Hermes がアプリのメニューに出るようになります。手で編集した項目を残したいときは、書き直しを止めてください。

```bash
hermes config set desktop.manage_launcher_entry false
```

項目が無いときは、この設定でも作られます。このフラグが止めるのは、すでにある項目を `hermes desktop` が書き直すことだけです。

アプリの一覧やメニューから Hermes を起動したとき（ランチャーが `DESKTOP_STARTUP_ID` を設定します）、項目が書かれるのはウィンドウが画面に出たあとです。ウィンドウが出る前にアプリが終われば、そのときは何も書かれません。次に端末から起動したとき、更新後の再起動のとき、あるいはウィンドウが出る一覧からの起動のときに書かれます。GNOME Shell のいくつかの版は、起動している最中に `.desktop` ファイルが変わったアプリを見失います（プロセスが終わるまでではなく、起動の通知が完了するか時間切れになるまでその状態が続きます）。それが後でセッション全体を巻き込んで落ちる原因になりうるので、ウィンドウを待つことで避けています。端末からの起動と、更新後の再起動では、これまでどおりすぐ書かれます。

| フラグ                 | 説明                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------- |
| `--skip-build`       | npm の導入とパッケージ化を飛ばし、`apps/desktop/release` にある展開済みのアプリを起動します |
| `--force-build`      | 内容のスタンプが一致していても、まるごとビルドし直します                                    |
| `--build-only`       | デスクトップアプリをビルドするだけで起動はしません（`hermes update` が使います）              |
| `--source`           | パッケージ化したアプリではなく、`apps/desktop/dist` に対して `electron .` で起動します        |
| `--cwd PATH`         | デスクトップの対話セッションが最初に開くプロジェクトのディレクトリです（`HERMES_DESKTOP_CWD` を設定します） |
| `--hermes-root PATH` | アプリが使う Hermes のソースの場所を上書きします（`HERMES_DESKTOP_HERMES_ROOT` を設定します） |
| `--ignore-existing`  | バックエンドを探すとき、`PATH` にある `hermes` の CLI を無視させます                         |
| `--fake-boot`        | 起動画面を確かめるために、決まった長さの遅延を入れます                                      |

## 仕組み {#how-it-works}

パッケージ化されたアプリには、Electron のシェルと、ネイティブな React の対話画面が入っています。初回の起動時に、Hermes Agent のランタイムを `HERMES_HOME`（`~/.hermes`、Windows では `%LOCALAPPDATA%\hermes`）へ導入できます。**CLI で入れたときとまったく同じ配置**で、だから両者を行き来できます。バックエンドの解決は、まず `HERMES_DESKTOP_HERMES_ROOT` を尊重し、次に導入が完了した管理下のもの、次に `PATH` 上で見つかった `hermes`（`--ignore-existing` や `HERMES_DESKTOP_IGNORE_EXISTING=1` が無い場合）、最後に Nix のようなパッケージャ向けの明示的な `HERMES_DESKTOP_HERMES` の上書きの順です。React の描画側は、アプリが立ち上げる画面なしのバックエンドとやり取りします。`tui_gateway` の JSON-RPC / WebSocket API を提供する `hermes serve` のプロセスで、`hermes --tui` を埋め込むのではなくエージェントのランタイムを使い回します。デスクトップアプリは**自己完結**していて、自分の `hermes serve` のバックエンドを動かし、[Web ダッシュボード](/hermes/docs/user-guide/features/web-dashboard/) を開くことも必要とすることもありません。（`serve` コマンドより古いランタイムでは、画面なしの `dashboard --no-open` へ自動で落ちるので、アプリの更新がバックエンドを追い越すことはありません。）導入・バックエンドの解決・自己更新の処理は、Electron のメインプロセスにあります。

## リモートのバックエンドにつなぐ {#connecting-to-a-remote-backend}

既定では、アプリは自分の**ローカル**なバックエンドを起動して面倒を見ます。その代わりに、別の端末で動いている Hermes のバックエンド（VPS、自宅のサーバー、Tailscale の向こうの Mini など）を指すこともできます。

接続まわりはすべて 1 つの設定ページにあります。**Settings → Gateways** です。（古いビルドでは **Gateway** と **Connections** の 2 ページに分かれていました。いまは 1 つにまとまり、古い `?tab=connections` のディープリンクは統合後のページへ転送されます。）

**Settings → Gateways → Connection mode** には、ローカルのゲートウェイ以外の選択肢が並びます。

- **Remote gateway** — 自分で動かしている `hermes serve` のバックエンドの URL を入れてサインインします。この節で説明していくのはこのやり方です。
- **Hermes Cloud** — Hermes Cloud に一度サインインし、アカウントにあるエージェントから選びます。URL を貼る必要はありません。アプリがエージェントを見つけてくれますし（アカウントが複数の組織にまたがるなら組織の選択も出ます）、1 つにつなぐとセッションが自動で切り替わります。つながっている間は、ステータスバーにクラウドの接続が出ます。

ゲートウェイの接続は**端末単位**です。Gateways のページは、このデスクトップがつなげるゲートウェイのバックエンドを管理し、プロファイルはつないだゲートウェイ*から*見つかります。セッションは一度に 1 つのゲートウェイを選び、隣のプロファイルのレールは、そのゲートウェイで見つかったプロファイルを選びます。

### 複数の接続の登録簿 {#the-multi-connection-registry}

同じ **Settings → Gateways** のページの下のほうにある **Registered gateways** は、アプリが知っているすべての Hermes ゲートウェイを名前つきの一覧で管理します。ローカルのランタイム、いくつでも登録できるリモートのゲートウェイ（LAN、Tailscale、インターネット）、Hermes Cloud の環境、SSH のホストが、まとめて 1 か所に保存されます。サイドバーのプロファイルのレールの右端にあるプラグのボタン（**Connect another Hermes gateway…**）や、**⌘K → Gateways** から開けます。全体をまとめたエージェントの名簿、`@name-device` の呼び名、全体への一斉更新、プラグイン SDK まで含めた案内は [Desktop を複数の Hermes につなぐ](/hermes/docs/user-guide/multi-connection-desktop/) にあります。

- **接続には重複しない名前が要ります**（「Homelab」「Work laptop」のような端末の名前です）。同じプロファイル名が複数の登録済みゲートウェイにあるときは、`@profile-device` の形で区別されます（たとえば `@research-homelab`）。
- **ゲートウェイは Sessions のサイドバーから切り替えます。** ゲートウェイが 2 つ以上登録されていると名前つきの選択が出て、いくつ登録しても、ゲートウェイがプロファイルのように見えてしまうことはありません。隣のプロファイルのレールには、そのゲートウェイのエージェントだけが並び、そこで最後に使ったプロファイルを覚えています。プロファイルが多いときは、レールのほうだけが独立して縮みます。
- **プロファイルのレールを隠す。** プロファイルがワークスペースではなくボットなら、サイドバーの下にある色の付いた四角の列は、セッションの一覧と同じものを見せているだけになります。Sessions のビューのメニュー（**Profile rail**）、シェルの右クリックメニュー、**⌘K → Toggle profile rail** で消せます。隠している間は、ステータスバーのゲートウェイの選択の隣に **Profiles** のドロップダウンが出て、同じ選択肢（このゲートウェイのプロファイル、ほかのゲートウェイのエージェント、**New profile**、**Import profile…**、**Manage profiles…**）が並びます。プロファイルの切り替えの入口が無くなることはありません。
- **再起動したあとに何を開くかを選ぶ。** **Open on launch** は、これまでどおりの **Primary gateway** を既定にすることも、接続に成功したら **Last used** のゲートウェイを開き直すこともできます。この設定はアプリの本体の外に保存されるので、Desktop を更新しても残ります。
- **接続の追加・編集・削除・テスト** をこのパネルから行えます。**Add** では 4 種類すべて（**Local**、**Hermes Cloud**、**Remote gateway**、**SSH**）を選べます（アプリが管理するローカルの項目がある間、Local のボタンは押せません。クラウドの追加は上のサインインと検出の流れへ案内が出ます）。ローカルの項目はアプリが管理していて、削除できません。**Test** は、その接続自身の HTTP と WebSocket の経路を直接確かめます。
- **重複は保存時にはじかれます**。**local** の項目は 1 つだけです。リモートとクラウドの項目は、正規化した URL（前後の空白を落とし、末尾のスラッシュを外し、小文字にしたもの）で、種類をまたいで重複を判定します。SSH の項目は、正規化した `user@host:port` とリモート側のプロファイルで判定します。
- 登録簿の入ったビルドを初めて動かすと、いまの設定が**自動で取り込まれます**。現在の全体の接続設定と、プロファイルごとの古い上書きが、名前つきの項目になります。古い設定ファイルはそのまま残るので、以前のビルドも動き続けます。
- クラウドの項目は、手で URL を打つのではなく、上に書いた Hermes Cloud のサインインと検出の流れから来ます。
- トークンは OS のキーリングで暗号化して保存されます（キーリングの無い Linux では、平文で保存することを明示的に選べます）。

横並びの経路はすでに動いています。登録済みのゲートウェイはそれぞれ、必要になったタイミングで自分のバックエンドとソケットにつなぎ（接続とプロファイルの組ごとに分かれます）、プラグイン SDK は全体をまとめたエージェントの名簿を提供し（`host.agents()` / `host.ensureAgent()`）、Gateways のページの **Update all instances** は対象となるすべてのゲートウェイへ一斉に `hermes update` を投げます。Hermes Cloud の項目は飛ばされ（プラットフォーム側が更新します）、環境ごとに結果が返ります。

:::info リモートのバックエンドとは、動いている `hermes serve` のプロセスのことです
「リモートのバックエンド」とは、リモートの端末で動いている **`hermes serve`** のサーバーのことで、デスクトップアプリがつなぐ相手はこのプロセスです。そのバックエンドが実際に立ち上がっていて届く状態でなければ、この節のどれも動きません。デスクトップアプリが代わりに起動してくれるわけではありません。リモートのホストでは、あなた（か `systemd` のサービス）が `hermes serve` を動かし続け、アプリがそこにつなぎます。メッセージ連携のチャンネル（Telegram、Discord など）も使うなら、**ゲートウェイ**は*別の*長く動かすプロセスで、自分で起動します。手順のあとの注記を見てください。
:::

接続には 2 つの側面があります。バックエンド側では**認証のしくみ**で守り、アプリ側ではバックエンドの URL を入れてサインインします。ループバック以外のアドレスにバックエンドを結び付けると自動で認証の入口が有効になり、そこを通す鍵になるのが、設定した認証のしくみです。

**バックエンドの置き場所で選んでください。**

- **OAuth（Nous Portal） — 自分の端末の外から届く場所なら、まずこちらです。** ログインは Nous のアカウントで検証されるので、VPS や公開のホスト、そのほかリモートのバックエンドに向いています。`hermes dashboard register`（または Portal の [`/local-dashboards`](https://portal.nousresearch.com/local-dashboards) のページ）でダッシュボードを登録して OAuth のクライアントを用意し、アプリから **Sign in with Nous Research** でサインインします。自前の ID 基盤を運用しているなら、自己ホストの OIDC でも同じように動きます。
- **ユーザー名とパスワード — ローカルや信頼できるネットワーク限定です。** バックエンドが同じ信頼できる LAN にあるか、VPN（Tailscale など）越しにしか届かない場合に、いちばん手軽な選択肢です。外部の ID 基盤なしに、共有の資格情報 1 組で守るだけなので、**公開のインターネットに晒したダッシュボードには使わないでください**。そこでは OAuth を選びます。

この節の残りでは、信頼できるネットワークで手早く立ち上げられるユーザー名とパスワードのやり方を説明します。OAuth のやり方は [Web ダッシュボード → 既定のしくみ: Nous Research](/hermes/docs/user-guide/features/web-dashboard/#default-provider-nous-research) を見てください。

### バックエンド側（リモートの端末）での作業 {#on-the-backend-the-remote-machine}

ユーザー名とパスワードを決めてから、届くアドレスに結び付けてバックエンドを起動します。資格情報は `~/.hermes/.env`（秘密の情報のファイル、権限は 0600）に置きます。

```bash
# 1. Set the dashboard login credentials.
cat >> ~/.hermes/.env <<'EOF'
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
# Recommended: a stable signing secret so sessions survive restarts.
# Without it a random key is generated per boot and you'll be logged out
# on every restart.
HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
EOF
chmod 600 ~/.hermes/.env

# 2. Run the backend bound to a reachable address. The non-loopback bind
#    engages the auth gate; the username/password provider handles login.
hermes serve --host 0.0.0.0 --port 9119
```

デスクトップアプリをつなげておきたい間は、その `hermes serve` のプロセスを動かし続けてください。止まれば、アプリはバックエンドに届かなくなります。ログアウトや再起動をまたいで生き残るように、`systemd`・`tmux`・お好みのプロセス管理の下で動かしてください。

これとは別に、メッセージ連携のチャンネルを使うなら、リモートのホストで**ゲートウェイが動いている**ことを確かめてください。デスクトップアプリがやり取りするのは `hermes serve` のバックエンドですが、Telegram / Discord / Slack のゲートウェイのセッションは別のプロセスで、自分で起動して動かし続けるものです。ゲートウェイの設定は [メッセージ連携](/hermes/docs/user-guide/messaging/) を見てください。

パスワードを平文で置いておきたくない場合は、代わりに `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH` に scrypt のハッシュを設定してください。ハッシュは `python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"` で作れます。設定できる項目の全体（config.yaml のキー、すべての環境変数、流量の制限）は [Web ダッシュボード → ユーザー名とパスワードのしくみ](/hermes/docs/user-guide/features/web-dashboard/#usernamepassword-provider-no-oauth-idp) にあります。

バックエンドを systemd のサービスとして動かすなら、ユニットに `EnvironmentFile=%h/.hermes/.env` を書いて、起動時に資格情報が環境へ入るようにしてください。

:::warning
バックエンドはあなたの `.env`（API キーや秘密の情報）を読み書きし、エージェントのコマンドを実行できます。上に示した**ユーザー名とパスワード**の構成は信頼できるネットワーク向けです。パスワードで守っただけのバックエンドを、そのまま公開のインターネットに晒さないでください。VPN の内側に置きます。[Tailscale](https://tailscale.com/) が素直な選択肢です。端末の tailscale の IP に結び付け（`--host <tailscale-ip>`）、Remote URL に `http://<tailscale-ip>:9119` を使えば、自分の tailnet からしか届きません。公開のインターネット越しに届かせたいなら、**OAuth（Nous Portal）**を使ってください。
:::

### アプリ側での作業 {#in-the-app}

**Settings → Gateways → Remote gateway** で行います。

1. **Remote URL** — `http://<backend-host>:9119` を入れます（リバースプロキシを前に置いているなら `/hermes` のようなパスの接頭辞も使えます）
2. **サインイン** — バックエンドがどのしくみを使っているかをアプリが見分け、ボタンが変わります。ユーザー名とパスワードのバックエンドなら **Sign in** のボタンが出て、資格情報の入力欄が開きます（手順 1 で決めたものを入れます）。OAuth のバックエンドなら **Sign in with `<provider>`**（たとえば *Sign in with Nous Research*）が出て、そのしくみのブラウザでのサインインが走ります。どちらでも、最後にはバックエンドに対して認証済みのセッションが手に入ります。
3. **保存してつなぎ直す** — デスクトップの画面がリモートのバックエンドへ切り替わります。セッションは自動で読み込み直され、`HERMES_DASHBOARD_BASIC_AUTH_SECRET` を設定してあれば、再起動してもサインインしたままです。

UI を使わずに、アプリを起動する前に環境変数 `HERMES_DESKTOP_REMOTE_URL` でバックエンドの URL を指定することもできます（アプリ内の設定より優先されます）。サインインは Gateways の設定パネルから行います。

:::note プロファイルごとのリモートのホスト
リモートのゲートウェイのホストは [プロファイル](/hermes/docs/user-guide/profiles/) ごとに設定するので、プロファイルごとに別のリモートのバックエンドを指せます（ローカルのままにもできます）。プロファイルを切り替えると、つなぐ先のリモートのホストも切り替わります。
:::

### 困ったときは {#troubleshooting}

- **サインインが 401 や「Invalid credentials」で失敗する** — ユーザー名かパスワードが、バックエンドの `HERMES_DASHBOARD_BASIC_AUTH_USERNAME` / `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD` と合っていません。バックエンドは、存在しないユーザーのときも間違ったパスワードのときも同じ一般的なエラーを返す（どちらかを言い当てられないようにする）ので、両方を確かめてください。認証の入口が有効かどうかは `curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'` で確認できます。`true` が返り、`"basic"` が含まれているはずです。
- **「Sign in」のボタンが出ず、セッションのトークンを求められる** — バックエンドのユーザー名とパスワードのしくみが動いていません。`/api/status` の `auth_providers` に `"basic"` が出ないはずです。ユーザー名とパスワード（またはパスワードのハッシュ）の両方が `~/.hermes/.env` に設定されていて、ダッシュボードのプロセスが実際にそれを読み込んでいるかを確かめてください。
- **再起動のたびにサインアウトされる** — `HERMES_DASHBOARD_BASIC_AUTH_SECRET` に固定の値を設定してください。設定しないと、トークンに署名する鍵が起動のたびに作り直され、すべてのセッションが無効になります。
- **接続を拒否される、または応答が返らない** — バックエンドが `127.0.0.1`（既定）に結び付いているか、ファイアウォールか VPN がポートを塞いでいます。`0.0.0.0` か tailscale の IP に結び付け、信頼できるネットワークに向けてポートを開けてください。

同じ構成を Web ダッシュボード側から見た説明は [Web ダッシュボード → Hermes Desktop をリモートのバックエンドにつなぐ](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend) にあります。環境変数の一覧は [環境変数 → Web ダッシュボードと Hermes Desktop](/hermes/docs/reference/environment-variables/#web-dashboard--hermes-desktop) にまとまっています。

## デスクトップアプリを拡張する {#extending-the-desktop-app}

デスクトップアプリは拡張を前提に作られています。ペイン、ページ、サイドバーの項目、ステータスバーの
項目、パレットのコマンド、キー割り当て、テーマは、すべて 1 つの SDK を通して登録されていて、
自分で追加できます。プラグインは、
`$HERMES_HOME/desktop-plugins/<id>/plugin.js` に置く単一の ESM ファイルです。アプリは数秒のうちに
読み込み、保存するたびに反映し直します。入れたプラグインは **Capabilities → Plugins** から
そのまま管理できます。

詳しくは [Desktop Plugin SDK](/hermes/docs/developer-guide/desktop-plugin-sdk/) を
参照してください。（これは [Web ダッシュボードのプラグインのしくみ](/hermes/docs/user-guide/features/extending-the-dashboard/) とは別のものです。）

**Capabilities → Plugins → Installed** には、実際に入っている状態が出ます。
**プラグイン 1 つにつき 1 行**で、詳細のペインに Desktop と Agent の操作が並びます。

- プラグインは **このアプリ**・**エージェント**・**その両方** のどれかを拡張できます。どちらなのかは
  行のバッジが示し、パッケージの中身から判断されます（`plugin.yaml`
  があればエージェント側、`plugin.js` があればデスクトップ側）。両方を持つプラグインも 1
  行で、2 行に分かれることはありません。
- **Desktop の列** — このアプリに読み込まれる側です。アプリ単位なので、ウィンドウが
  どのプロファイル・ゲートウェイ・リモートの端末を見ていても、同じスイッチで同じ値です。
  デスクトップ側のコードが読み込まれる場所はただ 1 つ、
  `~/.hermes/desktop-plugins/` です。エージェントとデスクトップを 1 つにまとめた
  パッケージのデスクトップ側は、導入時にアプリがそこへ複写します（更新や削除にも
  ついていきます）。だからプロファイルを切り替えても、ペインが読み込み直されたり、
  外れたり、範囲が変わったりしません。切り替えはその場で効きます。
- **Agent の列** — 選んでいるプロファイルのバックエンドに入っている側です
  （[エージェントのプラグイン](/hermes/docs/user-guide/features/plugins/): user、git、project、pip、
  持ち運び可能な導入）。カタログの固定先が動いたときは **Update** のチップが出ます。
  プロファイルの選択がこの列の見出しにあるのは、それがこの列にしか効かないからです。
  プロファイルが 1 つだけなら、選択そのものが出ません。
  リポジトリに同梱の組み込み（プラットフォームのアダプタ、プロバイダーのプラグイン）は
  一覧に出ません。有効な状態で配布され、それぞれの画面から設定します。
- そのプラグインが持たない側にはダッシュが出ます。デスクトップ側があって、
  エージェント側が選んでいるプロファイルに**入っていない**ときは **Install here** が出て、
  パッケージの出どころ（カタログの項目か git のリモート）から導入のダイアログを
  そのプロファイル向けに埋めてくれます。
  [Accent Picker](https://github.com/NousResearch/hermes-desktop-accent-picker)
  のような追加のものは、**Install from Git** でそれぞれのリポジトリから入れます。

その下には、見つけるための仕組みがあります。動いている [プラグインカタログ](/hermes/docs/user-guide/features/plugin-catalog/)
の選択画面は、内容を確認済みの項目を、固定されたコミットのまま、選んでいるプロファイルへ入れます。
**Install from Git** は、それ以外のどのリポジトリも、同じ「確認してから入れる」ダイアログに通します。
任意の **Pin to commit** の欄では、40 文字のコミット SHA をちょうどひとつ指定して入れられます
（非公開のリポジトリも使えます）。固定したプラグインには、一覧に `pinned @ <sha8>` のバッジが出ます。
古い `Settings → Plugins` のリンクはここへ転送されます。

## 困ったときは {#troubleshooting}

### アプリを再起動せずにつなぎ直す {#reconnect-without-restarting-the-app}

接続が **Connected** のままなのに Desktop の対話やボットが返事をしなくなったときは、そのボットやプロファイル、あるいはゲートウェイを選び、ステータスバーのゲートウェイのメニューから **Reconnect gateway** を押してください。つなぎ直しは、開いている・つなぎに行っている・切れている、どの状態でも使えます。Desktop を再起動したり、ほかの経路のソケットをわざわざ閉じたりせずに、いまの経路だけをつなぎ直します。選んだソケットで処理中のリクエストは中断されることがあります。これは明示的な復旧の操作であって、バックエンドやモデルの再起動ではありません。

### `hermes update` のあとにアプリが消えた {#the-app-vanished-after-hermes-update}

以前の更新が、`apps/desktop/release/` を残さずに作業ツリーを入れ替えてしまうと、起動できるパッケージ済みのアプリがなくなります。`HERMES_HOME/desktop-build-stamp.json`（Desktop のビルドが成功したときだけ書かれます）がまだ残っていれば、次の `hermes update` がアプリの欠けに気づいて作り直します。手で作り直すなら `hermes desktop --build-only --force-build` です。Windows では ZIP を使う代替の経路でも、入れ替えをまたいで、ビルド済みのアプリと描画側のバンドル、そして Electron の `node_modules` が残ります。

### ローカルのバックエンドが裏で止まった {#the-local-backend-stopped-in-the-background}

ローカルの Hermes のバックエンドが、準備が整ったあとで落ちた場合、Desktop は自分で起動し直し、**Hermes stopped working in the background** の知らせを出します。代わりのプロセスが立ち上がれば対話もつながり直します。`HERMES_HOME/logs/desktop.log` には終了コードと、バックエンドの最後の出力（`Hermes backend exited (1)` に続いて `Recent backend output:`）が記録されるので、アプリが勝手に復旧したときでも、落ちた理由はログに残ります。起動し直すたびに数秒で落ち続けるなら、原因はバックエンド側にあります。そのログの末尾にあるトレースバックを見てください。2 分のうちに 3 回こうした再起動が起きると、Desktop は立ち上げ直すのをやめ、繰り返す代わりに **keeps crashing** の知らせを出します。原因を直したら、アプリを起動し直してください。

### 失敗したターンは、どの層で失敗したかを示します {#failed-turns-name-the-failing-layer}

ターンが失敗すると、対話には**どの層で失敗したのか**を示すエラーのカードが出ます。
プロバイダーとモデル、独自のエンドポイント、ストリーミングの接続、
認証、課金、ゲートウェイ、ローカルのランタイム、ディスクのいずれかで、
一般的なエラーの通知ではありません。カードには、失敗に合わせた復旧の操作が並びます。

- **Retry** — 失敗したターンをその場でやり直します（内容の方針による拒否のように、
  やり直しても同じ結果になるとわかっているときは出ません）。レート制限や利用量の上限の
  応答が、いつ制限が解けるかを伝えてきたとき（`Retry-After` のヘッダーか `resets_at`
  の項目）、カードには Retry の隣に **Limit resets at HH:mm (in 1h 05m)** と出るので、
  いつやり直せば通るのかが分かります。CLI と TUI も、エラーの下に同じ行を出します。
  この案内自体はただの情報ですが、カードには **Retry when the limit resets (HH:mm)**
  も出ます。押すと、制限が解ける時刻に、残り時間を表示しながらそのターンを 1 回だけ
  やり直します。**Cancel** で取り消せます。この予定は開いているウィンドウの中にしか
  残りません。セッションを切り替える、別のメッセージを送る、アプリを閉じる、のどれかで
  消えますし、人が見ていないところで勝手にやり直すことはありません。
- **Switch provider** — プロバイダー、エンドポイント、認証、課金の失敗のときは、
  入力欄のモデルのメニューをその場で開くので、**いまのこの対話**を別のプロバイダーや
  モデルへすぐ移せます（Settings → Models で変わるのは、新しい対話の既定だけです）。
  対話の画面が出ていないときは、Settings → Models へ飛びます。
- **Open logs** — `HERMES_HOME/logs` をファイルマネージャで開きます。リモートや
  Cloud の接続では **Open Desktop logs** という表示になり、手元の Desktop 側のログ
  （通信の記録）を開きます。失敗したターンのゲートウェイやエージェントのログは、
  リモートの端末にあるからです。
- **Send diagnostics** — 同意の確認を経てから、伏せ字を施したデバッグ用の一式を
  Nous の内部ストレージへ送ります（`hermes debug share --nous` と同じ経路です。
  秘密の情報は常に伏せられ、送ったものは Nous のスタッフだけが見られて、14 日後に
  自動で消えます）。成功すると、サポートのやり取りに貼れる非公開の閲覧リンクと、
  GitHub Issues・Nous Portal のサポート・Discord への近道が出ます。リモートや Cloud の
  接続では、バックエンドが自分のエージェントとゲートウェイのログをまとめ、手元の
  Desktop のログも一緒に添えるので、サポートは両側を見られます。
- **Copy error details** — 層・コード・プロバイダーとモデル・エラーメッセージを
  まとめた短い文字列をコピーします。不具合の報告や Discord に貼れます。

層の判定には、エージェントの再試行の処理が使うのと同じ分類のしくみを使っています。
だから、メッセージの文面からの推測ではなく、実際の失敗の意味を表しています。
この情報を持たない古いバックエンドでも、一般的な見出しと Retry / Open logs /
Copy error details の操作を備えたカードは出ます。

起動時のログは `HERMES_HOME/logs/desktop.log` に残ります（バックエンドの出力と、直近の Python のトレースバックを含みます）。アプリが起動に失敗したと言ってきたら、まずここを見てください。CLI から流し見ることもできます。

```bash
hermes logs gui -f
```

よく使うリセットはこちらです。

```bash
# Force a clean first-launch setup (macOS/Linux)
rm "$HOME/.hermes/hermes-agent/.hermes-bootstrap-complete"

# Rebuild a broken Python venv (macOS/Linux)
rm -rf "$HOME/.hermes/hermes-agent/venv"

# Reset a stuck macOS microphone prompt
tccutil reset Microphone com.nousresearch.hermes
```

### 「The host key has CHANGED since you last connected」（SSH のリモート） {#the-host-key-has-changed-since-you-last-connected-ssh-remote}

SSH のリモートを入れ直したり、ホストの鍵を入れ替えたりすると、SSH は安全側に倒れて失敗し、
Desktop は再試行せずエラーの表示を掲げたままにします（古い鍵を消さないかぎり、再試行が
成功することはないからです）。その変更が想定どおりかを確かめたうえで、古い項目を消してから
表示の中の再試行を押してください。

```bash
ssh-keygen -R <host>
```

項目を消したら **Retry** を押す（または Settings → Gateway で接続を入れ直す）と、
掲げていた状態が解除され、次の接続からやり直します。

### 「Build desktop app」が Electron のダウンロードで止まる {#build-desktop-app-stuck-on-electron-download}

ビルドは Electron のランタイム（約 114&nbsp;MB）を `github.com/electron/electron/releases` から取ってきます。インストーラーが **Build desktop app** の段階で止まり、進行の表示に `retrying attempt=…` が繰り返し出るなら、あなたのネットワーク（ファイアウォール、プロキシ、地域）で GitHub が塞がれているか絞られています。

インストーラーはこれを自分で立て直します。ビルドに失敗すると、(1) 壊れたキャッシュ上の Electron の zip を消して再試行し、(2) それでも失敗して `ELECTRON_MIRROR` を設定していなければ、Electron の事実上のコミュニティミラーである `npmmirror.com` 経由でもう一度試します。`@electron/get` はダウンロードを SHASUM で検証しますが、そのチェックサムも同じミラーから来ます。つまり壊れたり途中で切れたりしたダウンロードは捕まえられますが、乗っ取られたミラーは捕まえられません。第三者のホストを信用したくないなら、自分で `ELECTRON_MIRROR` を指定してください（下記）。ビルドが、設定済みのものを上書きすることはありません。

**自分でミラーを選ぶ**（たとえば社内の信頼できるもの）には、インストールの前に `ELECTRON_MIRROR` を設定するか、手でビルドし直します。ビルドはその設定を尊重し、上書きしません。

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ \
  bash -c 'cd "$HOME/.hermes/hermes-agent/apps/desktop" && CSC_IDENTITY_AUTO_DISCOVERY=false npm run pack'
```

**ミラーが必要なほかのネイティブのダウンロード（たとえば Windows の `get-windows` のビルド済みバイナリ）** については、npm のキーを `$HERMES_HOME/npmrc`（Windows では `%LOCALAPPDATA%\hermes\npmrc`、それ以外では `~/.hermes/npmrc`）に書いてください。たとえば `node_get_windows_binary_host_mirror=https://<mirror>/sindresorhus/get-windows/releases/download/` のように書きます。更新処理が起動する `npm ci` や `npm run`（デスクトップ、Web、TUI のビルド）は、そのファイルがあれば `NPM_CONFIG_USERCONFIG` をそこへ向けるので、設定は `hermes update` をまたいで残ります。リポジトリ直下の `.npmrc` は git の管理下にあって更新のたびに自動で退避されますし、`~/.npmrc` は、デスクトップへの受け渡しが GUI の環境を引き継ぐ都合で見落とされることがあります。自分で設定した `NPM_CONFIG_USERCONFIG` が上書きされることはありません。

**`get-windows` が入っていない、または中途半端に入っている場合:** ビルドはもう失敗しません。`[stage-native-deps] get-windows not installed ... read_window_below will be unavailable in this build` と表示して、`read_window_below` のツールを載せずに出来上がります。パッケージのディレクトリはあるのに読み込めない場合（Hermes のウィンドウが動いたまま Windows でその場の更新が中断されたとき。導入のログに `TAR_ENTRY_ERROR` が出ます）は、同じ警告がそのディレクトリの名前を挙げ、次の `hermes desktop --force-build` か更新が、npm の導入の前にそれを消すので、パッケージは展開し直されます。展開がまた中断されないよう、Hermes のウィンドウとゲートウェイを先に全部閉じてください。ネイティブの結合部や macOS 側の補助が欠けているパッケージも同じように、ビルドを失敗させるのではなく、ウィンドウの列挙なしで出来上がります。

壊れたキャッシュ上の zip を手で消すには、次のようにします。

```bash
rm -f "$HOME/Library/Caches/electron"/electron-*.zip   # macOS
rm -f "$HOME/.cache/electron"/electron-*.zip            # Linux
```

## ソースからビルドする {#building-from-source}

アプリそのものに手を入れたいときは、リポジトリのルートでワークスペースの依存関係を一度入れてから、`apps/desktop` で開発用のサーバーを動かします。

```bash
npm install          # from repo root — links apps/desktop, web, apps/shared
cd apps/desktop
npm run dev          # Vite renderer + Electron, which boots the Python backend
```

特定のチェックアウトを見させたり、実際の設定から切り離したりもできます。

```bash
HERMES_DESKTOP_HERMES_ROOT=/path/to/clone npm run dev
HERMES_HOME=$HOME/.hermes/cache/scratch/throwaway npm run dev
npm run dev:fake-boot   # exercise the startup overlay with deterministic delays
```

インストーラーを作るには、次のようにします。

```bash
npm run dist:mac     # DMG + zip
npm run dist:win     # NSIS + MSI
npm run dist:linux   # AppImage + deb + rpm
npm run pack         # unpacked app under release/ (no installer)
```

macOS と Windows の署名と公証は、必要な資格情報が環境にあれば自動で走ります（macOS は `CSC_LINK` / `CSC_KEY_PASSWORD` / `APPLE_*`、Windows は `WIN_CSC_*` です）。

### macOS の許可とローカルでのビルドし直し（TCC） {#macos-permissions-and-local-rebuilds-tcc}

**フォルダの確認をひとつの設定で全部黙らせられます。** macOS は、Hermes が各フォルダに
触れるたびに種類ごと（デスクトップ、次にダウンロード、次に書類…）に尋ねてきます。
**フルディスクアクセス**を一度与えれば、そのすべてを永続的にまかなえます。しかも
Hermes の署名の身元は安定しているので、更新をまたいでも残ります。

1. システム設定 → **プライバシーとセキュリティ → フルディスクアクセス**（または
   `open "x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles"` を実行）
2. 使っている端末アプリを有効にします。Desktop を使うなら **Hermes.app** も有効にします。
3. どちらも完全に終了してから、一度起動し直します。

`hermes doctor` は、いまの端末の状況にこの許可があるかどうかを教えてくれますし、
`hermes setup` は macOS で許可が無いときにこの案内を出します。

macOS は、許可（フルディスクアクセス、デスクトップ・ダウンロード・書類、
アクセシビリティ、オートメーション、マイク）をアプリの*コード署名の身元*に対して
覚えます。パスに対してではありません。ローカルでビルドしたアプリや自己更新した
アプリは、識別子を固定したアドホックな署名がされるので、許可は更新をまたいで残ります。

一度だけの注意です。識別子を固定する署名の修正（PR #73681）*より前*の
ビルドに与えた許可は、古い cdhash に固定された条件を持っています。macOS はそうした
古い許可のスイッチを ON のまま表示しますが、保存された許可がビルドし直したバイナリと
一致しないので、それでも尋ね直してきます。しかも今の確認画面には「許可」のボタンが無いので、
確かめ直す手立てが無いように見えます。そうなったら、古い許可を一度リセットして
与え直してください。

```bash
tccutil reset ScreenCapture com.nousresearch.hermes   # repeat per service
```

そのうえで、システム設定で新しくできた項目を ON にし、Hermes を完全に終了して
起動し直します。これ以降は安定します。

いちばん確実にしたいなら、証明書に裏づけられた身元を使います。yabai や skhd の
利用者が頼っているのと同じしくみです。自己署名のコード署名証明書を一度作り、
Hermes にそれを使うよう伝えます。次のコマンドひとつで全部やってくれます
（ログインのキーチェーンに証明書を作り、`codesign` からのアクセスを許し、
設定を書き、パッケージ化したアプリに署名し直します）。

```bash
hermes desktop --setup-tcc-identity
```

手で行うなら、次のとおりです。

1. キーチェーンアクセス → 証明書アシスタント → **証明書を作成…**
2. 名前は `Hermes Local Signing`、固有名のタイプは *自己署名ルート*、
   証明書のタイプは **コード署名** にします。
3. キーチェーンアクセスで新しい証明書をダブルクリック → **信頼** →
   **コード署名** を *常に信頼* にします（読み込んだ自己署名の証明書は、コード署名で
   信頼するまで有効な署名の身元になりません。そのあと
   `security find-identity -v -p codesigning` の一覧に出るはずです）。
4. `hermes config set desktop.macos_signing_identity "Hermes Local Signing"`

別の名前の証明書を作ったり使ったりするには、コマンドに `--identity <name>` を
付けます（既定は `Hermes Local Signing` です）。このコマンドは何度実行しても同じ結果に
なるので、更新のあとに走らせて設定を指し直し、ビルドし直したアプリに署名し直せます。

次の更新では、その証明書でビルドし直したアプリに署名がされ、TCC の許可はすべて
残ります。Apple Developer のアカウントは要りません。公証済みのリリースのビルドは
判別され、署名し直されることはありません。

一度だけの注意です。署名の身元を変えると（この修正のあとの最初の更新も含みます）
アプリの身元が一度変わるので、macOS が最後にもう一度だけ尋ねてきます。これ以降は
安定します。許可がおかしくなったときは
`tccutil reset All com.nousresearch.hermes` でリセットして与え直してください。
