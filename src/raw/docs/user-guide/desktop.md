# Hermes Desktop {#hermes-desktop}

Hermes デスクトップアプリは、CLI やゲートウェイと**同じ**エージェントを核にしたネイティブアプリです。設定・API キー・セッション・スキル・メモリはすべて共通です。別のプロダクトや軽量なクローンではなく、同じ Hermes Agent のコアと設定を使い、それを洗練されたデザインの UI から操作します。ターミナルで `hermes` を使ったことがあれば、そこで設定した内容はすでにここにありますし、ここで行ったことはそこにも反映されます。

対応 OS は **macOS(Apple Silicon)、Windows、Linux** です。完全な対応表は [Platform Support](/hermes/docs/getting-started/platform-support/) を参照してください。

:::tip どのインターフェースを使えばいい?
Hermes には同じエージェントと話す複数のフロントエンドがあります。

- **デスクトップアプリ**(このページ) — チャット・設定・管理のために作られたネイティブアプリケーション。
- **CLI**(`hermes`)と **[TUI](/hermes/docs/user-guide/tui/)**(`hermes --tui`) — ターミナルインターフェース。
- **[Web Dashboard](/hermes/docs/user-guide/features/web-dashboard/)**(`hermes dashboard`) — ブラウザの管理パネル。任意の **Chat** タブは疑似端末を介して TUI を埋め込みます。

その場に合ったものを選んでください。状態は共有されるので、片方でセッションを始めて別のもので再開できます。
:::

## 導入 {#install}

[Hermes Desktop のプロダクトページ](https://hermes-agent.nousresearch.com/desktop) からアプリをダウンロードするか、[Hermes Desktop のインストール手順](/hermes/docs/getting-started/installation/) に従ってください。

すでに Hermes をインストールしているなら、次を実行するだけです。

```bash
hermes desktop
```

これで現在の設定・キー・セッション・スキルがそのまま使われます。

## アプリの中身 {#whats-in-the-app}

デスクトップアプリはチャットを中心に、左サイドバーでナビゲーションする構成になっています。複数のエージェントとの会話を同時に管理し、メッセージングプロバイダーを設定し、アーティファクトを作成し、プロジェクトのフォルダ構造を閲覧しながら、複数のプロジェクトを同時に扱えるように作られています。

サイドバーの選択はフォーカスされているチャットペインに従います。セッションタブを開く、あるいはフォーカスすると、ワークスペースがそのページのルートを保持していても、Kanban のような外部提供ページを含め、ページのハイライトはクリアされます。

### チャット {#chat}

アプリの中心です。以下が使えます。

- **ストリーミングレスポンス** — エージェントが作業する様子をライブのツール活動と構造化されたツールコールの要約として表示します。ツールが画像を扱う場合(例: バックエンドのファイルシステム上のファイルに対する `vision_analyze`)、その活動行を展開すると画像が表示され、クリックすると全画面で開けます。リモート接続の場合、画像はアプリを動かしているマシンではなくゲートウェイから取得されます。
- **Markdown の改行** はMarkdownのセマンティクスに従います。末尾のスペース2つはハード改行を作り、通常の改行はソフト改行のままです。メディアとプレビューの抽出は、削除された添付部分の外側にあるテキスト(先頭行のコードインデントや未完成のフェンス付きコードの空白を含む)を保持します。コードの表示とコピーは、Markdown パーサーからの先頭の空行・末尾のスペース・末尾の空行を保持します。
- **他のすべての Hermes 画面と同じ会話履歴** — ここで始めたセッションは CLI/TUI で再開できますし、逆も同様です。
- **ドラッグ&ドロップ** でチャット領域のどこにファイルを落としても、次のメッセージに添付されます。
- **独立したバックグラウンドドラフト** — 非表示のチャットタブは、表示中のコンポーザーのキャレットや選択範囲を動かさずにドラフトを更新できます。
- **未送信ドラフトはセッションが失われても残ります** — もう存在しないセッション(他所で削除された、あるいはプロファイルのリネームやバックエンドの初期化で古くなったタブ)に入力していたドラフトは、アプリがフォールバックする新しいチャットに引き継がれ、入力欄の上に **未送信メッセージを復元しました** という帯がインラインで表示されます。**元に戻す** で元の場所にテキストが戻ります。あなたの代わりに何かが送信されたり、遷移したり、フォーカスされたりすることはなく、この帯は失われたドラフトごとに一度だけ表示されます。
- **ディレクティブチップの操作** — アクション可能な参照(URL など)にホバーするとアクションピルが表示されます。短いグレース期間があり、チップからピルへ移動できます。ピル内で動いている間はピルが表示され続け、離れた後は無関係なポインタの移動で表示終了が遅れることはありません。アクションをクリックしてもドラフトの選択範囲は保持されます。
- **右側のプレビューレール** — チャットを続けながら、Web ページ・ファイル・ツールの出力をサイドバイサイドで表示できます。
- **状態を持つペインの Hide と Close** — Browser(または HTML プレビュー)や Terminal ペインを持つゾーンには、Minimize の代わりに **Hide** が用意されています。Hide するとゾーンは復元レールに縮小されますが、ペインの本体はマウントされたままです。ライブページなら未保存のフォーム入力・タイマー・スクロール位置・エージェントの `drive_preview` の自動操作対象が保持され、ターミナルなら実行中のシェルとスクロールバックが保持されます。**Restore** で同じ内容がリロードなしに表示されます。隠れている本体は不活性で、キーボードショートカットを受け取ったりコンポーザーのフォーカスを奪ったりすることはありません。実際にページやシェルを解放するのは(タブの ×)**Close** です。
- **アプリ内ブラウザのコメントモード** — プレビューブラウザのバーで **Annotate** をクリックし、ライブページ上の任意の要素をクリック(またはドラッグで範囲選択)してメモを入力します。保存されたコメントはページ上の番号付きピンとして残ります。ピンの保存でターンが送信されることはありません。完了したら **Add N comments** でピンごとに切り出したスクリーンショットと、各コメントを示す短いプロンプトがコンポーザーに添付されますが、送信自体は自分で行います。各要素コメントには CSS セレクタ・マークアップ・レイアウトに関わる計算済みスタイルが含まれるため、エージェントは画像から推測するのではなく、ソース内でその要素を見つけられます。パスワードや非表示フィールドの値、キーやトークンらしき属性は、マークアップがページから出る前にすべて redact されます。まとまった量のコメントは、ページのどの部分にあるかでグループ化されて届くため、20 個ほどのコメントが1件ずつのタスクではなく、ひとまとみりの作業に整理されます。グループは別々の DOM サブツリーなので通常は別々のファイルに触れることになり、これが並列のワーカーへ安全に振り分けられる理由です。ピンの番号は1つ削除しても保持され、チャットを切り替えるとスタックはクリアされます。
- **コンポーザーの履歴とキュー編集** — 空のコンポーザーで上下キーを押すと、過去のプロンプトを呼び出して再利用できます。送信前にキューに入れたメッセージも編集できます。ターンがキューされている間に Stop(または Esc)を押すとキューが一時停止してコンポーザーの上に展開表示され、そこから再開したり、個々のエントリを送信・編集・削除できます。
- **コンポーザー上部のタスク進行状況** — Tasks ヘッダーを展開すると各フェーズを確認できます。長いリストは入力欄の上に収まった状態を保ち、展開したリスト内をスクロールすれば会話全体を動かさずに最後のタスクまで見られます。
- **会話タイムラインレール** — 長いチャットでは、トランスクリプトの端に沿ってプロンプト1件につき1マーカーの細いレールが表示されます。ホバーするとプロンプトの一覧がポップアップし、クリックすると会話中のその地点へジャンプします。ジャンプした後、トランスクリプト上部の **Show earlier** で、そのプロンプトからさらにセッションの先頭までページを遡れます。(これはチャットにある程度の量のターンが積み重なると表示されます。)
- **読んでいた位置の記憶** — セッションに戻ると、常に最新メッセージへ飛ぶのではなく、保存されていた最下部からの距離が復元されます。最下部にいたまま離れたセッションは新しい出力に追随を続けます。**Scroll to bottom** で最新の端まで戻れます。この位置情報はこのデスクトップのインストール先のローカルストレージに保持され、バックエンド経由で同期はされません。
- **ページ内検索** — **Cmd/Ctrl+F** で、表示中のチャットトランスクリプトを検索する検索バーを開きます。Enter / Shift+Enter(バーが開いている間は Cmd/Ctrl+G / Cmd/Ctrl+Shift+G も)で一致箇所を移動でき、Esc で閉じます。

非同期の cron と delegation の完了は、折りたたまれたタイムラインの開閉項目として表示されます。完了ラベルを開くと、結果本文(ジョブの出力を含む)を Markdown として読めます。長いレポートはその開閉項目の中でスクロールします。タスクの指示や配送用のエンベロープはレポートの内容として表示されません。

#### ステータスバー {#status-bar}

チャット下部のバーには、ライブのセッション状態が表示され、Settings を開かなくても使えるクイック操作が並びます。

- **セッションごとの YOLO 切り替え** — このセッションだけ YOLO を on/off できます(TUI と同様)。YOLO は危険なコマンドの承認プロンプトを迂回するので、何を off にしているかを理解してから使ってください — [Security → YOLO Mode](/hermes/docs/user-guide/security/#yolo-mode) を参照。
- **コンテキスト使用率メーター** — セッションのコンテキストウィンドウの「使用率」をライブで表示するメーターです。クリックすると **Context Usage** ポップオーバーが開き、カテゴリ別(システムプロンプト・ツール定義・スキル・メモリ・ルール・MCP・サブエージェント定義・会話そのもの)のトークン内訳が見られるので、圧縮が始まる前に何がウィンドウを食っているかを正確に把握できます。
- **キャッシュヒット率と Tokens per second** — 既定では off です。右クリックメニューから on にできます。キャッシュヒット率は、そのセッションのプロンプトトークンのうち、プロバイダーのプロンプトキャッシュから提供された割合です(キャッシュされたトークンは安いので、高いほど安くなります。セッションがウォームアップするにつれて安くなっていく様子を確認できます)。Tokens per second は直近 10 回のモデル呼び出しで平均した出力スループットです。両方ともターン中にライブで更新されます。
- **カスタマイズできる項目** — ステータスバーを右クリック(**Show in status bar**)して、何を表示するかを選べます。コンテキストメーター・キャッシュヒット率・Tokens per second・ワークスペース・モデル・承認・ターン/セッションのタイマー・ターミナル・Command Center・バックエンドのバージョンなど、あるいはバーそのものを隠すこともできます(**Cmd/Ctrl+Shift+S** で切り替え)。ワークスペース項目のメニューにある **Open containing folder** は、フォーカス中のセッションがこのコンピュータ上で動いているときだけ使えます。リモートのゲートウェイ上のセッションはそのフォルダを別マシンに持っているので、代わりに **Reveal in filetree** を使ってください。OS のファイルマネージャがパスを見つけられない場合、アプリは何もしない代わりにその旨を伝えます。

別マシン上の Hermes インスタンスに、バンドルされているローカルバックエンドの代わりに接続していますか? 下の [リモートバックエンドへの接続](#connecting-to-a-remote-backend) を参照してください。リモートホストのダッシュボード接続がどう動くか(認証ゲート、`/api/ws` チャットソケット、WebSocket のクローズコードの切り分け)の全体像は [Web Dashboard → Connecting Hermes Desktop to a remote backend](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend) を参照してください。

#### フォント {#fonts}

**Settings → Appearance** には独立した2つのフォント設定があり、いずれもプロファイルごとに `config.yaml` に保存されます。

- **Chat Font**(`desktop.font_family`) — チャットとアプリの残りの UI 用です。OpenDyslexic や Atkinson Hyperlegible のような読みやすさ重視のフォントは、システムにインストールされていればそのまま使えます。アクティブなテーマのフォントスタックは選んだフォントの背後に残るので、欠けているグリフがあってもそこは表示されます。空欄はテーマのフォントを意味します。
- **Terminal Font**(`terminal.font_family`) — 組み込みのターミナルペイン用です。Nerd Fonts を使うとここでシェルのアイコンが表示されます。空欄は同梱の JetBrains Mono を意味します。

#### リポジトリの検出 {#repository-discovery}

Hermes Desktop は、ホームディレクトリを一定の深さまでスキャンして、Projects サイドバー用にローカルの Git リポジトリを検出します。これはプロファイルごとに **Settings → Workspace** で、または `config.yaml` で変更できます。

```yaml
desktop:
  repo_scan_enabled: true
  repo_scan_roots: []
  repo_scan_exclude_paths: []
```

- `repo_scan_enabled: false` にすると、ファイルシステムのスキャンを完全に止めます。そのプロファイルの既存のディスク検出キャッシュ行は消去されますが、明示的に追加したプロジェクトや、意図的な Hermes セッションから推測されたリポジトリは引き続き利用できます。
- `repo_scan_roots` にフォルダのリストを設定すると、スキャン対象を絞れます。空リストは既定のホームディレクトリスキャンを維持します。
- `repo_scan_exclude_paths` には、サブツリー全体をスキップしたいフォルダを設定します。

これらの値のいずれかを変更すると、そのプロファイルのディスク検出キャッシュだけが無効化され、方針に沿った再スキャンが始まります。**Hide from sidebar** は個別項目ごとの整理操作として別に残ります。

**Group by → Projects** では、各プロジェクトの行に直近3件のセッションがプレビューされます。それより多いプロジェクトは **Show all N sessions** 行で終わり、これをクリックするとその場で残りが展開されます。サイドバーのメニューにある **Show all sessions** トグルは、全プロジェクトのプレビュー件数の上限を一括で解除します。

#### モデルの選択 {#choosing-a-model}

モデルピッカーは**コンポーザー**内、マイクの左にあります。クリックするとモデルを切り替えられます。モデルの行にホバーするとそのオプション(thinking、effort、fast)が見られます。その隣の **reasoning pill** はアクティブなモデルの effort レベル(`Med`、`High` など)を表示し、クリックすると同じオプションが直接開くので、モデルの行を探さずに effort を変更できます。このピルは、カタログが reasoning の制御を持たないと報告するモデルでは表示されません。ルートが Hermes 内部のステップをクランプする場合(`ultra` はそのルートの最強レベル、例えば `max` として送られます)、ピルは両端(`Ultra→Max`)を表示し、そのツールチップは CLI と同じ文言 `Ultra (sends Max on this route)` を示すので、見えているレベルがそのまま送られるレベルになります。ゲートウェイが切り替えをリスクありとフラグ付けした場合(大きなキャッシュ済みコンテキスト、高価なモデル、データトレーニング階層)、アプリはまずダイアログで確認します。**Switch anyway** で適用し、**Keep current model**(または Esc)ですべてを元のままにします。

**マイク** はディクテーション用です。ホバーすると他の音声トグルが上に展開表示されます — **Read replies aloud** と wake word の耳アイコンです。オンになっているトグルはソリッドの円盤として表示されます。フルの音声会話を開始する操作は、右側のメインボタンのままです。HUD と幅の狭いタイルでは、同じ操作がマイクの裏の1つのメニューにまとめられます。ディクテーションが音声認識(speech-to-text)プロバイダーに直接話す場合(client-direct voice)、そのリクエストはゲートウェイ自身の transcription クライアントと同じ `stt.openai.timeout` の予算(既定 60 秒)に従うので、遅いエンドポイントはマイクが transcribing のまま固まる代わりに「Transcription timed out」で失敗します。

- **コンポーザーのピッカーは粘着性のある UI 状態で、既定値には一切触れません。** ローカル(デバイスごと)に記憶され、新しいチャットや再起動をまたいで**引き継がれ**、既定値に戻ることはありません。一度モデルを選べば、次の `Cmd/Ctrl+N` はそのモデルで開きます。ライブチャットの状態でモデルを切り替えると、変更はその**現在のチャット**に限定されます。どちらの場合も、その選択はセッション作成/切り替えのタイミングで引き継がれ、プロファイルの既定値には**決して**書き込まれません。ただし1つ例外があります。`model.default`/`model.provider` がまだ設定されていない新規プロファイルでは、最初の選択が保存され、再起動時にたまたま残っている API キーの環境変数へ落ち込む代わりに、アプリが実在する既定値を持てるようになります。この永続化は `/model` と同じ規則(`model.persist_switch_by_default`)に従います。既定値を意図的に変えるには **Settings → Model** を使ってください。([プロファイル](#sessions--profiles) を切り替えると、そのプロファイル自身の既定値に再設定されます。)
- **既定値は Settings → Model で設定します。** その「main」モデルはあなたの**プロファイルごとのグローバル既定値**であり、新しいチャット・cron・サブエージェント・補助タスクの起点になり、それを書き込む唯一の場所です。[プロファイル](#sessions--profiles) はそれぞれ自分の既定値を保持します。
- **モデルごとの effort/fast プリセット。** 各モデルは、デスクトップアプリの中で自分の reasoning effort と fast モードの選択を記憶しており、そのモデルを選ぶたびにセッションへ再適用されます。これらのプリセットはデスクトップ側の便宜であり、cron やサブエージェントを変えるものではありません。
- **チャット中のモデル切り替えはプロンプトキャッシュをリセットします。** ライブチャットの中でモデルを切り替えると、次のメッセージは会話全体をフル入力価格で読み直すことになります(プロバイダーのプロンプトキャッシュはモデルに紐づくため)。時々であれば問題ありませんが、長いチャットでは、あちこち切り替えるより新モデルで新しいチャットを始めるほうが安く済むことがよくあります。

### ファイルブラウザ {#file-browser}

アプリを離れずに作業ディレクトリを閲覧・プレビューできます。エージェントがファイルを読み書き・編集する様子を追うのに便利です。初期のプロジェクトディレクトリは `hermes desktop --cwd <path>`(または `HERMES_DESKTOP_CWD` 環境変数)で設定します。

### アーティファクト {#artifacts}

コンポーザーの上に出るプレビューリンクはそのセッションの提案であって、タスク完了のチェックリストではありません。1つ消しても、以後の履歴上のツール行がその提案を再び出すことはありません。新しく成功したツールの完了は、再度そのファイルを提案することがあります。読み取りのみのファイル検査と失敗した書き込みは提案を作りません。同じ名前のファイルは、区別できるだけのディレクトリ情報とともに表示されます。提案を消してもファイルやトランスクリプトが削除されるわけではありません。`/goal` の変更は会話のアーティファクトを消しません。

リモートゲートウェイに接続している場合、ファイルのアーティファクトを開くと、そのアーティファクトの発生元のプロファイルとセッションを使って、そのゲートウェイ経由でダウンロードされます。相対パスはセッションに保存された作業ディレクトリを基準に解決され、ホーム相対パスはデスクトップマシンのホームではなく、ゲートウェイのホームを使います。Windows 形式の相対パスはスラッシュ区切りのパスと並んで認識され、ファイル URI はゲートウェイが解釈できるようドライブとネットワーク共有の情報を保持します。セッションや作業ディレクトリが見つからない場合は、別のローカルファイルを選ぶのではなくエラーになります。

**Artifacts** ビューは、セッションが生成したもの — **画像・ファイル・リンク** — を1つの検索・閲覧可能なギャラリーに集めます。サイドバー、コマンドパレット(**Artifacts — Browse generated outputs**)、または自分で割り当てた `nav.artifacts` ショートカットから開けます。直近のセッションの出力を自動的にインデックスし、各アーティファクトはそれを生成したセッションと、そのチャットへ戻るジャンプリンクを表示します。画像とファイルはプレビューで開き、ダウンロード / ブラウザで開く / コピーの操作ができます。

### ウィンドウ、タブ、ペイン {#windows-tabs-panes}

このアプリは複数のことを同時に進める前提で作られています。

- **タブ** — **Cmd/Ctrl+T** で新しいセッションタブを開きます。**Ctrl+Tab** / **Ctrl+Shift+Tab** でセッションを巡回し、**Ctrl+1…9** で位置指定で直近のセッションへジャンプします。**Cmd/Ctrl+W** はフォーカス中のタブを閉じ、**Cmd/Ctrl+Shift+T** は最後に閉じたタブを再度開きます。
- **複数ウィンドウ** — **Cmd/Ctrl+Shift+N** で新しいウィンドウを開きます。任意のセッションはそのコンテキストメニュー(**New window**)またはコマンドパレットからポップアウトできます。ポップアウトされたウィンドウは、グローバルサイドバーなしにその1つのチャットだけを表示します。長時間動くセッションを別モニターに置いておくのに便利です。ライブのエージェント出力は、そのセッションを表示しているすべてのウィンドウにストリームされます。
- **ペイン** — **Cmd/Ctrl+B** で左サイドバー、**Cmd/Ctrl+J** で右サイドバーを切り替え、**Cmd/Ctrl+\\** でサイドバーがどちら側に座るかを入れ替えます。

#### トレイに最小化 {#minimize-to-tray}

**Settings → Appearance → Window layout → Minimize to tray** を有効にすると、最小化したウィンドウはタスクバーや Dock から隠れますが、セッションはそのまま動き続けます。この設定は既定で off で、このデバイスにのみ適用されます。

この設定を有効にし、トレイが利用可能な状態で、**X** や **Alt+F4** でメインウィンドウを閉じると、Hermes を止めたりセッションを破棄したりせずにウィンドウだけが隠れます。セカンダリウィンドウを閉じる場合は、そのままそのウィンドウが閉じます。隠れたウィンドウを復元するには、システムトレイ(macOS ではメニューバー)の **Show Hermes** を使います。トレイメニューの **Quit Hermes** と **Cmd+Q** は通常どおり終了し、通常のアクティブ作業の確認も行われます。トレイが利用できない場合、メインウィンドウを閉じる操作は通常の挙動になります。

macOS では、通常の Hermes ウィンドウが1つも残っていないときだけ Dock アイコンが隠れます。Linux では、登録済みの StatusNotifier トレイホストが必要です。それを持たないデスクトップ環境では通常の最小化動作が維持されます。ホストが消えた場合、隠れていたウィンドウは復元されます。

### ターミナル {#terminal}

右サイドバーには、ファイルブラウザの隣に実物のターミナルがあります。

- **Ctrl+`** でターミナルを表示します(存在しなければ新規に開きます)。**Ctrl+Shift+`** で追加のターミナルを生成します。複数のターミナルはタブレールに積み重なり、**Ctrl+Shift+↓/↑** で移動、**Ctrl+Shift+W** でアクティブなものを閉じます。
- **シェルは非表示の間も生き続けます。** パネルを閉じても隠しても、シェルが終了することはありません。開いているターミナルはすべて、明示的に閉じるまでスクロールバックと実行中のプロセスを保ったままマウントされ続けます。
- **Add to chat** — ターミナルの出力を選択して、次のメッセージのコンテキストとしてコンポーザーへ送れます。

### ライブサブエージェント {#live-subagents}

委任先のワーカーが動いている間、コンポーザーの上に **Subagents** フレームが現れ、件数・タスク名・経過時間・最新の活動が表示されます。最大3件までのワーカーがプレビューされます。ヘッダーを展開すると全ワーカーの一覧になり、ワーカーを選ぶと詳細と **Steer** / **Stop** の操作が見られます。各フレームはそのチャットに属し、分割ペインでも同様です。Steer は、その指示がチェックポイントに向けてキューされたことを認めるものであり、子がすでにそれを読んだことを意味しません。[Monitoring subagents](/hermes/docs/user-guide/features/delegation/#monitoring-running-subagents-agents) を参照してください。

### Git のレビューとワークツリー {#git-review-worktrees}

Git リポジトリの中で動いているセッションでは、アプリに組み込みのソースコントロール画面があります。

- **Review pane** — **Cmd/Ctrl+G** で作業ツリーのレビューペインを切り替えます。ブランチと ahead/behind の状態、変更されたファイル(リストまたはツリー表示)、そして **Uncommitted**、**Branch**、**Last turn**(エージェントが直前のターンで変更した内容だけ)の範囲に絞った diff が見られます。ファイルの Stage/unstage、変更の revert、コミットメッセージの記述(または **Generate commit message**)を行い、**Commit** または **Commit & Push** し、GitHub CLI(`gh`)経由で **Create PR** するか、**Ask Hermes to open PR** でその一式をエージェントに任せられます。ここからブランチの作成と切り替えもできます。
- **Worktrees** — **Cmd/Ctrl+Shift+B**(またはサイドバーのプロジェクト上の **New worktree**)で、新しいブランチ上に Git worktree を作成し、チェックアウトに触れずにエージェントがリポジトリの並行コピーで作業できるようにします。ワークツリーはプロジェクトの下に自分のレーンとして表示されます。1つを削除するとき、ワークツリーディレクトリを削除する(ブランチは残る)か、レーンを隠してディスク上には残しておくかを選べます。未コミットの変更がある場合は force オプションもあります。

### メモリグラフ {#memory-graph}

**Memory Graph**(コマンドパレット → *Memory Graph*、またはステータスバーの項目)は、Hermes があなたのために学んだことのインタラクティブな地図です。スキルとメモリがズーム可能なノードグラフとタイムラインで配置され、**All / Used / Learned** で絞り込めます。共有機能は、地図のレイアウトをコンパクトなコードとして書き出し(レイアウトのみ — メモリやスキルの本文は含まれません)、他の人に渡せます。コードは同じ方法で取り込めます。

### Quick Entry {#quick-entry}

Quick Entry は、**システムのどこからでも呼び出せるグローバルホットキー** で呼び出す、常に使える小さなコンポーザーです。メインウィンドウに切り替えたり(あるいは開いたりすらせずに)、プロンプトを送れます。**Settings → Advanced → Quick Entry** で有効にします。既定のショートカットは **Ctrl/Cmd+Shift+Space** で、自分で設定することもできます(修飾キーが最低1つ必要です)。すでに別のアプリがそのキーの組み合わせを使っている場合、設定の行がその旨を伝えるので、別のキーを選べます。

### 音声 {#voice}

Hermes と話し、返事を聞けます。他の画面でも使える同じ [voice mode](/hermes/docs/user-guide/features/voice-mode/) です。macOS では OS がマイクアクセスを一度だけ確認します。

### HUD モード {#hud-mode}

**⌘/Ctrl+Shift+H**(またはタイトルバーのボタン)は、チャットを、いま作業している画面の上に浮かぶ、クロームのない常時最前面のフロートバーへ切り離します。アプリのウィンドウは脇へ退き、HUD はライブの会話とコンポーザーを保持します。それをどこに置くかがコンテキストです。バーの位置が、あなたがどのアプリ・どの画面について尋ねているかを Hermes に伝えるので、「これ」「ここ」「そのページ」はその下にあるものを指すことになります。

- **バーの移動** — macOS と Windows では、コンポーザーの上のどこかを一瞬押し続けてからドラッグします。Linux/X11 では **Ctrl** を押しながらメインマウスボタンでドラッグすると即座につかめます(選択中のテキストの上でも可)。押し続ける方法もそのまま使えます。デスクトップ切り替えのショートカットを実行する間もつかんだ状態を保つと、HUD を別の仮想デスクトップへ持って行けます。ネイティブ Wayland では、コンポーザーバーはコンポジタのドラッグハンドルです(アプリが自分でウィンドウを配置できないための唯一の移動手段です)。
- **リサイズ** — バーの任意の辺または角をドラッグします。反対側の辺は固定されたままです。ネイティブ Wayland では右辺と下辺だけが露出しています。コンポジタがアプリ自身にトップレベルウィンドウの位置決めを許していないためです。
- **レイアウトのリセット** — バー上の discard 操作で、既定のサイズと(X11 / macOS / Windows では)位置が復元されます。保存されていたサイズのせいで HUD が使えなくなったときに使ってください。
- **タップで呼び出す** — **Settings → Keyboard Shortcuts → HUD gesture** の下で **Tap to summon HUD** を有効にし、macOS では **⌘+Option**、Windows/Linux X11 では **Ctrl+Alt** をタップして離します。他のキーやマウス操作を挟まずに、両方のキーを 0.5 秒以内に離してください。Windows では左 Alt を使います。右 Alt は AltGr レイアウト用に予約されています。この操作は別のアプリから HUD を開く/フォーカスするものであり、閉じたり、録音を始めたり、メッセージを送ったりはしません。既定で off で、このデバイスにのみ保存されます。macOS では Input Monitoring の権限が必要です。ページは、権限やその他のエラーへの対応が必要なときだけリカバリ操作を提示します。Linux Wayland ではこのジェスチャーは使えないので、そこでは引き続きアプリ内の HUD ショートカットを使ってください。
- **ポインタへスナップ** — **⌘/Ctrl+Shift+G**(どのアプリからでも動くグローバルホットキー)で、HUD をカーソルのある場所へジャンプさせます。ネイティブ Wayland ではこれは無効です。配置はコンポジタが握っています。
- **終了** — バー上の終了ボタンをクリックするか、**⌘/Ctrl+Shift+H** を再度押すか、HUD がフォーカスされている間に **⌘/Ctrl+W** を押します。アプリのウィンドウが、セッションとコンポーザー内のキャレットとともに前面へ戻ります。

#### Linux / Wayland {#linux-wayland}

Electron 20 以降は、Wayland セッション上ではすでにネイティブの Wayland クライアントとして動きます。ドラッグ、クリックスルー、リサイズはそのパス上で動作します。

**Hyprland**(Omarchy を含む)では、HUD はマップされた後にコンポジタの IPC 経由でフロート・ピン留めされます。そうしないと Hyprland は他のウィンドウと同様にこれをタイルしてしまい、`always-on-top` は無視され、コンポジタのドラッグは何も起こしません。追加のウィンドウルールは不要です。

一部のコンポジタ(特に COSMIC)は、ネイティブ Wayland ウィンドウの `always-on-top` を無視します。そこでピン留めを復元するには、アプリを XWayland 下で実行してください。

```yaml
desktop:
  ozone_platform_hint: x11
```

これは起動時に `ELECTRON_OZONE_PLATFORM_HINT` へブリッジされます(明示的な env var が設定されていればそちらが優先されます)。トレードオフは、X11 はマウスを無視した状態のウィンドウを復元できないので、HUD はクリックスルーではなく実体のあるウィンドウのままになる、という点です。一部の KDE 環境では X11 ozone バックエンドでキーボードの不具合も報告されているので、always-on-top が必要な場合を除き、ヒントは `auto` のままにしておいてください。

#### WSLg(WSL2 上での Windows GPU) {#wslg-windows-gpu-from-wsl2}

ローカルの WSLg 下では、Hermes は `--ozone-platform=wayland` で起動し、XWayland の最大化ウィンドウのオフセットとマウスのヒットテストのずれを避けます([microsoft/wslg#1015](https://github.com/microsoft/wslg/issues/1015))。このプラットフォームは、Electron がアプリケーションの JavaScript を読み込む前の、プロセス起動時に選択する必要があります。明示的な `--ozone-platform=x11` と `desktop.ozone_platform_hint: x11` はそのまま使えます。アプリは WSLg 上で自前の最小化・最大化・閉じるコントロールを描画します。

`hermes gui` が `/dev/dxg` の存在と Mesa の `d3d12_dri.so` のインストールを検知した状態で WSL2 内で動く場合、ランチャーは Electron 用に `GALLIUM_DRIVER=d3d12` を設定し、レンダリングが llvmpipe のソフトウェアラスタライザではなく Windows の GPU を使うようにします。環境変数 `GALLIUM_DRIVER`、`MESA_LOADER_DRIVER_OVERRIDE`、`LIBGL_ALWAYS_SOFTWARE`、`LIBGL_DRIVERS_PATH` を自分で明示的に設定している場合はそのまま変更されません(たとえば `GALLIUM_DRIVER=llvmpipe hermes gui` はソフトウェアレンダリングのままです)。

#### 起動フラグとレンダラーのヒープ上限 {#launch-flags-and-the-renderer-heap-ceiling}

2つの `desktop.*` キーは、`hermes desktop`・スタートメニューのショートカット・Linux の `.desktop` エントリのいずれの経路でも、起動時に Chromium へ渡されます(アプリは最初のウィンドウを開く前に `config.yaml` からこれらを読みます)。

```yaml
desktop:
  electron_flags: ["--ozone-platform=x11"]   # extra Chromium switches; a single string is split on spaces
  renderer_max_old_space_mb: 2048            # V8 heap ceiling for the chat renderer; 0 = Chromium default
```

`renderer_max_old_space_mb` は `--js-flags=--max-old-space-size=N` として適用され、すでに渡している `--js-flags` とマージされるので、どちらも上書きされません。とても長くツールを多用するセッションが、マシンが割ける以上にレンダラーを走らせてしまうときに設定してください。そうすればレンダラーはマシン全体をフリーズさせる代わりに、自身の上限に達してリロードします(1分あたり3回までのリロードに制限されます)。

両方のキーは、示したとおり正確に書く必要があります。トップレベルの `desktop:` キーの下に2スペースのインデント、ブロックリストの `-` の前に4スペースです。

```yaml
desktop:
  electron_flags:
    - "--ozone-platform=x11"
    - "--js-flags=--expose-gc"
```

起動前のこの読み取り処理は、Hermes の他の部分が使う完全なパーサーではなく、小さな YAML サブセットです。アプリが何かを読み込む前に動く必要があるためです。他のインデントも有効な YAML ではありますが、ここでは無視されます。そうなった場合、アプリは起動時に `desktop.electron_flags / desktop.renderer_max_old_space_mb were ignored` とログに出し、Chromium の既定値で起動します。

### 設定とオンボーディング {#settings-onboarding}

YAML を編集する代わりに、実際の UI からプロバイダー・モデル・ツール・認証情報を管理できます。初回起動のオンボーディングは、数秒で最初のメッセージまで案内します。設定のペインは、プロバイダー/キー、モデル選択、ツールセットの設定、MCP サーバー、ゲートウェイ、セッション管理をカバーします。

- **Providers 設定ペイン** — 推論プロバイダーを管理する専用の場所で、プロバイダーごとにサインインし認証情報を保存するための Accounts / API-keys の UX があります。Accounts、API keys、Custom Endpoints は Settings の **Applies to** 選択を共有します。認証情報の読み取りと編集、OAuth アカウントの削除、custom endpoint の保存/テスト、ここで開始したサインインは、アクティブなチャットプロファイルではなく選択されたプロファイルを対象にします。サインインのフローは、認証情報の保存とモデル選択を通じてその対象を保持します。**Applies to** を変更すると、未保存の認証情報のドラフトは破棄されます。サインインを閉じるとポーリングはキャンセルされ、遅れて届いた結果は無視されますが、すでに送信済みの認証情報の書き込みは元のプロファイルで完了することがあります。外部で管理される CLI の認証情報は、その CLI 自身が持つもので、このプロファイルセレクタの対象外です。その **Local Models** ビューは、オンデバイスの llama.cpp ランタイムをインストール・管理します — [Local Models](/hermes/docs/user-guide/local-models/) を参照。
- **メニューにあるすべてのプロバイダーとモデル** — GUI は `hermes model` が知っているプロバイダーの全リストとすべてのモデルを表示するので、絞り込まれた一部ではなく CLI と同じカタログから選べます。
- **API モードを持つ Custom endpoints** — **Settings → Providers → Custom Endpoints** には **API Mode** セレクタ(**Auto-detect**、**Chat Completions**、**Responses API**、**Anthropic Messages**)があり、これは `hermes model` がカスタムプロバイダーに対して提供する選択と同じものです。これは `config.yaml` の `providers.<id>.api_mode` として保存されるので、Responses のみ、または Anthropic 互換のホストが `/chat/completions` を呼び出されなくなります。**Test** は `/v1/models` だけでなく、実際に使うトランスポートを確認します。ピン留めされたモードのルート(または Auto-detect が解決するモード)へ1トークンのリクエストを送り、そのホストがそのトランスポートを提供していない場合はトランスポート名を挙げて失敗します。**Test** は、ゲートウェイが `/v1/models` で広告する alias のメタデータ(`canonical_model`、`reasoning_effort`)も保持します。`gpt-5.6-sol-high` のような alias を選ぶと、canonical モデルが保存され、その effort が `agent.reasoning_overrides` の下にピン留めされます。
- **xAI Grok OAuth** — Grok はランチャーの中で第一級の OAuth プロバイダーです。他の OAuth プロバイダーと同じようにブラウザ経由のフローでサインインします。
- **GUI からのツールバックエンドのインストール** — ターミナルに落ちずに、アプリから直接ツールバックエンドのセットアップ後のインストール手順を実行できます。ターミナルバックエンドのピッカーで **Needs setup** と表示されているバックエンドを選ぶと、まず確認を求められます。断ると現在のバックエンドが選ばれたままになります。
- **ターミナルフォントピッカー** — **Settings → Appearance** でインストール済みのフォントを選べます。`MesloLGS NF` のような Nerd Fonts は、対話用とエージェント用のどちらのターミナルでも Powerlevel10k のセパレータとアイコンを表示します。この設定はプロファイルごとに保存されます。
- **Reasoning Blocks** — **Settings → Chat → Reasoning Blocks**(`config.yaml` の `display.show_reasoning`)は、トランスクリプト内のモデルの思考を表示するか隠すかを決めます(off にすると回答だけが表示されます)。開いているチャットは、設定が保存された時点で更新されます。コンポーザーで `/reasoning hide` または `/reasoning show` と入力すると同じ設定が切り替わり、開いているトランスクリプトも即座に追随します。
- **Reopen Last Chat on Launch** — 既定では、アプリはコールドスタート時にやりかけの状態から再開します。**Settings → Appearance** で off にする(または `config.yaml` に `display.resume_last_session: false` を設定する)と、常に新しいチャットから始まります。ディープリンクと明示的な行き先は、どちらの設定でも上書きされません。
- **補助モデルの警告** — メインモデルを新しいプロバイダーに切り替えたのに、補助タスク(タイトル付け、要約など)がまだ別のプロバイダーに固定されている場合、アプリはその旨を警告します。知らないうちに作業を2つのプロバイダーに分割してしまわないようにするためです。
- **タスクごとの reasoning effort** — **Settings → Model → Auxiliary models** の各行には、プロバイダー/モデルの選択の隣に reasoning セレクタがあります。レベル、**Off**、または(既定で、そのタスクの上書きを取り除く)**inherit · main model effort** です。これは `config.yaml` の `auxiliary.<task>.reasoning_effort` として保存されます。`hermes model` が書き込むのと同じキーで、設定されているとその行の概要に表示されます。圧縮やタイトル付けのような頻繁に呼ばれる補助処理を低い、あるいは reasoning なしで動かし、メインエージェントは高いままにしておくのに使います。
- **VS Code Marketplace のテーマ** — 組み込みのテーマプリセットに加えて、appearance の設定にはライブの VS Code Marketplace 検索があります。任意のカラーテーマを選ぶと、アプリがそれをダウンロード・変換し、デスクトップテーマとしてインストールします。同じインポーターはコマンドパレット(*Install theme*)からも使えて、インポートしたテーマは appearance の設定から再び削除できます。
- **コンピュータを起こしたままにする** — **Settings → Advanced → Keep computer awake** は、長時間または夜間のエージェント実行が続くようにマシンがスリープしないようにします(画面は暗くなることがあります)。これはコンピュータごとの設定です。

初回起動時のオンボーディングは、統一されたオーバーレイのデザインシステムで作り直されており、**Choose provider later** を選ぶとプロバイダーの設定を後回しにして、まずアプリに入れます。

#### プロファイルごとの設定: 「Applies to」の範囲 {#per-profile-settings-the-applies-to-scope}

[プロファイル](/hermes/docs/user-guide/profiles/) を2つ以上持っている場合、設定バックエンドの各ページ — **Model、Workspace、Safety、Memory & Context、Voice、Chat、Advanced、Tools & Keys** — と、**Providers → Custom Endpoints**、そして **Messaging** オーバーレイの上部に、共有の **Applies to** チップ行が表示されます。これは、編集対象がどのプロファイルになるかを選ぶものです。

- 既定の選択は**アクティブなプロファイルに従い**、これまでと同じように振る舞います。つまり使っているプロファイルを編集します。
- 別のプロファイルを選ぶと、アプリ全体を切り替えずに*そのプロファイル*の設定を見たり編集したりできます。この選択は設定ページを移動しても保持されます。
- アプリのアクティブなプロファイルを切り替えると、このセレクタはリセットされます。編集内容が以前選んでいたプロファイルへ静かに反映され続けることはありません。
- プロファイルが1つしかない場合、チップ行は完全に隠れます。

(Gateways ページはプロファイルの扱いが異なり、**Per-profile overrides** サブセクションを介します。Capabilities と Scheduled Jobs のビューには、それぞれ独自のスコープセレクタがあります。)

### 管理用ペイン {#management-panes}

アプリは、ターミナルに落ちなくてもいいように、より広い Hermes の管理面も表示します。

- **Skills** — [skills](/hermes/docs/user-guide/features/skills/) を閲覧・インストール・管理します。Skills タブは、有効/無効のトグル付きでインストール済みのスキルを一覧表示し、その下に Hermes に同梱されている組み込みのオプションスキルのカタログ全体が並びます。各エントリにはワンクリックの **Install** ボタンがあり、完了するとその行がインストール済みリストへ切り替わります。
- **Memory graph(Star Map)** — チャットで `/journey`(別名 `/learning`、`/memory-graph`)と入力すると、学習したスキルとメモリの時系列のインタラクティブな星座図が開き、再生スクラバーも使えます。ノードはそのパネルから直接編集・削除できます(スキルはアーカイブされ、メモリは削除されます)。[Learning Journey](/hermes/docs/user-guide/features/memory/#learning-journey-journey) を参照。
- **Cron** — [scheduled jobs](/hermes/docs/reference/cli-commands/#hermes-cron) を表示・管理します。**All profiles** を on にすると、一覧はすべてのプロファイルのジョブを集約します。ジョブの実行履歴と操作(pause、resume、edit、delete)は、どのプロファイルがアクティブかにかかわらず、そのジョブを所有するプロファイルへ常に向かいます。
- **Profiles** — [Hermes プロファイル](/hermes/docs/user-guide/profiles/)(独立した設定/スキル/セッション)を切り替えます。
- **Messaging** — ゲートウェイのチャンネルを設定します。Telegram には **Quick setup** カードがあります。**Create with QR** をクリックし、Telegram でコードをスキャン(またはリンクを開く)すると、Hermes がボットを作成し、allowlist 用にあなたのユーザー ID を検出し、認証情報を保存して、ゲートウェイを再起動してくれます。認証情報の保存・クリア・有効化トグルはいずれも、ゲートウェイが実際に再起動するまでページに **Restart now** の帯を残します。再起動に失敗した場合もこの帯は残るので、再試行や手動での再起動ができます。
- **Agents** と **Command Center** — マルチエージェントの作業のためのオーケストレーション画面です。

### Bot Mode(組み込み) {#bot-mode-built-in}

**Bot Mode** はアプリに同梱されており既定で on です。各 [Hermes プロファイル](/hermes/docs/user-guide/profiles/) が、それぞれのアバター(ジオメトリックな顔、アップロードした画像、AI 生成のポートレート、あるいはピクセルペット)、それぞれの正規の **Bot Chat** 会話、それぞれの **Routines**(Hermes cron が支える定期タスク)を持つ1つのボットとして並ぶ「エージェント1体につきチャット1つ」の名簿です。この名簿は左サイドバーに、会話の下に積んだ2番目のペインとしてではなく、会話の隣にある1本のタブとして — **Sessions | Bots** タブの帯として — 収まっています。以前の積み重ね式レイアウトを使っていたインストールは、1度だけ自動的にタブ帯へ移行します。手動でペインを配置していた場合、そのレイアウトはそのままにされます。**Cronjobs**(Routines)ペインは Bots タブがアクティブな間だけチャットの横にドッキングし、Sessions に切り替えると消えます(旧いデスクトップビルドでは常に表示されたままです)。

名簿から新しいエージェントを作成できます — Name / Title / Description に加え、フルの capability 一式(モデル、SOUL、スキル、ツールセット、MCP サーバー)を持つ Advanced の開閉パネルです。それらをセクションにグループ化したり、複数のボットが議論するグループチャットを開いたりできます。グループチャットは名簿の中で Discord 風の独立した行として表示されます — 重なったメンバーのアバター、メンバー数、直近のルームの発言のプレビュー、「needs you」バッジがあり、ボットの行と同じ pin+recency の順序で混在します。グループ行をクリックすると、そのルームが**メインのチャットウィンドウ**を占有するタブとして開きます(旧いデスクトップビルドでは代わりに bots サイドパネルの中で開きます)。

ボットは互いにメッセージをやり取りします。どのチャットでも `@researcher have a look at this` と入力すると、アクティブなボットがそのメッセージを引き渡して結果を報告してくれますし、ボットは互いの Bot Chat に直接届きます(`hermes -p <bot> chat`)。バックエンドは、各ボットの正規の **Bot Chat** セッションにメッセージングプロトコルを自動的に教えます(設定 `agent.bot_mode_protocol`、既定 on)。これはチームメイトのボットが CLI からヘッドレスにそれを開いた場合も含むので、ボット同士の返信や引き渡しは SOUL.md に触れずに動作し、あなたの通常のセッションはそのまま影響を受けません。

Bot Mode のセッション — 各ボットの正規の Bot Chat と、グループチャットの各メンバーセッション — は、常にグローバルの Sessions サイドバーから隠されます。これらは(名簿の行、ルームビュー、各ボットのセッションブラウザといった)Bots ペインの中に住み、あなた自身の会話と混じることはありません。

使わないボットはしまっておけます。ボットの行を右クリック → **Hide Bot**。隠れたボットは名簿から消えますが動き続けます。@mention は引き続き解決され、グループチャットのメンバーシップも変わりません。少なくとも1つのボットが隠れている間、Bots ヘッダーに eye トグルが現れます。クリックすると隠れたボットがその場に薄く表示され(右クリック → **Unhide Bot** で1体を元に戻せます)、隠れたボットに未読の活動があるとその eye にドットが表示されます。隠れているという状態はそのボットのプロファイルに保存されるので、マシンをまたいでボットに付いてきます。

使いたくない場合は、**Capabilities → Plugins → Bots** で **Desktop** スイッチを off にしてください。名簿、routines ペイン、コンポーザーのミドルウェアはその場で登録解除され、再起動は不要です。

エージェントの作成(複数マシンをまたぐ **Create on** ピッカーを含む)、接続をまたいだ名簿、ボット同士のメンション、グループチャットが誰に返信させるかを決める仕組みについての完全なガイドは [Bot Mode: A Roster of Agents](/hermes/docs/user-guide/bot-mode/) にあります。

### キーボードとナビゲーション {#keyboard-navigation}

- **コマンドパレット** — **Cmd+K** または **Cmd+P**(Windows/Linux では Ctrl+K / Ctrl+P)を押すと、キーボードから操作やアプリ内のナビゲーションへジャンプできます。任意のページや設定セクションを開く、タイトルや ID でセッションへジャンプする、モデル/テーマ/カラーモードを切り替える、ターミナルを起動する、ゲートウェイを再起動する、Hermes を更新するなどが行えます。
- **リバインド可能なショートカット** — **Settings → Keyboard Shortcuts**(または **Cmd/Ctrl+/**)でショートカットパネルが開き、ほぼすべてのキー割り当て — プロファイルの切り替え、セッションのナビゲーション、ビューの切り替え、デスクトッププラグインが追加するショートカットを含む — を再割り当てできます。重複した割り当てはコンフリクトとしてフラグが立ちます。知っておくべき既定値のいくつかは、新規セッションが **Cmd/Ctrl+N**、Command Center が **Cmd/Ctrl+.**、Settings が **Cmd/Ctrl+,**、セッション検索が **Cmd/Ctrl+Shift+F**、プロファイル切り替えが **Cmd/Ctrl+1–9**、ライト/ダーク切り替えが **Shift+X** です。
- **カスタムズームショートカット** — インターフェースを半段階ずつ拡大縮小して、文字サイズをより細かく調整できます。
- **UI 言語切り替え** — アプリ内でインターフェース言語を変更できます。英語、簡体字中国語(zh-Hans)、繁体字中国語(zh-Hant)、日本語、アラビア語(RTL)、ロシア語です。

### セッションとプロファイル {#sessions-profiles}

- **セッションリストの一新** — アーカイブと一般的なセッション整理機能を備えた、作り直されたセッションリストです。増えていくリストを扱いやすい状態に保ちます。
- **ID でセッションを検索** — 特定のセッションをその ID で直接見つけられます。
- **同時実行の複数プロファイルセッション** — 複数の [プロファイル](/hermes/docs/user-guide/profiles/) をまたいでセッションを同時に動かし、プロファイルをまたいだ `@session` リンクで別のプロファイルのセッションを参照できます。
- **プロファイルのエクスポート/インポート** — 一式全体を1つのファイルとして共有できます。**⌘K → Export profile…**(またはレール上のプロファイルの四角を右クリック)は、スキル・メモリ・ペルソナ・cron・プラグイン・設定を含む `.tar.gz` を書き出します。API キーは取り除かれます。デスクトップからのエクスポートには、見た目や UI(スキン、ライト/ダークモード、カスタムテーマ、そのプロファイルのレールの色、ウィンドウレイアウト)もまとめて含まれるので、インポートされたプロファイルは送った側が見ていたのと同じ見た目で届きます。インポートは **⌘K → Import profile…** またはレールの **+** の隣のボタンから行い、オーバーレイを適用して新しいプロファイルへ移動します。同じアーカイブは、チャット内の `/export` / `/import` やシェルの `hermes profile export` / `import` とも互換です。[Export and import a profile file](/hermes/docs/user-guide/profile-distributions/#export-and-import-a-profile-file) を参照してください。

## 更新 {#updating}

アプリはバックグラウンドで更新を確認し、準備ができるとワンクリックの更新を提示します。

このバックグラウンドチェックは GitHub API にブランチの先端を尋ねます。匿名の GitHub リクエストは**ネットワークアドレスごと**に1時間60回に制限されているため、共有された接続(オフィスの NAT、VPN、proxy)では、このマシンがほとんどリクエストしていなくても `GitHub API rate limit reached` と表示されることがあります。1時間5,000件の予算を使うために、このチェックは次の順で最初に見つかった認証情報を使います。

1. アプリが起動された環境の `GITHUB_TOKEN`、次に `GH_TOKEN` — リクエストごとに読み取られ、保存はされません。
2. [GitHub CLI](https://cli.github.com/) 自身のログイン(`gh auth token`)。これは、Dock、Finder、デスクトップのランチャーから起動されたアプリ(シェルの変数を引き継がない最小限の環境を持つ)を助ける段です。`gh` は `PATH` と通常のインストール場所(Homebrew、`/usr/local/bin`、`~/.local/bin`、Windows の GitHub CLI インストーラー)で探され、その結果はアプリが再起動するまでキャッシュされるので、`gh` はセッションごとに最大1回しか実行されません。
3. 匿名。

GitHub が拒否した認証情報(HTTP 401 — 期限切れまたは失効)は、その出どころだけを名前で(トークン自体は決して)記して `desktop.log` に一度だけログされ、リクエストは匿名で再試行されます。更新の適用は API ではなく `git` を使うので、これには影響されません。

ローカルでの更新中、詳細なビルド出力は、切り離された `--gateway` の更新を含めて、アクティブなプロファイルの `logs/update.log` にストリームされます。これはターミナルには出ませんが、ビルドが終わる前のトラブルシューティングに使えます。Windows のハンドオフは、このログへの新しい出力をすべて進捗として数えます。何も出力を生成しない子プロセスも idle watchdog の対象のままです。プロセスが生きていることだけでは watchdog はリセットされず、更新をキャンセルしてもそのビルドの終了は待ちません。

デスクトップアプリと、それが話す Hermes バックエンドは別々の時計で更新されます — アプリのパッケージはあなたのマシン上、バックエンドはそれが動いている場所です。更新対象が複数存在する場合(リモートゲートウェイ、あるいは複数の登録済みゲートウェイ)、更新の操作(About パネルの **Update now**、⌘K の **Update Hermes** 行、更新準備完了のトースト)は**すべて**を更新します。接続中のバックエンドをまず更新し、次に他のすべての対象となる登録済みゲートウェイ(Hermes Cloud のエントリはプラットフォームが管理するのでスキップされます)、最後にデスクトップアプリ自身です。クライアントの更新を適用するとアプリが再起動するためです。単一マシンのインストールは、これまでと同じワンボタンの体験のままです。

バックエンドの更新後、アプリは自身のバージョンも再確認し、GUI がまだ古いままなら **Update desktop app** のワンクリック操作とともに警告します。リモートのバックエンドを更新したせいで、古いデスクトップビルドのまま静かに置いていかれることはありません。

[手動での更新手順](https://hermes-agent.nousresearch.com/docs/getting-started/updating) も GUI と一緒に使えます。

## アンインストール {#uninstalling}

**Settings → About → Danger zone** を開き、どこまで削除するかを選びます。

- **Uninstall Chat GUI only** — デスクトップアプリとそのデータを削除します。Hermes エージェント、設定、チャットはそのまま残ります。(`hermes uninstall --gui` と同じです。)
- **Uninstall GUI + agent, keep my data** — アプリとエージェントを削除しますが、将来の再インストールのために設定・チャット・シークレットは残します。(`hermes uninstall` と同じです。)
- **Uninstall everything** — アプリ、エージェント、すべてのユーザーデータを削除します。(`hermes uninstall --full` と同じです。)

作業を終えるためにアプリは終了します(クリーンアップは終了後に走るので、実行中のアプリ本体と自分の venv を削除できます)。ローカルのエージェントがインストールされていない場合(例えばリモートバックエンドに接続する GUI のみの「lite」クライアント)、エージェントを削除するオプションは自動的に隠されます。

同じことはターミナルからも行えます — GUI だけなら `hermes uninstall --gui`、エージェントも含めるなら `hermes uninstall` / `hermes uninstall --full` です。

:::note
**ソースからのチェックアウト**(`hermes desktop` の開発ビルド)から `hermes uninstall --gui` を実行すると、ワークスペースの `node_modules` と `apps/desktop/{dist,release}` のビルド出力も削除されます。これらは GUI のビルド生成物だからです。これらは `hermes desktop`(または `npm install` + 再ビルド)で復元できますが、デスクトップアプリを積極的にハックしているなら、その後は依存関係を再インストールすることになると想定してください。
:::

## CLI 一覧: `hermes desktop` {#cli-reference-hermes-desktop}

CLI から起動するには、単に `hermes desktop` を実行します。既定では、ワークスペースの Node 依存関係をインストールし、現在の OS 向けの unpacked な Electron アプリをビルドしてから、そのパッケージ済みのアーティファクトを起動します。

Linux では、起動のたびに `$XDG_DATA_HOME/applications/hermes.desktop`(既定では `~/.local/share/applications/hermes.desktop`)が更新されるので、Hermes はアプリケーションメニューに現れます。手動で編集したエントリを保持したい場合は、この更新を無効にしてください。

```bash
hermes config set desktop.manage_launcher_entry false
```

エントリが存在しない場合は、それでも作成されます。このフラグが止めるのは、すでに存在するエントリを `hermes desktop` が書き換えることだけです。

アプリケーショングリッドやメニューから Hermes を起動した場合(ランチャーが `DESKTOP_STARTUP_ID` を設定します)、そのエントリはウィンドウが画面に表示された後にだけ書き込まれます。ウィンドウが現れる前にアプリが終了した場合、その回は何も書き込まれません。次のターミナル起動、アップデータの再起動、あるいはウィンドウを表示するグリッド起動が、それをインストールします。一部の GNOME Shell のバージョンは、起動中に `.desktop` ファイルが変わったアプリを追跡できなくなり(起動通知が完了するかタイムアウトするまで、その状態を保持し続けます。プロセスが終了するまでではありません)、それが後にセッション全体をクラッシュさせることがあります。ウィンドウを待つことでこれを避けられます。ターミナルからの起動とアップデータの再起動は、それでもすぐにエントリを書き込みます。

| フラグ | 説明 |
| --- | --- |
| `--skip-build` | npm install/package をスキップし、`apps/desktop/release` にある既存の unpacked アプリを起動する |
| `--force-build` | コンテンツのスタンプが一致していてもフルリビルドを強制する |
| `--build-only` | デスクトップアプリをビルドするが起動しない(`hermes update` が使用) |
| `--source` | パッケージ済みアプリの代わりに `apps/desktop/dist` に対して `electron .` 経由で起動する |
| `--cwd PATH` | デスクトップのチャットセッション用の初期プロジェクトディレクトリ(`HERMES_DESKTOP_CWD` を設定する) |
| `--hermes-root PATH` | アプリが使う Hermes のソースルートを上書きする(`HERMES_DESKTOP_HERMES_ROOT` を設定する) |
| `--ignore-existing` | バックエンド解決の際、`PATH` 上に既にある `hermes` CLI を無視するようアプリに強制する |
| `--fake-boot` | 起動 UI の検証用に、決定的な起動の遅延を有効にする |

## 動作の仕組み {#how-it-works}

パッケージ済みのアプリには、Electron のシェルとネイティブの React チャット画面が含まれます。初回起動時には、Hermes Agent のランタイムを `HERMES_HOME`(`~/.hermes`、Windows では `%LOCALAPPDATA%\hermes`)にインストールできます — これは**CLI のインストールが使うのと同じレイアウト**で、両者が入れ替え可能な理由です。バックエンドの解決は、まず `HERMES_DESKTOP_HERMES_ROOT` を、次に完了済みの管理対象インストールを、続いて `PATH` 上でプローブされた `hermes` を(`--ignore-existing` / `HERMES_DESKTOP_IGNORE_EXISTING=1` が設定されていない限り)、最後に Nix のようなパッケージャー向けの明示的な `HERMES_DESKTOP_HERMES` コマンドの上書きを優先します。React のレンダラーは、アプリが起動するヘッドレスのバックエンド — `tui_gateway` の JSON-RPC/WebSocket API を提供する `hermes serve` プロセス — と話し、`hermes --tui` を埋め込む代わりにエージェントのランタイムを再利用します。デスクトップアプリは**自己完結**しています。自前の `hermes serve` バックエンドを動かし、[web dashboard](/hermes/docs/user-guide/features/web-dashboard/) を開いたり必要としたりすることはありません。(`serve` コマンドより古いランタイムは、ヘッドレスの `dashboard --no-open` へ自動的にフォールバックするので、アプリの更新がバックエンドを追い越すことはありません。)インストール、バックエンドの解決、自己更新のロジックは Electron のメインプロセスにあります。

## リモートバックエンドへの接続 {#connecting-to-a-remote-backend}

既定では、アプリは自分の**ローカル**バックエンドを起動・管理します。代わりに、別のマシン — VPS、ホームサーバー、Tailscale の裏にある Mac mini など — で動いている Hermes バックエンドを指すこともできます。

接続に関するすべては1つの設定ページにあります。**Settings → Gateways** です。(旧いビルドではこれが別々の **Gateway** ページと **Connections** ページに分かれていましたが、それらは統合され、旧い `?tab=connections` のディープリンクは統合ページへリダイレクトされます。)

**Settings → Gateways → Connection mode** は、ローカルゲートウェイに対する選択肢を提示します。

- **Remote gateway** — 自分で動かしている `hermes serve` バックエンドの URL を入力してサインインします。このセクションの残りはこのモードを進めます。
- **Hermes Cloud** — Hermes Cloud に一度サインインすれば、あなたのアカウントにあるエージェントから選べます。URL を貼り付ける必要はありません。アプリはあなたのエージェントを発見し(アカウントが複数の組織にまたがる場合は組織のピッカーも表示されます)、1つに接続するとセッションは自動的に切り替わります。ステータスバーは、有効な間クラウド接続を表示します。

ゲートウェイの接続は**マシンレベル**です。Gateways ページは、このデスクトップが接続できるゲートウェイバックエンドを管理し、プロファイルは接続したゲートウェイ*から*発見されます。セッションは一度に1つのゲートウェイを選び、隣接するプロファイルレールはそのゲートウェイ上で発見されたプロファイルを選びます。

### 複数接続レジストリ {#the-multi-connection-registry}

同じ **Settings → Gateways** ページの下のほうにある **Registered gateways** は、アプリが知っているすべての Hermes ゲートウェイ — ローカルランタイム、任意の数のリモートゲートウェイ(LAN、Tailscale、インターネット)、Hermes Cloud のインスタンス、SSH ホスト — を、1つの場所にまとめて永続化された名前付きリストとして管理します。サイドバーのプロファイルレールの右端にあるプラグボタン(**Connect another Hermes gateway…**)や **⌘K → Gateways** からそこへジャンプできます。統合エージェント名簿、`@name-device` ハンドル、fleet 全体の更新、プラグイン SDK の全体像を含む完全なガイドは [Connecting Desktop to Many Hermes Instances](/hermes/docs/user-guide/multi-connection-desktop/) にあります。

- **どの接続にも一意な名前が必要です**(「Homelab」や「Work laptop」のようなデバイス名)。同じプロファイル名が複数の登録済みゲートウェイに存在する場合、画面はそれを `@profile-device`(例: `@research-homelab`)として区別します。
- **Sessions サイドバーからゲートウェイを切り替えます。** 2つ以上のゲートウェイが登録されていると、名前付きのゲートウェイセレクタが現れ、ゲートウェイをプロファイルのように見せることなくどんなレジストリの規模にも対応します。隣接するプロファイルレールはそのゲートウェイのエージェントだけを表示し、そこで最後に使ったプロファイルを記憶します。大きなプロファイルの集合は独立して折りたたまれます。
- **プロファイルレールを隠す。** プロファイルがワークスペースではなくボットである場合、サイドバー下部の色付きのプロファイルの四角の帯はセッションリストと重複します。Sessions ビューのメニュー(**Profile rail**)、シェルの右クリックメニュー、または **⌘K → Toggle profile rail** から off にできます。隠れている間は、ステータスバーのゲートウェイセレクタの隣に **Profiles** ドロップダウンが現れ、同じ選択肢(そのゲートウェイのプロファイル、他のゲートウェイのエージェント、**New profile**、**Import profile…**、**Manage profiles…**)を提供するので、プロファイルの切り替えにはいつも入り口があります。
- **再起動後に何を開くか選ぶ。** **Open on launch** は後方互換の **Primary gateway** の既定を保つか、正常に接続できた後の **Last used** ゲートウェイを再開できます。この設定はアプリケーションバンドルの外に保存され、デスクトップの更新をまたいで残ります。
- パネルから接続を **Add / edit / remove / test** できます。**Add** のフローは4種類すべて — **Local**、**Hermes Cloud**、**Remote gateway**、**SSH** — を提示します(アプリ管理のローカルエントリが存在する間 Local ボタンは無効になり、ヒントはクラウドの追加を上のサインイン/検出フローへ導きます)。ローカルエントリはアプリが管理し、削除できません。**Test** は、その接続自身の HTTP と WebSocket の両方の経路を直接確認します。
- **重複は保存時に拒否されます**。**local** エントリは常に1つだけ。remote と cloud のエントリは正規化された URL(トリムし、末尾のスラッシュを除去し、小文字化したもの — 両方の種類をまたいで)で重複排除されます。SSH エントリは正規化された `user@host:port` とリモートプロファイルで重複排除されます。
- 既存の設定は、このレジストリを持つビルドを最初に実行したときに**自動的にインポートされます**。現在のグローバル接続と、レガシーなプロファイルごとの上書きは名前付きエントリになります。レガシーの設定ファイルには手を付けられないので、旧いビルドも動き続けます。
- クラウドのエントリは上のサインイン/検出フローから来るものであり、手で入力した URL からは来ません。
- トークンは OS のキーリングで暗号化して保存されます(キーリングのない Linux では明示的な平文オプトインがあります)。

サイドバイサイドのルーティングはライブです。登録済みの各ゲートウェイは必要に応じて自分自身のバックエンドとソケットを(接続+プロファイルごとにキー付けして)ダイヤルし、プラグイン SDK は統合エージェント名簿(`host.agents()` / `host.ensureAgent()`)を公開し、Gateways ページの **Update all instances** は対象となる登録済みゲートウェイすべてに一度で `hermes update` を発行します — Hermes Cloud のエントリはスキップされ(プラットフォームがそれらを更新します)、各インスタンスは自分の結果を報告します。

:::info リモートバックエンドは実行中の `hermes serve` プロセスです
「リモートバックエンド」とは、リモートマシン上で動いている**`hermes serve`**サーバーを指します — これがデスクトップアプリが接続するプロセスです。そのバックエンドが実際に立ち上がって到達可能でない限り、このセクションのどれも機能しません。デスクトップアプリはあなたのためにそれを起動してくれません。あなた(または `systemd` サービス)がリモートホスト上で `hermes serve` を動かし続け、アプリはそこへ接続します。メッセージングチャンネル(Telegram、Discord など)も使う場合、**ゲートウェイ**は別に起動して動かし続ける、それとは別の長時間動作するプロセスです — 設定ステップの後の注記を参照してください。
:::

接続には2つの側面があります。バックエンド側では**認証プロバイダー**で保護し、アプリ側ではバックエンドの URL を入力してサインインします。バックエンドをループバックでないアドレスに bind すると、その認証ゲートが自動的に有効になり、設定したプロバイダーがデスクトップアプリを通す役割を果たします。

**バックエンドがどこにあるかでプロバイダーを選んでください。**

- **OAuth(Nous Portal) — 自分のマシンの外から届く場合はこちらを推奨。** ログインはあなたの Nous アカウントに対して検証されるので、これは VPS、公開ホスト、あらゆるリモートバックエンドに適したオプションです。`hermes dashboard register`(または Portal の [`/local-dashboards`](https://portal.nousresearch.com/local-dashboards) ページ)でダッシュボードを登録し、その OAuth クライアントをプロビジョニングしてから、アプリで **Sign in with Nous Research** からサインインしてください。自前の identity provider を運用している場合、セルフホストの OIDC プロバイダーも同じ方法で使えます。
- **ユーザー名/パスワード — ローカル/信頼できるネットワークのみで使用。** バックエンドが同じ信頼できる LAN 上にある、あるいは VPN(例: Tailscale)経由でしか到達できない場合の最もシンプルなオプションです。単一の共有認証情報を、外部の identity provider を使わずに保護します。**公開インターネットに露出したダッシュボードには使わないでください** — そこでは代わりに OAuth を使ってください。

このセクションの残りでは、信頼できるネットワーク上で最も早く立ち上げられるユーザー名/パスワードの経路を示します。OAuth の経路については [Web Dashboard → Default provider: Nous Research](/hermes/docs/user-guide/features/web-dashboard/#default-provider-nous-research) を参照してください。

### バックエンド側(リモートマシン) {#on-the-backend-the-remote-machine}

ユーザー名とパスワードを設定し、到達可能なアドレスに bind してバックエンドを起動します。認証情報は `~/.hermes/.env`(モード 0600 のシークレットファイル)に置かれます。

```bash
# 1. Set the dashboard login credentials.
cat >> ~/.hermes/.env <<'EOF'
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
# Recommended: a stable signing secret so sessions survive restarts.
# Without it a random key is generated per boot and you'll be logged out
# on every restart.
HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
EOF
chmod 600 ~/.hermes/.env

# 2. Run the backend bound to a reachable address. The non-loopback bind
#    engages the auth gate; the username/password provider handles login.
hermes serve --host 0.0.0.0 --port 9119
```

デスクトップアプリがバックエンドに接続できる状態を保ちたい間は、その `hermes serve` プロセスを動かし続けてください。それが止まると、アプリはそのバックエンドに到達できなくなります。ログアウトや再起動をまたいで生き残るよう、`systemd`、`tmux`、あるいは好みのプロセスマネージャーの下で実行してください。

これとは別に、メッセージングチャンネルに依存するならリモートホスト上で**ゲートウェイが動いていること**を確認してください。デスクトップアプリが話しかけるのは `hermes serve` バックエンドですが、Telegram/Discord/Slack のゲートウェイセッションは別のプロセスで、自分で起動し動かし続ける必要があります。ゲートウェイの設定については [Messaging](/hermes/docs/user-guide/messaging/) を参照してください。

平文のパスワードを保存したままにしたくないですか? `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH` に scrypt のハッシュを設定してください。計算は `python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"` で行えます。設定サーフェス全体(config.yaml のキー、すべての env var、レートリミッタ)は [Web Dashboard → Username/password provider](/hermes/docs/user-guide/features/web-dashboard/#usernamepassword-provider-no-oauth-idp) にあります。

バックエンドを systemd サービスとして動かしていますか? unit に `EnvironmentFile=%h/.hermes/.env` を与えて、起動時に認証情報が環境変数に入るようにしてください。

:::warning
バックエンドは `.env`(API キー、シークレット)を読み書きし、エージェントのコマンドを実行できます。上に示した**ユーザー名/パスワード**の設定は信頼できるネットワーク向けです。パスワードで保護したバックエンドを公開インターネットに直接晒さないでください。VPN の裏に置いてください。[Tailscale](https://tailscale.com/) はきれいな選択肢です。マシンの tailscale IP に bind し(`--host <tailscale-ip>`)、Remote URL として `http://<tailscale-ip>:9119` を使えば、自分のテイルネットだけがそこへ到達できます。公開インターネットを経由してバックエンドに到達する場合は、代わりに **OAuth(Nous Portal)** プロバイダーを使ってください。
:::

### アプリ側 {#in-the-app}

**Settings → Gateways → Remote gateway:**

1. **Remote URL** — `http://<backend-host>:9119`(リバースプロキシで前段を組んでいれば `/hermes` のようなパスプレフィックスも使えます)
2. **Sign in** — アプリはバックエンドが広告するプロバイダーを検出し、ボタンをそれに合わせます。ユーザー名/パスワードのバックエンドの場合は **Sign in** ボタンが表示され、認証情報のフォームが開きます(手順1の認証情報を入力してください)。OAuth バックエンドの場合は **Sign in with `<provider>`**(例: *Sign in with Nous Research*)が表示され、プロバイダーのブラウザサインインが実行されます。いずれにせよ、アプリは最終的にバックエンドに対して認証済みのセッションを持つことになります。
3. **Save and reconnect** — デスクトップのシェルをリモートバックエンドへ切り替えます。セッションは自動的にリフレッシュされ、`HERMES_DASHBOARD_BASIC_AUTH_SECRET` が設定されていれば再起動をまたいでサインイン状態を保てます。

UI を使わずに、アプリを起動する前に `HERMES_DESKTOP_REMOTE_URL` 環境変数でバックエンドの URL を設定することもできます(アプリ内の設定を上書きします)。それでもサインインは Gateways の設定パネルから行います。

:::note プロファイルごとのリモートホスト
リモートゲートウェイのホストは [プロファイル](/hermes/docs/user-guide/profiles/) ごとに設定されるので、各プロファイルは自分自身のリモートバックエンド(あるいはローカルのまま)を指せます。プロファイルを切り替えると、アプリが接続するリモートホストも切り替わります。
:::

### トラブルシューティング {#troubleshooting}

- **サインインが 401 / "Invalid credentials" で失敗する** — ユーザー名かパスワードがバックエンドの `HERMES_DASHBOARD_BASIC_AUTH_USERNAME` / `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD` と一致していません。バックエンドは、未知のユーザーと間違ったパスワードに対して同じ汎用エラーを返します(列挙のオラクルにならないように)。両方を再確認してください。ゲートが on になっていることは `curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'` で確認できます。`true` と、`"basic"` を含む結果が返るはずです。
- **"Sign in" ボタンがなく、代わりにセッショントークンを求められる** — バックエンドのユーザー名/パスワードプロバイダーが有効になっていません。`/api/status` は `auth_providers` に `"basic"` を挙げません。ユーザー名とパスワード(またはパスワードハッシュ)の両方が `~/.hermes/.env` に設定されていて、ダッシュボードのプロセスが実際にそれを読み込んでいることを確認してください。
- **再起動ごとにログアウトされる** — `HERMES_DASHBOARD_BASIC_AUTH_SECRET` を安定した値に設定してください。これがないと、トークン署名キーが起動ごとに再生成され、すべてのセッションが無効になります。
- **接続が拒否される / タイムアウトする** — バックエンドが(既定の)`127.0.0.1` に bind されている、あるいはファイアウォール/VPN がそのポートをブロックしています。`0.0.0.0` か tailscale IP に bind し、信頼できるネットワークに向けてそのポートを開いてください。

web dashboard 側からの同じ設定については [Web Dashboard → Connecting Hermes Desktop to a remote backend](/hermes/docs/user-guide/features/web-dashboard/#connecting-hermes-desktop-to-a-remote-backend) を、env var の一覧は [Environment Variables → Web Dashboard & Hermes Desktop](/hermes/docs/reference/environment-variables/#web-dashboard--hermes-desktop) を参照してください。

## デスクトップアプリを拡張する {#extending-the-desktop-app}

デスクトップアプリは contribution 主導で作られています。ペイン、ページ、サイドバーのナビゲーション、ステータスバーの項目、パレットのコマンド、キーバインド、テーマはすべて1つの SDK を通じて登録され、自分のものを追加することもできます。プラグインは、`$HERMES_HOME/desktop-plugins/<id>/plugin.js` に置く単一の ESM ファイルです。アプリはこれを数秒以内に読み込み、保存ごとにホットリロードします。インストール済みプラグインの管理は **Capabilities → Plugins** から行います。

詳しい仕様は [Desktop Plugin SDK](/hermes/docs/developer-guide/desktop-plugin-sdk/) にあります。(これは [web dashboard のプラグインシステム](/hermes/docs/user-guide/features/extending-the-dashboard/) とは別物です。)

デスクトッププラグインは**サンドボックス化されていません**。アプリの内部で、アプリ自身の権限(ゲートウェイの RPC、ネイティブブリッジ、他のプラグインのストレージ)を持って動きます。自分で書いた、あるいはレビューしたファイルだけを読み込んでください。カタログからのインストールの場合、その保護は[カタログのトラストモデル](/hermes/docs/user-guide/features/plugin-catalog/#trust-model)(人間によるレビュー済み、SHA でピン留め)とインポートの allowlist によるものであり、分離ではありません。`register()` が例外を投げるプラグインはロールバックされ、その行にエラーとともに **Failed** と表示されます。**⌘K → Reload desktop plugins** は、インストーラーがその場で置き換えたものも含め、インストール済みのすべての `plugin.js` を再読み込みします。

**Capabilities → Plugins** は、Hermes を拡張するすべてを扱う唯一の場所です。**プラグイン1つにつき1行**で、2つのスイッチの列があります。

- プラグインは**このアプリ**、**エージェント**、あるいは**両方**を拡張できます — 各行のバッジは、パッケージの内容から推測して(`plugin.yaml` → エージェント側、`plugin.js` → デスクトップ側)どちらかを示します。両方の側を持つプラグインは1行のままで、2行になることはありません。
- **Desktop 列** — このアプリに読み込まれる側です。これはアプリレベルの設定です。ウィンドウが見ているプロファイル、ゲートウェイ、リモートマシンにかかわらず、同じスイッチ、同じ値です。デスクトップのコードは `~/.hermes/desktop-plugins/` という1つの場所からのみ読み込まれます。エージェント+デスクトップ統合パッケージのデスクトップ側は、そのパッケージがインストールされたときにアプリによってそこへコピーされ(更新とアンインストールにも追随します)、そのためプロファイルを切り替えてもペインが読み込まれたり、外れたり、スコープが変わったりすることはありません。トグルはライブに適用されます。
- **Agent 列** — 選択したプロファイルのバックエンドにインストールされている側([agent plugins](/hermes/docs/user-guide/features/plugins/): user、git、project、pip、portable のインストール)で、カタログのピンが動いたときには **Update** チップが付きます。プロファイルセレクタはこの列のヘッダーにあります。この列だけを支配するものだからです。プロファイルが1つだけならセレクタは一切表示されません。リポに同梱された組み込み(プラットフォームアダプタ、プロバイダープラグイン)はここに一覧されません。それらは有効な状態で出荷され、自分自身の画面から設定されます。例外は、自分の画面を持たない同梱のライフサイクルプラグイン(`disk-cleanup`、`security-guidance`)で、これらは他のエージェントプラグインと同じように切り替えられるようここに現れます。
- プラグインが出荷しない側にはダッシュが表示されます。エージェント側が選択したプロファイルに**インストールされていない**デスクトップ側は **Install here** を示し、これはそのプロファイル限定で、パッケージの出どころ(カタログのエントリまたは git のリモート)からインストールダイアログを事前入力します。[Accent Picker](https://github.com/NousResearch/hermes-desktop-accent-picker) のような任意の拡張は、**Install from Git** で自分自身のリポからインストールします。
- **Uninstall** — 選択したプロファイルの `plugins/` フォルダにインストールされた(user または git インストールの)すべてのプラグインには、名前の横にゴミ箱ボタンがあります。確認を求め、そのプロファイルからプラグインのファイルとインストールのメタデータを削除します — `hermes plugins remove <name>` と同じ操作です — そして統合パッケージのデスクトップ側のアプリレベルのコピーも刈り取ります。プラグインのコードをアンロードするにはゲートウェイを再起動してください。リポ同梱と pip インストール(entrypoint)のプラグインにはゴミ箱ボタンがありません。前者は削除できず、後者はその Python パッケージと一緒に削除されるためです。`~/.hermes/desktop-plugins/` にフォルダを落としただけの、エージェントパッケージを持たない単独のデスクトッププラグインにも同じゴミ箱ボタンがあります。確認すると、このコンピュータ上のそのフォルダが削除され、ゲートウェイを介さずにそのプラグインが即座にアンロードされます。

発見はその下にあります。ライブの [Plugin Catalog](/hermes/docs/user-guide/features/plugin-catalog/) のピッカーは、レビュー済みのエントリをピン留めされたコミットで選択中のプロファイルにインストールし、**Install from Git** は他の任意のリポジトリを同じレビューしてからインストールするダイアログに通します。その任意項目の **Pin to commit** フィールドは、40文字の完全なコミット SHA を1つ指定してインストールします(プライベートリポも含みます)。ピン留めされたプラグインは一覧に `pinned @ <sha8>` バッジを付けて表示されます。旧い `Settings → Plugins` へのリンクはここへリダイレクトされます。

## トラブルシューティング {#troubleshooting}

### アプリを再起動せずに再接続する {#reconnect-without-restarting-the-app}

接続が **Connected** と表示されているにもかかわらず、デスクトップのチャットやボットが応答しなくなった場合は、そのボット/プロファイルまたはゲートウェイを選び、ステータスバーのゲートウェイメニューを開いて **Reconnect gateway** をクリックしてください。Reconnect は、開いている、接続中の、切断されたトランスポートのいずれでも使えます。デスクトップを再起動したり、他のルートのソケットを意図的に閉じたりせずに、アクティブなルートを再ダイヤルします。選択中のソケット上の進行中のリクエストは中断される可能性があります。これは明示的なリカバリ操作であり、バックエンドやモデルの再起動ではありません。

### `hermes update` の後にアプリが消えた {#the-app-vanished-after-hermes-update}

`apps/desktop/release/` を保持しないままチェックアウトを置き換えた以前の更新は、起動できるパッケージ済みアプリを残しません。`HERMES_HOME/desktop-build-stamp.json`(Desktop のビルド成功時にのみ書き込まれます)が残っている限り、次の `hermes update` はアプリが失われていることに気づいて再ビルドします。手動で再ビルドするには `hermes desktop --build-only --force-build` を実行してください。Windows では ZIP のフォールバックも、置き換えをまたいでビルド済みアプリ・そのレンダラーバンドル・Electron の `node_modules` を保持します。

### バックグラウンドでローカルバックエンドが停止した {#the-local-backend-stopped-in-the-background}

準備完了後にローカルの Hermes バックエンドプロセスが終了すると、Desktop は自分でそれを再起動し、**Hermes stopped working in the background** の通知を表示します。チャットは、置き換わったプロセスが立ち上がると再接続します。`HERMES_HOME/logs/desktop.log` は、終了コードとバックエンドの最後の出力行を一緒に記録します(`Hermes backend exited (1)` の後に `Recent backend output:` が続きます)。そのため、アプリが自分で復旧できた場合でも、落ちた理由はログに残ります。再起動のたびに数秒で落ち続けるバックエンドは、バックエンド自体に問題があることを示しています。そのテールにあるトレースバックを見てください。2分以内に3回そうした再起動が続くと、Desktop は再起動をやめ、繰り返す代わりに **keeps crashing** の通知を表示します。原因を修正した後、アプリを再起動してください。

### 失敗したターンは失敗した層の名前を示す {#failed-turns-name-the-failing-layer}

ターンが失敗すると、チャットは汎用のエラートーストの代わりに、**どの層が失敗したか**(プロバイダー/モデル、カスタムエンドポイント、ストリーミング接続、認証、課金、ゲートウェイ、ローカルランタイム、ディスク)を示すエラーカードを表示します。このカードは失敗に合わせたリカバリ操作を提示します。

- **Retry** — 失敗したターンをその場で再実行します(再試行が確実に同じ失敗を再現する場合、例えばコンテンツポリシーによる拒否では隠されます)。レートリミットや使用量上限の応答が制限が解除される時刻(`Retry-After` ヘッダーまたは `resets_at` フィールド)を示している場合、カードは Retry の隣に **Limit resets at HH:mm (in 1h 05m)** を表示するので、再試行がいつ通るかが分かります。CLI/TUI もエラーの下に同じ行を表示します。このヒント自体は情報提供ですが、カードは **Retry when the limit resets (HH:mm)** も提示します。クリックすると、アプリはリセット時刻にそのターンを一度だけ再試行し、ライブのカウントダウンと **Cancel** 操作が表示されます。このスケジュールは開いているウィンドウの中にしか存在しません。セッションの切り替え、別のメッセージの送信、アプリを閉じることでこれは消え、放置していても何も再試行されません。
- **Switch provider** — プロバイダー、エンドポイント、認証、課金の失敗に対して、コンポーザーのライブなモデルメニューを開くので、**このチャット**をすぐに別のプロバイダー/モデルへ移せます(Settings → Models は新しいチャットの既定値だけを変更します)。チャットの画面が表示されていない場合は Settings → Models へフォールバックします。
- **Open logs** — ファイルマネージャで `HERMES_HOME/logs` を開きます。リモートまたは Cloud の接続では、このボタンは **Open Desktop logs** になります。失敗したターンのゲートウェイ/エージェントのログはリモートマシン上にあるので、ローカルの Desktop 側のログ(トランスポートの証跡)を開きます。
- **Send diagnostics** — 明示的な同意の確認の後、redact されたデバッグバンドルを Nous 内部のストレージにアップロードします(`hermes debug share --nous` と同じパイプラインです。シークレットは常に redact され、そのバンドルは Nous のスタッフだけが見られ、14日後に自動削除されます)。成功すると、サポートスレッドに貼り付けられる非公開の閲覧リンクと、GitHub Issues、Nous Portal Support、Discord へのクイックリンクが得られます。リモートまたは Cloud の接続では、バックエンド自身のエージェント/ゲートウェイのログをバンドルし、ローカルの Desktop ログも一緒に添付されるので、サポートは両方の側を見られます。
- **Copy error details** — 層、コード、プロバイダー/モデル、エラーメッセージを含む簡潔なプレーンテキストの要約をコピーします。バグレポートや Discord に貼り付けられます。

この層の情報は、エージェントの再試行ループが使う同じエラー分類器から来ているので、メッセージ文からの推測ではなく、実際の失敗のセマンティクスを反映しています。この descriptor より古いバックエンドでも、汎用のタイトルと Retry / Open logs / Copy error details の操作付きでこのカードが表示されます。

起動時のログは `HERMES_HOME/logs/desktop.log` に残ります(バックエンドの出力と直近の Python のトレースバックを含みます)。アプリが起動失敗を報告したら、まずここを確認してください。CLI からも tail できます。

```bash
hermes logs gui -f
```

Linux では、Chromium 自身のエラーは `HERMES_HOME/logs/desktop-chromium.log` に出ます。シェル自体がクラッシュした場合、ミニダンプが(Electron のユーザーデータディレクトリの中、`connection.json` の隣にある)アプリの `Crashpad/` ディレクトリ下に残ります。ウィンドウがジャーナルに `SIGTRAP` を残して消えた場合、そのログの `FATAL:` 行が発火したチェックの名前を示すので、バグレポートに添付してください。何もアップロードされません。

よくあるリセット方法です。

```bash
# Force a clean first-launch setup (macOS/Linux)
rm "$HOME/.hermes/hermes-agent/.hermes-bootstrap-complete"

# Rebuild a broken Python venv (macOS/Linux)
rm -rf "$HOME/.hermes/hermes-agent/venv"

# Reset a stuck macOS microphone prompt
tccutil reset Microphone com.nousresearch.hermes
```

### "The host key has CHANGED since you last connected"(SSH remote) {#the-host-key-has-changed-since-you-last-connected-ssh-remote}

SSH のリモートが再インストールされ、そのホストキーがローテートされた場合、SSH は fail closed になり、Desktop は再試行の代わりにエラーオーバーレイを固定します(古いキーが取り除かれるまで再試行は決して成功しません)。その変更が意図したものであることを確認してから、古いエントリを削除してオーバーレイから再試行してください。

```bash
ssh-keygen -R <host>
```

エントリを削除した後、**Retry** をクリックする(または Settings → Gateway で接続を再度適用する)と、固定状態が解除され、次の起動で新規にダイヤルします。

### "Build desktop app" が Electron のダウンロードで固まる {#build-desktop-app-stuck-on-electron-download}

ビルドは `github.com/electron/electron/releases` から Electron のランタイム(約114&nbsp;MB)をダウンロードします。インストーラーが **Build desktop app** のステップで固まり、ライブの出力が `retrying attempt=…` を繰り返している場合、あなたのネットワーク上で GitHub がブロックまたはスロットルされています(ファイアウォール、proxy、リージョン)。

インストーラーはこれを自動的に自己回復します。ビルドが失敗すると、(1) 壊れたキャッシュ済みの Electron の zip をクリアして再試行し、(2) それでも失敗し、Electron の配布物がまだ見つからず、`ELECTRON_MIRROR` を設定していない場合、事実上の Electron コミュニティミラーである `npmmirror.com` 経由でもう一度だけ再試行します。`@electron/get` はダウンロードを SHASUM で検証しますが、そのチェックサムも同じミラーから来ているので、これは壊れた/不完全なダウンロードを検知するものであり、改ざんされたミラーを検知するものではありません。サードパーティのホストを信頼したくない場合は、自分の `ELECTRON_MIRROR` をピン留めしてください(下記)。ビルドは、あなたが設定したものを上書きすることはありません。

**自分のミラーを選ぶ**(例: 社内/信頼できるもの)には、インストール前に `ELECTRON_MIRROR` を設定するか、手動で再ビルドしてください。ビルドはそれを尊重し、上書きしません。

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ \
  bash -c 'cd "$HOME/.hermes/hermes-agent/apps/desktop" && CSC_IDENTITY_AUTO_DISCOVERY=false npm run pack'
```

**ミラーが必要な他のネイティブダウンロード(例: Windows での `get-windows` の prebuilt):** npm のキーを `$HERMES_HOME/npmrc`(Windows では `%LOCALAPPDATA%\hermes\npmrc`、それ以外は `~/.hermes/npmrc`)に置いてください。例えば `node_get_windows_binary_host_mirror=https://<mirror>/sindresorhus/get-windows/releases/download/` です。アップデータが起動するすべての `npm ci`/`npm run`(デスクトップ、web、TUI のビルド)は、それが存在する場合そのファイルへ `NPM_CONFIG_USERCONFIG` を向けるので、その設定は `hermes update` をまたいで残ります。リポルートの `.npmrc` は git で追跡され、更新のたびに自動で stash されます。`~/.npmrc` は、デスクトップのハンドオフが GUI の環境を継承するため見落とされることがあります。自分で設定した `NPM_CONFIG_USERCONFIG` は決して上書きされません。

**`get-windows` が見つからない、または半端にインストールされている場合:** ビルドはもう失敗しません — `[stage-native-deps] get-windows not installed ... read_window_below will be unavailable in this build` と表示し、`read_window_below` ツールなしで出荷します。パッケージのディレクトリは存在するが読み込めない場合(実行中の Hermes ウィンドウによって中断された Windows のその場更新、インストールログの `TAR_ENTRY_ERROR`)、同じ警告がそのディレクトリ名を示し、次の `hermes desktop --force-build` または更新が npm install の前にそれを削除して再展開されるようにします。もう一度中断されないよう、すべての Hermes ウィンドウとゲートウェイを先に閉じてください。ネイティブバインディングや macOS のヘルパーが欠けているパッケージも同様に、ビルドを失敗させる代わりにウィンドウ列挙なしで出荷されます。

壊れたキャッシュ済みの zip を手動でクリアするには次のとおりです。

```bash
rm -f "$HOME/Library/Caches/electron"/electron-*.zip   # macOS
rm -f "$HOME/.cache/electron"/electron-*.zip            # Linux
```

## ソースからのビルド {#building-from-source}

アプリ自体をハックしたい場合、リポのルートから一度ワークスペースの依存関係をインストールし、`apps/desktop` から開発サーバーを実行してください。

```bash
npm install          # from repo root — links apps/desktop, web, apps/shared
cd apps/desktop
npm run dev          # Vite renderer + Electron, which boots the Python backend
```

特定のチェックアウトを指す、あるいは実際の設定からサンドボックス化するには次のとおりです。

```bash
HERMES_DESKTOP_HERMES_ROOT=/path/to/clone npm run dev
HERMES_HOME=$HOME/.hermes/cache/scratch/throwaway npm run dev
npm run dev:fake-boot   # exercise the startup overlay with deterministic delays
```

インストーラーをビルドするには次のとおりです。

```bash
npm run dist:mac     # DMG + zip
npm run dist:win     # NSIS + MSI
npm run dist:linux   # AppImage + deb + rpm
npm run pack         # unpacked app under release/ (no installer)
```

macOS/Windows の署名と notarization は、関連する認証情報が環境に存在する場合(macOS では `CSC_LINK` / `CSC_KEY_PASSWORD` / `APPLE_*`、Windows では `WIN_CSC_*`)自動的に実行されます。

オプトインの HUD の modifier-tap ヘルパーは Electron のバンドルとともにビルドされ、ASAR の外にパッケージされます。macOS では既存の Xcode command-line tools の前提条件を使います。Windows のビルドは OS の .NET Framework に含まれる C# コンパイラを使います。Clang や開発者向け SDK は不要です。Windows のパッケージングは、ヘルパーを黙って省略する代わりに失敗します。Linux のビルドには C コンパイラと X11/XInput の開発ヘッダー(Debian/Ubuntu では `libx11-dev` と `libxi-dev`)が必要です。これらの任意の Linux の前提条件がなければ、パッケージングは modifier-tap のサポートなしで続行します。ビルドは対象の OS 上で行ってください。Linux は対象アーキテクチャも必要とします。インストール済みのユーザーは開発者向けツールチェインを必要としません。Settings は、欠けているヘルパーと起動失敗、非対応のデスクトップセッションを区別します。X11/Wayland の警告は、Windows のヘルパーが欠けている/失敗した場合には表示されません。

### macOS の権限とローカルでの再ビルド(TCC) {#macos-permissions-and-local-rebuilds-tcc}

**1つのスイッチでフォルダのすべての確認を止める。** macOS は Hermes が各フォルダに触れるたびにカテゴリごとに(Desktop、次に Downloads、次に Documents、…)確認します。1つの **Full Disk Access** の許可がすべてを永続的にカバーし、Hermes の安定した署名 identity があれば、これは更新をまたいで残ります。

1. System Settings → **Privacy & Security → Full Disk Access**(または `open "x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles"` を実行)
2. ターミナルアプリを有効にし、Desktop を使う場合は **Hermes.app** も有効にします。
3. 一度完全に終了して再起動します。

`hermes doctor` は、現在のターミナルのコンテキストにすでにその許可があるかどうかを報告し、`hermes setup` は macOS でそれがない場合このヒントを示します。

macOS は権限の許可(Full Disk Access、Desktop/Downloads/Documents、Accessibility、Automation、マイク)を、パスではなくアプリの*コード署名 identity* に対して記憶します。ローカルでビルドされ自己更新するアプリは、安定した識別子でピン留めされた ad-hoc の署名で署名されているので、許可は更新をまたいで残ります。

一度限りの注記: 識別子でピン留めされた署名の修正(PR #73681)より*前*のビルドに対して行われた許可は、古い cdhash でピン留めされた要件を引き継いでいます。macOS はそうした古い許可に対してトグルを ON のまま表示し続けますが、それでも再度確認を求めます。保存されている許可が再ビルドされたバイナリと一致しなくなったためです。そして最近のプロンプトには Allow ボタンがないので、再確認するものが何もないように見えます。そうなった場合は、古い許可を一度リセットして再度許可してください。

```bash
tccutil reset ScreenCapture com.nousresearch.hermes   # repeat per service
```

その後 System Settings で新しいエントリを ON に切り替え、Hermes を完全に終了して再起動してください。それ以降、許可は安定します。

より強い保証 — yabai/skhd のユーザーが使っているのと同じ仕組みである、証明書に固定された identity — を得るには、一度自己署名のコード署名証明書を作成し、それを使うよう Hermes に伝えてください。ワンショットのコマンドがすべてを行います(ログインキーチェーンに証明書を作成し、`codesign` へのアクセスを許可し、設定を書き込み、パッケージ済みアプリを再署名します)。

```bash
hermes desktop --setup-tcc-identity
```

または手動で行うには次のとおりです。

1. Keychain Access → Certificate Assistant → **Create a Certificate…**
2. Name: `Hermes Local Signing`、Identity Type: *Self-Signed Root*、Certificate Type: **Code Signing**。
3. Keychain Access で、新しい証明書をダブルクリック → **Trust** → **Code Signing** を *Always Trust* に設定します(インポートされた自己署名証明書は、コード署名として信頼されるまで有効な署名 identity になりません — その後 `security find-identity -v -p codesigning` に一覧されるはずです)。
4. `hermes config set desktop.macos_signing_identity "Hermes Local Signing"`

このコマンドで `--identity <name>` を使うと、別名の証明書を作成/使用できます(既定: `Hermes Local Signing`)。このコマンドは冪等です — 更新後に再実行して、設定を再度指し直し、再ビルドされたアプリを再署名してください。

次の更新は、再ビルドされたアプリをその証明書で再署名します。すべての TCC の許可は残ります。Apple Developer アカウントは不要です。notarize されたリリースビルドは検出され、再署名されることはありません。

一度限りの注記: 署名 identity を変更する(この修正の後の最初の更新を含む)と、アプリの identity が一度変わるので、macOS は最後に一度だけ再確認します。それ以降、許可は安定します。権限が固まった場合は `tccutil reset All com.nousresearch.hermes` でリセットして再度許可してください。
