# デスクトップ版から複数の Hermes につなぐ {#connecting-desktop-to-many-hermes-instances}

自分が持っている Hermes のバックエンド — 手元のランタイム、LAN や VPS にある
リモートのゲートウェイ、SSH でつなぐホスト、Hermes Cloud のインスタンス — を
1つのデスクトップアプリにまとめて登録し、そのすべてのエージェントを並べて使えます。
接続は保たれたままで、登録した各ゲートウェイは必要になったときに自分のバックエンドと
WebSocket をつなぎます。別のゲートウェイを表示しているあいだも、裏で動いている
エージェントは応答を返し続けます。

これは[ゲートウェイを同時に複数動かす](/hermes/docs/user-guide/multi-profile-gateways/)の
デスクトップ側の対になる説明です。あちらは1台のマシンで複数のゲートウェイを動かす話で、
こちらは1つのデスクトップアプリから複数のマシンにつなぐ話です。

## どこにあるか {#where-to-find-it}

設定はすべて **設定 → ゲートウェイ** のページにまとまっています（古いビルドでは
**ゲートウェイ**と**接続**が別のページに分かれていました。旧「接続」への
ディープリンクはこちらへ転送されます）。入口は3つあります。

- **設定 → ゲートウェイ** — ページそのものです（**Cmd/Ctrl+,** を押し、設定の
  ナビゲーションから**ゲートウェイ**を選びます）。接続の登録一覧は、マシン単位の
  接続モードの設定の下にある、このページの一区画です。
- **サイドバーのプロフィールレール** — レールの右端にあるプラグのボタン
  （ツールチップは **"Connect another Hermes gateway…"**）から、ゲートウェイの
  ページへ直接移動できます。2つめのプロフィールや2つめの接続を作る前から、
  このボタンは常に表示されています。
- **コマンドパレット** — **Cmd/Ctrl+K** を押して *Gateways* と入力します
  （*connections*、*add gateway*、*remote*、*ssh*、*instances* でも見つかります）。

## ゲートウェイの登録一覧 {#the-gateway-registry}

**設定 → ゲートウェイ**の**登録済みゲートウェイ**の区画では、名前を付けた Hermes の
ゲートウェイの一覧を管理します。冒頭の説明にもそのまま書かれています。
*"Manage this device and every Hermes gateway it can reach through remote, SSH, or Cloud connections."*
それぞれの項目が1つの*接続*です。

| 種類 | 何を指すか | 認証 |
|---|---|---|
| **ローカル** | 「このアプリが管理する Hermes のランタイム」 | 自動 |
| **リモートゲートウェイ** | 「HTTP(S) でつながる Hermes のゲートウェイ。LAN、Tailscale、インターネット経由」 | セッショントークンまたは OAuth |
| **SSH** | 「SSH 越しにつなぐ Hermes」。アプリがトンネルを開き、ダッシュボードを起動します | SSH 鍵 ＋ 引き継いだトークン |
| **Hermes Cloud** | 「Hermes Cloud のアカウントから見つかったホスト型のインスタンス」 | ポータルへのサインイン |

知っておきたい決まりは次のとおりです。

- **接続ごとに、重複しない端末名が必要です**（「Homelab」「Work laptop」など）。
  この名前は、そのインスタンスが現れるあらゆる場所 — 一覧のバッジ、ハンドル、
  更新の結果 — に表示されます。大文字小文字は区別しないので、`Homelab` と
  `homelab` を同時に使うことはできません。
- **ローカル**の項目はアプリが管理していて（**App-managed** の印が付きます）、
  削除できません。それ以外の接続を削除すると、その接続が持っていたバックエンドと
  トンネルは片付けられますが、インスタンス自体には手を触れません。
- どれか1つが必ず**プライマリ**になります（その行に印が付きます）。ゲートウェイを
  指定しない複数ゲートウェイ向けの呼び出しでは、これが既定の宛先になります。
  **プライマリにする**を実行しても、いま開いているセッションの作業場所は
  切り替わりません。プライマリを削除すると、ローカルの項目が代わりになります。
- **起動時に、最後に使ったゲートウェイのセッションを開く**は、アプリを完全に
  再起動したあとにセッションがどのゲートウェイで開くかを決めます。既定では
  オフなので、セッションは**プライマリ**で開きます。オンにすると、最後に接続に
  成功したゲートウェイから再開します。切り替えに失敗したゲートウェイは記憶されず、
  削除されたり使えなくなったりしたゲートウェイが保存されていた場合はプライマリに戻ります。
- **テスト**は、その接続の HTTP と WebSocket の両方を確かめます。合格
  （*"Reachable"* の通知）が出れば、ホストに ping が通っただけでなく、
  実際にチャットできる状態だという意味になります。
- **保存の時点で重複は弾かれます**。**ローカル**の項目は常に1つだけです。
  **リモート**と**クラウド**の項目は、正規化した URL（前後の空白を取り、末尾の
  スラッシュを外し、小文字にそろえたもの）で重複を判定します。しかも種類をまたいで
  判定するので、クラウドの項目とリモートの項目が同じ URL を指すことはできません。
  **SSH** の項目は、正規化した `user@host:port` と、接続先のプロフィールの
  組み合わせで判定します。
- クラウドの項目はふつう、ゲートウェイのページ上部にある Hermes Cloud の
  サインイン・検出の流れから追加されます。接続を追加する画面の **Hermes Cloud** の
  種類を選ぶと、そちらへ案内されます。

ゲートウェイの切り替えは、**セッション**のサイドバーから行います。プロフィール、
チャット、メッセージング、cron は、どれもそのゲートウェイの範囲にとどまります。
アプリが管理するウィンドウのバックエンドは、これまでどおり上の接続モードの設定で
決まります。**プライマリ**は既定の宛先であって、いま開いている作業場所を
切り替えるものではありません。

## 接続を追加する手順 {#adding-a-connection-step-by-step}

1. **設定 → ゲートウェイ**を開き、接続の登録一覧までスクロールします
   （プロフィールレールのプラグをクリックしても同じです）。
2. **接続を追加**をクリックします。
3. 種類を選びます。**ローカル**、**Hermes Cloud**、**リモートゲートウェイ**、
   **SSH** のいずれかです。
   （**ローカル**は、アプリが管理するローカルの項目がある間は選べません。
   つまりほとんどの場合は選べません。**Hermes Cloud** を選ぶと、上にある
   クラウドのサインイン・検出の流れへ案内されます。）
4. 項目を入力します。
   - **名前** — 必須で、重複は不可です。このインスタンスが現れるあらゆる場所に
     表示される「端末名」になります（入力例: `Homelab`）。最大64文字です。
   - *リモートゲートウェイのみ:*
     - **ゲートウェイ URL** — 動いている `hermes serve` のバックエンドのベース
       URL です。たとえば `http://homelab.lan:9119` のように指定します。
       リバースプロキシでパスの接頭辞を付けている場合も使えます。
     - **認証** — **セッショントークン**か **OAuth** を選びます。
       - **セッショントークン** — 接続先のゲートウェイのダッシュボードの
         セッショントークンを貼り付けます。編集するときは
         *"Leave blank to keep the saved token."* と表示されます。
       - **OAuth** — Nous Portal のブラウザでの認証にサインインします。
         貼り付けるトークンはありません。
   - *SSH のみ:*
     - **SSH ホスト** — `user@host:22` の形でまとめて入力する欄が1つあります
       （ユーザー名とポートは省略できます）。手元の SSH 鍵が使われ、アプリは
       トンネル越しにダッシュボードのトークンを引き継ぎます。
5. **接続を保存**（または**キャンセル**）をクリックします。
6. 追加された行の**テスト**をクリックし、*"Reachable"* が出るまで待ちます。

ローカル以外の項目は、あとから鉛筆のボタンで編集できますし、ゴミ箱のボタンで
削除できます。削除するときは確認が入り、*"The instance itself is not touched —
you can add it again any time."* と念を押されます。

:::info 接続先のバックエンドは、動いている `hermes serve` のプロセスです
相手のマシンでバックエンドが実際に動いていて、つながる状態になっていなければ、
ここで説明したことは何も動きません。デスクトップアプリはそこにつなぎに行くだけで、
代わりに起動してくれるわけではありません（SSH の接続だけは例外で、必要になった
時点でアプリがトンネル越しにダッシュボードを起動します）。バックエンド側の準備 —
認証プロバイダ、ループバック以外のアドレスへの割り当て、Tailscale の使い方 — は
[リモートのバックエンドにつなぐ](/hermes/docs/user-guide/desktop/#connecting-to-a-remote-backend)
を参照してください。
:::

### 単一接続の設定から移行する {#migrating-from-the-single-connection-settings}

登録一覧に対応したビルドを初めて起動すると、いまの設定が自動的に取り込まれます。
全体の接続モードと、設定 → ゲートウェイにあったプロフィールごとの古い上書き設定が、
名前付きの登録項目になります（URL とホストで重複は取り除かれます）。
（新しいビルドでは、ゲートウェイの設定ページにプロフィールごとの上書きはもうありません。
ゲートウェイの接続はマシン単位のもので、プロフィールは接続したゲートウェイから
見つけ出されます。）
古い設定ファイルはそのまま残るので、同じマシンにある古いビルドも動き続けます。
取り込みで名前がぶつかった場合は、末尾に番号が付きます（`Homelab 2`）。

## ゲートウェイをまたいだエージェント {#agents-across-gateways}

登録したすべての接続にある、すべての[プロフィール](/hermes/docs/user-guide/profiles/)が
1つの*エージェント*です。複数ゲートウェイに対応した画面（および組み込みの
[ボットモード](/hermes/docs/user-guide/bot-mode/)の一覧）が表示するのは、
それらをまとめた一覧です。

- 同じプロフィール名が複数のゲートウェイにある場合、ハンドルは
  **`@name-device`** の形で区別されます。Homelab の `research` は
  `@research-homelab` と表示され、すべてのゲートウェイを通じて重複しない
  プロフィールは名前だけのままです。
- 一覧の作成は先回りして行われますが、通信路は必要になってから開かれます。
  アプリは REST でエージェントを列挙し、すべてのゲートウェイの WebSocket を
  つなぎにはいきません。つながらないゲートウェイがあっても、その行に印が出るだけで
  一覧全体が壊れることはありません。SSH の接続は、そのエージェントを最初に開くまで
  つながないままです（知らないうちにトンネルが開くことはありません）。
- エージェントを開くと、**そのエージェント自身のゲートウェイ**につながります。
  チャット、セッション、記憶は、そのプロフィールを持つマシンの上にあり、
  そのインスタンスを直接使っているときとまったく同じです。

`(connection, profile)` の組み合わせごとに専用のバックエンドと通信路が用意され、
ローカルのプロフィールごとのバックエンドと同じように、使われていないものは
まとめて片付けられます。別のゲートウェイを見ているあいだも、裏で動いている
エージェントは応答を返し続けます。

### 切り替えと範囲 {#switching-and-scoping}

サイドバーの下部は、**ゲートウェイ → プロフィール → セッション**というひとつの
階層に沿っています。ゲートウェイはマシンやホスト型のバックエンドで、プロフィールは
1つのゲートウェイの上で動く、独立した Hermes のエージェントです。

- 登録したゲートウェイが1つだけなら、ゲートウェイを選ぶ操作は追加されません。
  ローカルだけで使うデスクトップ版は、これまでと同じプロフィールレールと
  キーボード操作のままです。
- ゲートウェイが複数あると、サイドバーに名前付きのゲートウェイ選択欄が1つ現れます。
  端末、クラウド、ネットワーク、ターミナルのアイコンで接続の種類がわかります。
  プロフィールのアイコンは、区切りのあとに別の操作として残ります。この選択欄は
  2つのゲートウェイから、もっと大きな構成まで同じ形で使えるので、バックエンドが
  プロフィールのような記号に化けたり、プロフィールの操作をレールから
  押しのけたりすることはありません。
- ゲートウェイを選ぶと、そこで最後に使っていたプロフィールに戻ります。
  プロフィールレールにはそのゲートウェイのプロフィールだけが並び、ホームの印は
  既定のプロフィールへ戻り、重ね表示の印は**このゲートウェイのすべてのプロフィール**を
  示します。**Cmd/Ctrl+1〜9** は、これまでどおり有効なゲートウェイの中で
  プロフィールを切り替えます。
- 選んだゲートウェイが終了・再起動をまたいで残るのは、**設定 → ゲートウェイ →
  起動時に、最後に使ったゲートウェイのセッションを開く**がオンのときだけです。
  この設定とゲートウェイの ID はアプリのユーザーデータの登録先に保存されるので、
  アプリ本体を入れ替えたり更新したりしても消えません。
- 有効なゲートウェイに13を超えるプロフィールがある場合、アイコンの列は名前付きの
  プロフィール選択欄にまとまります。つまり、ゲートウェイもプロフィールも多い構成が、
  **ゲートウェイ → プロフィール → セッション**という考え方を変えずに成り立ちます。
- リモートの接続がプライマリになっていても、**この端末**は一人前のゲートウェイの
  ままです。リモートが落ちているあいだも手元のセッションを使い続けられますが、
  アプリはこれを「オフラインモード」とは呼びません。選んでいるモデルやツールが、
  やはりインターネットを必要とすることがあるからです。
- セッションの一覧、メッセージングのチャンネル、cron のジョブ、設定、ファイル、
  記憶は、すべて有効な `(gateway, profile)` の範囲に収まります。Telegram の
  ゲートウェイから Signal のゲートウェイへ切り替えたときに、前のゲートウェイの
  チャンネルのまとまりやセッションがサイドバーに残ることはありません。
- 切り替え欄を表示するだけなら、読むのは Electron の手元にある接続の一覧だけです。
  リモートのゲートウェイは選んだときにだけ開かれ、定期的に全体を問い合わせることは
  ありません。
- エージェントにマウスを重ねると、そのバックエンドが先に温められるので、
  切り替えたときに起動待ちが起きません。
- **機能**のページ（スキル／ツール／MCP）にも、同じ考え方の範囲があります。
  **設定対象**の選択欄には、まとめた一覧のすべての `(profile, device)` の
  エージェントが並び、1つ選ぶと**そのマシンの**スキル、ツール一式、MCP サーバーを
  読み書きします。セッションの作業場所は切り替わりません。ハブからの導入、
  環境変数のキー、MCP の設定は、どれも選んだエージェントのバックエンドに
  反映されます。MCP タブの*動いているセッションへその場で読み込ませる*ボタンは、
  いまのウィンドウがつながっているゲートウェイのエージェントにだけ表示されます。
  他のマシンでの変更は、次のセッションから効きます。

ゲートウェイの追加、テスト、名前の変更、削除は**設定 → ゲートウェイ**で行います。
プロフィールの操作の横にあるプラグのボタンは、その管理場所への近道であって、
2つめの追加画面ではありません。

### セッションとボットモード {#sessions-and-bot-mode}

セッションは、あえて一度に1つのゲートウェイだけを表示します。こうすることで、
ファイル、ツール、チャンネル、cron、セッションの履歴が、1つのわかりやすい実行環境に
まとまります。ボットモードは役目が違うので、まとめた一覧をゲートウェイごとに分けて
見せることがあります。NAS の上のエージェントと VPS の上のエージェントを、1つの画面から
開けるようにするためです。ボットを開いたときも、その `(gateway, profile)` の経路が
そのまま有効になります。

ボットへの直接の呼びかけや委任は、既定ではそのゲートウェイの中に閉じています。
バックエンドの境界をまたぐと、ファイルシステム、認証情報、ツール、信頼の前提が
すべて変わります。ですから、ゲートウェイをまたいだ実行は、1つのデスクトップの
ウィンドウを共有した結果うっかり起きるものではなく、はっきりと橋を架ける行為で
あるべきです。

## すべてのインスタンスをまとめて更新する {#updating-every-instance-at-once}

**設定 → ゲートウェイ → すべてのインスタンスを更新**（接続が2つ以上登録されると
表示されます）は、対象になるすべての接続へ `hermes update` を同時に投げます。

- **ローカル**は、アプリ自身の更新のしくみで更新されます（設定 → 更新と同じ流れです）。
- **リモート**と **SSH** の接続には、それぞれのバックエンド経由で自分自身を更新するよう
  伝えます。更新は*そのマシンの上で*行われます。
- **Hermes Cloud** のインスタンスは *"Managed by Hermes Cloud"* と表示されて
  飛ばされます。バージョンの管理はプラットフォーム側が行うためです。

インスタンスごとに結果が返るので、つながらないマシンが1つあっても全体が止まることは
ありません。更新を外部（Docker、Nix）に任せているバックエンドは、行ごとに自分の
メッセージで丁寧に断ってきます。

とはいえ、設定のボタンを使う場面はあまりありません。更新の対象が2つ以上になると、
ふだんの更新の入口（About パネルの**今すぐ更新**、⌘K の **Update Hermes**、
更新の準備ができたときの通知）が、同じ一斉更新を自動で行います。まず有効な
バックエンド、次に対象となる他のすべてのゲートウェイ、最後にデスクトップアプリ本体
という順番です。デスクトップ版の案内の[更新](/hermes/docs/user-guide/desktop/#updating)も
あわせてご覧ください。

## セキュリティについて {#security-notes}

- **トークンの置き場所。** リモートゲートウェイのセッショントークンは、Electron の
  `safeStorage`（OS の鍵束 — macOS なら Keychain、Windows なら DPAPI、Linux なら
  セッションのキーリング）で暗号化して保存され、Electron のメインプロセスの中に
  とどまります。描画側やプラグインがトークンの中身を見ることはありません。
  ネイティブのサインインで使う OAuth のトークンも同じように、ゲートウェイのベース
  URL をキーにして保存され、期限が切れる前に自動で更新されます。
- **鍵束のない Linux。** 使える鍵束がない Linux のセッションでは、アプリはトークンを
  暗号化できません。その場合、保存しようとすると、平文で保存してよいかを尋ねる
  確認画面がはっきり表示されます。
- **登録一覧のファイル**（アプリのユーザーデータのディレクトリにある
  `connections.json`）が持つのは、名前、URL、ホストだけです。秘密の情報は、
  暗号化された入れ物の中にしか現れません。
- プラグイン SDK の `host.connections()` は、あえて名前、種類、プライマリの ID だけを
  返します。トークンの中身を返すことはありません。

## プラグインを作る方へ {#for-plugin-authors}

デスクトップ版の[プラグイン SDK](/hermes/docs/developer-guide/desktop-plugin-sdk/) は、
複数ゲートウェイのしくみをそのまま扱えるようにしています。

- `host.connections()` — 登録された接続の一覧（名前、種類、プライマリ。
  トークンの中身は決して含みません）。
- `host.agents()` — まとめた一覧です。`(gateway, profile)` ごとに1行で、
  `@name-device` の形のハンドルが計算済みで入っています。
- `host.ensureAgent(connectionId, profile)` — エージェントのゲートウェイを有効にして、
  以降の `host.request` の呼び出しがそのバックエンドに届くようにします。
- `host.warmAgent(connectionId, profile)` — 結果を待たずに通信路を温めます
  （マウスを重ねた時点で呼ぶ用途です）。

この4つはいずれも、あるかどうかを調べてから使う形です。古いデスクトップ版のビルドでは
存在しないので、プラグイン側は単一ゲートウェイ向けの `profiles.list` の流れに
戻してください。ボットモードの複数ゲートウェイ対応の一覧が、お手本になる利用例です。

## 困ったときは {#troubleshooting}

- **「接続テストに失敗しました」** — この端末から、その URL でバックエンドに
  つながっていません。相手のホストで `hermes serve` が動いているか、ポートが
  開いているか、トークン認証なら
  トークンが最新かを確認してください。直したら**テスト**をやり直します。
- **エージェントは見えるのに開けない** — その接続で**テスト**を実行してください。
  HTTP は通るのに WebSocket が通らない場合、たいていはプロキシ、ファイアウォール、
  またはゲートウェイの認証・オリジンの検査が `/api/ws` を止めています。
- **リモートのゲートウェイが一覧に出てこない** — そのバックエンドが落ちているか、
  つながらない状態です。一覧にはゲートウェイの側にエラー付きで表示されます。
  SSH の接続は、最初に使うまで*必要になったらつなぐ*と表示されます。これは仕様であって
  不具合ではありません。
- **"Update Hermes Desktop to chat with agents on other connections"** — アプリが
  複数接続のしくみより古いバージョンです。デスクトップアプリ自体を更新してください。
- **端末名が重複している** — そうはなりません。名前は保存の時点で重複しないよう
  強制されます。取り込みで名前がぶつかった場合は、末尾に番号が付いています（`Homelab 2`）。
- **「接続を保存できませんでした」** — たいていは**名前**が空、名前がすでに
  使われている、**ゲートウェイ URL** や **SSH ホスト**の書式が正しくない、
  のいずれかです。エラーメッセージに、何が問題かがそのまま書かれています。
